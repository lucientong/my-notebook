## 0. 系统设计方法论与 Back-of-envelope

面试/方案设计建议按固定节奏推进，由浅入深，避免一上来堆组件。

### 0.1 七步节奏

| 步骤 | 做什么 | 产出 |
|------|--------|------|
| **1. Clarify** | 明确功能/非功能：DAU、峰值 QPS、读写比、一致性、延迟、合规 | 需求边界与取舍 |
| **2. Estimate** | Back-of-envelope：QPS、存储、带宽、机器量级 | 数量级（差 10 倍要重估） |
| **3. API** | 画出核心接口与错误码/幂等键 | 契约 |
| **4. Data** | 实体、主键、索引、分片键、缓存键 | 数据模型 |
| **5. Design** | 单机 → 有状态拆分 → 异步 → 多级缓存 | 一版可讲的架构 |
| **6. Deep Dive** | 热点、一致性、故障、分页、过期 | 面试官最爱追问处 |
| **7. Scale** | 分片、多活、降级、容量与观测 | 演进路线 |

### 0.2 估算速查表（背数量级即可）

| 量 | 约数 | 备注 |
|----|------|------|
| 1 天秒数 | ≈ 8.64×10⁴ ≈ **10⁵** | QPS≈日请求/10⁵ |
| 1 年秒数 | ≈ 3.15×10⁷ ≈ **π×10⁷** | |

## 1. 限流策略

> **与《12-微服务架构》分工**：本章给**系统设计视角**的算法选型与分布式配额；网关插件、Sentinel/Hystrix 细则见 [12-微服务架构 §9 限流算法](./12-微服务架构.md#9-限流算法)。


### 1.1 为什么需要限流？

**场景**：
- 突发流量（秒杀、热点事件）
- 恶意攻击（DDoS、爬虫）
- 下游服务保护（防止雪崩）

**不限流的后果**：
- 服务器CPU/内存耗尽
- 数据库连接池耗尽
- 整个系统崩溃

### 1.2 常见限流算法

#### 1.2.1 固定窗口计数器

**原理**：统计固定时间窗口内的请求数

```go
type FixedWindowLimiter struct {
    limit    int64         // 限制数量
    window   time.Duration // 窗口大小
    counter  int64         // 当前计数
    lastTime time.Time     // 窗口开始时间
    mu       sync.Mutex
}

func (l *FixedWindowLimiter) Allow() bool {
    l.mu.Lock()
    defer l.mu.Unlock()

    now := time.Now()

    // 新窗口，重置计数
    if now.Sub(l.lastTime) >= l.window {
        l.counter = 0
        l.lastTime = now
    }

    // 检查是否超限
    if l.counter >= l.limit {
        return false
    }

    l.counter++
    return true
}

// 使用示例
limiter := &FixedWindowLimiter{
    limit:  100,              // 100次
    window: 1 * time.Second,  // 1秒
}

if limiter.Allow() {
    // 处理请求
} else {
    // 返回429 Too Many Requests
}
```

**优点**：实现简单
**缺点**：临界问题（窗口边界流量突刺）

**临界问题示例**：
```
窗口1: 09:59:00 - 09:59:59  →  99次请求（在59秒时）
窗口2: 10:00:00 - 10:00:59  →  99次请求（在00秒时）
实际：1秒内处理了198次请求（突破限制）
```

#### 1.2.2 滑动窗口

**原理**：将固定窗口划分为多个小窗口，统计滑动窗口内的请求数

```go
type SlidingWindowLimiter struct {
    limit      int64
    window     time.Duration
    smallWindow time.Duration
    counters   map[int64]int64  // 时间戳 -> 计数
    mu         sync.Mutex
}

func (l *SlidingWindowLimiter) Allow() bool {
    l.mu.Lock()
    defer l.mu.Unlock()

    now := time.Now()
    windowStart := now.Add(-l.window)

    // 清理过期窗口
    for ts := range l.counters {
        if time.Unix(0, ts).Before(windowStart) {
            delete(l.counters, ts)
        }
    }

    // 统计当前窗口内的请求数
    var total int64
    for _, count := range l.counters {
        total += count
    }

    if total >= l.limit {
        return false
    }

    // 当前小窗口计数+1
    currentWindow := now.Truncate(l.smallWindow).UnixNano()
    l.counters[currentWindow]++

    return true
}
```

**优点**：解决临界问题
**缺点**：内存占用较大

#### 1.2.3 令牌桶（推荐）

**原理**：按固定速率生成令牌，请求消耗令牌，桶满则丢弃令牌

```go
import "golang.org/x/time/rate"

// 创建限流器
limiter := rate.NewLimiter(100, 200)  // 100 token/s, burst 200

// 方式1：阻塞等待
err := limiter.Wait(context.Background())

// 方式2：非阻塞
if limiter.Allow() {
    // 处理请求
} else {
    // 返回429
}

// 方式3：等待N个令牌
reservation := limiter.Reserve()
if !reservation.OK() {
    // 无法获取令牌
    return
}
time.Sleep(reservation.Delay())  // 等待
```

**优点**：
- 平滑流量，允许突发（burst）
- Go官方库支持

**参数说明**：
- `rate`：令牌生成速率（QPS）
- `burst`：桶容量（允许的突发请求数）

#### 令牌桶手写实现（完整版）⭐⭐⭐

**为什么要手写？**
- 面试高频：手写限流器
- 理解原理：令牌如何生成、如何消费
- 自定义需求：官方库无法满足的场景

**核心思想**：
1. 不真正"生成"令牌（太耗费CPU）
2. 记录上次取令牌的时间，计算当前应该有多少令牌
3. 惰性生成：取令牌时才计算

```go
// 令牌桶限流器（手写实现）
// 注意：tokens/rate 必须用 float64。若用 int64(elapsed.Seconds()*rate)，
// 亚秒时间会被截断为 0，导致短时间内几乎不补令牌。
type TokenBucket struct {
    capacity float64       // 桶容量
    tokens   float64       // 当前令牌数（允许小数累积）
    rate     float64       // 生成速率（token/s）
    lastTime time.Time     // 上次补充时间
    mu       sync.Mutex
}

func NewTokenBucket(rate, capacity float64) *TokenBucket {
    return &TokenBucket{
        capacity: capacity,
        tokens:   capacity, // 初始满桶
        rate:     rate,
        lastTime: time.Now(),
    }
}

func (tb *TokenBucket) Allow() bool {
    return tb.AllowN(1)
}

func (tb *TokenBucket) AllowN(n float64) bool {
    tb.mu.Lock()
    defer tb.mu.Unlock()

    now := time.Now()
    elapsed := now.Sub(tb.lastTime).Seconds()
    tb.tokens += elapsed * tb.rate // 浮点累积，避免整数截断丢令牌
    if tb.tokens > tb.capacity {
        tb.tokens = tb.capacity
    }
    tb.lastTime = now

    if tb.tokens >= n {
        tb.tokens -= n
        return true
    }
    return false
}

// 等待获取N个令牌（阻塞）
func (tb *TokenBucket) WaitN(ctx context.Context, n float64) error {
    for {
        if tb.AllowN(n) {
            return nil
        }

        tb.mu.Lock()
        needed := n - tb.tokens
        waitTime := time.Duration(needed / tb.rate * float64(time.Second))
        tb.mu.Unlock()
        if waitTime < time.Millisecond {
            waitTime = time.Millisecond
        }

        select {
        case <-time.After(waitTime):
        case <-ctx.Done():
            return ctx.Err()
        }
    }
}

// 使用示例
func main() {
    // 100 QPS，允许突发200个请求
    limiter := NewTokenBucket(100, 200)

    for i := 0; i < 200; i++ {
        if limiter.Allow() {
            fmt.Println("请求", i, "通过")
        }
    }
    // 前200个通过，桶空后被拒绝

    time.Sleep(1 * time.Second)
    if limiter.Allow() {
        fmt.Println("1秒后请求通过") // 约补充100个令牌
    }
}
```

**关键点**：

1. **惰性计算**：不启定时器；取令牌时才按 `elapsed * rate` 补充。
2. **必须用浮点**：`int64(elapsed.Seconds()*rate)` 在 `elapsed<1/rate` 时恒为 0，高 QPS 下几乎不补令牌。
3. **突发**：桶容量=burst；桶空后按 rate 平滑恢复。

#### 令牌桶 vs 漏桶（底层原理对比）⭐⭐⭐

**为什么令牌桶能允许突发，漏桶不行？**

| 维度 | 令牌桶 | 漏桶 |
|------|--------|------|
| **核心思想** | 令牌定速生成，请求变速消费 | 请求变速进入，定速流出 |
| **突发流量** | ✅ 允许（消费已存的令牌） | ❌ 不允许（队列+定速处理） |
| **流量曲线** | 锯齿状（允许瞬时峰值） | 平滑（恒定速率） |
| **实现复杂度** | 简单（计数器） | 中等（需要队列） |

**图解**：

```
【令牌桶】
令牌生成：    ─┬─┬─┬─┬─┬─┬─┬─> (恒定速率)
            令桶桶桶桶桶桶桶
请求消费：    ████─█─█─> (变速，可突发)

时刻T1: 桶满（100个令牌）
时刻T2: 瞬间100个请求 → 全部通过（消费100个令牌）
时刻T3: 桶空，新请求需要等待

【漏桶】
请求进入：    ████─█─█─> (变速)
            ┌──────┐
            │ 队列 │ (缓冲区)
            └──────┘
请求流出：    ─┬─┬─┬─┬─┬─┬─┬─> (恒定速率)

时刻T1: 100个请求瞬间到达 → 进入队列
时刻T2: 按固定速率处理（如每秒10个）
时刻T3: 需要10秒才能处理完100个请求
```

**为什么漏桶不能突发？**

```go
// 漏桶的leak()协程
func (lb *LeakyBucket) leak() {
    ticker := time.NewTicker(lb.rate)  // 固定速率
    defer ticker.Stop()

    for range ticker.C {
        select {
        case <-lb.queue:
            processRequest()  // 每个tick只处理1个请求
        default:
        }
    }
}

// 即使队列有1000个请求，也只能按固定速率处理
// 无法利用"空闲时段"加速处理
```

**应用场景对比**：

| 场景 | 推荐算法 | 原因 |
|------|----------|------|
| **API限流** | 令牌桶 | 用户体验好（允许短时突发） |
| **写数据库** | 漏桶 | 保护数据库（平滑QPS） |
| **消息队列消费** | 漏桶 | 避免下游被打垮（恒速） |
| **CDN流量** | 令牌桶 | 允许大文件快速下载（突发） |

**应用场景**：

#### 1.2.4 漏桶

**原理**：请求进入队列，按固定速率处理

```go
type LeakyBucket struct {
    capacity int           // 桶容量
    rate     time.Duration // 处理速率
    queue    chan struct{} // 请求队列
}

func NewLeakyBucket(capacity int, rate time.Duration) *LeakyBucket {
    lb := &LeakyBucket{
        capacity: capacity,
        rate:     rate,
        queue:    make(chan struct{}, capacity),
    }
    go lb.leak()
    return lb
}

func (lb *LeakyBucket) leak() {
    ticker := time.NewTicker(lb.rate)
    defer ticker.Stop()

    for range ticker.C {
        select {
        case <-lb.queue:
            // 处理一个请求
        default:
        }
    }
}

func (lb *LeakyBucket) Allow() bool {
    select {
    case lb.queue <- struct{}{}:
        return true
    default:
        return false  // 队列满
    }
}
```

**对比令牌桶**：
| 算法 | 流量特点 | 适用场景 |
|------|----------|----------|
| 令牌桶 | 允许突发 | API限流 |
| 漏桶 | 平滑流量 | 消息队列 |

### 1.3 分布式限流

**场景**：多个服务实例共享限流配额

**方案1：Redis + Lua 固定窗口（简单分布式限流）**

> ⚠️ 下面脚本是 **固定窗口计数器**（`INCR` + `EXPIRE`），不是令牌桶。
> 令牌桶见后文章节「案例：分布式限流服务」中的 `HMSET tokens/last_refill` Lua。

```lua
-- 固定窗口计数器（Fixed Window）
-- KEYS[1]=限流key  ARGV[1]=窗口内上限  ARGV[2]=窗口秒数
local key = KEYS[1]
local limit = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local current = redis.call('INCR', key)

if current == 1 then
    redis.call('EXPIRE', key, window)
end

if current > limit then
    return 0  -- 超限
else
    return 1  -- 允许
end
```

```go
func AllowByRedisFixedWindow(key string, limit int64, window time.Duration) bool {
    script := `...` // 上面的固定窗口 Lua
    result, err := redis.Eval(script, []string{key}, limit, int(window.Seconds())).Result()
    if err != nil {
        return true // fail-open，或降级本地限流
    }
    return result.(int64) == 1
}

if AllowByRedisFixedWindow("rate_limit:user:1001", 100, 1*time.Second) {
    // 处理请求
}
```

**算法对照**：

| Redis 实现 | 本质 | 适用 |
|------------|------|------|
| `INCR`+`EXPIRE` | 固定窗口 | 简单配额、实现成本低（有临界突刺） |
| ZSET 时间戳 | 滑动窗口 | 更精确的用户/IP 限流 |
| Hash(`tokens`,`last_refill`) | 令牌桶 | 允许突发的 API 限流 |

## 2. 熔断与降级

> **与《12》分工**：本章保留状态机、降级策略与系统选型；Hystrix/Sentinel 细节见 [12-微服务架构 §4](./12-微服务架构.md#4-服务熔断与降级)。


### 2.1 熔断器（Circuit Breaker）

**原理**：当下游服务故障率超过阈值时，自动切断请求，快速失败

**状态机**：
```
关闭（Closed） → 打开（Open） → 半开（Half-Open） → 关闭
```

**状态转换**：
1. **Closed**：正常请求，统计失败率
2. **Open**：失败率超阈值，拒绝所有请求，快速返回错误
3. **Half-Open**：一段时间后，允许少量请求尝试
4. **Closed**：尝试成功，恢复正常

**Go实现（使用 gobreaker 库）**：

```go
import "github.com/sony/gobreaker"

// 创建熔断器
breaker := gobreaker.NewCircuitBreaker(gobreaker.Settings{
    Name:        "my-service",
    MaxRequests: 3,      // 半开状态允许3个请求
    Interval:    10 * time.Second,  // 统计周期
    Timeout:     60 * time.Second,  // 熔断持续时间
    ReadyToTrip: func(counts gobreaker.Counts) bool {
        // 失败率 > 50% 触发熔断
        failureRatio := float64(counts.TotalFailures) / float64(counts.Requests)
        return counts.Requests >= 10 && failureRatio >= 0.5
    },
})

// 使用熔断器
result, err := breaker.Execute(func() (interface{}, error) {
    return callDownstreamService()
})

if err != nil {
    if err == gobreaker.ErrOpenState {
        // 熔断器打开，快速失败
        return nil, errors.New("服务熔断")
    }
    return nil, err
}
```

**监控指标**：
```go
state := breaker.State()  // Closed/Open/Half-Open
counts := breaker.Counts()
log.Printf("State: %v, Requests: %d, Failures: %d",
    state, counts.Requests, counts.TotalFailures)
```

### 2.2 降级

**定义**：系统负载过高时，关闭非核心功能，保障核心功能

**降级策略**：
1. **功能降级**：关闭推荐、评论等非核心功能
2. **读降级**：返回缓存数据
3. **写降级**：限制写操作，或异步写入
4. **返回默认值**：返回兜底数据

**实现方式**：

**方式1：配置中心（推荐）**
```go
type FeatureSwitch struct {
    EnableRecommendation bool `json:"enable_recommendation"`
    EnableComment        bool `json:"enable_comment"`
    EnableSearch         bool `json:"enable_search"`
}

var featureSwitch FeatureSwitch

// 定时从配置中心拉取
func LoadFeatureSwitch() {
    config := fetchFromConfigCenter()
    featureSwitch = config
}

// 使用
```

## 3. 分布式事务

> **与《12》分工**：本章保留**选型表与适用场景**；2PC/TCC/SAGA/本地消息表实现细节见 [12-微服务架构 §7](./12-微服务架构.md#7-分布式事务)。


### 3.1 2PC（两阶段提交）

**流程**：
1. **准备阶段**：协调者询问所有参与者是否可以提交
2. **提交阶段**：所有参与者都同意，则提交；否则回滚

**缺点**：
- 同步阻塞（性能差）
- 单点故障（协调者挂了）
- 数据不一致（网络分区）

**结论**：❌ 不推荐使用

---

### 3.2 方案对比

| 方案 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| **2PC** | 协调者两阶段提交 | 强一致性 | 同步阻塞、单点故障 | ❌ 不推荐 |
| **TCC** | Try预留→Confirm提交→Cancel回滚 | 性能好、不阻塞；业务层强隔离预留 | 业务侵入强，需实现3接口；Confirm/Cancel 仍要幂等与空回滚 | 资金冻结/预扣等需显式资源预留的场景 |
| **SAGA** | 多个本地事务+补偿事务 | 长事务友好 | 最终一致、补偿逻辑复杂 | 订单流程等长链路 |
| **本地消息表** | 本地事务写业务+消息，定时发MQ | 可靠性高、实现简单 | 需定时扫描、有延迟 | ✅ 推荐默认方案 |

### 3.3 TCC核心流程

```
Try阶段（业务层强隔离预留）→ Confirm阶段（确认提交）→ Cancel阶段（取消回滚）

示例-转账：
Try:     冻结转出方资金（预留成功才进入后续）
Confirm: 扣减已冻结额度，增加收款方余额
Cancel:  解冻转出方资金
```

**澄清**：TCC 提供的是**业务层资源预留与隔离**（Try 占住额度/库存），Confirm/Cancel 仍需幂等、空回滚、悬挂处理；它追求的是可控的业务正确性，不宜简单等同于“数据库级强一致/线性一致”。

> 算法细节、框架与金融实践：见 [12-微服务架构 §7 分布式事务](./12-微服务架构.md#7-分布式事务) 与《专项知识库/02-金融支付专项》。
### 3.4 SAGA核心流程

```
编排式(Orchestration)：中央协调者编排执行步骤和补偿
    创建订单 → 扣减库存 → 扣减余额 → 发送通知
    (补偿)取消订单 ← 恢复库存 ← 退款

协同式(Choreography)：各服务通过MQ事件自行响应
    ✅ 更解耦    ❌ 调试困难
```

### 3.5 本地消息表（推荐）

**原理**：在本地事务中同时写业务数据和消息，定时扫描消息表发送MQ

**实现**（参考前面MySQL章节的代码）

## 4. 分布式一致性

### 4.1 CAP理论

| 特性 | 说明（对齐 Brewer/Gilbert-Lynch 常见工程表述） |
|------|------|
| **C**onsistency | **线性一致性**：一次成功写入后，任意非故障节点的后续读都应看到该写入（或更新的值） |
| **A**vailability | **非故障节点必须响应**：每个收到请求的非故障节点都返回一个非错误响应（不要求读到最新值） |
| **P**artition Tolerance | **分区容错**：节点间通信丢失/延迟时，系统仍按既定语义继续运行（分区是客观现实，不是“仍可用”的同义词） |

**正确表述**：分布式系统必须面对分区（P）。**分区发生时，只能在 C 与 A 之间权衡**——不是抽象地“三者任选其二”。

**选择（分区下的行为）**：
- **CP**：分区时拒绝可能不一致的读写，优先线性一致（如：ZooKeeper、etcd、HBase）
- **AP**：分区时非故障节点继续响应，接受短暂不一致/最终一致（如：Cassandra、DynamoDB 默认取向）
- **CA**：仅在“无分区”假设下同时谈 C+A；广域分布式中分区不可避免，故 **CA 不是可选架构标签**
---

#### 4.1.1 分区下为什么不能同时要 C 和 A？（推导）⭐⭐⭐

**为什么需要理解证明？**
- 面试高频：不是背“三选二”，而是讲清分区时的取舍
- 架构选型：按业务容忍度选 CP 或 AP 行为
- 避免误区：CA 不是分布式可选档位；P 不是“可用性”
---

##### 证明：C + A + P 不可能同时满足

**场景设定**：
```
分布式系统：
- 节点N1：master（可读可写）
- 节点N2：slave（可读可写）
- 客户端C1、C2
```

**步骤1：网络分区发生**
```
初始状态：N1和N2数据一致，都是v0

时刻T1：网络分区
    ┌────┐          ┌────┐
    │ N1 │ ╳╳╳╳╳╳╳╳ │ N2 │
    └────┘ 网络断开  └────┘
     v0              v0
```

**步骤2：客户端写入N1**
```
时刻T2：C1向N1写入v1
    ┌────┐          ┌────┐
    │ N1 │ ╳╳╳╳╳╳╳╳ │ N2 │
    └────┘          └────┘
     v1              v0

问题：N1无法将v1同步到N2（网络断开）
```

**步骤3：客户端读取N2**
```
时刻T3：C2从N2读取数据

选择1：坚持线性一致（C）+ 容忍分区（P）→ 牺牲 A
  - N2 拒绝读/写："无法确认是否已有更新"
  - 非故障节点不保证响应 → 违反可用性

选择2：坚持可用性（A）+ 容忍分区（P）→ 牺牲 C
  - N2 返回 v0（本地可见值）
  - 与 N1 的 v1 不一致 → 违反线性一致
```

**结论**：
```
分区（P）一旦发生：
- 选 CP：宁可拒绝，也不返回可能过期的值
- 选 AP：宁可返回过期/分叉值，也要响应

不存在“分区时同时保证线性一致 + 非故障节点必响应”。
所谓“三选二”是口语简化；工程上应说「分区下的 C/A 权衡」。
```
---

##### 为什么CA不存在？

**误区**：单机系统是CA（无网络分区）

**反驳**：
```
1. 单机系统不是分布式系统
   - CAP是针对分布式系统的定理
   - 单机没有"分布式"的概念

2. 网络分区不可避免
   - 即使在同一数据中心，也可能网络故障
   - 交换机故障、光缆断裂、路由器宕机
   - P是客观存在的，不是可选项

3. CA的真正含义
   - 在P不存在的假设下，可以同时满足C和A
   - 但P是客观存在的 → CA在实际中不存在
```

---

##### CP系统示例：ZooKeeper

**ZooKeeper的选择**：牺牲A，保证C和P

```
场景：ZooKeeper有5个节点（N1-N5），N1是Leader

时刻T1：网络分区
分区1：N1、N2（2个节点，少数派）
分区2：N3、N4、N5（3个节点，多数派）

时刻T2：客户端写入
- 向N1写入 → 失败（无法同步到多数派）
- 向N3写入 → 成功（N3、N4、N5达成共识）

时刻T3：客户端读取
- 从N1读取 → 失败（N1发现自己不是Leader）
- 从N3读取 → 成功（返回最新数据）

牺牲可用性（A）：
- 分区1中的节点拒绝服务（保证一致性）
- 只有多数派可用
```

**ZooKeeper的过半机制**：
```
写操作需要过半节点确认：
- 5个节点 → 至少3个确认
- 3个节点 → 至少2个确认

为什么？
- 保证任意两个多数派必有交集
- 5个节点：多数派=3
  - {N1, N2, N3} ∩ {N3, N4, N5} = {N3} ≠ ∅
  - 保证至少有1个节点知道最新数据

网络分区时：
- 只有多数派能提供服务（保证一致性）
- 少数派拒绝服务（牺牲可用性）
```

---

##### AP系统示例：Cassandra

**Cassandra的选择**：牺牲C，保证A和P

```
场景：Cassandra有5个节点（N1-N5）

时刻T1：网络分区
分区1：N1、N2
分区2：N3、N4、N5

时刻T2：客户端写入
- 向N1写入v1 → 成功（写入N1、N2，W=2）
- 向N3写入v2 → 成功（写入N3、N4、N5，W=3）

时刻T3：客户端读取
- 从N1读取 → 返回v1
- 从N3读取 → 返回v2
- 不一致！

牺牲一致性（C）：
- 允许分区内独立写入（可用性）
- 分区恢复后，通过Last-Write-Wins解决冲突
```

**Cassandra 的可调一致性（不要和 CAP 标签混贴）**：
```
W + R > N  →  一次成功写入后，法定人数读可读到该写入（会话/仲裁一致性）
W + R ≤ N  →  可能读到旧副本

W/R/N：写确认数 / 读确认数 / 副本数

示例（N=3）：
- W=1, R=1 → 最可用，易读旧数据（典型最终一致取向）
- W=QUORUM, R=QUORUM（如 W=2,R=2）→ 健康集群下强读己之所写；分区时可能双方都达不到法定人数
- W=3, R=1 → 写需全部副本确认：健康时读单副本也能看到已成功写入；
              分区/掉节点时写更容易失败。这是「一致性级别」选择，
              不能因此把 Cassandra 整体改标为 CP 系统。
```

> Cassandra 产品定位仍是 **AP + 可调一致性**：调高 W/R 换更强读己写保证，同时降低分区下的可用性。面试忌把某一组 W/R 直接等同于“系统是 CP”。

---

##### CP vs AP 选择指南

| 业务场景 | 倾向 | 原因与常见实现 |
|----------|------|----------------|
| **金融账务/配置中心** | CP | 错误值不可接受；ZK/etcd 等多数派提交 |
| **社交点赞/计数** | AP | 短暂不准可接受；异步聚合 |
| **购物车** | AP | 体验优先，冲突可合并 |
| **秒杀库存** | **业务正确性 ≠ CAP-CP** | 要「不超卖」，常用 Redis 原子扣减 + MQ 异步落库（最终一致到 DB），并不是把秒杀做成 ZooKeeper 式 CP 集群 |
| **DNS** | AP | 可用性优先，接受缓存过期 |

##### CAP定理的实际应用（工程中的权衡）

**1. 牺牲一致性（AP）的常见做法**：

```go
// 最终一致性：异步同步
func WriteData(key, value string) error {
    // 1. 立即写入主节点
    if err := master.Write(key, value); err != nil {
        return err
    }

    // 2. 异步同步到从节点（允许短暂不一致）
    go func() {
        for _, slave := range slaves {
            slave.Write(key, value)
        }
    }()

    return nil  // 立即返回（可用性）
}

// 读取时可能读到旧数据（不一致）
func ReadData(key string) (string, error) {
    // 从任意节点读取
    return randomSlave().Read(key)
}
```

**2. 牺牲可用性（CP）的常见做法**：

```go
// 强一致性：同步等待多数派确认
func WriteData(key, value string) error {
    // 需要多数派（3/5）确认才返回
    successCount := 0
    errChan := make(chan error, len(nodes))

    for _, node := range nodes {
        go func(n *Node) {
            errChan <- n.Write(key, value)
        }(node)
    }

    // 等待多数派确认
    for i := 0; i < len(nodes); i++ {
        if <-errChan == nil {
            successCount++
            if successCount >= len(nodes)/2 + 1 {
                return nil  // 多数派成功
            }
        }
    }

    return errors.New("无法达成多数派共识")  // 牺牲可用性
}
```

### 4.2 BASE理论

BASE 不是“扩展 CAP”，而是相对 **ACID** 的一套**大规模互联网工程哲学**：在可接受范围内用最终一致换可用性与扩展性。

| 特性 | 说明 |
|------|------|
| **B**asically Available | 基本可用：故障时允许降级/部分功能不可用，而不是全站不可用 |
| **S**oft State | 软状态：允许存在中间态（如“支付中”“库存预扣”） |
| **E**ventually Consistent | 最终一致性：停止写入后，副本在有限时间内收敛 |

**与 ACID / CAP 的关系**：
- 相对 ACID：弱化隔离与即时一致，强调可分区扩展与体验
- 相对 CAP：BASE 常落在 **AP + 补偿/对账** 一侧，并不否定分区下仍可对关键路径做 CP

**应用**：
- 电商订单（下单与库存异步收敛，靠对账/补偿）
- 社交点赞（计数最终一致）

### 4.3 一致性Hash

**问题**：分布式缓存中，节点增减导致大量缓存失效

**方案**：一致性Hash

**原理**：
1. 将Hash空间组织成环（0 ~ 2^32-1）
2. 节点映射到环上（Hash(IP)）
3. 数据顺时针找到第一个节点

**优点**：节点增减只影响相邻节点

**实现**：
```go
type ConsistentHash struct {
    circle       map[uint32]string  // Hash值 -> 节点
    sortedHashes []uint32            // 排序的Hash值
    replicas     int                 // 虚拟节点数
}

func (ch *ConsistentHash) Add(node string) {
    for i := 0; i < ch.replicas; i++ {
        hash := crc32.ChecksumIEEE([]byte(fmt.Sprintf("%s:%d", node, i)))
        ch.circle[hash] = node
        ch.sortedHashes = append(ch.sortedHashes, hash)
    }
    sort.Slice(ch.sortedHashes, func(i, j int) bool {
        return ch.sortedHashes[i] < ch.sortedHashes[j]
    })
}

func (ch *ConsistentHash) Get(key string) string {
    hash := crc32.ChecksumIEEE([]byte(key))

    // 二分查找第一个 >= hash 的节点
    idx := sort.Search(len(ch.sortedHashes), func(i int) bool {
        return ch.sortedHashes[i] >= hash
    })

    if idx == len(ch.sortedHashes) {
        idx = 0  // 环形，回到第一个节点
    }

    return ch.circle[ch.sortedHashes[idx]]
}
```

### 4.4 Raft一致性协议⭐⭐⭐

> Raft是目前最主流的分布式一致性协议，etcd、Consul、TiKV等均基于Raft。比Paxos更易理解和实现。

**三种角色**：
```
Leader：   唯一的写入入口，负责日志复制和心跳
Follower： 被动接收Leader的日志和心跳
Candidate：选举期间的临时角色（Follower超时后变为Candidate）
```

**Leader选举流程**：
```
1. Follower在election timeout内未收到Leader心跳
2. Follower → Candidate，term+1，投票给自己，向其他节点RequestVote
3. 收到多数派投票 → 成为Leader
4. 新Leader立即发送心跳抑制其他选举

关键规则：
- 每个term每个节点只投一票（先到先得）
- Candidate日志不能比自己旧的节点不投票
- election timeout随机化（150~300ms）避免同时选举（split vote）
```

**日志复制流程**：
```
1. 客户端写请求 → Leader
2. Leader将日志追加到本地Log
3. Leader并行发送AppendEntries给所有Follower
4. 多数派确认 → Leader提交日志（commit）
5. Leader返回成功给客户端
6. 后续心跳通知Follower也提交

日志匹配原则：
- 相同index和term的日志内容一定相同
- Leader发现Follower日志不一致时，回退Follower日志到一致点重新复制
```

**Raft vs Paxos**：
| 维度 | Raft | Paxos |
|------|------|-------|
| 可理解性 | 高（明确的Leader） | 低（多Proposer并发） |
| Leader | 必须有唯一Leader | 无强制Leader |
| 日志 | 连续的日志复制 | 可以乱序提交 |
| 工程实现 | etcd/Consul/TiKV | ZooKeeper(ZAB,Paxos变体) |

### 5.2 超时与重试

**超时配置**：
```go
client := &http.Client{
    Timeout: 5 * time.Second,  // 总超时
    Transport: &http.Transport{
        DialContext: (&net.Dialer{
            Timeout: 2 * time.Second,  // 连接超时

    },

```

**重试策略**：
```go
func CallWithRetry(fn func() error, maxRetries int) error {
    var err error
    for i := 0; i < maxRetries; i++ {
        err = fn()
        if err == nil {
            return nil
        }

        // 指数退避
        backoff := time.Duration(1<<uint(i)) * time.Second
        time.Sleep(backoff)
    }
    return err
}
```

**注意**：
- **幂等性**：重试前提是操作幂等
- **退避策略**：指数退避、随机抖动


### 5.3 SLO、可用性与「几个 9」

| 可用性 | 年不可用时间（约） | 工程含义 |
|--------|-------------------|----------|
| 99%（2 个 9） | ~3.65 天 | 个人项目/内部工具常见 |
| 99.9%（3 个 9） | ~8.8 小时 | 一般在线业务基线 |
| 99.99%（4 个 9） | ~52 分钟 | 核心交易/支付链路目标 |
| 99.999%（5 个 9） | ~5 分钟 | 需多活、极强运维与演练 |

**写法**：`SLO = 成功请求占比 / 延迟达标占比`（按业务选 SLI）。可用性不是堆机器，而是**故障域 + 冗余 + 演练 + 变更纪律**。

**粗算**：串联依赖时，端到端可用率 ≈ 各依赖可用率之积。若 5 个关键依赖各 99.9%，整体约 99.5%。

### 5.4 多活要点（同城双活 / 异地多活）

```
目标：单元化闭环——多数请求在本单元完成，跨单元是例外
路由：GSLB / 按 user_id 哈希到单元，避免请求在多单元漂移
数据：单元内强一致；跨单元异步复制 + 冲突解决（LWW / 业务仲裁）
切换：单元故障时切流 + 对账补偿；关注 RPO/RTO，而不是“绝对零丢失”口号
约束：全局唯一约束（手机号、证件号）要有中心化或可合并方案
```

> 全球化多活设计题见文末面试题 D01。

## 6. 幂等设计

### 6.1 为什么需要幂等

超时、重试、MQ 至少一次投递、用户双击都会导致**同一业务意图执行多次**。支付、扣库存、发券若不幂等，会直接资损。

**定义**：同一请求执行一次与执行多次，对业务的可观察结果一致；更优实践是**返回首次处理结果**，而不是只回“重复请求”。

### 6.2 常见方案

| 方案 | 做法 | 适用 |
|------|------|------|
| **幂等键** | 客户端 `Idempotency-Key`，服务端 Redis SETNX / 表唯一键 | HTTP 写接口 |
| **业务唯一键** | 订单号、支付流水号 UNIQUE | DB 最终防线 |
| **状态机** | `created→paid`，非法迁移直接返回当前态 | 订单/工单 |
| **Token 一次性** | 先发 token，提交时校验并删除（Lua/事务） | 表单防重 |
| **乐观锁** | `UPDATE ... WHERE version=?` | 库存/余额 |

### 6.3 落地要点

```
写接口：幂等键（入口） + 唯一索引（存储） + 返回首成结果
MQ 消费：consumer 侧去重表 / 业务键；假设至少一次投递
分布式事务：TCC Confirm/Cancel、SAGA 补偿必须幂等
```

## 7. 多级缓存与穿透 / 击穿 / 雪崩

### 7.1 多级缓存

```
浏览器/CDN → 接入层本地缓存 → Redis → DB
```

| 层级 | 特点 | 注意 |
|------|------|------|
| CDN/本地 | 极低延迟 | 失效与一致性难，适合静态/可脏读 |
| Redis | 共享热点 | 热 key、大 value、过期策略 |
| DB | 权威数据 | 被击穿时是最后防线，必须有限流 |

### 7.2 三类经典问题

| 问题 | 现象 | 常用解法 |
|------|------|----------|
| **穿透** | 查不存在的 key，打穿到 DB | 布隆过滤器；缓存空值（短 TTL） |
| **击穿** | 热点 key 过期瞬间并发打 DB | 互斥重建（单飞）；逻辑过期 + 异步刷新 |
| **雪崩** | 大量 key 同时过期或缓存集群宕机 | TTL 加抖动；多级降级；限流 + 依赖隔离 |

### 7.3 更新策略（选型一句话）

- **Cache Aside**：读 miss 回源再写缓存；更新先写 DB 再删缓存（最常用）
- **Read/Write Through**：缓存代理持久化（框架/中间件多）
- **延迟双删 / 订阅 binlog**：进一步降低并发下的脏缓存窗口

## 10. 分布式 ID（Snowflake / 号段）

#### Snowflake 算法详解

Snowflake（雪花算法）由 Twitter 开源，核心思想是用一个 **64bit 的 long** 来编码全局唯一 ID：

```
 0 | 00000000 00000000 00000000 00000000 00000000 0 | 00000000 00 | 00000000 0000
 ↑                      ↑                                ↑              ↑
1bit                 41bit 时间戳                    10bit 机器ID    12bit 序列号
符号位(0)        (当前时间-纪元, ~69年)            (最多1024节点)   (同毫秒内自增, 每ms 4096个)
```

| 字段 | 位数 | 说明 |
|------|------|------|
| 符号位 | 1 bit | 始终为 0，保证 ID 为正数 |
| 时间戳 | 41 bit | 毫秒级，自定义纪元起始，可用约 69 年 |
| 机器 ID | 10 bit | 可拆为 5bit 数据中心 + 5bit 机器，共 1024 节点 |
| 序列号 | 12 bit | 同一毫秒内自增，单节点每毫秒最多生成 4096 个 ID |

**核心优势**：趋势递增、不依赖外部存储、高性能（本地生成）、ID 中可反解出时间。

#### 时钟回拨问题

**产生原因**：
- NTP（Network Time Protocol）同步时将系统时钟向回调整
- 闰秒调整
- 虚拟机快照恢复后时间回退

**检测方案**：每次生成 ID 时比较当前时间戳与上次生成 ID 的时间戳，若 `currentTimestamp < lastTimestamp` 则发生了回拨。

**处理策略**：

| 策略 | 做法 | 适用场景 |
|------|------|----------|
| 直接报错 | 抛异常，调用方重试 | 回拨容忍度为 0 的场景 |
| 短暂等待 | 若回拨 < 阈值（如 5ms），spin 等待追上 | 微小回拨（NTP 微调） |
| 借用未来时间戳 | 在序列号中"借位"，使用 lastTimestamp+1 | 不允许报错的高可用场景 |
| 扩展位 | 预留 2-3bit 作为时钟序列号，每次回拨 +1 | 回拨频繁但幅度小的环境 |

#### Go 完整实现（含时钟回拨处理）

```go
package snowflake

import (
    "errors"
    "sync"
    "time"
)

const (
    epoch             int64 = 1609459200000 // 自定义纪元: 2021-01-01 00:00:00 UTC
    workerIDBits      uint8 = 10
    sequenceBits      uint8 = 12
    maxWorkerID       int64 = -1 ^ (-1 << workerIDBits) // 1023
    maxSequence       int64 = -1 ^ (-1 << sequenceBits) // 4095
    workerIDShift           = sequenceBits               // 12
    timestampShift          = sequenceBits + workerIDBits // 22
    maxClockBackward        = 5 // 允许最大时钟回拨毫秒数
)

type Generator struct {
    mu            sync.Mutex
    lastTimestamp int64
    workerID      int64
    sequence      int64
}

func NewGenerator(workerID int64) (*Generator, error) {
    if workerID < 0 || workerID > maxWorkerID {
        return nil, errors.New("worker ID out of range [0, 1023]")
    }
    return &Generator{workerID: workerID}, nil
}

func (g *Generator) currentMillis() int64 {
    return time.Now().UnixMilli()
}

func (g *Generator) waitUntil(target int64) int64 {
    for {
        now := g.currentMillis()
        if now >= target {
            return now
        }
        time.Sleep(time.Millisecond)
    }
}

func (g *Generator) NextID() (int64, error) {
    g.mu.Lock()
    defer g.mu.Unlock()

    now := g.currentMillis()

    // ---- 时钟回拨处理 ----
    if now < g.lastTimestamp {
        offset := g.lastTimestamp - now
        if offset <= maxClockBackward {
            // 短暂回拨：spin 等待追上
            now = g.waitUntil(g.lastTimestamp)
        } else {
            return 0, errors.New("clock moved backwards, refusing to generate ID")
        }
    }

    if now == g.lastTimestamp {
        g.sequence = (g.sequence + 1) & maxSequence
        if g.sequence == 0 {
            // 当前毫秒序列号用完，等待下一毫秒
            now = g.waitUntil(g.lastTimestamp + 1)
        }
    } else {
        g.sequence = 0
    }

    g.lastTimestamp = now

    id := ((now - epoch) << timestampShift) |
        (g.workerID << int64(workerIDShift)) |
        g.sequence
    return id, nil
}
```

**Worker ID 分配方案**：
- **配置文件 / 环境变量**：最简单，适合节点固定的场景
- **ZooKeeper 顺序节点**：创建 `/snowflake/workers/` 顺序子节点，取编号 mod 1024
- **数据库自增**：启动时 INSERT 获取自增 ID，取 mod 1024
- **IP/端口 Hash**：`hash(ip + port) % 1024`，需注意碰撞

#### 号段模式（Leaf-Segment）

美团 Leaf-Segment 方案核心思路：每次从 DB **批量领取**一段 ID（号段），本地发号，号段用完再取。

**数据库表设计**：

```sql
CREATE TABLE leaf_alloc (
    biz_tag    VARCHAR(128) NOT NULL COMMENT '业务标识',
    max_id     BIGINT       NOT NULL COMMENT '当前已分配的最大ID',
    step       INT          NOT NULL COMMENT '每次领取的号段长度',
    version    INT          NOT NULL COMMENT '乐观锁版本号',
    update_time TIMESTAMP   NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (biz_tag)
) ENGINE=InnoDB;
```

**领号 SQL（乐观锁）**：

```sql
UPDATE leaf_alloc
   SET max_id = max_id + step, version = version + 1
 WHERE biz_tag = #{bizTag} AND version = #{version};
```

**双 Buffer 预加载**：

```
                ┌──────────────────────┐
                │  Segment Buffer[0]   │  ← 当前使用中
                │  [1001 ... 2000]     │
                ├──────────────────────┤
                │  Segment Buffer[1]   │  ← 后台预加载
                │  [2001 ... 3000]     │
                └──────────────────────┘
触发条件：当前 Buffer 使用率 > 10%（可配置）时，异步加载下一个号段到另一个 Buffer
切换条件：当前 Buffer 用完，原子切换到另一个已就绪的 Buffer
```

**优缺点**：
- ✅ 可容忍短暂 DB 宕机（本地还有余量）
- ✅ ID 严格递增（非趋势递增，是真递增）
- ❌ 服务重启号段浪费
- ❌ 依赖数据库，DB 长时间不可用仍会中断

#### 分布式 ID 方案对比

| 方案 | 有序性 | 性能 | 可用性 | 外部依赖 | 信息安全 | 适用场景 |
|------|--------|------|--------|----------|----------|----------|
| UUID v4 | 无序 | ★★★★★ | 无单点 | 无 | ★★★★★（不可反解） | 需全局唯一但不需有序 |
| Snowflake | 趋势递增 | ★★★★★ | 无单点 | 无（需分配workerID） | ★★（可反解时间/机器） | 高并发、趋势有序 |
| Leaf-Segment | 严格递增 | ★★★★ | 较高（双Buffer） | MySQL | ★★★（连续可预测） | 订单号等需递增场景 |
| Redis INCR | 严格递增 | ★★★★ | 取决于Redis HA | Redis | ★★★ | 已有 Redis 基础设施 |
| 数据库自增 | 严格递增 | ★★ | 单点瓶颈 | MySQL | ★★★ | 低并发、简单业务 |

> **面试高频追问**：为什么 Snowflake ID 用作 MySQL 主键时，比 UUID 性能好？——因为趋势递增的 ID 在 B+ Tree 上是顺序写入，不会导致频繁的页分裂；UUID 是随机的，插入位置随机，页分裂严重，写放大大。

## 11. 分布式锁与 RedLock

#### Redis 单节点分布式锁：标准实现

**加锁**（原子操作）：

```redis
SET lock_key <random_value> NX PX 30000
```

- `NX`：key 不存在才设置（互斥）
- `PX 30000`：过期时间 30s（防死锁）
- `random_value`：客户端唯一标识（防误删别人的锁）

**解锁**（Lua 脚本保证原子性）：

```lua
-- KEYS[1] = lock_key, ARGV[1] = random_value
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

> **为什么不能直接 DEL？**——客户端 A 持锁超时后锁自动过期，客户端 B 获得新锁，此时 A 的 DEL 会误删 B 的锁。必须先比较 `random_value` 确认是自己的锁再删。

#### 锁续期：Watchdog 机制（Redisson 方案）

**问题**：业务执行时间不可控，若锁在业务完成前过期，其他客户端可获得锁，导致并发冲突。

**Redisson Watchdog 工作原理**：

```
客户端获取锁（默认 leaseTime = 30s）
    │
    ├── 启动 Watchdog 定时任务（每 leaseTime/3 = 10s 执行一次）
    │       │
    │       ├── 检查客户端是否仍持有锁
    │       │       │
    │       │       ├── 是 → PEXPIRE lock_key 30000（续期）
    │       │       └── 否 → 停止 Watchdog
    │       │
    │       └── 循环直到锁释放
    │
    └── 业务执行完毕 → 释放锁 → Watchdog 自动停止
```

**关键细节**：
- 只有未指定 `leaseTime` 时 Watchdog 才启动；手动指定了过期时间则不续期
- 客户端进程崩溃 → Watchdog 线程一起挂掉 → 锁到期自动释放 → 不会死锁

#### RedLock 算法

Redis 作者 Antirez 提出的分布式锁方案，目标是解决**单节点 Redis 宕机导致锁丢失**的问题。

**算法步骤（5 个独立 Redis 节点）**：

```
1. 获取当前时间 T1
2. 依次向 5 个节点发送 SET lock NX PX <ttl>
3. 获取当前时间 T2
4. 计算：锁获取耗时 = T2 - T1
         锁实际有效时间 = ttl - (T2 - T1) - 时钟漂移补偿
5. 判断：
   - 成功获取 >= 3 个节点（多数派）的锁
   - 且锁实际有效时间 > 0
   → 加锁成功
6. 若加锁失败 → 向所有节点发送释放锁请求
```

#### Martin Kleppmann vs Antirez 之争

这是分布式系统领域最经典的一次公开技术辩论（2016年）。

**Kleppmann 的核心观点**（"How to do distributed locking"）：

1. **分布式锁有两种用途**：
   - **效率型**（避免重复工作）：单节点锁就够了，锁偶尔失效可接受
   - **正确性型**（保护数据一致性）：必须绝对安全，RedLock 做不到

2. **RedLock 依赖时钟假设，这在分布式系统中不安全**：
   - 进程可能被 GC pause / 系统调度挂起任意时间
   - 持锁客户端在 GC 暂停期间锁已过期，但客户端不知道
   - NTP 跳变可能导致节点感知时间不一致

3. **正确的方案是 Fencing Token**：
   ```
   Client A 获取锁 → 拿到 token=33
   Client A GC暂停... 锁过期
   Client B 获取锁 → 拿到 token=34
   Client A 恢复，带 token=33 写存储
   存储层拒绝：已见过更大的 token=34
   ```
   通过单调递增的 fencing token，让存储层拒绝过期的写操作。

**Antirez 的反驳**（"Is Redlock safe?"）：

1. **GC pause 不是问题**：锁获取后会检查剩余有效时间，GC pause 发生在获取过程中会被检测到
2. **时钟漂移可控**：现代运维环境下 NTP 配置得当，时钟漂移在毫秒级，远小于锁的 TTL
3. **Fencing Token 要求存储层支持 CAS**：如果存储层本身能做 CAS，某些场景根本不需要锁
4. **RedLock 对"合理的系统假设"下是安全的**：不追求拜占庭容错，只要时钟大致正确即可

**争论核心总结**：

| 维度 | Kleppmann | Antirez |
|------|-----------|---------|
| 理论立场 | 异步系统模型，不能假设时钟 | 半同步模型，时钟有界漂移 |
| 对 GC pause | 致命缺陷 | 获取阶段可检测 |
| 推荐方案 | Fencing token + 单节点锁 | RedLock |
| 核心分歧 | 分布式锁**不应该**依赖时钟 | 工程实践中时钟**足够可靠** |

#### 工程实践：分布式锁选型决策

| 场景 | 推荐方案 | 理由 |
|------|----------|------|
| 防重复执行（效率型） | Redis 单节点锁 | 简单高效，偶尔失效无严重后果 |
| 高并发抢锁 + 中等一致性 | Redis 单节点锁 + Watchdog | Redisson 开箱即用，性能好 |
| 强一致性 + 已有 ZK 集群 | ZooKeeper 临时顺序节点 | CP 系统，锁语义严格 |
| 强一致性 + 云原生 / K8s | etcd Lease + Revision | 轻量、已集成在 K8s 中 |
| 跨机房 + 极端可用性要求 | RedLock（谨慎使用） | 无单点，但要确保 NTP 同步良好 |
| 金融级正确性 | ZK/etcd + Fencing Token | 遵循 Kleppmann 建议 |

> **面试回答模板**：先说清楚场景是效率型还是正确性型；效率型直接 Redis 单节点锁；正确性型用 ZK/etcd，如果面试官追问 RedLock，能讲出 Kleppmann vs Antirez 的核心分歧即为加分项。

#### etcd 分布式锁实现（Lease + Revision）

etcd 基于 **Raft 一致性协议**，天然适合做分布式锁：

**核心机制**：

1. **Lease（租约）**：类似 Redis 的过期时间，客户端需要定期续租（KeepAlive）
2. **Revision（全局版本号）**：etcd 每次写操作全局递增，天然的 Fencing Token
3. **Watch**：监听 key 变更，实现阻塞等待

**加锁流程**：

```
1. 创建 Lease（如 TTL=15s），启动 KeepAlive 自动续租
2. 在锁前缀下创建 key：PUT /lock/my-resource/<lease-id>
   - 使用 Lease ID 作为 key 后缀保证唯一
3. 获取该前缀下所有 key，按 Revision 排序
4. 若自己的 key 的 Revision 最小 → 获得锁
5. 否则 Watch Revision 比自己小的前一个 key
   - 前一个 key 被删除 → 轮到自己 → 获得锁
```

**Go 实现（使用 etcd clientv3）**：

```go
import (
    "context"
    clientv3 "go.etcd.io/etcd/client/v3"
    "go.etcd.io/etcd/client/v3/concurrency"
)

func acquireEtcdLock(endpoints []string) error {
    cli, err := clientv3.New(clientv3.Config{Endpoints: endpoints})
    if err != nil {
        return err
    }
    defer cli.Close()

    // 创建 Session（内含 Lease + KeepAlive）
    session, err := concurrency.NewSession(cli, concurrency.WithTTL(15))
    if err != nil {
        return err
    }
    defer session.Close()

    // 创建分布式锁
    mutex := concurrency.NewMutex(session, "/lock/my-resource")

    // 加锁（阻塞直到获取）
    if err := mutex.Lock(context.TODO()); err != nil {
        return err
    }

    // mutex.Header().Revision 即为 Fencing Token
    fencingToken := mutex.Header().Revision

    // --- 执行业务逻辑（使用 fencingToken 做写保护）---
    _ = fencingToken

    // 释放锁
    return mutex.Unlock(context.TODO())
}
```

**etcd 锁 vs Redis 锁 vs ZK 锁**：

| 维度 | Redis | ZooKeeper | etcd |
|------|-------|-----------|------|
| 一致性模型 | AP（主从异步复制） | CP（ZAB 协议） | CP（Raft 协议） |
| Fencing Token | 不原生支持 | zxid 可用 | Revision 天然支持 |
| 锁释放 | 过期 / DEL | 临时节点自动删除 | Lease 过期自动删除 |
| 性能 | ★★★★★ | ★★★ | ★★★★ |
| 运维复杂度 | 低 | 高（JVM 调优、ZAB） | 中（Go 原生、K8s 友好） |
| 惊群效应 | N/A | 顺序节点避免 | Watch 前一个 key 避免 |

## 13. 系统设计案例

### 案例：设计一个短链接服务

按 §0 模板：Clarify → Estimate → API → Data → Design → Deep Dive。

#### 1) Clarify

- 功能：长链→短码；短码 301/302 跳转；可选过期、自定义码、点击统计
- 非功能：写 QPS（创建）远小于读 QPS（跳转）；读延迟敏感；短码尽量短且全局唯一

#### 2) Estimate（示例假设）

| 假设 | 数量级 |
|------|--------|
| 日新建短链 | 1e7 |
| 日跳转 | 1e9 → 平均 ≈ 1e4 QPS，峰谷 10× → 峰值 ~1e5 QPS |
| 短码长度 | 6 位 Base62 → 空间 ≈ 568 亿 |
| 单条存储 | short+long+元数据 ≈ 500B～1KB → 年增 TB 内（可冷热分层） |

#### 3) API

```
POST /api/v1/links  {long_url, expire_at?} → {short_code}
GET  /{short_code} → 重定向到 long_url
```

#### 4) 短码生成与碰撞

| 方案 | 优点 | 碰撞 |
|------|------|------|
| **分布式 ID + Base62**（推荐） | 天然唯一、趋势有序 | 基本无碰撞 |
| Hash(长链)+Base62 截断 | 同长链可稳定映射 | **必须处理碰撞** |

**碰撞处理（Hash 方案必备）**：

```go
func GenerateShortCode(longURL string) (string, error) {
    for salt := 0; salt < 5; salt++ {
        sum := md5.Sum([]byte(fmt.Sprintf("%s#%d", longURL, salt)))
        code := base62.Encode(sum[:6]) // 截断有碰撞可能
        // INSERT short_code PK；冲突则换 salt 重试
        if err := db.InsertIgnore(code, longURL); err == nil {
            return code, nil
        }
    }
    return "", errors.New("short code collision exhausted")
}
```

Snowflake/号段方案见 [§10](#10-分布式-idsnowflake--号段)。

#### 5) 301 vs 302

| | 301 永久 | 302 临时 |
|--|----------|----------|
| 缓存 | 浏览器/CDN 可强缓存 | 每次多回源，利于统计与变更 |
| 适用 | 永不变更的短链 | 要计点击、要支持失效/更换长链（更常见） |

生产多选 **302**（或 307）以便统计与管控；若短链不可变且要极致省流量可用 301 + CDN。

#### 6) 过期与存储

```sql
CREATE TABLE short_links (
  short_code VARCHAR(16) PRIMARY KEY,
  long_url   TEXT NOT NULL,
  expire_at  TIMESTAMP NULL,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY idx_expire (expire_at)
);
```

- 读路径：Redis `GET short:{code}` → miss 查 DB → 回填（TTL ≤ 剩余有效期）
- 过期：懒过期（读时校验 `expire_at`）+ 定时任务删；缓存同步删/短 TTL
- 防滥用：创建接口鉴权 + 限流；恶意循环跳转做域名黑名单

#### 7) 架构

```
[用户] → [CDN] → [LB] → [短链服务]
                           ├─ Redis（热点跳转）
                           └─ MySQL（权威数据，短码 PK）
```

### 案例：设计秒杀系统

#### 需求分析

**业务特点**：
- 瞬时超高并发（百万级QPS）
- 读多写少（浏览:下单 ≈ 1000:1）
- 库存有限（通常几百到几千件）
- 业务正确性要求（绝对不能超卖；可用最终落库，不必整链 CAP-CP）

**核心指标**：
| 指标 | 目标 |
|------|------|
| 峰值QPS | 100万+ |
| 库存准确性 | 绝对不超卖 |
| 下单延迟 | < 500ms |
| 可用性 | 99.99% |

#### 架构设计

```
                        ┌─────────────────────────────────────────────────────┐
                        │                    秒杀全链路架构                      │
                        └─────────────────────────────────────────────────────┘

   [用户] ──→ [CDN静态页] ──→ [Nginx限流+本地缓存]
                                      │ 峰值约 100 万 QPS
                          ┌───────────┴───────────┐
                          │    第一层：接入层过滤     │  放行约 1000 QPS（拦掉 ~99.9%）
                          │  • 验证码/答题防刷       │
                          │  • 令牌桶限流(1000QPS)   │
                          │  • 用户维度频控          │
                          └───────────┬───────────┘
                                      │ ~1000 QPS
                          ┌───────────┴───────────┐
                          │   第二层：Redis预扣库存   │  仅库存份数可成功（如几百～几千）
                          │  • Lua原子扣减           │
                          │  • stock < qty 直接拒绝  │
                          │  • 扣减成功发MQ          │
                          └───────────┬───────────┘
                                      │ ~库存量级消息
                          ┌───────────┴───────────┐
                          │   第三层：Kafka异步下单   │
                          │  • 削峰填谷              │
                          │  • 消费者慢慢处理        │
                          └───────────┬───────────┘
                                      │
                          ┌───────────┴───────────┐
                          │   第四层：订单服务        │
                          │  • 创建订单              │
                          │  • MySQL扣库存(乐观锁)   │
                          │  • 发送支付通知          │
                          └───────────────────────┘
```

**核心思想：层层过滤。** 100 万 → 1000 QPS 是拦掉约 **99.9%**（不是 90%）；真正成功下单量级由库存决定。
一致性模型是 **Redis 原子预扣 + MQ 最终落库**，追求「不超卖」，不宜把整条链路标成 CAP-CP。
#### 核心代码

**1. Redis Lua预扣库存（原子操作）**

```lua
-- seckill_deduct.lua
-- KEYS[1]: 库存key  seckill:stock:{sku_id}
-- KEYS[2]: 已购用户集合  seckill:bought:{sku_id}
-- ARGV[1]: 用户ID
-- ARGV[2]: 扣减数量(通常为1)

-- 1. 判断用户是否已购买（防重复下单）
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -1  -- 已购买
end

-- 2. 获取当前库存，并校验「库存 ≥ 扣减数量」（避免 stock=1 却 DECRBY 2 扣成负数）
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil then
    return -2  -- 活动不存在
end

local qty = tonumber(ARGV[2])
if qty == nil or qty <= 0 then
    return -3  -- 参数非法
end

if stock < qty then
    return 0   -- 库存不足
end

-- 3. 扣减库存 + 记录用户（原子操作）
redis.call('DECRBY', KEYS[1], qty)
redis.call('SADD', KEYS[2], ARGV[1])

return 1  -- 扣减成功
```

**2. 秒杀服务（Go实现）**

```go
package seckill

import (
    "context"
    "encoding/json"
    "fmt"
    "time"

    "github.com/go-redis/redis/v8"
    "github.com/segmentio/kafka-go"
)

// SeckillService 秒杀服务
type SeckillService struct {
    rdb         *redis.Client
    kafkaWriter *kafka.Writer
    luaScript   *redis.Script
}

// SeckillOrder 秒杀订单消息
type SeckillOrder struct {
    UserID    int64  `json:"user_id"`
    SkuID     int64  `json:"sku_id"`
    OrderID   string `json:"order_id"`
    Timestamp int64  `json:"timestamp"`
}

func NewSeckillService(rdb *redis.Client, kafkaWriter *kafka.Writer) *SeckillService {
    // 加载Lua脚本（启动时加载，运行时用SHA调用，减少网络开销）
    luaScript := redis.NewScript(`
        if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
            return -1
        end
        local stock = tonumber(redis.call('GET', KEYS[1]))
        if stock == nil then return -2 end
        local qty = tonumber(ARGV[2])
        if qty == nil or qty <= 0 then return -3 end
        if stock < qty then return 0 end
        redis.call('DECRBY', KEYS[1], qty)
        redis.call('SADD', KEYS[2], ARGV[1])
        return 1
    `)
    return &SeckillService{rdb: rdb, kafkaWriter: kafkaWriter, luaScript: luaScript}
}

// DoSeckill 执行秒杀（核心入口）
func (s *SeckillService) DoSeckill(ctx context.Context, userID, skuID int64) (string, error) {
    stockKey := fmt.Sprintf("seckill:stock:%d", skuID)
    boughtKey := fmt.Sprintf("seckill:bought:%d", skuID)

    // 1. Redis Lua原子扣库存
    result, err := s.luaScript.Run(ctx, s.rdb,
        []string{stockKey, boughtKey},
        userID, 1,
    ).Int()
    if err != nil {
        return "", fmt.Errorf("redis error: %w", err)
    }

    switch result {
    case -1:
        return "", fmt.Errorf("already purchased")
    case -2:
        return "", fmt.Errorf("activity not found")
    case 0:
        return "", fmt.Errorf("sold out")
    }

    // 2. 扣减成功，发送Kafka异步下单
    orderID := generateOrderID(userID, skuID)
    msg := SeckillOrder{
        UserID:    userID,
        SkuID:     skuID,
        OrderID:   orderID,
        Timestamp: time.Now().UnixMilli(),
    }
    body, _ := json.Marshal(msg)

    err = s.kafkaWriter.WriteMessages(ctx, kafka.Message{
        Key:   []byte(fmt.Sprintf("%d", userID)),
        Value: body,
    })
    if err != nil {
        // Kafka写入失败 → 回滚Redis库存
        s.rdb.Incr(ctx, stockKey)
        s.rdb.SRem(ctx, boughtKey, userID)
        return "", fmt.Errorf("send message failed: %w", err)
    }

    // 3. 返回订单号，前端轮询订单状态
    return orderID, nil
}

func generateOrderID(userID, skuID int64) string {
    return fmt.Sprintf("SK%d%d%d", skuID, userID, time.Now().UnixNano())
}
```

**3. 订单消费者（Kafka Consumer）**

```go
// ConsumeOrders 消费秒杀消息，创建真实订单
func (s *SeckillService) ConsumeOrders(ctx context.Context) error {
    reader := kafka.NewReader(kafka.ReaderConfig{
        Brokers:  []string{"kafka:9092"},
        Topic:    "seckill-orders",
        GroupID:  "seckill-consumer",
        MinBytes: 1e3,
        MaxBytes: 10e6,
    })
    defer reader.Close()

    for {
        msg, err := reader.ReadMessage(ctx)
        if err != nil {
            return err
        }

        var order SeckillOrder
        if err := json.Unmarshal(msg.Value, &order); err != nil {
            continue // 跳过无法解析的消息
        }

        // 创建订单（MySQL乐观锁扣库存）
        err = s.createOrder(ctx, &order)
        if err != nil {
            // 记录失败日志，后续补偿
            log.Printf("create order failed: %v, order: %+v", err, order)
        }
    }
}

// createOrder MySQL 乐观锁扣库存 + 创建订单
func (s *SeckillService) createOrder(ctx context.Context, order *SeckillOrder) error {
    tx, err := db.BeginTx(ctx, nil)
    if err != nil {
        return err
    }
    defer tx.Rollback()

    // 先读出版本号，再按 version 条件更新（currentVersion 必须来自本次读，不能是未定义变量）
    var currentVersion int64
    err = tx.QueryRowContext(ctx,
        "SELECT version FROM sku_stock WHERE sku_id = ?", order.SkuID,
    ).Scan(&currentVersion)
    if err != nil {
        return err
    }

    result, err := tx.ExecContext(ctx,
        "UPDATE sku_stock SET stock = stock - 1, version = version + 1 "+
            "WHERE sku_id = ? AND stock > 0 AND version = ?",
        order.SkuID, currentVersion)
    if err != nil {
        return err
    }
    affected, _ := result.RowsAffected()
    if affected == 0 {
        // 版本冲突或库存不足：可重试读版本，或直接失败后走补偿回滚 Redis
        return fmt.Errorf("stock deduct failed (optimistic lock)")
    }

    // 订单号唯一索引兜底幂等
    _, err = tx.ExecContext(ctx,
        "INSERT INTO orders (order_id, user_id, sku_id, status, created_at) "+
            "VALUES (?, ?, ?, 'CREATED', NOW())",
        order.OrderID, order.UserID, order.SkuID)
    if err != nil {
        return err
    }

    return tx.Commit()
}
```

#### 关键难点

| 难点 | 解决方案 | 说明 |
|------|----------|------|
| **超卖** | Redis Lua原子扣减 + MySQL乐观锁双重保障 | Lua保证Redis操作原子性，乐观锁保证DB最终一致 |
| **重复下单** | Redis SISMEMBER判重 + 订单表唯一索引 | 两层防护，即使Redis判重失效，DB也能兜底 |
| **流量洪峰** | 多级过滤：CDN→Nginx→Redis→Kafka | 100万→接入约1000QPS（拦 ~99.9%）；成功单量级≈库存 |
| **Kafka写失败** | 回滚Redis库存（INCR + SREM） | 保证Redis和下游状态最终一致 |
| **热key问题** | 库存分片：将1000库存拆为10个key各100 | 分散单个Redis节点压力 |
| **服务降级** | 活动未开始返回静态页、库存为0全局标记直接拒绝 | 尽早拦截无效请求 |

**降级策略分级**：
```
Level 0（正常）：全链路正常处理
Level 1（轻度）：关闭推荐、评论等非核心模块
Level 2（中度）：Redis预扣库存失败 → 直接返回"系统繁忙"
Level 3（重度）：Kafka不可用 → 同步写DB（限流到极低QPS）
Level 4（熔断）：全站返回"活动太火爆，请稍后再试"静态页
```

### 案例：设计Feed流系统

#### 需求分析

**业务场景**：
- 用户关注其他用户后，在首页看到关注人的动态（类似微博、朋友圈、Twitter）
- 核心操作：发布动态（写）、刷Feed流（读）、关注/取关（关系变更）

**核心指标**：
| 指标 | 目标 |
|------|------|
| Feed读取延迟 | P99 < 200ms |
| 发布延迟 | < 1s（异步可接受） |
| 日活用户 | 1亿+ |
| 单用户关注上限 | 5000人 |
| 大V粉丝数 | 千万级 |

#### 推/拉/混合模式对比

```
【推模式（Write Fanout / Push）】

用户A发布动态 → 写入A的所有粉丝的收件箱（Timeline）

  A发布帖子P1
      │
      ├──→ 写入粉丝B的inbox: [P1, ...]
      ├──→ 写入粉丝C的inbox: [P1, ...]
      └──→ 写入粉丝D的inbox: [P1, ...]

  读取：直接读自己的inbox，已排好序 → 极快
  写入：N个粉丝 → N次写操作 → 大V写放大严重

  ✅ 读快（O(1)直接取inbox）
  ❌ 写放大（大V百万粉丝 → 百万次写）
  ❌ 存储大（每个粉丝都存一份引用）


【拉模式（Read Fanout / Pull）】

用户B刷Feed → 实时拉取所有关注人的最新动态 → 合并排序

  B刷Feed
      │
      ├──→ 拉取关注人A的最新动态
      ├──→ 拉取关注人C的最新动态
      └──→ 拉取关注人D的最新动态
      │
      └──→ 合并排序，取Top N

  读取：拉取K个关注人的动态，合并排序 → 关注多则慢
  写入：只写自己的发件箱 → 极快

  ✅ 写快（只写一份）
  ✅ 存储小
  ❌ 读放大（关注5000人 → 5000次读+排序）
  ❌ 延迟高


【混合模式（推荐方案）】

  普通用户（粉丝<10万）→ 推模式（写粉丝inbox）
  大V用户（粉丝≥10万）→ 拉模式（读时实时拉取）

  B刷Feed:
      inbox（已有普通关注人推过来的动态）
        +
      实时拉取关注的大V的最新动态
        ↓
      合并排序，取Top N
```

#### 架构设计

```
                    ┌──────────────────────────────────────────────────┐
                    │              Feed流混合架构                       │
                    └──────────────────────────────────────────────────┘

  【写入路径】
  用户发布动态 ──→ [发布服务] ──→ [MySQL写入动态表]
                       │
                       ├──→ 判断粉丝数
                       │    ├── < 10万 → [Kafka: fanout-topic]
                       │    │              → [Fanout消费者] → 写入粉丝inbox(Redis ZSET)
                       │    │
                       │    └── ≥ 10万 → 只写发件箱(Redis ZSET)，不扇出
                       │
                       └──→ [更新用户发件箱 outbox:user_id]

  【读取路径】
  用户刷Feed ──→ [Feed服务]
                    │
                    ├── 1. 读取自己的inbox (ZREVRANGE，已有推过来的内容)
                    │
                    ├── 2. 获取关注的大V列表
                    │      → 逐个拉取大V的outbox最新内容

                    ├── 3. 合并排序 (归并排序，按时间戳倒序)
                    │
                    └── 4. 补全内容详情 (批量mget帖子内容)
```

```go
// Publish 发布动态
func (s *FeedService) Publish(ctx context.Context, authorID, postID int64) error {
    score := float64(time.Now().UnixMilli())

    // 1. 写入自己的发件箱
    s.rdb.ZAdd(ctx, outboxKey(authorID), &redis.Z{
        Score:  score,
        Member: postID,
    })
    s.rdb.ZRemRangeByRank(ctx, outboxKey(authorID), 0, -inboxMaxSize-1) // 裁剪

    // 2. 判断是否需要扇出
    followerCount, _ := s.relationSvc.GetFollowerCount(ctx, authorID)
    if followerCount >= bigVThreshold {
        // 大V：不扇出，粉丝读时拉取
        return nil
    }

    // 3. 普通用户：异步扇出到粉丝inbox（通过Kafka）
    return s.sendFanoutMessage(ctx, authorID, postID, score)
}

// FanoutToFollowers Kafka消费者调用：推送到粉丝inbox
func (s *FeedService) FanoutToFollowers(ctx context.Context, authorID, postID int64, score float64) error {
    // 分批获取粉丝列表
    var cursor int64
    for {
        followers, nextCursor, err := s.relationSvc.GetFollowersBatch(ctx, authorID, cursor, 1000)
        if err != nil {
            return err
        }

        // Pipeline批量写入（减少网络往返）
        pipe := s.rdb.Pipeline()
        for _, followerID := range followers {
            key := inboxKey(followerID)
            pipe.ZAdd(ctx, key, &redis.Z{Score: score, Member: postID})
            pipe.ZRemRangeByRank(ctx, key, 0, -inboxMaxSize-1) // 保持inbox大小
        }
        _, err = pipe.Exec(ctx)
        if err != nil {
            return err
        }

        if nextCursor == 0 {
            break
        }
        cursor = nextCursor
    }
    return nil
}
```

**3. 读取Feed流（混合模式）**

```go
// GetFeed 游标分页（修复：不能对 inbox 做 offset 后再与大V合并——会漏数据/重页）
// cursorScore：上一页最后一条的 score；cursorID：同 score 时的 postID 打破并列
func (s *FeedService) GetFeed(ctx context.Context, userID int64, cursorScore float64, cursorID int64, limit int64) ([]FeedItem, float64, int64, error) {
    // 多取一些候选，再在合并后按游标过滤（首页 cursorScore=+Inf）
    fetch := limit * 3
    if fetch < 50 {
        fetch = 50
    }

    maxScore := "+inf"
    if cursorScore > 0 {
        maxScore = fmt.Sprintf("(%f", cursorScore) // 开区间，避免重复上一页最后一条
    }
    inboxItems, err := s.rdb.ZRevRangeByScoreWithScores(ctx, inboxKey(userID), &redis.ZRangeBy{
        Min: "-inf", Max: maxScore, Count: fetch,
    }).Result()
    if err != nil {
        return nil, 0, 0, err
    }

    bigVList, err := s.relationSvc.GetFollowingBigVs(ctx, userID)
    if err != nil {
        return nil, 0, 0, err
    }

    var bigVItems []redis.Z
    if len(bigVList) > 0 {
        pipe := s.rdb.Pipeline()
        cmds := make([]*redis.ZSliceCmd, len(bigVList))
        for i, bigVID := range bigVList {
            cmds[i] = pipe.ZRevRangeByScoreWithScores(ctx, outboxKey(bigVID), &redis.ZRangeBy{
                Min: "-inf", Max: maxScore, Count: fetch,
            })
        }
        pipe.Exec(ctx)
        for _, cmd := range cmds {
            items, _ := cmd.Result()
            bigVItems = append(bigVItems, items...)
        }
    }

    merged := mergeAndSort(inboxItems, bigVItems)
    // 同 score 用 postID 二次过滤，防止并列时漏/重
    page := make([]redis.Z, 0, limit)
    for _, item := range merged {
        pid := toInt64(item.Member)
        if cursorScore > 0 && (item.Score > cursorScore || (item.Score == cursorScore && pid >= cursorID)) {
            continue
        }
        page = append(page, item)
        if int64(len(page)) >= limit {
            break
        }
    }

    items, err := s.batchGetPostContent(ctx, page)
    if err != nil || len(page) == 0 {
        return items, 0, 0, err
    }
    last := page[len(page)-1]
    return items, last.Score, toInt64(last.Member), nil
}

// mergeAndSort 合并两个有序列表并按score倒序排列
func mergeAndSort(a, b []redis.Z) []redis.Z {
    merged := append(a, b...)
    sort.Slice(merged, func(i, j int) bool {
        return merged[i].Score > merged[j].Score // 按时间倒序
    })
    // 去重（同一个postID可能在inbox和outbox都出现）
    seen := make(map[interface{}]bool)
    result := make([]redis.Z, 0, len(merged))
    for _, item := range merged {
        if !seen[item.Member] {
            seen[item.Member] = true
            result = append(result, item)
        }
    }
    return result
}
```

#### 关键难点

| 难点 | 解决方案 | 说明 |
|------|----------|------|
| **大V写放大** | 混合模式：大V不扇出，读时拉取 | 粉丝>10万的用户只写outbox，粉丝拉取时合并 |
| **Feed读延迟** | inbox用Redis ZSET + Pipeline批量拉大V | ZREVRANGE O(logN+M)，Pipeline减少RTT |
| **关注/取关一致性** | 取关时异步清理inbox中该用户的内容 | 不立即一致没关系，下次刷新自然过滤 |
| **新用户冷启动** | 关注时回填最近 N 条到 inbox；大V 不回填、读时拉 outbox | 避免关注后空白；回填异步限流防写放大 |
| **混合分页正确性** | **游标（score+id）在合并流上切片**，禁止 inbox offset 后再拼大V | offset 分页会与大V实时流错位导致漏页/重页 |
| **内存控制** | inbox设上限2000条，ZREMRANGEBYRANK裁剪 | 老内容归档到MySQL/HBase |
| **排序模型扩展** | score可改为算法打分（时间+热度+兴趣） | 从Timeline模型升级为推荐Feed |


**冷启动回填流程**：
```
用户 B 新关注普通用户 A
  → 异步任务：把 A 的 outbox 最近 N 条 ZADD 到 B 的 inbox
  → 限流/削峰：明星互关风暴时用队列聚合
用户 B 新关注大V
  → 不回填 inbox（避免写放大）
  → 读 Feed 时按游标拉取大V outbox 再合并
```
**大V判定策略**：
```
静态判定：粉丝数 ≥ 10万 → 标记为大V（定时任务更新）
动态判定：实时统计，粉丝数变化时更新标记
边界处理：粉丝数在阈值附近波动 → 加入滞后区间（如8万以下才降级回普通用户）
```

|----|----------|

#### Deep Dive

|------|------|

**1. 令牌桶——本地单机版（Go完整实现）**

```go
package ratelimit

import (
    "sync"
    "time"
)

// TokenBucketLimiter 令牌桶限流器（单机版）
type TokenBucketLimiter struct {
    rate       float64       // 令牌生成速率(token/s)
    capacity   float64       // 桶容量
    tokens     float64       // 当前令牌数
    lastRefill time.Time     // 上次补充时间
    mu         sync.Mutex
}

func NewTokenBucketLimiter(rate float64, capacity float64) *TokenBucketLimiter {
    return &TokenBucketLimiter{
        rate:       rate,
        capacity:   capacity,
        tokens:     capacity,   // 初始满桶
        lastRefill: time.Now(),
    }
}

func (l *TokenBucketLimiter) Allow() bool {
    return l.AllowN(1)
}

func (l *TokenBucketLimiter) AllowN(n float64) bool {
    l.mu.Lock()
    defer l.mu.Unlock()

    now := time.Now()
    // 惰性补充令牌
    elapsed := now.Sub(l.lastRefill).Seconds()
    l.tokens += elapsed * l.rate
    if l.tokens > l.capacity {
        l.tokens = l.capacity
    }
    l.lastRefill = now

    if l.tokens >= n {
        l.tokens -= n
        return true
    }
    return false
}
```

**2. 滑动窗口——本地单机版（Go完整实现）**

```go
// SlidingWindowLimiter 滑动窗口限流器（单机版）
type SlidingWindowLimiter struct {
    limit       int64             // 窗口内最大请求数
    window      time.Duration     // 窗口大小
    precision   time.Duration     // 小窗口精度
    counters    map[int64]int64   // 小窗口时间戳 → 计数
    mu          sync.Mutex
}

func NewSlidingWindowLimiter(limit int64, window, precision time.Duration) *SlidingWindowLimiter {
    return &SlidingWindowLimiter{
        limit:     limit,
        window:    window,
        precision: precision,
        counters:  make(map[int64]int64),
    }
}

func (l *SlidingWindowLimiter) Allow() bool {
    l.mu.Lock()
    defer l.mu.Unlock()

    now := time.Now()
    // 当前小窗口的key
    currentBucket := now.Truncate(l.precision).UnixNano()
    // 窗口起始时间
    windowStart := now.Add(-l.window).UnixNano()

    // 清理过期小窗口 + 统计窗口内总数
    var total int64
    for ts, count := range l.counters {
        if ts < windowStart {
            delete(l.counters, ts)
        } else {
            total += count
        }
    }

    if total >= l.limit {
        return false
    }

    l.counters[currentBucket]++
    return true
}
```

**3. Redis分布式令牌桶（Lua脚本）**

```lua
-- distributed_token_bucket.lua
-- KEYS[1]: 限流key（如 ratelimit:api:/order/create:user:1001）
-- ARGV[1]: 桶容量(capacity)
-- ARGV[2]: 令牌生成速率(rate, token/s)
-- ARGV[3]: 当前时间戳(秒，精确到毫秒用浮点)
-- ARGV[4]: 请求的令牌数(通常为1)

local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local requested = tonumber(ARGV[4])

-- 获取当前桶状态
local bucket = redis.call('HMGET', key, 'tokens', 'last_refill')
local tokens = tonumber(bucket[1])
local last_refill = tonumber(bucket[2])

-- 首次访问，初始化满桶
if tokens == nil then
    tokens = capacity
    last_refill = now
end

-- 惰性补充令牌
local elapsed = math.max(0, now - last_refill)
tokens = math.min(capacity, tokens + elapsed * rate)

-- 判断是否有足够令牌
local allowed = 0
if tokens >= requested then
    tokens = tokens - requested
    allowed = 1
end

-- 更新桶状态
redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
redis.call('EXPIRE', key, math.ceil(capacity / rate) * 2)  -- 自动过期

return allowed
```

**4. Redis分布式滑动窗口（Lua脚本）**

```lua
-- distributed_sliding_window.lua
-- KEYS[1]: 限流key
-- ARGV[1]: 窗口大小(秒)
-- ARGV[2]: 窗口内最大请求数
-- ARGV[3]: 当前时间戳(毫秒)
-- ARGV[4]: 唯一请求ID(member)

local key = KEYS[1]
local window = tonumber(ARGV[1]) * 1000  -- 转毫秒
local limit = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local member = ARGV[4]

-- 清除窗口外的过期记录
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)

-- 统计当前窗口内的请求数
local count = redis.call('ZCARD', key)

if count >= limit then
    return 0  -- 超限
end

-- 添加当前请求（score=时间戳, member=唯一ID）
redis.call('ZADD', key, now, member)
redis.call('PEXPIRE', key, window)  -- 设置过期

return 1  -- 允许
```

```go
import (
    "context"
    "fmt"
    "time"

    "github.com/go-redis/redis/v8"
    "github.com/google/uuid"
)

// DistributedRateLimiter 分布式限流器
type DistributedRateLimiter struct {
    rdb                *redis.Client
    tokenBucketScript  *redis.Script
    slidingWindowScript *redis.Script
}

func NewDistributedRateLimiter(rdb *redis.Client) *DistributedRateLimiter {
    return &DistributedRateLimiter{
        rdb:                rdb,
        tokenBucketScript:  redis.NewScript(tokenBucketLua),   // 上面的Lua
        slidingWindowScript: redis.NewScript(slidingWindowLua), // 上面的Lua
    }
}

// AllowTokenBucket 分布式令牌桶判定
func (l *DistributedRateLimiter) AllowTokenBucket(
    ctx context.Context, key string, capacity, rate float64,
) (bool, error) {
    now := float64(time.Now().UnixMilli()) / 1000.0 // 秒级浮点
    result, err := l.tokenBucketScript.Run(ctx, l.rdb,
        []string{key},
        capacity, rate, now, 1,
    ).Int()
    if err != nil {
        return true, err // Redis故障时默认放行（fail-open）
    }
    return result == 1, nil
}

// AllowSlidingWindow 分布式滑动窗口判定
func (l *DistributedRateLimiter) AllowSlidingWindow(
    ctx context.Context, key string, window time.Duration, limit int64,
) (bool, error) {
    now := time.Now().UnixMilli()
    member := uuid.New().String() // 唯一请求ID
    result, err := l.slidingWindowScript.Run(ctx, l.rdb,
        []string{key},
        int(window.Seconds()), limit, now, member,
    ).Int()
    if err != nil {
        return true, err // fail-open
    }
    return result == 1, nil
}

// ---- Gin中间件集成 ----

func RateLimitMiddleware(limiter *DistributedRateLimiter) gin.HandlerFunc {
    return func(c *gin.Context) {
        // 多维度限流key
        userID := c.GetString("user_id")
        path := c.FullPath()
        key := fmt.Sprintf("ratelimit:%s:user:%s", path, userID)

        allowed, err := limiter.AllowTokenBucket(c.Request.Context(), key, 100, 50)
        if err != nil {
            // Redis故障：降级为本地限流或直接放行
            c.Next()
            return
        }

        if !allowed {
            c.JSON(429, gin.H{
                "error":       "Too Many Requests",
                "retry_after": "1s",
            })
            c.Abort()
            return
        }
        c.Next()
    }
}
```

#### 关键难点

| 难点 | 解决方案 | 说明 |
|------|----------|------|
| **Redis故障** | fail-open（故障时放行）+ 本地限流兜底 | 限流不可用不应阻塞业务，降级为单机限流 |
| **Lua原子性** | 所有判定逻辑封装在单个Lua脚本中 | Redis单线程执行Lua，天然原子 |
| **时钟不一致** | 使用Redis服务端时间（redis.call('TIME')） | 或NTP同步，容忍毫秒级误差 |
| **热点key** | 本地缓存"已超限"标记 + Redis分片 | 超限后短时间内本地直接拒绝，不访问Redis |
| **规则热更新** | 配置中心推送 + SDK本地监听刷新 | 规则变更秒级生效，无需重启 |
| **精度 vs 性能** | 滑动窗口精度越高（小窗口越小）内存越大 | 通常1秒窗口用100ms精度即可 |

**限流算法选型指南**：
```
┌──────────────────────┬────────────────────────────────────────┐
│      场景            │              推荐算法                   │
├──────────────────────┼────────────────────────────────────────┤
│ API网关全局限流       │ 令牌桶（允许突发，用户体验好）           │
│ 用户维度精确限流      │ 滑动窗口（精确计数，无临界突刺）         │
│ 保护数据库写入        │ 漏桶（恒速流出，平滑写入）              │
│ 秒杀活动限流         │ 令牌桶 + 计数器（预设固定配额）          │
│ 防爬虫/防刷          │ 滑动窗口 + IP黑名单                    │
└──────────────────────┴────────────────────────────────────────┘
```

### 基础（Q01–Q08）

**Q01｜对应 §0｜高并发、高可用、高一致性分别指什么？**
高并发：高峰是否扛得住；高可用：故障时能否继续服务；高一致性：多副本/多服务数据是否满足约定一致级别。
**追问**：三者冲突时你怎么和业务对齐？

**Q02｜对应 §0｜为什么要做 Back-of-envelope？**
先数量级后组件：QPS/存储/带宽差一个数量级，架构可能完全不同。
**追问**：日 PV 1 亿、峰谷比 10，峰值 QPS 怎么估？

**Q03｜对应 §6｜什么是接口幂等？支付为何必须做？**
同一意图执行多次业务结果一致；支付重试否则资损。更优：返回首次结果。
**追问**：幂等键和 DB 唯一约束分工是什么？

**Q04｜对应 §5｜什么是单点故障？为何强调故障域隔离？**
单点挂则全链路挂；隔离把故障限制在机房/线程池/单元内。
**追问**：串联 5 个 99.9% 依赖，端到端大约多少？

**Q05｜对应 §5.3｜99.9% 和 99.99% 年不可用时间差多少量级？**
约 8.8 小时 vs 约 52 分钟。SLO 要配 SLI 与错误预算。
**追问**：错误预算用尽时发布策略怎么变？

**Q06｜对应 §1 / §2｜隔离、限流、熔断各拦哪一层？**
隔离：局部扩散；限流：总流量；熔断：下游已病还猛打。
**追问**：和《12》里舱壁/线程池隔离如何对应？

**Q07｜对应 §9｜缓存、MQ、分库分表各解决什么瓶颈？**
缓存：热点读；MQ：解耦与削峰；分片：单机容量/写吞吐。
**追问**：分片后跨片分页为什么危险？（链 §9 / 《10》）

**Q08｜对应 §5｜为何灰度与回滚是架构的一部分？**
变更必错；小流量验证 + 可回滚控制爆炸半径。
**追问**：DB 变更如何做到可回滚？

### 进阶（Q09–Q20）

**Q09｜对应 §1｜常见限流算法？令牌桶 vs 漏桶？**
固定窗口、滑动窗口、令牌桶、漏桶。令牌桶允许突发，漏桶平滑流出。
**追问**：手写令牌桶为何不能用整数截断 `elapsed*rate`？

**Q10｜对应 §1.3｜分布式限流怎么做？下面 Lua 是什么算法？**
多实例共享配额：Redis+Lua。`INCR+EXPIRE` 是**固定窗口**，不是令牌桶；令牌桶要用 tokens/last_refill 惰性补充（见 §13 限流案例）。
**追问**：fail-open 还是 fail-close？限流挂了默认放行的代价？

**Q11｜对应 §2｜熔断状态机如何切换？熔断 vs 降级？**
Closed→Open→Half-Open。熔断保下游，降级保自身核心路径。
**追问**：半开放多少探针？如何防探针打满？

**Q12｜对应 §3｜分布式事务方案对比？TCC 是强一致吗？**
2PC / TCC / SAGA / 本地消息表。TCC 是**业务层强隔离预留**，Confirm/Cancel 仍要幂等与空回滚，不是简单“DB 强一致”。
**追问**：默认为何推荐本地消息表？

**Q13｜对应 §4.1｜CAP 为何不能「三者兼得」？**
分区必须面对；分区时在线性一致与非故障节点必响应之间权衡。口语「三选二」应说成 **分区下 C/A 权衡**。
**追问**：C、A、P 各自准确定义？Cassandra `W=3,R=1` 能否贴 CP 标签？

**Q14｜对应 §4.2｜BASE 是什么？和 CAP/ACID 关系？**
Basically Available / Soft State / Eventually Consistent；是相对 **ACID** 的工程哲学，不是“扩展 CAP”。
**追问**：哪些路径仍应坚持 CP？

**Q15｜对应 §4.3｜一致性 Hash 与虚拟节点？**
环上映射，加减节点影响邻居；虚拟节点缓解倾斜。
**追问**：虚拟节点数量量级怎么选？

**Q16｜对应 §4.4｜Raft 选举与日志复制？**
超时变候选、多数派、随机 timeout；日志多数派提交。
**追问**：为何少数派不能提交？和 ZK 过半的关系？

**Q17｜对应 §7｜穿透 / 击穿 / 雪崩怎么区分与治理？**
穿透：不存在的键；击穿：热点过期；雪崩：大面积失效/缓存挂。布隆/空值、单飞/逻辑过期、TTL 抖动+限流。
**追问**：只加 Redis 为什么仍可能雪崩？

**Q18｜对应 §8｜Kafka / RabbitMQ / RocketMQ 怎么选？**
吞吐流式→Kafka；灵活路由→RabbitMQ；事务消息/电商语义→RocketMQ。
**追问**：至少一次如何配合幂等？

**Q19｜对应 §10｜Snowflake 结构与时钟回拨？**
1+41+10+12；回拨等待/拒绝/借号；也可用号段。
**追问**：为何 Snowflake 主键比 UUID 更友好？

**Q20｜对应 §11｜RedLock 争议核心？工程怎么选锁？**
效率型 vs 正确性型；Kleppmann：时钟/GC 下 RedLock 难证安全，应用 fencing token；Antirez：工程时钟假设。正确性优先 ZK/etcd。
**追问**：etcd Revision 如何当 fencing token？

### 案例与设计（Q21–Q26 + D01–D04）

**Q21｜对应 §13 秒杀｜全链路怎么挡流量？一致性模型是什么？**
CDN/静态→接入限流（100万→1000 是 **~99.9%** 不是 90%）→Redis Lua 预扣（`stock < qty` 才扣）→MQ→DB 乐观锁（先读 `version`）。模型是**原子预扣 + 最终落库**，不要标成整条 CP。
**追问**：Kafka 写失败如何回滚 Redis？热 key 库存怎么分片？

**Q22｜对应 §13 Feed｜推拉结合？混合分页坑在哪？**
普通用户写扇出，大V读时拉；合并要用 **score+id 游标**，禁止 inbox `offset` 后再拼大V。冷启动：关注普通用户异步回填，大V不回填。
**追问**：取关后 inbox 脏数据怎么办？

**Q23｜对应 §13 短链｜短码如何生成？碰撞？301 vs 302？**
推荐 Snowflake+Base62；Hash 截断必须冲突重试。302 利统计与变更，301 利缓存。
**追问**：过期短链缓存 TTL 如何设？

**Q24｜对应 §13 限流服务｜本地桶 + Redis 如何配合？**
本地预拒绝热点 + Redis 原子判定；Redis 故障 fail-open + 本地兜底。
**追问**：滑动窗口 ZSET 的内存代价？

**Q25｜对应 §13 任务调度｜如何保证不丢不重？**
选主调度 + 分片触发 + 至少一次投递 + 执行记录唯一键/业务幂等；长任务租约续期。
**追问**：misfire 策略有哪些？

**Q26｜对应 §5.4 / D01｜多活的核心矛盾？**
单元闭环 vs 全局一致；跨单元异步与冲突；切换看 RPO/RTO。
**追问**：全局唯一手机号怎么做？

### 开放式设计题

**D01｜对应 §5.4｜全球化多活电商**
单元化路由、单元内强一致/跨单元最终一致、冲突解决、切流与对账。
**追问**：支付回调打到非归属单元怎么办？

**D02｜对应 §5｜P99 从 50ms 到 500ms 如何排查？**
分层（接入→应用→中间件→DB）+ 追踪 + 变更对比 + 回滚验证。
**追问**：P99 与 P50 差距大说明什么？

**D03｜对应 §13｜设计 IM 在线消息（或与任务调度二选一深挖）**
连接层有状态（网关粘滞/路由表）、消息存储与同步、多端已读、推送降级；群聊扇出 vs 读扩散。
**追问**：用户上线补消息如何做游标？

**D04｜对应 §13 秒杀｜从 0 白板设计秒杀（设计题）**
先估峰值与库存、定不超卖与允许的下单延迟、画四层过滤、讲 Lua 与幂等、讲降级级别与演练。
**追问**：只读 DB 行锁行不行？代价是什么？

### 资深综合（Q27–Q32）

**Q27｜对应 §6｜为何幂等最好返回首次结果？**
重试方要的是业务结局，不是“你重复了”。
**追问**：如何存储首次响应？

**Q28｜对应 §2 / §5｜为何降级策略要需求阶段定？**
降级是业务取舍，故障时拍脑袋易资损。
**追问**：举一个不能降级的核心路径。

**Q29｜对应 §0 / §5｜容量规划四步？**
估峰值→压测单机→冗余算实例→扩容阈值与回滚。
**追问**：限流阈值和容量规划如何互相校验？

**Q30｜对应 §1 / §5｜重试预算如何设计？**
次数、总时长、指数退避+抖动、可重试白名单、与熔断联动。
**追问**：重试如何制造雪崩？

**Q31｜对应 §4｜一致性和可用性冲突时如何给业务决策框架？**
资损/合规走强一致；统计/推荐走最终一致；写清延迟与补偿时限。
**追问**：购物车与扣款为何不同档？

**Q32｜对应 全文｜审架构优先追问哪五类？**
流量模型、一致性、故障模型、可观测性、变更/扩容。
**追问**：补一个你经历过的失败决策复盘结构（背景→指标→根因→重来验证）。

## 总结

系统设计核心考点（由浅入深）：
1. **方法论**：Clarify → Estimate → API → Data → Design → Deep Dive → Scale
2. **稳定**：限流 / 熔断降级 / 超时重试 / 舱壁隔离（与《12》分工：本章选型，《12》实现）
3. **一致与事务**：分区下 C/A 权衡、BASE 相对 ACID、TCC 预留隔离、本地消息表
4. **扩展**：幂等、多级缓存三板斧、MQ 选型、读写分离与分片
5. **组件深水区**：Snowflake/号段、Redis 锁与 RedLock 争议、etcd fencing
6. **案例**：短链、秒杀、Feed、任务调度、分布式限流——用同一套模板讲清估算与故障
