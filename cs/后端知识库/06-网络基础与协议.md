## 1. 网络分层与数据传输

### 1.1 OSI 七层模型

| 层次 | 名称 | 协议/设备 | 作用 |
|------|------|-----------|------|
| 7 | **应用层** | HTTP、FTP、DNS | 应用程序接口 |
| 6 | **表示层** | 加密、压缩 | 数据格式转换 |
| 5 | **会话层** | Session | 建立、管理会话 |
| 4 | **传输层** | TCP、UDP | 端到端通信 |
| 3 | **网络层** | IP、ICMP、路由器 | 路由选择 |
| 2 | **数据链路层** | MAC、交换机 | 局域网通信 |
| 1 | **物理层** | 网卡、光纤 | 比特流传输 |

### 1.2 TCP/IP 四层模型

| TCP/IP | OSI | 协议 |
|--------|-----|------|
| **应用层** | 7-5层 | HTTP、DNS、FTP、SMTP |
| **传输层** | 4层 | TCP、UDP |
| **网络层** | 3层 | IP、ICMP、ARP |
| **链路层** | 2-1层 | Ethernet、Wi-Fi |

### 1.3 封装、解封装与一次请求的数据旅程

#### 先建立直觉：寄一封「加密挂号信」

把一次 HTTPS 请求想成：你要给「api.example.com 公司」寄一封**加密挂号信**，问「把用户列表给我」。

| 现实生活 | 网络里对应什么 |
|----------|----------------|
| 公司名 `api.example.com` | **域名**（好记，但不直接能寄） |
| 查黄页/地图拿到门牌号 | **DNS** 把域名查成 IP |
| 你家门牌号、对方门牌号 | **源 IP / 目的 IP** |
| 你家哪扇窗、对方哪个窗口 | **源端口 / 目的端口**（443 是 HTTPS 常用窗口） |
| 先打电话约好、再寄信 | 先 **TCP 建连**，再传数据 |
| 先交换保险箱密码，再塞信 | 先 **TLS 握手**，再发 HTTP |
| 信外面再套信封、贴条码 | **封装**：HTTP → TCP → IP → 以太网帧 |
| 小区门卫把「内部房间号」改成「小区对外地址」 | **NAT**（内网 IP 换成公网 IP） |
| 快递中转站一站站转发 | **路由器** 一跳跳转发 |
| 公司前台、保安、分诊台 | **CDN / 防火墙 / 负载均衡 / 网关** |
| 真正办事的员工 | **业务进程 / Pod** |

你点一下按钮，背后其实是：**查地址 → 出门 → 改门牌 → 路上转运 → 进公司大门 → 前台分诊 → 员工办事 → 回信原路回来**。

#### 封装是什么：一层层「套袋子」

电脑不会直接把「GET /users」丢到电线上。它会像套娃一样加标签：

```text
最里面：HTTP 内容（我要 GET /users）
  + TCP 头：从我家哪个端口 → 对方 443，序号多少（保证不丢、不乱）
  + IP 头：从哪个 IP → 到哪个 IP，还能活多少跳（TTL）
  + 以太网头：这一跳交给谁的网卡（MAC）
  → 最后变成网卡发出去的电信号/光信号
```

对方收到后反过来拆：先看「这一跳是不是给我」→ 再看「这个 IP 包是不是给我」→ 再看「这个 TCP 连接是不是这个端口」→ 最后才解开 HTTP。

#### 角色设定

假设你在家里用电脑打开 App，请求 `https://api.example.com/users`：

```text
你的电脑：内网地址 10.0.0.8（外人直接找不到这个号）
家里路由器：对内 10.0.0.1，对外公网 198.51.100.8（整个小区对外一个门牌）
DNS 查到入口：203.0.113.10（公司大门/CDN，不一定是写业务代码那台机器）
公司里面还有：
  前台保安（WAF/防火墙）
  导诊台（负载均衡 LB）
  分诊护士（反向代理 / API 网关）
  真正办事员工（业务程序 10.20.0.15:8080）
```

---

#### 第 0 步：你点了「查询用户」，但 HTTP 还不能直接发

App/浏览器心里想的是：

> 我要访问 `https://api.example.com/users`，发一个 `GET /users`，可能还要带上登录 Token。

但现在只有「公司名」和「要办的事」，还不能直接把请求丢到网上。真正发出 HTTP 之前，至少要先做三件事：

1. 查清楚 `api.example.com` 对应哪个入口 IP（DNS）
2. 先和对方 `:443` 端口建立一条可靠传输连接（TCP）
3. 确认对方身份，并协商后续加密用的会话密钥（TLS）

所以：**HTTP 不是链路上第一个发出去的东西**。更准确的顺序是：

```text
DNS 查地址 → TCP 接通管道 → TLS 确认身份并约好密钥 → 才在加密通道里发送 HTTP
```

---

#### 第 1 步：DNS——先查「公司名对应哪扇大门」

域名是给人看的，网络真正转发包时认的是 IP。DNS（Domain Name System，域名系统）就像黄页或地图：把 `api.example.com` 查成一个可以发包的入口地址。

```text
1）先看本地有没有记过：浏览器缓存、系统缓存、hosts
2）没有就问递归 DNS：运营商 DNS / 公司 DNS / 公共 DNS
3）递归 DNS 不知道时，再去问：根 → .com → example.com 权威 DNS
4）最终得到：api.example.com → 203.0.113.10
```

这里要保持一点专业判断：这个 `203.0.113.10` 往往是**公司大门**，也就是 CDN、GSLB 或 Anycast 入口；它不一定是最终处理 `/users` 的业务机器或 Pod。DNS 成功，只代表“地址查到了”，不代表 TCP、TLS 或业务一定成功。

---

#### 第 2 步：本机路由——「这封信先交给谁」

电脑发现 `203.0.113.10` 不在自己家这个局域网里，不能直接送到对方手里，于是查路由表：跨网段的包先交给**默认网关**，比如家里路由器 `10.0.0.1`。

但在局域网里发以太网帧，还需要知道网关的 MAC 地址。于是会查邻居表；如果没有，就用 ARP（IPv4）或 NDP（IPv6）问一声：

```text
谁是 10.0.0.1？
路由器回答：我是，MAC 是 aa:bb:...
电脑把这一跳先交给路由器
```

最容易混的是：**IP 地址和 MAC 地址负责的范围不同**。

```text
IP 头里的目的地址：仍然是 203.0.113.10（最终入口）
以太网帧里的目的 MAC：这一跳的网关 MAC
```

像快递：包裹最终地址写的是上海某公司，但你第一步只是把它交给小区驿站；驿站不是最终收件人。

---

#### 第 3 步：本机封装并发包——选一个「临时窗口号」

电脑还要从临时端口池里选一个源端口，比如 `52341`。服务端 HTTPS 固定听 `443`，客户端这边的源端口则通常是临时分配的。

```text
从：10.0.0.8:52341
到：203.0.113.10:443
四元组：(10.0.0.8, 52341, 203.0.113.10, 443)
```

为什么要有源端口？因为你电脑可能同时开很多连接：

```text
浏览器标签 A：52341 → api.example.com:443
浏览器标签 B：52342 → api.example.com:443
后台下载：   52343 → other.example.com:443
```

端口可以理解成「我家哪扇窗在跟外面说话」。专业一点说，内核靠四元组把回包匹配到正确的 socket / 进程。

---

#### 第 4 步：家里路由器做 NAT——把「内部房间号」换成「小区对外门牌」

互联网上的服务器通常看不到你家里的 `10.0.0.8`，只看到路由器的公网 IP。于是出口路由器会做 NAT（Network Address Translation，网络地址转换），更具体地说常见是 SNAT / NAPT。

```text
你电脑发出去：
  10.0.0.8:52341  →  203.0.113.10:443

路由器改写成：
  198.51.100.8:40001  →  203.0.113.10:443

同时在 NAT/conntrack 表里记一行：
  外面回 198.51.100.8:40001 的包，要转回 10.0.0.8:52341
```

可以把它理解成：小区只有一个对外门牌，门卫把“3 栋 502 室”改成“小区大门 + 取件码 40001”；回信到大门时，再按取件码送回家。

防火墙也常在这一层工作：你主动出去建立的连接，回包通常允许进来；陌生人从外面主动敲你内网机器的门，一般会被拦住。

---

#### 第 5 步：互联网一跳跳转发——「快递中转」

公网路由器主要看目的 IP：`203.0.113.10` 往哪边走，就把包转给下一跳。这个过程像快递经过一个个中转站。

```text
运营商路由器 A → B → C → …
每一跳都会：
  · 按路由表选下一跳
  · TTL 减 1（防止包永远转圈）
  · 换这一跳的链路层地址（下一跳 MAC）
  · 目的 IP 通常仍是 203.0.113.10
```

如果这个入口 IP 是 **Anycast**（多地同时宣告同一地址），BGP 会把你送到“路由意义上最近”的 POP 节点。对客户端来说还是同一个 IP，背后可能落到上海节点，也可能落到广州节点。

---

#### 第 6 步：到了公司大门——CDN / 防火墙 / 负载均衡 / 网关

包终于到了 `203.0.113.10:443`。大型网站很少是“大门后面就一台业务机器”，更像一栋写字楼：先过保安，再到前台，再分诊到真正办事的人。

注意：这一节先讲**路径上可能遇到哪些组件**，不代表它们已经完成了 L7 解析。真正的时间顺序仍然是：先 TCP 建连，再在这条 TCP 连接上做 TLS；如果某个 L7 网关负责终止 TLS，它也是在 TCP 建立之后参与 TLS 握手。

```text
① CDN / 边缘节点
   · 静态文件命中缓存：边缘节点可以直接返回
   · 动态接口（如 /users）：通常继续回源

② WAF / 安全设备
   · 过滤明显攻击、恶意扫描、异常请求模式

③ 四层负载均衡（L4）
   · 主要看 IP、端口、连接，不理解 HTTP 语义
   · 可能只是转发这条 TCP 流（NAT/DSR），也可能自己终止客户端 TCP 后再连后端

④ 七层网关 / 反向代理（L7）
   · 如果前面的 L4 是透传/转发，L7 网关就是这条 TCP 的实际对端
   · 如果前面的 L4 是 TCP 代理，L7 网关接到的是 L4 重新建立的后端 TCP
   · 然后在这条 TCP 上终止 TLS，也就是完成 HTTPS 的加密层
   · TLS 完成后才能看 HTTP Host、Path、Header：例如 /users 该去用户服务
   · 记录真实来源，如 X-Forwarded-For / Forwarded
   · 再转到后面的业务机器 10.20.0.15:8080
```

所以你以为自己在跟“api.example.com 那台服务器”说话，实际上常常是：

```text
你 ↔ 公司大门/CDN ↔ 导诊台(LB) ↔ 分诊台(网关) ↔ 办事员工(业务)
```

---

#### 第 7 步：TCP 三次握手——先建立传输连接

在发 `GET /users` 之前，客户端与入口 `203.0.113.10:443` 先完成 TCP 握手。四元组此时是：

```text
(10.0.0.8, 52341, 203.0.113.10, 443)   # 本机视角
经 NAT 后公网侧看到：
(198.51.100.8, 40001, 203.0.113.10, 443)
```

实际报文：

```text
① 客户端 → 服务端：SYN=1，seq=x，并协商 MSS、窗口缩放、SACK 等选项
② 服务端 → 客户端：SYN=1，ACK=1，seq=y，ack=x+1（半连接曾占 SYN 队列）
③ 客户端 → 服务端：ACK=1，seq=x+1，ack=y+1
→ 双方进入 ESTABLISHED；连接进入全连接/accept 队列，等网关/服务进程 accept
```

直觉：先确认「双向都能通、初始序列号对齐」。此时：

- NAT/conntrack 已记录该流，回包按映射还原到 `10.0.0.8:52341`
- 载荷仍可能是明文控制信息；**业务 HTTP 还没发**
- 如果这是 HTTPS，接下来还要在这条 TCP 连接上做 TLS；不能把 TCP ESTABLISHED 当成「已经安全」

---

#### 第 8 步：TLS 握手——认证服务器并导出会话密钥

TCP 通了只表示「管道通了」。HTTPS 还要在这条 TCP 上再跑 **TLS（Transport Layer Security）**。以 **TLS 1.3** 完整握手为主（生产常见）：

```text
① ClientHello
   · supported_versions、cipher_suites
   · SNI（Server Name Indication）= api.example.com   ← 同 IP 多证书靠它选
   · key_share（如 x25519 公钥，提前带上，换密钥材料）
   · ALPN（Application-Layer Protocol Negotiation）：h2 / http/1.1 …

② ServerHello
   · 选定 TLS 版本与密码套件
   · 服务端 key_share
   · 随后多数握手消息已加密：
        {EncryptedExtensions}
        {Certificate}           ← 服务器证书链
        {CertificateVerify}     ← 用证书私钥签名握手摘要，证明持有私钥
        {Finished}

③ 客户端校验证书（在信任根 CA 下）
   · 证书链是否完整、签名是否有效
   · SAN（Subject Alternative Name）是否包含 api.example.com
   · 是否在 notBefore～notAfter 有效期内
   · 吊销状态（OCSP Stapling / CRL 等，视实现）

④ 客户端发送 {Finished}；双方用 ECDHE 等共享秘密导出握手密钥与应用流量密钥（AEAD）
→ 之后 HTTP 以 TLS 记录（Record）形式加密传输；中间人只能看到密文、SNI（1.3 有 ECH 等演进）、五元组等元数据
```

和「工牌 / 保险箱」类比的对应关系（类比只辅助记忆，以协议字段为准）：

| 类比 | 协议里实际是什么 |
|------|------------------|
| 亮工牌 | `Certificate` + `CertificateVerify` |
| 约保险箱密码 | `key_share` + 密钥导出，得到会话密钥 |
| 之后信件放进保险箱 | HTTP 字节进入 TLS Record，用 AEAD（如 AES-GCM）加密 |

补充：

- TLS 1.2 通常还要多一趟密钥交换，整体约 **2-RTT**；TLS 1.3 约 **1-RTT**（详见 §6）。
- 若 L7 网关**终止 TLS**，证书校验发生在客户端 ↔ 网关；网关到业务可能是内网明文或另建 mTLS。
- 抓包时 TLS 1.3 握手后半段多为密文，需 `SSLKEYLOGFILE` 才能解密分析。

---

#### 第 9 步：发送 HTTP——应用层请求真正发出

TLS 应用流量密钥就绪后，客户端在加密记录里发送 HTTP：

```http
GET /users HTTP/1.1
Host: api.example.com
Authorization: Bearer xxxxx
Accept: application/json
```

若 ALPN 在这条 TLS/TCP 连接里协商为 `h2`，则发送的是 HTTP/2 帧（HEADERS/DATA），不再是上面这种明文文本形态，但语义仍是「对 `/users` 发 GET」。HTTP/3 的 ALPN 是在 QUIC 的 TLS 握手里协商，走 UDP，不会把已经建立好的 TCP 连接“改成 UDP”。

网关/业务侧常见处理：

```text
L7 网关：按 Host/Path 路由 → 用户服务；注入 X-Forwarded-For / Forwarded
业务进程：鉴权 → 查 DB/缓存 → 序列化 JSON
响应：HTTP/1.1 200 OK + body，或 HTTP/2 HEADERS+DATA
```

链路上仍是：`HTTP 字节 → TLS Record → TCP Segment → IP Packet → Ethernet Frame`；区别只是 HTTP 已处于密文中。

---

#### 第 10 步：响应返回与连接复用

```text
业务响应
  → L7 网关 / L4 LB（可能再经 CDN）
  → 公网按源/目的反向转发
  → 出口 NAT：目的 198.51.100.8:40001 还原为 10.0.0.8:52341
  → 客户端 TCP 重组 → TLS 解密 → 应用拿到 JSON 渲染
```

连接收尾：

- **短连接**：请求结束后四次挥手（FIN/ACK）；主动关闭方常进 `TIME_WAIT`
- **Keep-Alive / HTTP/2**：TCP（及 TLS 会话）复用，后续请求省去握手成本

---

#### 总览：直觉路径 + 协议对照

```text
应用点击
  │
  ├─① DNS：api.example.com → A/AAAA（递归/权威查询，结果常是入口 IP）
  ├─② 路由：目的非本地网段 → 选默认网关（ip route）
  ├─③ ARP/NDP：解析网关 MAC，封装以太网帧
  ├─④ 分配临时源端口，构造四元组，发起 TCP
  ├─⑤ NAT/SNAT：改写源 IP:端口，写入 conntrack
  ├─⑥ 公网转发：逐跳路由，TTL--；入口可能是 Anycast
  ├─⑦ 入口链：到达 CDN/WAF/LB/Gateway 的入口；L4 可透传或代理 TCP
  ├─⑧ TCP：SYN / SYN-ACK / ACK → ESTABLISHED
  ├─⑨ TLS 1.3：ClientHello(SNI,key_share,ALPN) ↔ ServerHello+Cert…
  │         → 证书校验 → 导出应用密钥
  ├─⑩ HTTP：GET /users（可能是 h2 帧）→ 业务处理 → 响应
  └─⑪ 回程：NAT 还原 → TLS 解密 → 应用展示；连接关闭或复用
```

| 现象 | 更可能卡在哪一层 |
|------|------------------|
| 找不到主机 / 解析到错误 IP | DNS、hosts、GSLB |
| ping/mtr 异常 | 路由、网关、ARP、运营商链路 |
| connect 超时、SYN 重传 | 防火墙/安全组、未监听、回程黑洞 |
| 证书错误、握手失败 | TLS、SNI、证书链、系统时间、协议版本 |
| 502 / 503 / 504 | CDN、LB、网关、上游超时/无健康实例 |
| 网络「通」但业务数据错 | 鉴权、缓存、路由到错误服务、应用逻辑 |

排障顺序：

```text
DNS → 路由/L2 → 端口与防火墙 → TCP → TLS → 网关/HTTP → 应用依赖
```

## 2. IP、链路、路由与 NAT

### 2.1 IPv4、CIDR 与子网

IPv4（Internet Protocol version 4）地址是 32 位。CIDR（Classless Inter-Domain Routing，无类别域间路由）用 `/前缀长度` 表示网络位数量：

```text
192.168.10.34/24

前 24 位：网络部分 → 192.168.10.0
后 8 位：主机部分 → 可表示该网段内不同主机
常见范围：192.168.10.0 ～ 192.168.10.255
```

常见私网地址（RFC 1918）：

| 范围 | CIDR | 常见用途 |
|------|------|----------|
| `10.0.0.0` ～ `10.255.255.255` | `10.0.0.0/8` | 云 VPC、大型内网 |
| `172.16.0.0` ～ `172.31.255.255` | `172.16.0.0/12` | 容器、企业网 |
| `192.168.0.0` ～ `192.168.255.255` | `192.168.0.0/16` | 家庭、小型网络 |

判断同网段的本质：`IP AND 子网掩码` 是否相同。

```text
192.168.1.10/24  → 网络地址 192.168.1.0
192.168.1.20/24  → 网络地址 192.168.1.0  → 同网段，直接二层通信
192.168.2.20/24  → 网络地址 192.168.2.0  → 不同网段，交给网关路由
```

```bash
# 查看地址和掩码
ip addr

# 用系统路由表判断访问目标走哪张网卡、哪个源 IP、哪个网关
ip route get 8.8.8.8
```

### 2.2 IPv6 与双栈

IPv6 使用 128 位地址，解决 IPv4 地址不足，并取消广播、改用 NDP（Neighbor Discovery Protocol，邻居发现协议）。

| IPv4 | IPv6 |
|------|------|
| 32 位，如 `192.0.2.1` | 128 位，如 `2001:db8::1` |
| ARP 找邻居 | NDP（基于 ICMPv6）找邻居 |
| NAT 很普遍 | 理论上端到端地址充足，仍可能有防火墙 |
| DNS `A` 记录 | DNS `AAAA` 记录 |

双栈环境下客户端可能同时拿到 A/AAAA；Happy Eyeballs 会并行或快速交错尝试 IPv6/IPv4，避免某一栈配置坏导致长时间卡住。

### 2.3 MAC、ARP 与同网段通信

MAC（Media Access Control，媒体访问控制）地址用于本地链路上的帧交付。IP 决定**最终去哪里**，MAC 决定**这一跳交给谁**。

```text
同网段：
主机 A 先 ARP：「谁是 192.168.1.20？」
主机 B 回：「我的 MAC 是 bb:bb:...」
A 发帧：目的 MAC=B，目的 IP=B

跨网段：
A 发帧：目的 MAC=默认网关，目的 IP=远端服务器
路由器收到后重新封装下一跳 MAC；目的 IP 通常保持不变（NAT 除外）
```

```bash
ip neigh                    # 查看 ARP/NDP 邻居表
arp -n                      # 旧命令
ip neigh flush all          # 清邻居缓存（排障时谨慎）
```

常见故障：掩码配置错、重复 IP、ARP 缓存陈旧、网关不可达。

### 2.4 路由、默认网关与 ICMP

路由表按**最长前缀匹配**选路：越具体的前缀优先；都不匹配才走默认路由 `0.0.0.0/0`。

```text
10.1.2.0/24 via 192.168.1.2   ← 最具体
10.0.0.0/8 via 192.168.1.3
default via 192.168.1.1       ← 兜底
```

```bash
ip route                      # 路由表
ip route get 10.1.2.3         # 实际选路结果
ping -c 4 10.1.2.3            # ICMP Echo，验证基本可达性
traceroute 10.1.2.3           # 利用 TTL 递增观察路径
mtr -rw 10.1.2.3              # 连续统计每跳延迟/丢包
```

ICMP（Internet Control Message Protocol，互联网控制消息协议）不只用于 `ping`，还承载 Destination Unreachable、Time Exceeded、Fragmentation Needed 等网络控制错误。防火墙把 ICMP 全禁掉可能造成 PMTUD 黑洞。

### 2.5 MTU、MSS、分片与 PMTUD

| 概念 | 全称 | 说明 |
|------|------|------|
| **MTU** | Maximum Transmission Unit，最大传输单元 | 一条链路可承载的最大 IP 包，Ethernet 常见 1500 字节 |
| **MSS** | Maximum Segment Size，最大报文段长度 | TCP 单段应用数据上限，IPv4 常见 `1500-20(IP)-20(TCP)=1460` |
| **PMTUD** | Path MTU Discovery，路径 MTU 发现 | 探测整条路径可通过的最大包 |

```text
应用数据
  → TCP 按 MSS 分段
  → IP 包不能超过路径 MTU
  → IPv4 可能分片；IPv6 路由器不分片
```

典型 MTU 黑洞：小包和 TCP 握手正常，大响应/上传却超时。常见于 VPN、VXLAN、容器 Overlay 引入额外头部，而中间防火墙又丢弃 ICMP Fragmentation Needed。

```bash
# Linux：禁止分片测试路径可承载大小（1472 + IPv4/ICMP 头约 28 = 1500）
ping -M do -s 1472 example.com

ip link show                 # 查看接口 MTU
```

### 2.6 端口、四元组与 NAT

端口标识主机内的进程/Socket。服务端监听固定端口；客户端通常由内核分配临时源端口。TCP/UDP 流由四元组唯一标识：

```text
(源 IP, 源端口, 目的 IP, 目的端口)
```

NAT（Network Address Translation，网络地址转换）在经过网关时改写地址/端口：

| 类型 | 改写 | 典型场景 |
|------|------|----------|
| **SNAT** | 源 IP/端口 | 内网主机共用公网 IP 出网 |
| **DNAT** | 目的 IP/端口 | 公网端口转发到内网服务 |
| **PAT/NAPT** | 同时利用端口区分多条映射 | 家用路由、云 NAT 网关 |

```text
内网客户端 10.0.0.5:52341 → 203.0.113.10:443
经 NAT 后：198.51.100.8:40001 → 203.0.113.10:443

NAT 表记住两组四元组，响应回来后反向改写。
```

Linux 常用 conntrack（连接跟踪）保存 NAT 和有状态防火墙所需的连接状态。表满时会出现新连接随机失败：

```bash
sysctl net.netfilter.nf_conntrack_count
sysctl net.netfilter.nf_conntrack_max
conntrack -S                # 需安装 conntrack-tools
```

NAT/端口相关高频问题：临时端口耗尽、conntrack 表满、空闲连接被 NAT 超时清理、Hairpin NAT 配置错误。长连接应有应用心跳；大量出站短连接应使用连接池。

### 2.7 专线、VPN 与广域网互联

前面讲的是“主机经过默认网关访问另一个网络”。企业和云环境还要解决更大的问题：**办公室、分支机构、IDC、云 VPC 和合作方网络，如何互联；这条连接是否需要稳定带宽、私有路由、加密和故障切换？**

#### 2.7.1 专线和 VPN 先解决什么问题？

假设公司 IDC A 的业务需要访问云 VPC B：

```text
IDC A: 10.1.0.0/16  ─────  云 VPC B: 10.2.0.0/16
```

直接走公网并不理想：私网地址不会自动在公网传播；公网 NAT 会让地址规划和回程路由变复杂；公网路径的时延、丢包和抖动不可控；数据库和管理流量还需要明确的安全边界。

专线和 VPN 都解决“两个网络之间的私有互联”，但手段不同：

| 方案 | 真实含义 | 主要优势 | 主要代价 |
|------|----------|----------|----------|
| **互联网 VPN** | 在公网 IP 网络上建立加密隧道 | 部署快、成本低、地点灵活 | 共享公网质量，受 MTU/NAT/运营商影响 |
| **运营商专线** | 运营商提供隔离或逻辑隔离的 WAN 承载 | 时延和带宽更可预测 | 成本高、开通慢、扩容不灵活 |
| **云专线/云互联** | IDC/企业边界通过专用接入连接云网络 | VPC 和多云互联更稳定 | 依赖云厂商/运营商，仍需设计路由冗余 |
| **SD-WAN** | 用控制器管理专线、互联网、5G 等多条链路 | 统一编排、按应用选路、自动切换 | 控制器、设备和策略体系更复杂 |

专线和 VPN 不是“安全/不安全”的简单二分：**专线通常提供路径隔离和质量承诺，但不必然提供端到端加密；VPN 通常提供加密隧道，但底层仍可能使用不稳定的公网。** 高敏感数据即使走专线，也可能叠加 IPsec。

#### 2.7.2 专线是什么？为什么不是“拉一根网线”？

专线是运营商或云厂商提供的可管理 WAN 承载服务，典型路径是：

```text
企业 IDC ── 客户侧 CPE ── 运营商接入 ── MPLS/IP 骨干 ── 云侧/对端 CPE
```

运营商可以使用 MPLS（Multiprotocol Label Switching，多协议标签交换）等技术，通过 VRF、标签和边缘设备把不同客户的地址空间隔离开。常见交付形态：

- **L2 专线**：两端像接在同一个二层链路上，客户自己负责 VLAN、ARP、STP 或三层网关；灵活但广播域和故障域更大。
- **L3 VPN/MPLS 专线**：运营商或云侧维护 VRF 和三层路由，客户通过 BGP/静态路由交换前缀；更适合多站点互联。
- **云专线**：客户 CPE/路由器接入云厂商节点，再连接 VPC、Transit Gateway 或云联网。

“专线质量好”通常意味着 SLA 对可用性、时延、丢包或带宽有约束，并不意味着绝对不丢包，也不意味着应用可以不做超时、重试和故障切换。

#### 2.7.3 VPN 的本质：在已有网络上构造逻辑网络

VPN（Virtual Private Network，虚拟专用网络）是在不可信或共享的 Underlay 上建立由两端控制的 Overlay 隧道：

```text
内层业务包：10.1.0.10 → 10.2.0.20
  → VPN 网关封装/加密
外层包：公网 IP A → 公网 IP B
  → 公网路由器只转发外层包
  → VPN 网关解密/解封装
内层业务包：继续送到 10.2.0.20
```

类比成快递：专线像运营商给你预留一条管理过的货运线路；VPN 像在普通公路上把货物放进只有两端能打开的封闭集装箱。前者更容易承诺路径质量，后者更强调加密和灵活部署。

VPN 建立成功不等于业务可达，还要分别确认：对端认证是否成功、数据是否加密、哪些网段走隧道、两端是否有回程路由、防火墙是否允许内层流量、DNS 是否走正确的内网解析以及 MTU 是否适配。

#### 2.7.4 常见 VPN 技术与使用场景

| 技术 | 特点 | 适合场景 | 关键注意点 |
|------|------|----------|------------|
| **IPsec site-to-site** | IP 层加密隧道，常用 IKEv2 协商 | IDC↔云、分支↔总部 | IKE/ESP、隧道两端、路由、NAT-T、MTU |
| **SSL/TLS VPN** | 通过 TLS 建立客户端或应用访问隧道 | 员工远程接入 | 身份认证、客户端权限、全隧道/分流 |
| **WireGuard** | 基于 UDP 的现代加密隧道 | 远程接入、轻量站点互联 | 密钥和 AllowedIPs 同时承担身份/路由语义 |
| **GRE** | 通用封装，本身不加密 | 承载动态路由或多协议 | 常与 IPsec 叠加 |
| **VXLAN** | 数据中心 Overlay 封装 | IDC/云内部租户网络 | 不等于公网安全 VPN |
| **MPLS L3VPN** | 运营商 VRF/标签转发 | 多分支企业 WAN | 承载隔离不等于端到端加密 |

**GRE over IPsec** 是常见组合：GRE 负责承载 OSPF、BGP、多播或复杂内层协议，IPsec 负责加密。灵活性更强，但额外封装会消耗 MTU。

#### 2.7.5 IPsec 建立连接时发生什么？

以 IKEv2 + ESP tunnel mode 为例：

```text
站点 A 网关                                      站点 B 网关
  |  IKE_SA_INIT：算法、DH 参数、随机数                  |
  |-------------------------------------------------->|
  |  IKE_AUTH：身份认证、证书/PSK、子网和 CHILD_SA      |
  |<--------------------------------------------------|
  |  ESP 加密数据：10.1.0.0/16 ↔ 10.2.0.0/16            |
```

- **IKE_SA_INIT**：协商算法、Diffie-Hellman 参数并产生初始密钥材料。
- **IKE_AUTH**：认证双方并确认内层网段。
- **CHILD_SA**：为业务流量建立安全关联和密钥。
- **ESP**：真正保护业务 IP 包，提供加密、完整性、序列号和重放保护。

如果中间有 NAT，ESP 可能无法直接穿越，NAT-T 会将 ESP 放进 UDP 4500；IKE 通常使用 UDP 500。外层是 UDP，不代表 VPN 失去了 IPsec 的安全语义。

#### 2.7.5.2 DH 到底做了什么：双方怎么“不传密钥却得到同一把密钥”？

DH（Diffie-Hellman）先别理解成“加密算法”。它不是拿来直接加密 HTTP、IPsec 数据包的，也不是对称加密算法；它解决的是**密钥协商**：两端在网络上只交换公开材料，却各自算出同一个共享秘密。

先用一个类比建立直觉：

```text
公开材料：一桶公共底色（所有人都看得到）
客户端秘密：只知道自己的红色配方
服务端秘密：只知道自己的蓝色配方

客户端：公共底色 + 红色配方 → 橙色混合物，发给服务端
服务端：公共底色 + 蓝色配方 → 绿色混合物，发给客户端

客户端：收到绿色混合物，再加入自己的红色配方 → 最终颜色
服务端：收到橙色混合物，再加入自己的蓝色配方 → 同一个最终颜色
```

旁观者能看到公共底色、橙色混合物和绿色混合物，但不知道红色/蓝色的秘密配方；如果“混合”这个操作很容易做、但几乎无法反向拆出秘密配方，双方就能得到同一个最终结果。这个“最终颜色”对应后续用来导出会话密钥的共享秘密。

把类比映射回数学：

| 类比 | DH 里的对应物 | 是否公开传输 |
|------|---------------|--------------|
| 公共底色 | 大素数 `p`、生成元 `g` | 是 |
| 客户端秘密红色配方 | 客户端随机私钥 `a` | 否 |
| 服务端秘密蓝色配方 | 服务端随机私钥 `b` | 否 |
| 橙色混合物 | `A = g^a mod p` | 是 |
| 绿色混合物 | `B = g^b mod p` | 是 |
| 最终颜色 | `K = g^(ab) mod p` | 否，双方各自算出 |

经典有限域 DH 写成公式就是：

```text
公开约定：大素数 p、生成元 g
客户端随机生成私钥 a
服务端随机生成私钥 b

客户端计算 A = g^a mod p，并发送 A
服务端计算 B = g^b mod p，并发送 B

客户端：K = B^a mod p = (g^b)^a mod p = g^(ab) mod p
服务端：K = A^b mod p = (g^a)^b mod p = g^(ab) mod p
```

网络上真正传输的是 `p、g、A、B`，不是 `a、b`，也不是最终的 `K`：

```text
客户端                         服务端
  私钥 a                         私钥 b
  A = g^a mod p  ─────────────→
                 ←────────────  B = g^b mod p
  K = B^a mod p                  K = A^b mod p
                    两边得到相同 K
```

难点在于反推：旁观者知道 `A = g^a mod p`，想得到 `a`，需要求离散对数；在参数足够大或使用安全椭圆曲线时，现实中不可行。

所以颜色例子只帮助记忆三件事：**公开材料可以传，双方私有随机数不传，最终共享秘密由双方各自算出**。真正的安全性来自模幂/椭圆曲线运算的单向困难性，而不是颜色本身。

##### ECDH/ECDHE 和 DH 的关系

- **DH**：最初的有限域模幂版本。
- **ECDH**：把相同的协商思想放到椭圆曲线点运算上，密钥更短、计算效率和安全强度更好。
- **ECDHE**：`E` 表示 Ephemeral（临时），每次握手都生成新的临时私钥，提供前向保密（PFS）。

TLS 1.3 中的 `key_share` 就是 ECDHE 的临时公钥材料。它可以公开发送，因为公开的是 `A` 或椭圆曲线点，不是临时私钥，也不是最终 AEAD 会话密钥。

##### DH 能协商密钥，为什么还需要身份认证？

原始 DH 有一个关键缺陷：**它能让双方算出同一个秘密，却不能证明对方是谁。** 攻击者 Mallory 可以分别和客户端、服务端做两次 DH：

```text
客户端 ↔ Mallory：共享 K1
Mallory ↔ 服务端：共享 K2
```

客户端以为 K1 是和服务端共享的，服务端以为 K2 是和客户端共享的；Mallory 可以解密、修改，再分别加密转发，这就是中间人攻击。

HTTPS 用证书和签名补上身份认证：

```text
DH/ECDHE：双方协商“这次通信使用哪把临时会话密钥”
证书/CertificateVerify：证明服务端确实拥有受信任证书对应的私钥
AEAD：用协商出的对称密钥高效加密实际 HTTP 数据
```

所以 DH 解决的是“共同生成秘密”，证书解决的是“你到底是不是我想连接的服务器”，二者不能互相替代。

#### 2.7.5.3 IKE SA、CHILD SA、IPsec SA 到底分别是什么？

“SA（Security Association，安全关联）”不是一条物理线路，而是一组**单向有效的安全参数**。它告诉 IPsec 数据面：哪些报文匹配这条策略、用哪把密钥、哪种算法、从哪个接口发出，以及如何防重放。

需要区分三种容易混淆的对象：

| 对象 | 作用 | 是否直接承载业务 IP 包 |
|------|------|------------------------|
| **IKE SA** | 保护 IKE 控制报文，协商和管理后续 SA | 否 |
| **CHILD SA** | IKEv2 中协商出来的一组业务安全关联，可用于初始业务或 rekey | 间接对应 |
| **IPsec SA** | ESP/AH 数据面实际使用的单向密钥和参数 | 是 |

一条双向 VPN 通常至少有两条方向相反的 IPsec SA：

```text
SA-A→B：站点 A 出站到站点 B，使用密钥 K1、SPI 1001
SA-B→A：站点 B 出站到站点 A，使用密钥 K2、SPI 2001
```

不要把 SA 理解成“双方共享一条双向连接”。IPsec 数据面通常按方向分别维护密钥、SPI、序列号和生命周期。

#### 2.7.5.4 控制面如何把 SA 变成数据面转发？

网关内部通常有两个重要状态表：

- **SPD（Security Policy Database）**：安全策略表，判断某个内层流量是 `PROTECT`（必须加密）、`BYPASS`（直接放行）还是 `DISCARD`（丢弃）。
- **SAD（Security Association Database）**：SA 参数表，根据 SPI、方向等找到密钥、算法、封装模式、序列号和重放窗口。

以 `10.1.0.0/16 → 10.2.0.0/16` 为例，出站过程是：

```text
1. 主机把普通 IP 包交给站点 A 网关
2. 网关查 SPD：该源/目的网段必须 PROTECT
3. 根据策略选择 SA-A→B，查 SAD 得到密钥/算法/SPI
4. ESP 加密内层 IP 包，增加 SPI、序列号、认证标签
5. 添加外层 IP：源 = A 网关公网/专线地址，目的 = B 网关地址
6. 普通路由器只根据外层目的地址转发
7. B 网关收到后按 SPI 找 SA-B→A，校验重放/完整性并解密
8. 删除 ESP 和外层头，把原始内层包路由给 10.2.0.20
```

回程方向使用另一条 SA，不能假设“解密后自动知道怎么回去”；B 侧还必须有回程路由和 SPD 策略。

#### 2.7.5.5 ESP tunnel mode 的报文长什么样？

站点到站点 VPN 最常见的是 tunnel mode：

```text
外层 Ethernet
  → 外层 IP：VPN 网关 A → VPN 网关 B
    → ESP Header：SPI + Sequence Number
      → 加密部分：原始内层 IP Header + TCP/UDP + Payload + Padding
        → ESP Trailer / Authentication Tag
```

隧道两端看到的是外层网关地址；被保护的是完整的内层 IP 包，所以中间网络看不到租户主机的真实地址和端口（但仍可能看到流量时间、大小和两端网关等元数据）。

transport mode 只保护原始 IP 包中的传输层部分，保留原始 IP Header，常见于同一组主机或主机到主机的场景。不要把 `IPsec tunnel mode` 和“任何 UDP 隧道”混为一谈：前者定义了 IPsec 的安全处理和 SA，后者只是可能的外层承载。

#### 2.7.5.6 SA 生命周期、rekey 和故障表现

SA 通常同时有时间和流量生命周期。到期前，双方通过 IKE rekey 协商新密钥，短时间内可能同时保留旧/新 SA，以避免正在传输的包突然失效。

| 状态/故障 | 常见表现 |
|-----------|----------|
| IKE SA 失效 | 不能继续协商或刷新 CHILD SA，隧道可能最终停止 |
| CHILD/IPsec SA 失效 | 控制通道可能还在，但业务包无法正常加密/解密 |
| SPI 找不到 | 对端仍发旧 SA 的包，本端丢弃或请求重新建立 |
| 序列号/重放窗口异常 | 报文被判断为重复或乱序过度而丢弃 |
| 两端策略不一致 | 隧道显示已建立，但特定网段流量不通 |
| 一端 rekey、另一端状态陈旧 | 短暂丢包、反复重协商或单向通信 |

因此排障要分别看 IKE 控制状态、CHILD/IPsec SA、SPD/SAD、路由表、防火墙计数器和实际 ESP/NAT-T 抓包，不能只看“VPN 隧道绿色”。

#### 2.7.6 全隧道、分隧道与路由

```text
全隧道：所有流量 → VPN → 企业出口 → 互联网或内网
分隧道：企业网段 → VPN；普通公网流量 → 本地互联网出口
```

全隧道便于审计和统一防护，但增加企业出口带宽和时延；分隧道体验和成本更好，但本地公网流量绕过企业安全边界。排障时要确认 IKE/CHILD_SA、客户端路由/策略路由、对端回程路由、防火墙、DNS 和 MTU，而不能只看客户端显示 `Connected`。

#### 2.7.7 专线/VPN 高可用与 SD-WAN

生产互联不应只有一条链路：

```text
IDC CPE1 ── 专线/VPN 1 ── 云侧网关 1
IDC CPE2 ── 专线/VPN 2 ── 云侧网关 2
             └── 互联网 VPN / 5G 备用
```

高可用还需要双 CPE/双网关、BGP 动态路由、主备或主动主动策略、BFD/健康检查以及经过验证的 MTU 和切换时间。主动主动还要考虑 ECMP、NAT/会话状态和非对称路径。

SD-WAN 不是新的加密协议，而是广域网控制和编排方式。它把 MPLS、互联网、4G/5G、云专线等 Underlay 统一纳管，根据时延、丢包、抖动、成本和应用类型选择路径，也可以在路径上叠加 IPsec/GRE 隧道。

#### 2.7.8 专线、VPN、Overlay 和 DCI 的边界

| 概念 | 主要回答的问题 | 是否天然加密 | 是否天然保证带宽 |
|------|----------------|--------------|------------------|
| 专线 | 两个地点如何获得受管控的 WAN 承载？ | 不一定 | 通常有 SLA，但看合同和接入方式 |
| IPsec VPN | 如何在已有 IP 网络上建立加密隧道？ | 是 | 不保证，受 Underlay 质量影响 |
| GRE | 如何封装和承载内层协议/动态路由？ | 否 | 不保证 |
| MPLS L3VPN | 运营商如何隔离多个客户的三层 WAN？ | 通常不等于端到端加密 | 通常有 SLA |
| VXLAN Overlay | IDC/云内如何虚拟租户网络？ | 通常不负责加密 | 依赖 Underlay |
| DCI | 多个 IDC 如何互联、复制或延伸网络？ | 取决于具体方案 | 取决于承载方式 |

一句话：**专线是承载服务，VPN 是加密/隧道机制，Overlay 是虚拟网络，SD-WAN 是多链路控制方式，DCI 是跨数据中心互联场景。**

## 3. TCP 协议详解

### 3.1 TCP vs UDP

| 特性 | TCP | UDP |
|------|-----|-----|
| **连接** | 面向连接（三次握手） | 无连接 |
| **可靠性** | 可靠（确认、重传） | 不可靠 |
| **顺序** | 保证顺序 | 不保证顺序 |
| **速度** | 慢 | 快 |
| **头部开销** | 20字节 | 8字节 |
| **应用场景** | HTTP、FTP、邮件 | DNS、视频、**游戏** |

### 3.2 TCP 三次握手

```
客户端                     服务器
  |                          |
  |  ①SYN seq=x             |
  |------------------------->|
  |                          |
  |  ②SYN-ACK seq=y ack=x+1 |
  |<-------------------------|
  |                          |
  |  ③ACK seq=x+1 ack=y+1   |
  |------------------------->|
  |                          |
  |   [连接建立]              |
```

**为什么需要三次握手？**
- **两次不够**：服务器无法确认客户端能收到SYN-ACK
- **四次太多**：第②③次可以合并（SYN-ACK）

**状态变化**：
```
客户端：CLOSED → SYN_SENT → ESTABLISHED
服务器：CLOSED → LISTEN → SYN_RECV → ESTABLISHED
```

### 3.2.1 三次握手内核实现要点

> 以下内容基于Linux 5.x内核源码分析

**为什么必须三次？** 核心目的：①确认对端在线能即时响应（面向连接）；②双方确认数据传输的起始序列号（双向的seq确认需要三次交互）。两次握手无法让服务端确认客户端收到了自己的序列号。

**SYN Flood、半连接队列与 syncookie**

**什么是半连接队列（SYN queue / 半开连接队列）？**

三次握手中间态：服务端收到 SYN、已回 SYN-ACK，但还没收到客户端最终 ACK → 连接处于 `SYN_RECV`。这些「还没完成握手」的条目放在**半连接队列**里，每条都要占内核内存（TCB 等）。

```text
客户端 SYN 到达
  → 服务端分配半连接项（SYN_RECV），入半连接队列
  → 回 SYN-ACK
  → 收到最终 ACK → 移入全连接队列（accept 队列），变为 ESTABLISHED
  → 应用 accept() 取走
```

和**全连接队列**（`listen` 的 backlog / `somaxconn`）区分：半连接 = 握手做到一半；全连接 = 握手完成、等应用 `accept`。

```bash
# 半连接队列上限（大致）
cat /proc/sys/net/ipv4/tcp_max_syn_backlog  # 常见默认 1024～2048
```

**什么是 SYN Flood？**

攻击者伪造大量源 IP 发 SYN，**故意不发第三次握手的 ACK**（或源 IP 根本收不到 SYN-ACK）。服务端为每个假 SYN 在半连接队列里占一项，队列被塞满后：

- 正常用户的 SYN 进不了队列 → 握手失败 / 极慢
- 本质是**用假半连接耗尽服务端内存与队列资源**，不是打垮 CPU 算力那么简单

```text
攻击者：SYN, SYN, SYN, ...（从不完成握手）
服务端：半连接队列 [假, 假, 假, ...] 满了
正常用户：SYN → 被拒或超时
```

**不启用 syncookie 时：怎么建连？**

| 步骤 | 行为 |
|------|------|
| 收到合法 SYN | 在半连接队列**分配并保存**状态（四元组、seq、选项等） |
| 回 SYN-ACK | 等客户端 ACK |
| 收到 ACK | 用队列里存的状态完成连接 |
| 队列满且无 cookie | **无法再接纳新 SYN**（或依赖丢弃/重试），正常用户也被挡 |

优点：可完整保存 TCP 选项（窗口扩大、SACK、Timestamp 等）。缺点：SYN Flood 时内存/队列被打爆。

**启用 syncookie 时：怎么建连？（默认 `tcp_syncookies=1`：队列耗尽后才启用）**

| 步骤 | 行为 |
|------|------|
| 收到 SYN（队列已满或强制 cookie） | **不分配**半连接项，不算「占坑」 |
| 用四元组 + 密钥 + 时间戳等算出 cookie，编码进 SYN-ACK 的 **seq** | 状态「藏」在包里，不占队列内存 |
| 合法客户端回最终 ACK（ack = cookie+1） | 服务端**验算 cookie**，通过则**当场**建 ESTABLISHED |
| 攻击者从不回 ACK | 服务端无状态可耗尽，只多几次 hash 计算 |

```text
【无 syncookie / 队列未满的正常路径】
SYN → 半连接队列占坑 → SYN-ACK → ACK → 建连

【syncookie 路径】
SYN → 不算占坑，cookie 写进 SYN-ACK.seq
    → 客户端 ACK 带回
    → 服务端验证 cookie → 建连（跳过「在队列里等」）
攻击者只发 SYN 不回 ACK → 服务端几乎不占内存
```

**syncookie 原理（一句话）**：把「半连接状态」从服务端内存挪到 SYN-ACK 的序号里；只有能正确完成第三次握手的客户端，才能带回可验证的 cookie。内存耗尽型攻击变成可承受的 CPU 校验。

```bash
cat /proc/sys/net/ipv4/tcp_syncookies
# 0 = 关闭
# 1 = 默认：半连接队列耗尽后启用 cookie
# 2 = 始终用 cookie（忽略半连接队列）
```

**启用 vs 不启用的关键差别**：

| | 不启用 / 未触发 cookie | 启用 syncookie |
|--|------------------------|----------------|
| 半连接状态存在哪 | 服务端内存队列 | 编码在 SYN-ACK 序号中 |
| SYN Flood | 队列易满，正连接被挤掉 | 假 SYN 几乎不占坑，正连接仍可验 cookie 建连 |
| TCP 选项 | 可完整协商保存 | 部分选项在 cookie 模式下支持有限（历史局限；现代内核有改善） |
| 代价 | 内存 | 每次可疑/溢出路径多做 hash |

生产一般保持 `tcp_syncookies=1`：平时走半连接队列（选项完整）；被打满时自动切 cookie 保命。

**listen backlog — 全连接队列**：

```bash
# listen(fd, backlog) 的backlog限制的是已完成三次握手但未被accept的连接队列长度
# 实际生效值 = min(backlog, somaxconn)
cat /proc/sys/net/core/somaxconn  # 默认128

# 查看全连接队列使用情况
ss -lnt
# LISTEN  Recv-Q  Send-Q  Local:Port
# LISTEN  3       128     0.0.0.0:80
#         ↑当前排队数    ↑最大长度

# 队列溢出时：新连接SYN无回应，客户端重试直到超时
# 溢出计数器
netstat -s | grep "listen queue"  # 或 nstat | grep ListenOverflows
```

**SYN/SYN-ACK重试次数**：

```bash
cat /proc/sys/net/ipv4/tcp_syn_retries      # 默认6（最长等待63秒，2^n指数退避）
cat /proc/sys/net/ipv4/tcp_synack_retries    # 默认5（最长等待31秒）
```

**TFO（TCP Fast Open）**：允许在SYN包中携带应用数据，减少一次RTT。

```bash
# 开启TFO
echo 3 > /proc/sys/net/ipv4/tcp_fastopen
# 0=关闭, 1=客户端, 2=服务端, 3=双向

# 工作流程：

# 后续连接：客户端SYN+cookie+数据 → 服务端验证cookie后直接处理数据（省1个RTT）
```

### 3.3 TCP 四次挥手

```
客户端                     服务器
  |                          |
  |  ①FIN seq=u             |
  |------------------------->|  [客户端主动关闭]
  |                          |
  |  ②ACK seq=v ack=u+1     |
  |<-------------------------|  [服务器确认]
  |                          |
  |  ③FIN seq=w ack=u+1     |
  |<-------------------------|  [服务器关闭]
  |                          |
  |  ④ACK seq=u+1 ack=w+1   |
  |------------------------->|  [客户端确认]
  |                          |
  |   [连接关闭]              |
```

**TIME_WAIT状态**：
- 主动关闭方等待2MSL（Maximum Segment Lifetime，通常60秒）
- 原因：确保最后的ACK到达，防止旧连接数据干扰新连接

---

#### 为什么TIME_WAIT是2MSL？底层原理深度剖析⭐⭐⭐

**为什么需要了解TIME_WAIT？**
- 面试高频：为什么是2MSL而不是1MSL或3MSL？
- 性能调优：TIME_WAIT过多导致端口耗尽
- 故障排查：大量TIME_WAIT的原因和解决方案

---

**什么是MSL？**

```
MSL（Maximum Segment Lifetime）：报文段最大生存时间
- Linux默认：60秒
- Windows默认：120秒
- RFC标准建议：2分钟

含义：IP数据包在网络中存活的最长时间
- 超过MSL，路由器丢弃数据包（TTL=0）
```

**为什么需要TIME_WAIT？（2个原因）**

**原因1：确保最后的ACK到达对方**

```
四次挥手过程：
客户端                              服务器
  |                                    |
  | ①FIN(seq=u)                        |
  |─────────────────────────────────→  |
  |                                    |
  | ②ACK(ack=u+1)                      |
  |←─────────────────────────────────  |
  |                                    |
  | ③FIN(seq=v)                        |
  |←─────────────────────────────────  |
  |                                    |
  | ④ACK(ack=v+1)                      |
  |─────────────────────────────────→  |
  |                                    |
  | [TIME_WAIT: 2MSL]                  |
  |                                    |

问题场景：
- 客户端发送最后的ACK（④）
- ACK在网络中丢失
- 服务器没收到ACK，超时重传FIN（③）
- 如果客户端立即关闭，无法响应重传的FIN
- 服务器会一直重传FIN，直到超时（可能等待数分钟）

TIME_WAIT的作用：
- 客户端等待2MSL期间，可以接收并响应服务器重传的FIN
- 2MSL = 1MSL（FIN重传到达）+ 1MSL（ACK返回）
```

**原因2：防止旧连接数据干扰新连接**

```
场景：快速复用四元组（相同的src_ip:port → dst_ip:port）

时刻0：连接A关闭
      客户端:1234 → 服务器:80
      最后发送的数据包：seq=1000

时刻1：立即创建连接B（相同四元组）
      客户端:1234 → 服务器:80
      新连接的seq从1开始

时刻2：旧连接A的数据包（seq=1000）延迟到达
      问题：服务器如何区分这是旧连接A的数据，还是新连接B的数据？
      → 可能导致数据混乱

TIME_WAIT的作用：
- 等待2MSL，确保旧连接的所有数据包都已消失（TTL超时）
- 2MSL = 1MSL（旧数据发送）+ 1MSL（旧数据返回）
- 新连接不会收到旧连接的数据
```

**为什么是2MSL，而不是1MSL或3MSL？**

```
1MSL不够：
- 无法覆盖"发送FIN重传 + 接收ACK"的往返时间
- 旧连接的返回数据可能干扰新连接

3MSL太长：
- 浪费资源（端口、内存）
- 不必要（2MSL已足够覆盖往返）

2MSL刚好：
- 去程1MSL：对方重传的FIN到达（或旧数据到达）
- 返程1MSL：我方的ACK返回（或旧数据返回）
- 覆盖所有可能的网络延迟情况
```

---

**TIME_WAIT过多的问题**：

**问题1：端口耗尽**

先澄清：**「临时端口」不是服务端监听端口，也不是 HTTP 里写死的 80/443。**

| 角色 | 端口谁定 | 是否固定 |
|------|----------|----------|
| **服务端**（被连的一方） | 监听端口，如 80、443、3306 | **固定**（或配置固定） |
| **客户端**（主动 `connect` 的一方） | 内核从**临时端口范围**里分配源端口 | **每次（或每个连接）往往不同**，不写死在业务里 |

TCP 连接用**四元组**标识：`(源IP, 源端口, 目的IP, 目的端口)`。
你访问 `https://example.com` 时：

```text
目的：example.com:443     ← 对端端口固定（HTTPS）
源：  本机IP:随机临时端口  ← 本机端口由内核分配，如 52341、52342…

连接1：(10.0.0.2, 52341) → (1.2.3.4, 443)
连接2：(10.0.0.2, 52342) → (1.2.3.4, 443)   ← 目的相同，源端口不同，是两条连接
```

业务代码通常只写「连哪个 IP:端口」，**不会、也不该**自己指定源端口（除非做特殊绑定）。内核在 `connect()` 时从临时端口池选一个空闲的。

```bash
# Linux 临时端口范围（常见约 32768～60999，可配）
cat /proc/sys/net/ipv4/ip_local_port_range
# 例：32768  60999  → 大约 2.8 万个，不是「永远 64000」
```

为何短连接容易耗尽：同一对 `(本机IP → 服务IP:服务端口)` 上，区分连接主要靠**不同的源端口**；连接主动关闭后，该源端口常进入 **TIME_WAIT（约 60s）**，这段时间不能立刻复用给同一四元组，可用源端口被占满就会：

```
客户端短连接场景：
- 客户端向同一服务连续发起大量 HTTP 短连接
- 每次 connect 分配一个临时源端口
- 关闭后端口进 TIME_WAIT（约 60 秒）
- 窗口内并发/新建连接数 ≈ 临时端口数量 → 再 connect 失败

错误信息：
connect: Cannot assign requested address
```

注意：连**不同目的 IP/端口**时，源端口可以复用（四元组仍唯一）；端口耗尽主要卡在「对同一目标狂打短连接」的场景。

**问题2：内存占用**

```
每个TIME_WAIT连接占用约4KB内存：
- TCP控制块（TCB）
- 套接字缓冲区

100,000个TIME_WAIT连接 = 400MB内存
```

**解决方案**：

```bash
# 方案1：启用TIME_WAIT端口复用（推荐）⭐⭐⭐
sysctl -w net.ipv4.tcp_tw_reuse=1
# 允许将TIME_WAIT端口分配给新的出站连接
# 注意：只对客户端有效（出站连接）

# 方案2：缩短FIN_WAIT_2超时
sysctl -w net.ipv4.tcp_fin_timeout=30
# 默认60秒 → 30秒

# 方案3：启用TIME_WAIT快速回收（危险，不推荐）
sysctl -w net.ipv4.tcp_tw_recycle=1
# 已在Linux 4.12+内核中移除（不安全）
# 原因：NAT环境下可能拒绝合法连接

# 方案4：增大端口范围
sysctl -w net.ipv4.ip_local_port_range="1024 65535"
# 增加可用临时端口数量

# 方案5：使用连接池（最佳方案）⭐⭐⭐
# HTTP连接池（复用连接，避免频繁创建/销毁）
http.Transport{
    MaxIdleConns:        100,
    MaxIdleConnsPerHost: 10,
    IdleConnTimeout:     90 * time.Second,
}
```

**为什么tcp_tw_reuse安全，tcp_tw_recycle不安全？**

```
tcp_tw_reuse（安全）：
- 只复用客户端的TIME_WAIT端口
- 检查新连接的时间戳（timestamp）
- 如果新连接timestamp > 旧连接timestamp，允许复用
- 前提：双方都启用TCP timestamp（默认启用）

tcp_tw_recycle（不安全）：
- 快速回收TIME_WAIT连接（< 2MSL）
- 依赖对方的timestamp递增
- NAT环境问题：
  - NAT后多个客户端共享同一个公网IP
  - 客户端A的timestamp=100，客户端B的timestamp=50
  - 服务器认为B的连接是旧连接（timestamp倒退），拒绝
  → 导致合法连接被拒绝

Linux 4.12+已移除tcp_tw_recycle
```

**TIME_WAIT过多的根因分析**：

```bash
# 查看TIME_WAIT数量
ss -s | grep TIME-WAIT
# 或
netstat -an | grep TIME_WAIT | wc -l

# 查看哪个进程产生TIME_WAIT（主动关闭方）
ss -tapn | grep TIME-WAIT

# 常见原因
1. 短连接频繁（HTTP/1.0无Keep-Alive）
   → 解决：使用HTTP/1.1 Keep-Alive或HTTP/2

2. 应用主动关闭连接（客户端）
   → 解决：让服务器主动关闭（TIME_WAIT在服务器）

3. 负载均衡健康检查
   → 解决：增大检查间隔、使用UDP健康检查
```

**最佳实践**：

```
1. 客户端（高并发爬虫、压测工具）
   ✅ 启用tcp_tw_reuse
   ✅ 使用连接池
   ✅ 减少短连接（使用Keep-Alive）

2. 服务器（Web服务器、API网关）
   ✅ 增大文件描述符限制（ulimit -n 100000）
   ✅ 增大端口范围
   ✅ 让客户端主动关闭连接（TIME_WAIT在客户端）
   ❌ 不要启用tcp_tw_recycle（已移除）

3. 监控TIME_WAIT数量
   ✅ 阈值告警（> 10000）
   ✅ 定期检查（Prometheus + Grafana）
```

---

**TIME_WAIT过多的问题**：
```bash
# 查看TIME_WAIT数量
ss -s | grep TIME-WAIT

# 解决方案
sysctl -w net.ipv4.tcp_tw_reuse=1      # 复用TIME_WAIT端口
sysctl -w net.ipv4.tcp_fin_timeout=30  # 缩短FIN_WAIT_2超时
```

### 3.3.1 四次挥手内核实现要点

**Linux上实际常为三次挥手**：由于Linux的延迟ACK机制，被动关闭方收到FIN后不会立即发送ACK，而是等待延迟发送。如果在延迟期间应用层也确认关闭连接，FIN和ACK会合并为一个包发出，四次挥手变为三次。

**TIME_WAIT内核实现**：

```bash
# Linux固定等待60秒（非RFC的2×MSL=4分钟）
# 内核代码：#define TCP_TIMEWAIT_LEN (60*HZ)

# 限制TIME_WAIT总数（防止内存耗尽）
cat /proc/sys/net/ipv4/tcp_max_tw_buckets  # 超限后直接RST关闭

# TIME_WAIT每个连接占用约4KB slab内存
# 大量TIME_WAIT还会增加CPU消耗（定时器处理、哈希查找）
```

**各关闭状态驻留问题**：

| 状态 | 驻留原因 | 超时机制 | 调优手段 |
|------|----------|----------|----------|
| **FIN_WAIT1** | 对端未回ACK | tcp重传定时器，受tcp_orphan_retries限制（默认0→实际8次） | 减小tcp_orphan_retries |
| **FIN_WAIT2** | 对端未发FIN | tcp_fin_timeout（默认60秒） | 减小tcp_fin_timeout |
| **CLOSE_WAIT** | **本端应用层未close** | 无内核超时，完全依赖应用 | 修复应用代码BUG |
| **LAST_ACK** | 对端未回最后ACK | tcp重传定时器 | 同FIN_WAIT1 |
| **TIME_WAIT** | 等待旧包消失 | 固定60秒 | tcp_max_tw_buckets / tcp_tw_reuse |

```bash
# tcp orphan（已脱离应用的tcp连接）数量限制
cat /proc/sys/net/ipv4/tcp_max_orphans  # 超限后RST关闭

# FIN重传次数（同时影响FIN_WAIT1和LAST_ACK）
cat /proc/sys/net/ipv4/tcp_orphan_retries  # 默认0=内核实际用8次
```

**SO_LINGER选项**：对socket设置SO_LINGER后，close时直接发送RST关闭连接，跳过所有状态直接进入CLOSED。激进方案，慎用。

### 3.4 TCP 滑动窗口与流量控制⭐⭐⭐

> 滑动窗口是TCP实现可靠传输和流量控制的核心机制，也是理解拥塞控制的前提。

#### 为什么需要滑动窗口？

```
没有窗口（停等协议）：
发送方发1个包 → 等ACK → 发下一个
效率极低：每个RTT只发一个包

有窗口（流水线发送）：
发送方连续发N个包（N=窗口大小）→ 收到ACK后窗口向前滑动
效率高：一个RTT内发N个包
```

#### 发送窗口与接收窗口

```
发送方维护的窗口：
┌───────────────────────────────────────────────────────┐
│  已发送已确认  │  已发送未确认  │  可以发送  │  不可发送  │
│  (可以释放)    │  (在窗口内)    │ (在窗口内)  │ (窗口外)  │
└───────────────────────────────────────────────────────┘
                  ← ────── 发送窗口 ────── →

发送窗口大小 = min(cwnd, rwnd)
- cwnd（拥塞窗口）：由拥塞控制算法决定，反映网络承受能力
- rwnd（接收窗口）：接收方在TCP报头中通告，反映接收方缓冲区剩余空间

接收方维护的窗口：
┌───────────────────────────────────────────────────────┐
│  已接收已确认  │  等待接收（接收窗口）  │  不可接收    │
└───────────────────────────────────────────────────────┘
                  ← ── rwnd（通告给发送方）── →
```

#### 滑动窗口运作过程

```
初始：rwnd = 4000字节，MSS = 1000字节

时刻1：发送方发送seq=1000~4000（4个MSS）
  已发送未确认：[1000, 2000, 3000, 4000]
  可以发送：无（窗口满）

时刻2：接收方确认ACK=3000（前2个包已收到）
  接收方rwnd更新：rwnd = 4000（缓冲区已被应用层读走）
  → 发送方窗口右移：释放[1000, 2000]，新增可发送空间
  已发送未确认：[3000, 4000]
  可以发送：[5000, 6000]

时刻3：接收方缓冲区满（应用层来不及读取）
  接收方通告：rwnd = 0
  → 发送方停止发送，等待窗口更新
```

#### 零窗口与窗口探测

```
问题场景：
1. 接收方缓冲区满 → 通告 rwnd = 0
2. 发送方停止发送
3. 接收方缓冲区释放 → 通告 rwnd > 0
4. 但这个窗口更新ACK丢失了！
5. 发送方永远不知道可以发送 → 死锁

解决方案：零窗口探测（Zero Window Probe）
- 发送方收到rwnd=0后，启动持续定时器（Persist Timer）
- 定时发送1字节的探测报文（ZWP, Zero Window Probe）
- 接收方收到探测后回复当前rwnd
- 探测间隔：指数退避（类似TCP重传），最大60秒
```

```bash
# Linux中零窗口探测相关参数
# 探测次数上限（默认15次，超过后RST关闭连接）
cat /proc/sys/net/ipv4/tcp_retries2
```

#### 流量控制 vs 拥塞控制

| 维度 | 流量控制 | 拥塞控制 |
|------|----------|----------|
| **解决什么问题** | 发送方不要淹没接收方 | 发送方不要淹没网络 |
| **控制变量** | rwnd（接收方通告窗口） | cwnd（拥塞窗口） |
| **谁决定** | 接收方（根据缓冲区剩余空间） | 发送方（根据网络反馈） |
| **反馈机制** | TCP报头的Window字段 | 丢包（超时/重复ACK） |
| **协作关系** | 实际发送窗口 = min(cwnd, rwnd) | 两者共同约束发送速率 |

```
发送速率的双重约束：

接收方缓冲区充足，但网络拥塞：
  rwnd = 100KB, cwnd = 10KB → 发送窗口 = 10KB（受拥塞控制限制）

网络畅通，但接收方处理慢：
  rwnd = 5KB, cwnd = 100KB → 发送窗口 = 5KB（受流量控制限制）
```

#### Nagle算法与延迟ACK的交互

```
Nagle算法（发送方）：
- 目的：减少小包数量（避免大量1字节TCP段）
- 规则：如果有已发送未确认的数据，新数据积累到MSS（最大报文长度）后再发送
- 如果没有未确认数据，立即发送（即使很小）

延迟ACK（接收方）：
- 目的：减少ACK数量（攒一批数据一起确认）
- 规则：收到数据后不立即回ACK，等待最多200ms（或收到第二个包后立即ACK）

两者叠加可能的问题：
- 发送方发了一个小包，等ACK才发下一个（Nagle）
- 接收方等200ms才回ACK（延迟ACK）
- → 每个小包都有200ms额外延迟，交互式应用（SSH/游戏）卡顿

解决：
setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &on, sizeof(on));
// TCP_NODELAY=1 关闭Nagle算法，小包立即发送
// 适用场景：游戏、SSH、实时交互
```

---

### 3.5 TCP 拥塞控制

**四大算法**：

**1. 慢启动（Slow Start）**
- 初始窗口小（cwnd=1 MSS）
- 每收到一个ACK，cwnd翻倍
- 指数增长至ssthresh（慢启动阈值）

**2. 拥塞避免（Congestion Avoidance）**
- cwnd > ssthresh后，每收到一个ACK，cwnd+1
- 线性增长

**3. 快速重传（Fast Retransmit）**
- 收到3个重复ACK，立即重传（不等超时）

**4. 快速恢复（Fast Recovery）**
- 快速重传后，ssthresh = cwnd/2，cwnd = ssthresh
- 进入拥塞避免

---

#### TCP拥塞控制底层原理深度剖析⭐⭐⭐

**为什么需要拥塞控制？**
- 面试高频：慢启动为什么是指数增长？拥塞避免为什么是线性增长？
- 性能调优：如何避免慢启动影响性能？
- 原理理解：TCP如何平衡速度和稳定性？

---

**核心概念**：

```
cwnd（Congestion Window，拥塞窗口）：
- 发送方维护的窗口大小
- 表示"我认为网络能承受多少数据"

ssthresh（Slow Start Threshold，慢启动阈值）：
- 初始值：通常很大（65535字节）
- 作用：区分慢启动和拥塞避免的分界线

实际发送窗口 = min(cwnd, rwnd)
- rwnd：接收方通告窗口（流量控制）
- cwnd：拥塞窗口（拥塞控制）
```

---

##### 1. 慢启动（Slow Start）详解⭐⭐⭐

**为什么叫"慢启动"？**

```
相对于"直接发送最大窗口"，慢启动是"慢"的：
- 不慢启动：初始cwnd=65535字节，可能导致网络拥塞
- 慢启动：初始cwnd=1 MSS（约1460字节），逐步探测网络容量
```

**慢启动的指数增长过程**：

```
初始：cwnd = 1 MSS，ssthresh = 65535字节

第1轮RTT：
发送：1个MSS（1460字节）
收到ACK：cwnd = 2 MSS

第2轮RTT：
发送：2个MSS
收到2个ACK：cwnd = 2 + 2 = 4 MSS

第3轮RTT：
发送：4个MSS
收到4个ACK：cwnd = 4 + 4 = 8 MSS

第4轮RTT：
发送：8个MSS
收到8个ACK：cwnd = 8 + 8 = 16 MSS

每个RTT，cwnd翻倍（指数增长）
1 → 2 → 4 → 8 → 16 → 32 → 64 → ...
```

**为什么是指数增长？**

```
目标：快速探测网络的可用带宽

线性增长（+1）太慢：
1 → 2 → 3 → 4 → 5 → ... → 100（需要100个RTT）

指数增长（×2）很快：
1 → 2 → 4 → 8 → 16 → 32 → 64 → 128（只需7个RTT）

优势：
- 快速达到合理的发送速率
- 避免长时间低效传输
```

**慢启动何时结束？**

```
条件1：cwnd >= ssthresh
→ 转入拥塞避免阶段

条件2：发生丢包（超时或3个重复ACK）
→ 重新设置ssthresh，重新慢启动
```

---

##### 2. 拥塞避免（Congestion Avoidance）详解⭐⭐⭐

**为什么需要拥塞避免？**

```
慢启动的指数增长太快：
- 接近网络容量时，再翻倍可能导致拥塞
- 需要更谨慎地探测网络容量
```

**拥塞避免的线性增长过程**：

```
进入条件：cwnd >= ssthresh

示例：cwnd = 16 MSS，ssthresh = 16 MSS

第1轮RTT：
发送：16个MSS
收到16个ACK：每个ACK增加 1/16 MSS
cwnd = 16 + 16×(1/16) = 17 MSS

第2轮RTT：
发送：17个MSS
收到17个ACK：每个ACK增加 1/17 MSS
cwnd = 17 + 17×(1/17) = 18 MSS

每个RTT，cwnd只增加1 MSS（线性增长）
16 → 17 → 18 → 19 → 20 → ...
```

**为什么是线性增长？**

```
目标：谨慎探测网络容量，避免拥塞

指数增长（×2）太激进：
16 → 32 → 64（可能立即拥塞）

线性增长（+1）刚好：
16 → 17 → 18（缓慢接近容量上限）

优势：
- 避免突然的流量激增
- 网络拥塞时能快速察觉（丢包）
```

---

##### 3. 快速重传（Fast Retransmit）详解⭐⭐⭐

**为什么需要快速重传？**

```
传统重传：依赖超时（RTO，通常1秒）
问题：超时时间太长，影响性能

快速重传：收到3个重复ACK，立即重传
优势：不等超时，立即恢复
```

**快速重传的触发过程**：

```
发送方：
发送seq=1000, 1500, 2000, 2500, 3000

接收方：
收到seq=1000 → 返回ACK=1500（期待1500）
收到seq=2000 → seq=1500丢失，返回ACK=1500（重复1）
收到seq=2500 → seq=1500仍丢失，返回ACK=1500（重复2）
收到seq=3000 → seq=1500仍丢失，返回ACK=1500（重复3）

发送方：
收到3个重复ACK=1500 → 立即重传seq=1500
（不等超时）

为什么是3个重复ACK？
- 1-2个重复ACK：可能是乱序（不是丢包）
- 3个重复ACK：大概率是丢包
- 权衡：误判率 vs 恢复速度
```

---

##### 4. 快速恢复（Fast Recovery）详解⭐⭐⭐

**快速恢复的核心思想**：

```
传统方式（Tahoe算法）：
丢包 → ssthresh = cwnd/2，cwnd = 1
→ 重新慢启动（太慢）

快速恢复（Reno算法）：
丢包 → ssthresh = cwnd/2，cwnd = ssthresh
→ 直接进入拥塞避免（更快）

为什么更快？
- 收到3个重复ACK，说明网络仍有传输能力（不是完全拥塞）
- 没必要降到cwnd=1，直接减半即可
```

**快速恢复的详细过程**：

```
初始：cwnd = 20 MSS，ssthresh = 40 MSS

步骤1：收到3个重复ACK
→ ssthresh = cwnd / 2 = 10 MSS
→ cwnd = ssthresh = 10 MSS
→ 重传丢失的数据包

步骤2：继续收到重复ACK（表示后续包已到达）
→ cwnd = cwnd + 1（临时膨胀，允许发送新数据）

步骤3：收到新的ACK（确认重传的包）
→ cwnd = ssthresh = 10 MSS
→ 进入拥塞避免阶段
```

---

##### 5. 完整的拥塞控制状态机⭐⭐⭐

**完整流程示例**：

```
时刻0：连接建立
cwnd = 1 MSS，ssthresh = 65535字节

阶段1：慢启动（指数增长）
RTT 1: cwnd = 1 → 2
RTT 2: cwnd = 2 → 4
RTT 3: cwnd = 4 → 8
RTT 4: cwnd = 8 → 16（达到ssthresh=16）

阶段2：拥塞避免（线性增长）
RTT 5: cwnd = 16 → 17
RTT 6: cwnd = 17 → 18
RTT 7: cwnd = 18 → 19
RTT 8: cwnd = 19 → 20

阶段3：丢包（3个重复ACK）
cwnd = 20，ssthresh = 20
→ ssthresh = 20/2 = 10
→ cwnd = 10（快速恢复）

阶段4：拥塞避免（线性增长）
RTT 9: cwnd = 10 → 11
RTT 10: cwnd = 11 → 12
...

阶段5：超时（网络严重拥塞）
cwnd = 15，ssthresh = 10
→ ssthresh = 15/2 = 7
→ cwnd = 1（重新慢启动）

阶段6：慢启动（指数增长）
RTT 11: cwnd = 1 → 2
RTT 12: cwnd = 2 → 4
RTT 13: cwnd = 4 → 8（达到ssthresh=7）

阶段7：拥塞避免...
```

**状态转换图**：

```
慢启动 ─────────────→ 拥塞避免
  ↑        cwnd>=ssthresh    │
  │                          │
  │                          │ 3个重复ACK
  │                          ↓
  └────────超时────────── 快速恢复
       (cwnd=1)           (cwnd=ssthresh)
```

##### 6. 拥塞控制算法演进⭐⭐

**Tahoe（1988）**：
```
丢包 → cwnd = 1，重新慢启动
缺点：太保守，性能差
```

**Reno（1990）**：
```
3个重复ACK → 快速恢复（cwnd = ssthresh）
超时 → cwnd = 1，慢启动
改进：减少慢启动次数
```

**NewReno（1999）**：
```
改进快速恢复：处理多个丢包
当前主流算法
```

**CUBIC（2008，Linux默认）**：
```
目标：高带宽网络（如10Gbps）
特点：窗口增长函数是三次函数（不是线性）
优势：更快达到高带宽
```

**BBR（2016，Google）**：
```
革命性：不基于丢包，而是基于带宽和RTT
目标：最大化带宽利用率，最小化延迟
YouTube、Google Cloud使用
```

| **数据中心内部** | DCTCP | 专为数据中心优化 |

**慢启动优化**：

```bash
# 增大初始拥塞窗口（Linux 3.0+默认10 MSS）
ip route change default via 192.168.1.101 initcwnd 10

# 禁用慢启动重启（长时间空闲后不重新慢启动）
sysctl -w net.ipv4.tcp_slow_start_after_idle=0
```

##### 8. 慢启动内核实现要点⭐⭐

**初始拥塞窗口（initcwnd）**：

内核中 `tcp_init_cwnd()` 决定初始cwnd，默认 `TCP_INIT_CWND = 10`（即10个MSS ≈ 14480字节）。这就是为什么新连接发送约14KB后就会暂停等待ACK。

```bash
# 通过路由表修改initcwnd（不需要改内核代码）
ip route change 10.0.0.0/24 dev eth0 initcwnd 20

# 实际发送窗口 = min(cwnd, 接收方通告窗口rwnd)
# 即使cwnd调到100，也受限于对端第一个SYN中通告的窗口（通常64240字节）
```

**慢启动对中等数据的性能影响**（实验数据）：

| 网络延迟(RTT) | 512KB数据传输耗时 | 慢启动中断次数 |
|---------------|-------------------|----------------|
| ~0.3ms | 8ms | 6次（几乎无感知） |
| ~3ms | 44ms | 6次 |
| ~7ms | 63ms | 6次（延时影响显著） |

**关键结论**：中等大小数据（几百KB）在RTT稍有增加时，传输延时会放大数倍。原因是每次窗口等待都要消耗一个RTT，6次中断×7ms RTT = 42ms额外开销。

**tcp_slow_start_after_idle**：

```bash
# 默认为1：长连接空闲后重新慢启动（cwnd重置为initcwnd）
# 设为0：空闲后复用之前的大窗口，第二次传输可大幅加速
sysctl -w net.ipv4.tcp_slow_start_after_idle=0

# 实验：512KB数据在长连接中连续两次传输（RTT=3ms）
# 开启(默认)：两次均耗时~19ms
# 关闭后：第一次19ms，第二次仅5ms（窗口延续）
```

### 3.6 TCP 粘包/拆包问题

**粘包/拆包原因**：
- TCP是字节流协议，无消息边界
- Nagle算法（合并小包）
- MSS限制（拆分大包）

**解决方案**：
1. **固定长度**：每个包固定N字节
2. **分隔符**：用特殊字符（如\n）分隔
3. **消息头+长度**（推荐）：

```go
// 编码
func Encode(data []byte) []byte {
    length := uint32(len(data))
    buf := make([]byte, 4+len(data))
    binary.BigEndian.PutUint32(buf[:4], length)
    copy(buf[4:], data)
    return buf
}

// 解码
func Decode(buf []byte) ([]byte, int) {
    if len(buf) < 4 {
        return nil, 0  // 数据不完整
    }

    length := binary.BigEndian.Uint32(buf[:4])
    if len(buf) < int(4+length) {
        return nil, 0  // 数据不完整
    }

    data := buf[4 : 4+length]
    return data, int(4 + length)
}
```

### 3.7 Socket 缓存与 TCP 性能调优

> Socket缓存大小直接影响TCP在高延时网络上的带宽利用率

#### 3.7.1 缓存参数体系

```bash
# 全局Socket缓存（影响TCP和UDP）
cat /proc/sys/net/core/rmem_default  # 接收缓存默认值 212992
cat /proc/sys/net/core/rmem_max      # setsockopt可设最大值
cat /proc/sys/net/core/wmem_default  # 发送缓存默认值
cat /proc/sys/net/core/wmem_max      # setsockopt可设最大值

# TCP专用缓存（覆盖core下的默认值）
cat /proc/sys/net/ipv4/tcp_rmem  # min default max
# 4096  131072  6291456
cat /proc/sys/net/ipv4/tcp_wmem  # min default max
# 4096  16384   4194304

# default：TCP socket创建时的默认缓存大小
# min-max：tcp_moderate_rcvbuf开启时的动态调整范围
# 注意：setsockopt设置后，动态调整被关闭，上限仍受rmem_max/wmem_max限制
# 注意：setsockopt实际生效值 = 设置值 × 2
```

#### 3.7.2 高延时网络的带宽利用问题

**核心问题**：TCP发送数据需等待ACK确认，在高延时网络上，等待时间远大于数据发送时间，导致带宽利用率极低。

**带宽延时积（BDP）公式**：

```
BDP = 带宽 × RTT
   = 125MB/s × 0.4s = 50MB

# BDP就是"管道"中同时在传输的数据量
# Socket缓存必须 >= BDP，否则发送方会因缓存满而暂停发送
```

**调优实验**（1000Mbit/s带宽 + 400ms RTT）：

| 配置 | 下载速度 | 带宽利用率 |
|------|----------|-----------|
| 默认缓存（16KB wmem） | 13.4 MB/s | ~10% |
| 仅调大发送方wmem=50MB | 14.9 MB/s | ~12% |
| 同时调大接收方rmem=100MB | **92.7 MB/s** | **~74%** |

**关键发现**：仅调发送方缓存不够！TCP发送窗口受接收方通告窗口（rwnd）限制，而rwnd由接收方**剩余**rmem决定。所以**必须同时调整两端缓存**。

#### 3.7.3 调优指南

```bash
# 计算目标缓存大小
# 发送方tcp_wmem max >= BDP
# 接收方tcp_rmem max >= 2 × BDP（留余量给overhead）

# 示例：1Gbps带宽，200ms RTT
# BDP = 125MB/s × 0.2s = 25MB
echo "4096 131072 52428800" > /proc/sys/net/ipv4/tcp_wmem   # max=50MB
echo "4096 131072 104857600" > /proc/sys/net/ipv4/tcp_rmem  # max=100MB

# 确保动态调整已开启
cat /proc/sys/net/ipv4/tcp_moderate_rcvbuf  # 1=开启(默认)

# tcp_adv_win_scale：控制缓存中overhead占比
cat /proc/sys/net/ipv4/tcp_adv_win_scale
# 默认1：1/2缓存用于overhead，2：1/4用于overhead
```

**调优优先级**：
1. **低延时网络（RTT<5ms）**：缓存调整对性能几乎无影响，瓶颈在带宽本身
2. **中等延时（5-50ms）**：适当调大缓存，关注慢启动影响
3. **高延时（>50ms）**：缓存调整效果显著，需计算BDP精确调整
4. **高延时+丢包**：缓存调整+选择BBR拥塞控制算法（对丢包不敏感）

## 4. UDP 与传输选型

### 4.1 UDP 特点

**优势**：
- ✅ **无连接**：无需握手，减少延迟
- ✅ **快速**：无确认、无重传
- ✅ **低开销**：头部只有8字节
- ✅ **支持广播/组播**

**劣势**：
- ❌ **不可靠**：丢包、乱序
- ❌ **无流量控制**
- ❌ **无拥塞控制**

### 4.2 UDP 在实时业务中的应用

**为什么游戏适合UDP？**
1. **实时性要求高**：FPS、MOBA需要低延迟（<100ms）
2. **允许丢包**：丢弃过时的位置数据，用最新的
3. **高频更新**：20-60次/秒发送位置，TCP重传会导致卡顿

**游戏场景选择**：
| 场景 | 协议 | 原因 |
|------|------|------|
| **登录、充值** | TCP | 必须可靠 |
| **聊天** | TCP | 必须可靠 |
| **移动、攻击** | UDP | 实时性优先 |
| **游戏结果** | TCP | 必须可靠 |

### 4.3 基于 UDP 的可靠传输（KCP、QUIC）

**问题**：UDP不可靠，如何在应用层实现可靠传输？

**KCP协议**（快速可靠协议）：
- 比TCP快30%-40%
- ARQ（自动重传请求）
- 快速重传、快速恢复
- 牺牲带宽换速度

**Go示例（KCP）**：
```go
import "github.com/xtaci/kcp-go"

// 服务端
listener, _ := kcp.ListenWithOptions(":8080", nil, 10, 3)
for {
    conn, _ := listener.AcceptKCP()
    go handleKCPConn(conn)
}

// 客户端
conn, _ := kcp.DialWithOptions("127.0.0.1:8080", nil, 10, 3)
conn.Write([]byte("Hello KCP"))
```

**QUIC协议**（HTTP/3基础）：
- 基于UDP
- 0-RTT握手（减少延迟）
- 多路复用、无队头阻塞
- 连接迁移（网络切换无需重连）

| **PUT** | 更新资源（完整替换） | ✅ | ❌ |
| **PATCH** | 更新资源（部分更新） | ❌ | ❌ |
| **DELETE** | 删除资源 | ✅ | ❌ |

**安全（Safe）**表示按语义不应修改服务端状态；**幂等（Idempotent）**表示同一个请求执行一次和多次，预期最终状态相同。幂等不代表没有副作用日志，也不代表一定能放心重试；涉及扣款、创建订单时仍应使用幂等键。

```http
POST /payments
Idempotency-Key: order-20260727-10001
```

### 5.3 状态码与常用 Header

| 类别 | 含义 | 常见状态码 |
|------|------|------------|
| `1xx` | 信息/协议切换 | `101 Switching Protocols` |
| `2xx` | 成功 | `200 OK`、`201 Created`、`204 No Content` |
| `3xx` | 重定向/缓存 | `301/308` 永久、`302/307` 临时、`304 Not Modified` |
| `4xx` | 客户端请求问题 | `400`、`401` 未认证、`403` 无权限、`404`、`409`、`429` |
| `5xx` | 服务端/网关问题 | `500`、`502 Bad Gateway`、`503 Unavailable`、`504 Gateway Timeout` |

高频网关错误：

```text
502：网关连到了上游，但上游响应无效/连接被拒/重置
503：服务暂不可用，可能无健康上游、过载、主动熔断
504：网关等待上游响应超时
```

| Header | 用途 |
|--------|------|
| `Host` | HTTP/1.1 虚拟主机；同一 IP 区分域名 |
| `Content-Type` | 请求/响应体格式，如 `application/json` |
| `Accept` | 客户端能接收的表示格式 |
| `Authorization` | 携带访问凭据，如 `Bearer` Token |
| `Cookie` / `Set-Cookie` | 客户端状态与会话 |
| `Connection` | HTTP/1.1 连接管理；HTTP/2 禁用连接级 Header |
| `Transfer-Encoding: chunked` | 不预先给总长度，分块传输 |
| `Content-Length` | 消息体字节数 |
| `Range` / `Content-Range` | 断点续传、分段下载 |
| `X-Forwarded-For` / `Forwarded` | 代理链传递原始客户端信息；必须定义可信代理边界 |
| `Traceparent` | W3C 分布式追踪上下文 |

### 5.4 HTTP/1.1 vs HTTP/2 vs HTTP/3

| 特性 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|------|----------|--------|--------|
| **传输协议** | TCP | TCP | QUIC (UDP) |
| **多路复用** | ❌ | ✅ | ✅ |
| **头部压缩** | ❌ | ✅ (HPACK) | ✅ (QPACK) |
| **队头阻塞** | ✅ | 部分解决 | ✅ 完全解决 |

**HTTP/3（QUIC）优势**（游戏场景）：
- 基于UDP，减少握手延迟（0-RTT）
- 彻底解决队头阻塞
- 连接迁移（Wi-Fi切换到4G无需重连）

### 5.5 HTTP 缓存策略⭐⭐⭐

> HTTP缓存是Web性能优化的核心手段，分为强缓存和协商缓存两种机制。

#### 强缓存（不需要请求服务器）

```
命中强缓存 → 浏览器直接从本地读取，不发送请求，状态码200 (from cache)

两个控制字段（优先级：Cache-Control > Expires）：

1. Cache-Control（HTTP/1.1，推荐）
   常用指令：
   - max-age=3600     → 资源有效期3600秒（从响应生成时间算起）
   - no-cache         → 不使用强缓存，每次都要走协商缓存验证
   - no-store         → 完全不缓存（敏感数据：银行页面等）
   - public           → 允许CDN/代理服务器缓存
   - private          → 只允许浏览器缓存（默认值）
   - s-maxage=3600    → CDN/代理的有效期（覆盖max-age）
   - must-revalidate  → 缓存过期后必须重新验证，不能使用过期缓存

2. Expires（HTTP/1.0，已过时）
   - 值为绝对时间：Expires: Thu, 26 Mar 2026 08:00:00 GMT
   - 缺点：依赖客户端时钟准确，客户端时间偏差会导致缓存失效
```

#### 协商缓存（需要请求服务器验证）

```
强缓存失效后 → 浏览器发请求到服务器验证资源是否变化

命中协商缓存 → 服务器返回304 Not Modified，浏览器用本地缓存
未命中 → 服务器返回200 + 新资源

两组验证字段（优先级：ETag > Last-Modified）：

1. ETag / If-None-Match（推荐，精确）
   响应头：ETag: "5d8c72a5edda8"（资源的唯一标识，通常是内容hash）
   请求头：If-None-Match: "5d8c72a5edda8"
   - 服务器对比ETag，相同返回304，不同返回200+新资源
   - 优点：精确到内容变化，即使时间变了但内容没变也不会失效
   - 缺点：服务器需要计算hash，有性能开销

2. Last-Modified / If-Modified-Since（兼容性好）
   响应头：Last-Modified: Thu, 26 Mar 2026 08:00:00 GMT
   请求头：If-Modified-Since: Thu, 26 Mar 2026 08:00:00 GMT
   - 服务器对比文件修改时间，未修改返回304
   - 缺点：精度只到秒（1秒内多次修改无法感知）
   - 缺点：文件被touch但内容没变也会失效
```

#### 缓存决策流程

```
浏览器请求资源
  │
  ├─ 有缓存？
  │   ├─ 否 → 请求服务器 → 缓存响应
  │   │
  │   └─ 是 → 检查强缓存（Cache-Control / Expires）
  │         ├─ 未过期 → 200 (from cache)，不发请求 ✅
  │         │
  │         └─ 已过期 → 发起协商缓存请求
  │               │   携带 If-None-Match / If-Modified-Since
  │               │
  │               ├─ 资源未变 → 304 Not Modified，用本地缓存 ✅
  │               │
  │               └─ 资源已变 → 200 + 新资源，更新缓存
```

#### 实际应用策略

```
不同资源的缓存策略：

HTML页面：
  Cache-Control: no-cache
  → 每次都协商验证（保证用户看到最新版本）

CSS/JS/图片（带hash文件名，如 app.a1b2c3.js）：
  Cache-Control: public, max-age=31536000 (1年)
  → 长期强缓存（文件名含hash，内容变了hash变，自动失效）

API接口：
  Cache-Control: no-store
  → 完全不缓存（数据实时性要求高）

CDN资源：
  Cache-Control: public, s-maxage=86400, max-age=3600
  → CDN缓存1天，浏览器缓存1小时
```

### 5.6 Cookie、Session、Token 与 CORS

| 机制 | 状态放哪 | 特点 |
|------|----------|------|
| **Cookie** | 浏览器保存，每次按域/路径规则自动携带 | 传输载体，不等于登录态；应设 `Secure`、`HttpOnly`、`SameSite` |
| **Session** | 服务端保存状态，Cookie 只带 Session ID | 易撤销；集群需共享或粘性会话 |
| **Token/JWT** | 客户端持有凭据，服务端验签/查状态 | 跨服务方便；撤销、续期和泄漏治理更复杂 |

CORS（Cross-Origin Resource Sharing，跨源资源共享）是**浏览器安全策略**，不是服务端之间通信限制。复杂跨源请求会先发 `OPTIONS` 预检：

```http
OPTIONS /api/orders HTTP/1.1
Origin: https://frontend.example.com
Access-Control-Request-Method: POST

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://frontend.example.com
Access-Control-Allow-Methods: POST
Access-Control-Allow-Credentials: true
```

当允许凭据时，`Access-Control-Allow-Origin` 不能写 `*`；反向代理和应用不要重复写出冲突的 CORS Header。

## 6. HTTPS 与 TLS

### 6.1 HTTPS 解决什么问题

**HTTPS（HTTP Secure / HTTP over TLS，安全 HTTP）= HTTP over TLS（Transport Layer Security，传输层安全协议）**。在 TCP 之上先完成 TLS，再跑 HTTP。

**SSL 和 TLS 的关系**：

| 名称 | 全称 | 状态 | 关系 |
|------|------|------|------|
| **SSL 2.0 / 3.0** | Secure Sockets Layer（安全套接字层） | 已废弃，不应使用 | 早期 Netscape 设计的安全协议 |
| **TLS 1.0** | Transport Layer Security（传输层安全协议） | 已废弃 | 基于 SSL 3.0 标准化而来，名字从 SSL 改为 TLS |
| **TLS 1.1** | Transport Layer Security | 已废弃 | TLS 1.0 的小幅增强 |
| **TLS 1.2** | Transport Layer Security | 仍广泛使用 | 现代兼容性基线 |
| **TLS 1.3** | Transport Layer Security | 推荐优先使用 | 更快、更安全、握手更简洁 |

所以不是「TLS 之前的版本都叫 SSL」。准确关系是：**SSL 是 TLS 的前身；TLS 1.0 是从 SSL 3.0 演进并标准化后的新名称；现代生产环境应使用 TLS 1.2/1.3**。日常有人说「SSL 证书」，多数只是历史叫法，实际用于 HTTPS 的通常是 **TLS 证书 / X.509 证书**。

| 能力 | 含义 |
|------|------|
| **机密性** | 窃听者看不到明文（对称加密传输应用数据） |
| **完整性** | 篡改可被检测（MAC（Message Authentication Code，消息认证码）/ AEAD（Authenticated Encryption with Associated Data，带关联数据的认证加密）） |
| **身份认证** | 通常先认证**服务器**（证书）；客户端证书可选（mTLS（mutual TLS，双向 TLS 认证）） |

浏览器地址栏的锁、证书警告，都发生在 **TLS 握手 / 证书校验** 阶段，与 HTTP 方法、路径无关。

```text
[应用] HTTP 请求/响应
[安全] TLS 记录层（加密后的数据）
[传输] TCP
[网络] IP
```

生产现状：新站点以 **TLS 1.2 + TLS 1.3** 为主；**TLS 1.0/1.1 已废弃**。读握手时以 **1.3 为默认**，用 **1.2 对照**理解「为什么 1.3 值得学」。

---

### 6.2 为什么要单独讲 TLS 1.3？要不要和 1.2 比？

**有必要对比。** 不是考古，而是面试/排障时仍会碰到 1.2，且 1.3 的「特别」几乎都是相对 1.2 改出来的：

| 维度 | TLS 1.2 | TLS 1.3 |
|------|---------|---------|
| **完整握手往返** | 通常 **2-RTT（Round-Trip Time，往返时延）** 后才能发应用数据 | 通常 **1-RTT** |
| **密钥交换时机** | 先协商套件，再单独一轮密钥交换 | ClientHello **就带上** Key Share，ServerHello 立刻选定并完成交换 |
| **加密开始时机** | 握手后半段仍有明文证书等（视套件） | ServerHello 之后，证书等多数握手消息已加密 |
| **算法清理** | 遗留 RSA（Rivest-Shamir-Adleman）密钥传输、CBC（Cipher Block Chaining）、RC4、SHA-1 等历史包袱 | 砍掉大量不安全套件；强调 ECDHE（Elliptic Curve Diffie-Hellman Ephemeral，临时椭圆曲线 DH）+ AEAD（如 AES-GCM、ChaCha20-Poly1305） |
| **前向保密（PFS，Perfect Forward Secrecy）** | 可选（静态 RSA 密钥交换时无 PFS） | **强制** 临时密钥交换（ECDHE 等） |
| **会话恢复** | Session ID / Session Ticket，多为 1-RTT 恢复 | **PSK（Pre-Shared Key，预共享密钥）/ 0-RTT** 恢复（更快，但 0-RTT 有重放风险） |

**TLS 1.3 特别在哪（记三条）**：

1. **更快**：首次握手少一趟 RTT（移动网 RTT 大时体感明显）。
2. **更干净**：默认密码套件更少、更安全，配置踩坑面变小。
3. **更早加密**：减少握手阶段明文暴露；和 QUIC「内置 TLS 1.3」也一脉相承（见第 12 章）。

### 6.3 TLS 1.2 握手（对照：为什么是 2-RTT）

以现代常见的 **ECDHE** 完整握手为例（省略次要扩展）：

```text
客户端                                              服务器
  |  ① ClientHello（版本、随机数、密码套件列表…）      |
  |------------------------------------------------->|
  |  ② ServerHello + 证书 + ServerKeyExchange         |
  |     + ServerHelloDone                             |
  |     （服务端此时才给出自己的临时公钥）               |
  |<-------------------------------------------------|
  |     （此时双方还不能安全传应用数据）                 |
  |  ③ ClientKeyExchange（客户端临时公钥）             |
  |     + ChangeCipherSpec + Finished                 |
  |------------------------------------------------->|
  |  ④ ChangeCipherSpec + Finished                   |
  |<-------------------------------------------------|
  |  ⑤ 应用数据（HTTP）加密传输                        |
```

要点：

- 第 ①② 轮：先谈「用什么算法、你是谁（证书）」，**客户端往往还没把自己的密钥交换材料发出去**。
- 第 ③④ 轮：客户端看到服务端选定的曲线/参数后，再发 `ClientKeyExchange`，双方才齐备密钥材料并 Finished → 相对发出 Hello，到能发 HTTP，常常要 **多等一个 RTT**（故称 2-RTT 握手）。
- 更早的 **RSA 密钥传输**模式更「绑死」顺序：客户端要用证书里的 RSA 公钥加密 premaster secret，所以必须先拿到证书，更不可能在 `ClientHello` 里提前完成密钥交换。该模式也无前向保密；现代 1.2 应强制 ECDHE。

所以 1.2 多一趟，主因是**历史握手消息顺序 + 旧密钥交换形态**，不是「提前传公钥太危险所以故意多等一趟」。

---

### 6.4 TLS 1.3 握手（主流程：为什么能 1-RTT）

#### 先纠正一个常见误解

> 「TLS 1.3 之所以能在首包传密钥，是因为以前这么做有风险，1.3 把风险解决了？」

**不对。**

- `key_share` 里带的是 **ECDHE 临时公钥**，本来就可以明文传输；安全性不靠「第二趟才敢发公钥」。
- 1.3 能 1-RTT，是因为**握手流程重设计**：允许客户端在 `ClientHello` 里**猜测**常用曲线并带上 `key_share`，服务端一趟回复自己的 `key_share`，双方立刻能做 DH。
- 真正更敏感、有明确风险的是后面的 **0-RTT Early Data**（早期应用数据可被重放），那是另一回事，见 §6.5。
  **首包 `key_share` ≠ 0-RTT 应用数据。**

#### 1.3 做对了什么，才省下一趟 RTT

相对 1.2，关键变化是：

1. **砍掉 RSA 密钥传输等旧模式**，密钥建立以 **(EC)DHE / PSK** 为主，并强制前向保密。不再依赖「先拿证书 → 用证书公钥加密 premaster」。
2. **允许客户端投机**：在 `ClientHello` 里直接带一个或多个 `key_share`（常见如 x25519），不必等服务端先发 `ServerKeyExchange`。
3. **协商与密钥交换解耦得更干净**：服务端在 `ServerHello` 选定版本/套件/分组，同时带回服务端 `key_share`；其后证书等用握手密钥加密。
4. 若客户端猜的曲线服务端不支持，走 **HelloRetryRequest（HRR）**，再多一趟 RTT——这是「猜错」的代价，不是常态路径。

#### 主路径时序（约 1-RTT）

```text
客户端                                              服务器
  |  ① ClientHello                                   |
  |     · supported_versions / cipher_suites         |
  |     · supported_groups（支持哪些曲线/分组）         |
  |     · key_share（先带上「猜的」临时公钥，如 x25519） |
  |     · SNI、ALPN 等扩展                            |
  |------------------------------------------------->|
  |                                                  |
  |  ② ServerHello                                   |
  |     · 选定版本、套件、分组                         |
  |     · 服务端 key_share                            |
  |     · {EncryptedExtensions}                      |
  |     · {Certificate}                              |
  |     · {CertificateVerify} 证明持有证书私钥          |
  |     · {Finished}                                 |
  |<-------------------------------------------------|
  |     {} = ServerHello 之后已用握手密钥加密            |
  |                                                  |
  |  ③ {Finished}（客户端）                            |
  |------------------------------------------------->|
  |  ④ 应用数据（HTTP）可加密发送  ← 相对 Hello 约 1-RTT |
```

上图按阶段合并，不是逐个 TLS Record。重点：**发出 ClientHello 后约 1 个 RTT，即可开始发加密应用数据**；不是说 1.3「只有两条消息」。

密钥怎么出来（直觉版）：

```text
客户端临时私钥 + 服务端临时公钥  →  共享秘密
服务端临时私钥 + 客户端临时公钥  →  同一共享秘密
再用 HKDF 等导出：握手密钥 → 应用流量密钥（AEAD）
```

DH/ECDHE 的通用密钥协商原理见 §2.7.5.2；TLS 1.3 的 `key_share` 是 ECDHE 临时公钥材料，证书和 `CertificateVerify` 负责身份认证。

证书校验仍在这条路径上完成（链、SAN、有效期、吊销等），只是证书报文本身在 1.3 里多为密文。

#### 和 1.2 对照：差在「谁先交出临时公钥」

```text
TLS 1.2 ECDHE（简化）：
  ClientHello
  ← ServerHello + Cert + ServerKeyExchange（服务端临时公钥）
  ClientKeyExchange（客户端临时公钥）+ Finished
  ← Finished
  → 应用数据          …… 相对 Hello，约 2-RTT

TLS 1.3（简化）：
  ClientHello（已带客户端 key_share）
  ← ServerHello（带服务端 key_share）+ {Cert… Finished}
  {Finished}
  → 应用数据          …… 相对 Hello，约 1-RTT
```

一句话：1.2 是「服务端先亮出临时公钥，客户端再回」；1.3 是「客户端先猜一把带上，服务端同意就对着算」。

#### 猜错曲线：HelloRetryRequest

不是每次都能 1-RTT。若客户端 `key_share` 的分组服务端都不接受：

```text
ClientHello（带了 A 曲线的 key_share）
← HelloRetryRequest（请改用 B 曲线）
ClientHello（按 B 再带 key_share）
← ServerHello + …
→ 这时会多一趟 RTT，接近「又变慢了」
```

实践里客户端会优先带业界常用分组（如 x25519），HRR 相对少见，但排障时要知道「1.3 不保证永远 1-RTT」。

#### `key_share` 提前发送，到底安不安全？

| 点 | 说明 |
|----|------|
| 传的是什么 | ECDHE **临时公钥**，不是会话密钥本身，也不是应用数据 |
| 中间人看得见吗 | 看得到公钥材料、SNI（明文扩展；后续有 ECH 等演进）等元数据 |
| 会不会泄漏将来流量 | 不会单靠截获公钥就解密后续 AEAD 流量；还需要完成合法握手与密钥导出 |
| 和证书的关系 | 身份仍靠证书链 + `CertificateVerify`；密钥交换负责「约会话密钥」 |
| 真正要小心的 | **0-RTT 早期应用数据**可被重放，见 §6.5；别和首包 `key_share` 混谈 |

#### 证书在干什么（1.2 / 1.3 两边通用）

```text
浏览器内置信任根 CA（Certificate Authority，证书颁发机构）
  → 校验服务器证书链（域名是否匹配、是否过期、是否被吊销等）
  → CertificateVerify：用证书对应私钥签名握手摘要，证明「我就是证书主体」
```

只拿证书、不能证明私钥，不够；所以 1.3 里 **Certificate + CertificateVerify** 成对出现（且多为加密传输）。

#### 小结（面试可直接背）

```text
1. 1.3 能 1-RTT：ClientHello 可带 key_share，服务端一趟回 key_share + 证书等
2. 不是「解决了提前传密钥的风险」：临时公钥本来就可明文传
3. 1.2 多一趟：旧消息顺序 + 常等 ServerKeyExchange / 甚至 RSA 先拿证书
4. 猜错分组会 HRR，可能变回多一趟
5. 有风险的是 0-RTT Early Data（重放），不是 key_share 本身
```

---

### 6.5 会话恢复与 0-RTT

| 模式 | 延迟 | 说明 |
|------|------|------|
| 完整握手 | 1.3 约 **1-RTT** | 首次访问或票证失效 |
| 1-RTT PSK 恢复 | **1-RTT** | 用上次会话票据/PSK，少做部分公钥运算 |
| **0-RTT**（Early Data） | **0-RTT** 即可带应用数据 | 重连极快；**早期数据可被重放**，只适合幂等读（如部分 GET），支付/下单勿用 |

```text
0-RTT 风险（简图）：
攻击者截获「带着 Early Data 的 ClientHello」→ 原样重放给服务器
→ 若服务器接受 early data，可能重复执行同一请求
```

---

### 6.6 实践要点

- 服务器同时开 **TLS 1.2 + 1.3**，优先协商 1.3；关掉 1.0/1.1。
- 证书用权威 CA 或内网私有 CA；注意中间证书是否配齐（链不完整是常见踩坑）。
- 抓包：TLS 1.3 握手后半段和证书多为密文，需 SSLKEYLOGFILE 等才能解密分析。
- 和 HTTP/2、HTTP/3：浏览器用 HTTPS；HTTP/3 跑在 QUIC 上，TLS 1.3 嵌在 QUIC 握手里（见第 12 章），不要和「TCP + 独立 TLS 记录层」混为一谈。

### 6.7 PKI 与证书运维

PKI（Public Key Infrastructure，公钥基础设施）把「域名身份」和「公钥」绑定起来：

```text
根 CA（操作系统/浏览器内置信任）
  └─ 中间 CA
      └─ api.example.com 服务器证书
```

客户端校验：证书链能否到可信根、域名是否匹配 SAN、当前时间是否在有效期、签名是否正确、证书是否被吊销。

| 概念 | 作用 |
|------|------|
| **SNI** | Server Name Indication；ClientHello 携带目标域名，让同一 IP 返回不同证书 |
| **ALPN** | Application-Layer Protocol Negotiation；协商 `h2`、`http/1.1` 等应用协议 |
| **OCSP Stapling** | 服务端附带 CA 的证书状态响应，避免客户端单独查询 |
| **HSTS** | HTTP Strict Transport Security；要求浏览器后续只用 HTTPS |
| **mTLS** | 双向 TLS；服务端也校验客户端证书，常用于内网服务身份 |

```bash
# 查看握手、证书链、SNI、协商协议
openssl s_client -connect api.example.com:443 \
  -servername api.example.com -showcerts -alpn h2

# 查看证书主题、SAN、有效期、签发者
openssl x509 -in cert.pem -noout -subject -issuer -dates -ext subjectAltName
```

高频故障：中间证书漏配、证书过期、SAN 不含目标域名、SNI 配错、客户端系统时间错误、内网 CA 未加入信任库、mTLS 客户端证书轮换失败。

### 7.1 WebSocket 握手

**升级请求**：
```http
GET /chat HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
```

**升级响应**：
```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

### 7.2 Go 实现 WebSocket

```go
import "github.com/gorilla/websocket"

var upgrader = websocket.Upgrader{
    CheckOrigin: func(r *http.Request) bool { return true },
}

func handleWebSocket(w http.ResponseWriter, r *http.Request) {
    conn, _ := upgrader.Upgrade(w, r, nil)
    defer conn.Close()

    for {
        messageType, message, err := conn.ReadMessage()
        if err != nil {
            break
        }
        conn.WriteMessage(messageType, message)
    }
}
```

### 7.3 WebSocket 心跳保活

```go
func keepAlive(conn *websocket.Conn) {
    ticker := time.NewTicker(30 * time.Second)
    defer ticker.Stop()

    for range ticker.C {
        conn.WriteMessage(websocket.PingMessage, []byte{})
    }
}
```

### 7.4 WebSocket、SSE、长轮询与 gRPC

| 方案 | 方向 | 传输 | 适合场景 |
|------|------|------|----------|
| **短轮询** | 客户端周期请求 | HTTP | 低频状态，最简单但浪费请求 |
| **长轮询** | 服务端挂起请求直到有数据/超时 | HTTP | 兼容性要求高、消息不密集 |
| **SSE** | 服务端 → 客户端单向流 | HTTP `text/event-stream` | 通知、日志流、AI 流式输出；浏览器原生重连 |
| **WebSocket** | 全双工 | HTTP Upgrade 后独立帧协议 | 聊天、协作、实时控制 |
| **gRPC Streaming** | 单向/双向流 | HTTP/2 | 服务间 RPC；浏览器直连受限 |

选择原则：只有服务端推送优先 SSE；需要浏览器双向低延迟用 WebSocket；内部服务的强类型流式调用用 gRPC。无论哪种长连接，都要设计心跳、断线重连、背压、消息幂等和连接上限。

### 7.5 视频传输链路：推流、转码、分发、互动

讨论视频协议时，不要先把 RTMP、HLS、WebRTC 放进同一张表里简单比较。它们通常站在不同位置，解决不同问题：

```text
采集/主播/摄像机
  → ① 推流 ingest：把直播流送到平台入口
  → ② 转码/转封装：生成多码率、多清晰度、多协议形态
  → ③ 分发/拉流 delivery：观众从 CDN/边缘节点播放
  → ④ 互动 real-time：连麦、会议、云游戏等低延迟双向链路
```

#### ① 推流：从采集端到平台源站

推流关注的是“怎么把一路持续产生的音视频稳定送进平台”。这段通常是一对一或少量连接，不直接面对海量观众。

| 协议 | 底层 | 典型位置 | 特点 |
|------|------|----------|------|
| **RTMP**（Real-Time Messaging Protocol） | TCP | OBS/编码器 → 直播源站 | 兼容性极好、链路简单，仍大量用于推流入口 |
| **SRT**（Secure Reliable Transport） | UDP + ARQ/FEC | 远程采集、弱网回传、专业制作 | 可控重传、抗抖动，适合不稳定网络 |
| **RIST** | UDP + 可靠性增强 | 广电/专业传输 | 偏标准化和互通，定位类似专业可靠传输 |
| WebRTC | UDP + RTP/SRTP | 低延迟采集/连麦入口 | 延迟低，但服务端架构和 NAT 穿越更复杂 |

RTMP 还没消失，主要因为 OBS、硬件编码器和直播平台都支持，生产链路成熟；但它不适合现代浏览器直接播放，也不适合靠边缘缓存服务千万观众。

#### ② 转码与转封装：把一路流变成多种可分发形态

源站收到推流后，通常会做几件事：

```text
原始直播流
  → 解复用 / 解码（视情况）
  → 转码：1080p / 720p / 480p，多码率 ABR
  → 转封装：HLS、DASH、LL-HLS、fMP4、CMAF 等
  → 切片 / 生成播放列表
  → 推送或供 CDN 回源
```

转码解决“不同网络和设备能不能流畅看”；转封装解决“用什么播放协议分发”。编码格式（H.264/H.265/AV1）、封装格式（FLV、MP4、fMP4、TS）和传输协议（RTMP、HTTP、QUIC、RTP）不是同一层概念，排障时要分开看。

#### ③ 分发/拉流：面向海量观众和 CDN

观众播放关注的是“海量并发、就近访问、可缓存、可降级”。因此大规模直播/点播最常见的是 HTTP 切片协议：

| 协议 | 底层 | 典型延迟 | 为什么适合分发 |
|------|------|----------|----------------|
| **HLS**（HTTP Live Streaming） | HTTP/TCP，或 HTTP/3/QUIC | 数秒～十几秒 | `.m3u8` + 切片文件，浏览器/移动端/CDN 生态成熟 |
| **DASH** | HTTP/TCP，或 HTTP/3/QUIC | 数秒～十几秒 | 标准化自适应码率，适合多码率播放 |
| **LL-HLS / LL-DASH** | HTTP 分块/部分切片 | 约 1～3 秒 | 在 CDN 友好和低延迟之间折中 |
| HTTP/3 分发 | QUIC/UDP | 取决于切片和播放器 | 减少 TCP 队头阻塞，移动网络切换更友好 |

CDN 喜欢 HLS/DASH，是因为切片文件天然可以缓存、预热、合并回源和多级分发。它牺牲了一部分实时性，换来稳定性和海量并发。

#### ④ 互动低延迟：实时性优先于完美可靠

连麦、视频会议、在线教育、云游戏这类场景，目标不是“每一帧都完整有序到达”，而是“尽快把当前画面和声音送到”。

WebRTC 常用于这类链路：

```text
信令：WebSocket / HTTPS
媒体：RTP/RTCP over UDP + SRTP 加密
穿透：ICE + STUN/TURN
弱网：NACK/PLI、FEC、Jitter Buffer、码率自适应
```

实时视频偏爱 UDP 系协议，是因为视频有时效性：2 秒前丢掉的 B/P 帧，补回来也可能没意义；TCP 的有序字节流会让后面的数据等前面丢包重传，形成队头阻塞。UDP 之上可以只重传关键数据、丢弃过期帧、用 FEC 抗少量丢包，再用抖动缓冲和自适应码率兜底。

但 UDP 不是银弹：企业防火墙可能限制 UDP，NAT 映射超时更短，公网拥塞仍要靠拥塞控制、FEC、重传和播放器缓冲来权衡。很多系统会同时准备 TCP/TLS 或 TURN Relay 兜底。

一句话总结：

```text
推流：RTMP 仍常见，SRT/RIST 更适合专业弱网回传
转码：把一路流加工成多码率、多封装、多播放协议
分发：HLS/DASH/LL-HLS 借 CDN 服务海量观众
互动：WebRTC/RTP 更适合百毫秒级双向实时通信
```

### 7.6 直播卡顿怎么归因：拉流、CDN、源站还是播放器？

看球赛、演唱会这类大直播时，卡顿通常不是单点问题，而是一条长链路上的某一段抖了：

```text
球场/电视台信号
  → 推流到源站
  → 转码/切片/封装
  → CDN 核心/中间层
  → CDN 边缘节点
  → 运营商网络 / 最后一公里
  → 家庭 Wi-Fi / 移动网络
  → 播放器缓冲 / 解码 / 渲染
```

排障时先看影响范围：

| 现象 | 更可能的问题 |
|------|--------------|
| 只有你卡，别人不卡 | 家庭 Wi-Fi、移动网络、设备解码、播放器缓冲 |
| 同城市/同运营商大量用户卡 | 本地 CDN 节点拥塞、运营商互联拥塞、GSLB 调度错误 |
| 全国大量用户一起卡 | 源站、转码、CDN 中心层、直播流本身 |
| 清晰度越高越卡，降码率变好 | 带宽不足、设备解码能力不足、码率自适应不及时 |
| 刚开赛/进球瞬间卡 | 突发流量、热点切片、回源风暴、边缘节点带宽打满 |

CDN 在体育直播里不仅能用，而且通常必须用。没有 CDN，千万观众直接打源站，源站出口和连接数会被瞬间打爆。直播 CDN 常用几类手段：

- **树状分发**：源站只推给核心/中间层，边缘节点再就近服务用户。
- **切片缓存**：HLS/DASH 的 `.ts`、`.m4s` 等短切片可在边缘缓存，降低源站压力。
- **动态调度**：GSLB/HTTPDNS/调度系统按地域、运营商、节点负载分配边缘节点。
- **防回源风暴**：请求合并、预热、热点切片保护、源站限流。
- **多 CDN**：大活动常同时接多家 CDN，按质量/成本/区域动态切换。
- **P2P-CDN / P2SP**：部分客户端之间共享切片，降低边缘带宽压力；要权衡隐私、稳定性和体验。

直播永远在「低延迟」和「不卡顿」之间做取舍：

```text
大缓冲：更稳，但延迟高，容易被隔壁剧透
小缓冲：延迟低，但一点抖动就卡
```

因此排障指标不能只看“是否能连上”，还要看首帧时间、播放缓冲区长度、下载速率/码率比、丢包、重传、CDN 命中率、回源比例、边缘节点带宽、播放器解码耗时。

## 8. DNS与域名解析

DNS（Domain Name System，域名系统）负责把人类可读的域名解析成 IP 地址或其他资源记录。它不是单台服务器，而是一套分层、缓存、分布式的命名系统。

### 8.1 DNS 解析流程

```
浏览器
  → 浏览器缓存
  → 操作系统缓存 / hosts
  → 本地递归 DNS（运营商 DNS、企业 DNS、公共 DNS）
  → 根 DNS（.）
  → 顶级域 DNS（.com / .cn）
  → 权威 DNS（example.com 的最终记录）
  → 返回结果并按 TTL 缓存
```

**递归查询 vs 迭代查询**：

| 查询类型 | 谁负责继续问下去 | 典型场景 |
|----------|------------------|----------|
| **递归查询** | DNS 服务器替客户端问到底，并返回最终答案 | 客户端问本地 DNS：`example.com` 是什么 IP？ |
| **迭代查询** | 被问服务器只返回「下一步该问谁」 | 本地 DNS 问根 / 顶级域 / 权威 DNS |

```text
客户端 → 本地 DNS：帮我查 example.com       （递归）
本地 DNS → 根 DNS：.com 找谁？              （迭代）
本地 DNS → .com DNS：example.com 找谁？     （迭代）
本地 DNS → 权威 DNS：www.example.com 的 A？ （迭代）
本地 DNS → 客户端：答案是 1.2.3.4
```

### 8.2 DNS记录类型

| 类型 | 说明 | 示例 |
|------|------|------|
| **A** | IPv4地址 | example.com → 192.168.1.1 |
| **AAAA** | IPv6地址 | example.com → 2001:db8::1 |
| **CNAME** | 别名 | www.example.com → example.com |
| **MX** | 邮件服务器 | example.com → mail.example.com |
| **TXT** | 文本记录 | SPF、DKIM、域名验证 |
| **NS** | 权威域名服务器 | example.com → ns1.provider.com |
| **SOA** | 起始授权记录 | 区域序列号、刷新时间等 |
| **SRV** | 服务发现 | `_sip._tcp.example.com` |

**CNAME 注意点**：

- 一个名称如果配置了 `CNAME`，通常不能再同时配置 `A`、`MX` 等其他记录。
- 根域（apex，如 `example.com`）很多 DNS 服务不允许直接配 `CNAME`，会提供 `ALIAS` / `ANAME` / CNAME Flattening 这类厂商能力。
- CNAME 会多一次解析链路；缓存命中后影响较小，但排障时要沿链查到底。

### 8.3 TTL、缓存与变更生效

TTL（Time To Live，生存时间）决定 DNS 记录在缓存中保留多久。

```text
权威 DNS 设置：
www.example.com A 1.2.3.4 TTL=300

本地 DNS 查到后缓存 300 秒。
300 秒内客户端再查，可能直接拿缓存，不会访问权威 DNS。
```

**为什么 DNS 改了不立刻生效？**

- 浏览器 / 操作系统 / 本地递归 DNS 都可能缓存。
- 旧记录 TTL 未过期前，递归 DNS 可以继续返回旧 IP。
- 有些运营商递归 DNS 会最小 TTL / 最大 TTL 钳制，实际行为不完全受权威 DNS 控制。

**客户端是不是只能干等缓存过期？**

对「全网所有用户」来说：基本是的。权威 DNS 改了之后，**没有标准机制能强制清空全世界运营商递归 DNS 的缓存**；旧记录通常要等到各自 TTL 到期才会重新向权威查询。

但对「某一个客户端 / 某一台机器」来说：不是完全没事可做。

| 能做什么 | 实际效果 | 局限 |
|----------|----------|------|
| 清浏览器 DNS 缓存 / 重开浏览器 | 清掉浏览器自己的缓存 | 不影响系统缓存和运营商递归 DNS |
| 清操作系统 DNS 缓存 | 本机立刻向递归 DNS 重新查询 | 若递归 DNS 仍握着旧记录，拿到的还是旧 IP |
| 临时改用未缓存旧值的公共 DNS（如 `1.1.1.1` / `8.8.8.8`） | 可能更快拿到新记录 | 取决于该公共 DNS 是否已缓存、以及企业网络是否允许改 |
| 本机写 `hosts` 指向新 IP | 立刻生效，且绕过 DNS | 只影响本机；忘记删会埋雷 |
| App 用 HTTPDNS / 自建解析 | 可主动缩短/清掉应用侧缓存 | 只覆盖你的 App，不覆盖浏览器与其他客户端 |
| 企业自建递归 DNS 上强制刷新/清缓存 | 整网段用户可加快切换 | 管不到家用宽带运营商的递归 DNS |

一句话：

```text
本机缓存：可以清，立竿见影只对本机
运营商 / 公共递归 DNS：一般清不了别人的，只能等 TTL
正确迁移姿势：不是指望用户手动 flush，而是提前降 TTL + 新旧 IP 并行服务
```

变更建议：

1. 大迁移前先把 TTL 从 1 小时/1 天降到 60～300 秒。
2. 等旧 TTL 过期后再切记录。
3. 切完后**旧 IP 继续能服务一段时间**（至少覆盖旧 TTL），避免手里还拿旧缓存的用户直接挂。
4. 观察错误率、流量分布，再把 TTL 调回合理值。
5. 排障时本机可 `flush` / 换公共 DNS / 查权威记录，用来区分「权威已改」还是「中间缓存未过期」。

### 8.4 GSLB：基于 DNS 的全局流量调度

GSLB（Global Server Load Balancing，全局服务器负载均衡）常用 DNS 做入口调度：同一个域名，根据用户来源、运营商、地域、健康状态返回不同 IP 或 CNAME。

```text
用户 A（华东电信）查 api.example.com → 返回上海电信机房 IP
用户 B（华南移动）查 api.example.com → 返回广州移动机房 IP
用户 C（海外）    查 api.example.com → 返回新加坡节点 IP
```

| 能力 | 说明 |
|------|------|
| 就近访问 | 按 Local DNS 出口 IP / ECS 信息判断用户大致位置 |
| 故障切换 | 某机房健康检查失败后，不再返回该机房 IP |
| 权重调度 | 灰度、扩容、迁移时按比例分流 |
| 运营商调度 | 电信走电信、移动走移动，减少跨网延迟 |

**局限**：

- DNS 看到的常是**递归 DNS 的 IP**，不一定是用户真实 IP；ECS（EDNS Client Subnet，扩展 DNS 客户端子网）可改善但有隐私与兼容问题。
- TTL 导致切换不是实时的；故障摘除后，客户端仍可能拿着旧缓存访问一段时间。
- DNS 只负责「把用户引到哪里」，不感知单个 TCP 连接内的实时质量。

### 8.5 Anycast：同一个 IP，多地同时宣告

Anycast（任播）不是 DNS 记录类型，而是一种 **BGP（Border Gateway Protocol，边界网关协议）路由发布方式**：多个机房同时对外宣告同一个 IP 段，互联网路由会把用户流量送到「路由上最近 / 最优」的节点。

```text
同一个 Anycast IP：203.0.113.53

北京节点宣告 203.0.113.0/24
上海节点宣告 203.0.113.0/24
新加坡节点宣告 203.0.113.0/24

用户访问 203.0.113.53 → BGP 路由选择最近的可达节点
```

常见用途：

- 公共 DNS：如 `8.8.8.8`、`1.1.1.1`
- CDN 边缘入口
- DDoS 清洗入口
- 全球统一入口服务

| 对比 | GSLB（DNS 调度） | Anycast（路由调度） |
|------|------------------|---------------------|
| 调度层级 | 应用层 / DNS 层 | 网络层 / BGP 路由 |
| 返回结果 | 不同用户可能拿到不同 IP | 所有人访问同一个 IP |
| 切换速度 | 受 TTL 和缓存影响 | 依赖 BGP 收敛，通常对客户端透明 |
| 控制粒度 | 可按域名、地域、权重精细控制 | 由路由策略决定，应用层控制较弱 |
| 常见组合 | DNS 返回 CDN / 机房入口 | DNS 返回的 IP 本身可能是 Anycast |

**二者不是互斥**：很多全球服务会先用 DNS/GSLB 选区域或产品入口，再让返回的 IP 使用 Anycast 在区域内或全球就近接入。

### 8.6 DNS 排障命令

```bash
# 看最终解析结果
dig www.example.com

# 指定 DNS 服务器查询
dig @8.8.8.8 www.example.com

# 查解析链路（根 → 顶级域 → 权威）
dig +trace www.example.com

# 查看 CNAME 链和 TTL
dig www.example.com CNAME
dig www.example.com A +ttlunits

# 查某域名的权威 NS
dig example.com NS
```

排障顺序：

1. 先查本地结果是否异常：`dig domain`
2. 再指定公共 DNS 对比：`dig @8.8.8.8 domain`
3. 再查权威链路：`dig +trace domain`
4. 若只有部分地区异常，考虑 GSLB 调度、运营商递归 DNS 缓存、ECS、Anycast 路由问题。

### 8.7 私有 DNS、加密 DNS 与安全

| 机制 | 解决的问题 | 注意点 |
|------|------------|--------|
| **Split-horizon DNS**（分割视图） | 同一域名在内外网返回不同地址 | VPN、办公网、云 VPC 常见；排障必须确认使用了哪个递归 DNS |
| **DNSSEC** | 用签名验证 DNS 数据未被伪造 | 提供完整性/来源认证，不加密查询内容 |
| **DoT** | DNS over TLS | 通常 TCP 853，加密客户端到递归 DNS |
| **DoH** | DNS over HTTPS | 走 HTTPS，穿透性强，但可能绕过企业 DNS 策略 |
| **HTTPDNS** | 应用直接通过 HTTP(S) 查询域名结果 | 移动端抗劫持/精细调度；需自己处理缓存、HTTPS SNI 和降级 |

企业/云环境还要理解私有 Zone、条件转发和 CoreDNS：服务发现问题可能不是公网 DNS，而是内部 Zone、搜索域、转发链或缓存配置错误。

## 9. 负载均衡、代理、CDN 与全球流量调度

### 9.1 正向代理、反向代理与网关

| 组件 | 代表谁 | 客户端是否知道真实服务端 | 常见用途 |
|------|--------|--------------------------|----------|
| **正向代理** | 代表客户端访问外部 | 通常知道 | 企业出口、访问控制、缓存 |
| **反向代理** | 代表服务端接收请求 | 通常只看到代理 | TLS 终止、路由、负载均衡、缓存 |
| **API 网关** | 面向 API 的反向代理 + 治理 | 通常只访问网关 | 鉴权、限流、路由、协议转换、观测 |

代理传递真实客户端信息时，只能信任受控代理写入的 `Forwarded` / `X-Forwarded-For`；否则客户端可以自行伪造。四层代理可使用 PROXY Protocol 在 TCP 数据前传递源地址，但前后端必须同时正确配置。

### 9.2 L4 与 L7 负载均衡

| 维度 | L4（传输层） | L7（应用层） |
|------|--------------|--------------|
| 依据 | IP、端口、TCP/UDP | Host、路径、Header、Cookie、方法 |
| 是否理解 HTTP | 否 | 是 |
| TLS | 常透传 | 常终止 TLS 并检查 HTTP |
| 性能 | 高、通用 | 功能强但开销更高 |
| 实现 | LVS/IPVS、云四层 LB | Nginx、Envoy、HAProxy、云七层 LB |

负载均衡器还要处理：

- 调度：轮询、最少连接、一致性哈希、权重。
- 健康检查：TCP 端口通不等于业务健康；关键服务应有轻量 L7 readiness。
- 连接排空：摘实例时停止新流量，等待旧连接结束。
- 会话保持：优先让应用无状态；必须保持时用 Cookie/一致性哈希并接受热点风险。
- 分阶段超时：连接、请求头、上游响应、空闲连接不能混成一个超时。

### 9.3 CDN：边缘缓存与回源

CDN（Content Delivery Network，内容分发网络）把内容放到靠近用户的 POP（Point of Presence，边缘节点）：

```text
用户 → DNS/GSLB 或 Anycast → CDN POP
                                  ├─ 命中缓存：直接返回
                                  └─ 未命中：回源 → 源站/对象存储
```

| 概念 | 说明 |
|------|------|
| 缓存键 | 通常由 Host + Path + Query + 部分 Header 组成；错误会串数据或降低命中率 |
| 回源 | 边缘未命中时请求源站；需防热点过期造成回源风暴 |
| 回源 Host/SNI | CDN 连接源站时的 HTTP Host 与 TLS SNI 必须匹配 |
| 缓存刷新 | 全球刷新并非瞬时；版本化文件名通常更可靠 |
| 动静分离 | 静态资源长缓存；动态 API 多为透传或短缓存 |

排障先判断错误来自 DNS、CDN 边缘、回源链路、代理还是应用。`Age`、`Via`、`X-Cache` 等响应头常可判断缓存状态（实际 Header 因厂商而异）。

### 9.4 CDN、边缘计算与内网 CDN

**CDN 和边缘计算的区别**

CDN 先解决的是「把内容放近」；边缘计算进一步解决「把计算也放近」。

| 维度 | CDN | 边缘计算 |
|------|-----|----------|
| 核心目标 | 缓存、分发静态/流式内容 | 在边缘节点执行代码和实时处理 |
| 典型数据 | 图片、JS/CSS、安装包、视频切片 | 鉴权、A/B、边缘函数、AI 推理、流处理 |
| 主要收益 | 降低延迟、节省源站带宽、抗高并发 | 降低回源、就近决策、减少中心计算压力 |
| 典型产品 | CDN、对象存储加速、直播 CDN | Cloudflare Workers、Lambda@Edge、边缘容器、边缘 GPU |

以直播为例：

```text
CDN：把视频切片缓存在省/市边缘节点，观众就近拉流
边缘计算：在边缘做鉴权、防盗链、广告决策、轻量转码、AI 字幕/美颜等
```

现实中二者越来越融合：很多 CDN POP（Point of Presence，边缘节点）已经能跑函数、WASM、容器或轻量 AI 任务。但设计时仍要问清楚：你要的是「缓存分发」，还是「边缘执行逻辑」。

**公网 CDN 能不能用来解决内网跨 IDC 同步？**

通常不应该直接这么用。

```text
错误直觉：
IDC A 资源同步慢 → 上传到公网 CDN → IDC B 从 CDN 拉

问题：
内网数据绕公网，暴露到第三方边缘节点，安全/合规/防火墙边界都很别扭
```

商业公网 CDN 的默认假设是：内容可以经公网域名访问，边缘节点也在公网服务用户。若拿它解决内网系统、跨 DC（Data Center，数据中心）同步、私有图片分发，会遇到：

- **网络边界错位**：内网请求绕到公网再回来，不符合 VPC/专线/内网隔离模型。
- **安全合规风险**：内部文档、用户隐私图片、未公开素材可能落到第三方公网节点。
- **防火墙与回源复杂**：生产 IDC 往往不允许任意公网出站，也不允许公网 CDN 回源访问内网。
- **故障归因困难**：问题从内网同步变成公网 DNS、CDN、回源、证书、访问控制混合问题。

更合理的解法：

| 需求 | 推荐方向 |
|------|----------|
| 内网静态资源跨 DC 分发 | 自建内网 CDN：Nginx/Varnish/对象存储网关 + 内网 DNS/GSLB |
| 大文件/图片跨地域同步 | 对象存储跨区域复制、消息队列异步同步、专线增量同步 |
| 多 IDC 服务互访 | 内网负载均衡、专线/VPN、服务网格或云联网 |
| 公网用户访问静态内容 | 商业 CDN |

一句话：公网 CDN 是给公网用户加速的；内网跨 IDC 分发要么走私有 CDN，要么走对象存储/专线/复制系统，不要为了“快”把安全边界打穿。

### 9.5 全球入口的分层职责

GSLB 与 Anycast 的机制见 §8.4～§8.5，它们与 L4/L7 LB 不是同一层：

```text
全球用户
  → DNS/GSLB：选区域、运营商或产品入口
  → Anycast：把同一 IP 路由到就近 POP（可选）
  → CDN/WAF/DDoS 清洗：边缘防护和缓存
  → 边缘计算：就近鉴权、轻量逻辑、实时处理（可选）
  → L4 LB：连接级分发
  → L7 Gateway：按域名/路径路由、鉴权限流
  → Service / Pod
```

| 层级 | 解决的问题 |
|------|------------|
| DNS/GSLB | 全球哪个区域/机房 |
| Anycast/BGP | 同一 IP 路由到哪个接入点 |
| CDN | 内容能否在边缘直接返回 |
| 边缘计算 | 逻辑能否就近执行 |
| L4 LB | 连接交给哪台后端 |
| L7 Gateway | HTTP/RPC 请求交给哪个服务 |

## 10. IDC 数据中心网络：从大二层到 Spine-Leaf 与 SDN

IDC（Internet Data Center，互联网数据中心）网络不是单个协议，而是一套从物理链路、交换机、路由协议到虚拟网络控制面的演进体系。理解它的主线，比背单个名词更重要：

```text
传统大二层：VLAN + STP + 堆叠
  → 过渡方案：TRILL / RBridge / FabricPath 等二层多路径
  → 现代主流：L3 Clos / Spine-Leaf + ECMP
  → 云网络：VXLAN Overlay + EVPN/SDN 控制面
```

直觉上看，早期是在努力把很多交换机“看成一个大交换机”；现代是在承认物理网络应该做稳定的三层路由，再用 Overlay 给业务虚拟出它想要的二层/三层网络。

### 10.1 交换机的控制面与转发面

网络设备通常拆成两个平面：

| 平面 | 在做什么 | 典型组件 |
|------|----------|----------|
| **控制面** | 算路由、跑协议、生成表项 | CPU、网络 OS、BGP/OSPF/STP/LACP 进程 |
| **转发面 / 数据面** | 按表项线速转发包 | ASIC、MAC 表、FIB、ACL/TCAM |

可以把控制面想成“算地图的大脑”，转发面想成“按地图高速分拣包裹的流水线”。普通业务流量不会每个包都慢慢问 CPU，而是命中 ASIC 里的 MAC 表、FIB（Forwarding Information Base，转发表）或 ACL 表项后线速转发。

二层交换机主要看 MAC 地址：

```text
收到以太网帧 → 查 MAC 表 → 从对应端口转发
未知单播 / 广播 → 在 VLAN 内泛洪
```

三层交换机不只是“多接了一台路由器”，而是在交换机 ASIC 中加入了路由转发能力：

```text
收到 IP 包 → 查 FIB / 路由表 → 改写下一跳 MAC → 从出接口线速转发
```

SVI（Switched Virtual Interface，交换虚拟接口）常用于在交换机上作为某个 VLAN 的网关：

```text
VLAN 10: 192.168.10.0/24
SVI vlan10: 192.168.10.1  # 该 VLAN 的默认网关
```

所以“从 L2 变成 L3”的关键，不是机架旁边多放一个小路由器，而是三层网关和路由能力下沉到接入/Leaf 交换机，东西向流量不再必须绕到远处的汇聚或核心层。

### 10.2 传统大二层：VLAN、STP 与三层树

传统数据中心常见拓扑是接入层 → 汇聚层 → 核心层：

```text
服务器 → 接入交换机(ToR) → 汇聚交换机 → 核心交换机
```

为什么曾经需要这么做？

- 端口密度和交换芯片能力有限：不能把几千台服务器直接插到核心交换机。
- VLAN 需要跨多个机架延伸：同一业务、同一虚拟机网段可能分布在不同接入交换机后面。
- 早期虚拟化希望 VM 迁移后 IP 不变：这推动了“大二层”网络，即同一个二层广播域横跨多个机架。

二层网络的问题是环路。以太网帧没有 TTL，一旦交换机之间形成环路，广播/未知单播可能无限复制，形成广播风暴。

STP（Spanning Tree Protocol，生成树协议）通过 BPDU 选出一棵无环树：

```text
1. 选根桥 Root Bridge（通常人工把核心/汇聚设备优先级调低）
2. 每台交换机选到根桥最短路径
3. 冗余链路进入 Blocking/Discarding，防止二层环路
```

注意：STP 本身不认识“核心、汇聚、接入”这些架构角色。它只根据 Bridge ID、路径开销和端口角色计算树。核心交换机常成为根桥，是网络工程师规划优先级的结果，不是协议天然知道谁更“权威”。

STP 的代价：

- 冗余链路很多处于阻塞状态，买了链路但平时不能同时跑流量。
- 收敛需要时间，早期 STP 故障切换慢；RSTP/MSTP 改善了收敛和多 VLAN 实例，但仍是“算一棵树”的思路。
- 大二层广播域越大，故障扩散越大：环路、广播风暴、ARP 异常都可能影响大片业务。

### 10.3 TRILL 与 RBridge：二层多路径的过渡方案

TRILL（Transparent Interconnection of Lots of Links，多链路透明互联）试图解决 STP 的核心痛点：既保留二层语义，又不要把冗余链路都阻塞掉。

TRILL 里的设备叫 RBridge（Routing Bridge，路由桥）。名字很准确：

```text
对服务器/边缘看：它像二层桥，仍然转以太网帧
在 RBridge 内部看：它像路由器，跑链路状态协议计算最短路径
```

TRILL 的基本思路：

1. RBridge 之间运行 IS-IS（Intermediate System to Intermediate System，中间系统到中间系统协议），学习拓扑。
2. 入口 RBridge 给原始以太网帧加 TRILL Header，标记出口 RBridge。
3. 中间 RBridge 按最短路径转发，不再依赖 STP 阻塞冗余链路。
4. TRILL Header 中有 Hop Count，类似 TTL，避免二层帧在环路中无限转。
5. 出口 RBridge 解封装，还原原始以太网帧交给目标主机。

```text
原始以太网帧
  → 入口 RBridge 封装 TRILL
  → RBridge Fabric 内按 IS-IS 最短路径多路径转发
  → 出口 RBridge 解封装
  → 目标主机
```

对比 STP：

| 维度 | STP 大二层 | TRILL / RBridge |
|------|------------|-----------------|
| 冗余链路 | 阻塞一部分 | 多路径可用 |
| 控制面 | 生成树 | IS-IS 链路状态 |
| 转发 | MAC 学习 + 树形转发 | 封装后按 RBridge 最短路径转发 |
| 防环 | 阻塞链路 | Hop Count + 链路状态计算 |
| 目标 | 避免二层环路 | 保留二层语义并提升链路利用率 |

为什么现代云数据中心没有普遍停在 TRILL？

- 云网络需要大规模租户隔离，VLAN 的 4096 限制不够，VXLAN 的 VNI 可到 1600 万级别。
- 数据中心更希望 Underlay 简单稳定，用纯 L3 BGP/ECMP 承载，业务二层语义放到 Overlay。
- 硬件、运维和生态逐渐转向 VXLAN/EVPN；TRILL、FabricPath 等更多是特定时期/厂商体系下的过渡方案。
- 大二层本身的广播域、故障域和跨地域延迟问题并不会因为 TRILL 完全消失。

所以 TRILL 不是“错误方案”，它是在 STP 和现代 VXLAN/EVPN 之间的一条重要演进路线：用路由思想改造二层 Fabric，但最终主流云网络选择了更彻底的 L3 Underlay + Overlay 解耦。

### 10.4 Bond、LACP、堆叠与 M-LAG：服务器接入高可用

服务器接入网络时，最基本诉求是：网卡、网线、交换机坏一部分，业务不能立刻断。

```text
服务器
  ├─ NIC0 ── Leaf/接入交换机 A
  └─ NIC1 ── Leaf/接入交换机 B
```

**Bond / Team：服务器侧网卡绑定**

Bond 是 Linux/服务器侧的叫法，Team 是另一个实现；交换机侧常叫 LACP、Port-Channel、Eth-Trunk。

| 模式 | 作用 | 注意点 |
|------|------|--------|
| active-backup | 一主一备，故障切换 | 最简单稳定，不要求复杂交换机能力 |
| 802.3ad / LACP | 多链路聚合，按 hash 分流 | 需要交换机配合；同一流通常只走一条成员链路 |
| balance-xor | 固定策略 hash 分流 | 要确认交换机兼容性 |
| balance-alb/tlb | 发送或收发负载均衡 | 更多依赖主机侧行为，生产需谨慎验证 |

常见误区：两块 10G 网卡做 LACP，不等于一个 TCP 连接能跑 20G。为了避免乱序，同一五元组通常固定在一条成员链路上；多连接、多客户端、多目的地时，总吞吐才更容易叠加。

**物理堆叠：多台交换机合体**

```text
[交换机 A] == 堆叠线 == [交换机 B]
        \               /
         \             /
          [服务器 Bond]
```

优点：统一管理、跨设备链路聚合、逻辑上像一台交换机，减少 STP 阻塞。缺点：控制面和软件版本强耦合，堆叠分裂、主控故障、升级 bug 可能影响整组，故障半径较大。

**M-LAG：不合体，但对服务器协同表现为一台**

M-LAG（Multi-Chassis Link Aggregation，跨设备链路聚合；厂商名还包括 vPC、MC-LAG 等）让两台交换机保持独立控制面，但在下联链路聚合上协同：

```text
控制面：A/B 各自跑自己的 OS、BGP、LACP、管理进程
数据面：通过 peer-link / keepalive 同步必要状态，对服务器表现为同一个 LACP 伙伴
```

| 维度 | 物理堆叠 | M-LAG |
|------|----------|-------|
| 控制面 | 合并/强耦合 | 独立运行 |
| 数据面 | 像一台交换机 | 协同转发 |
| 故障域 | 堆叠组可能一起受影响 | 单台故障通常只损失部分带宽 |
| 升级 | 往往要整组维护或风险较高 | 更容易逐台滚动维护 |
| 适合场景 | 中小规模、管理简单优先 | 大规模 IDC、追求故障隔离 |

一句话：堆叠是“合体”；M-LAG 是“各自有脑子，但对服务器协同演戏”。现代 IDC 倾向去堆叠，是为了缩小故障半径、减少厂商耦合、支持滚动升级。

### 10.5 现代 L3 Clos / Spine-Leaf 与 ECMP

Clos 网络是一类多级无阻塞/低阻塞拓扑，现代数据中心常见实现就是 Spine-Leaf：

```text
          Spine1   Spine2   Spine3   Spine4
             |       |       |       |
Leaf1 -------+-------+-------+-------+
Leaf2 -------+-------+-------+-------+
Leaf3 -------+-------+-------+-------+

服务器接 Leaf；Leaf 到所有 Spine 全互联
```

Leaf 通常就是 ToR（Top of Rack，机架顶交换机）。Spine 不直接接服务器，只负责在 Leaf 之间提供多条等价路径。

现代 Spine-Leaf 通常是纯三层 Underlay：

```text
Leaf/Spine 接口都是三层 IP
Leaf 与 Spine 跑 BGP/OSPF/IS-IS 等路由协议
目的 VTEP/网段有多条等价下一跳 → ECMP hash 分流
```

为什么它可以替代 STP/堆叠？

- L3 包有 TTL，即使路由异常也会在有限跳数后丢弃，不会像二层广播那样无限复制。
- 路由协议本身有防环逻辑，例如 BGP 的 AS-PATH、OSPF/IS-IS 的链路状态数据库与 SPF 计算。
- ECMP（Equal-Cost Multi-Path，等价多路径）允许多条链路同时转发，不需要像 STP 那样把冗余链路阻塞掉。
- 任一 Spine 或 Leaf 故障通常只损失一部分带宽或一部分机架，不会把整片二层广播域拖垮。

Spine-Leaf 不等于 SDN。没有 SDN，也可以手工配置 BGP/OSPF 跑一张纯 L3 Spine-Leaf。SDN 解决的是自动化、租户隔离、Overlay 映射、策略编排和生命周期联动。

### 10.6 Underlay、Overlay、VXLAN 与 VTEP

Underlay 是真实物理网络；Overlay 是叠在上面的虚拟网络。

```text
Underlay：Leaf/Spine 组成的 L3 IP 网络，跑 BGP/OSPF + ECMP
Overlay ：VXLAN 隧道虚拟出来的 L2/L3 租户网络
```

VXLAN（Virtual eXtensible LAN，虚拟可扩展局域网）把原始二层帧封进 UDP/IP：

```text
外层以太网
  外层 IP：VTEP A 物理/Loopback IP → VTEP B 物理/Loopback IP
    外层 UDP：dst port 4789
      VXLAN Header：VNI（租户/虚拟网络标识）
        原始以太网帧：VM A → VM B
```

容易混淆的一点：VXLAN 用 UDP 4789 做封装载体，但 Underlay 仍是 L3。中间 Spine/Leaf 主要看外层目的 IP，把包路由到目标 VTEP；它不关心内层 VM IP、MAC 或 VNI。

VTEP（VXLAN Tunnel Endpoint，VXLAN 隧道终结点）负责封装和解封装：

| 类型 | 位置 | 特点 |
|------|------|------|
| 硬件 VTEP | Leaf 交换机 | ASIC 线速封装/解封装，常见于物理网络网关 |
| 软件 VTEP | 宿主机 / Hypervisor / CNI | Open vSwitch、Linux 内核隧道、eBPF 等实现 |

一次 VM A 到 VM B 的流量：

```text
VM A 发出原始二层帧
  → VTEP A 查表：VM B 的 MAC/IP 在 VTEP B 后面
  → 外层封装：src = VTEP A IP，dst = VTEP B IP，UDP 4789，VNI = 租户网络
  → Underlay 按外层 IP 经 Spine-Leaf + ECMP 转发
  → VTEP B 解 VXLAN，还原原始帧
  → 交给 VM B
```

VXLAN 解决的是：让业务仍像在一个二层网络里通信，但物理网络不再需要真的拉一个巨大二层广播域。VNI（VXLAN Network Identifier）也把隔离空间从 VLAN 的 4096 扩展到约 1600 万。

### 10.7 EVPN-BGP：Overlay 的控制面

VXLAN 只是数据面封装。关键问题是：VTEP A 怎么知道 VM B 在哪个 VTEP 后面？

早期/简单方案：

- 静态配置：人工维护 MAC/IP → VTEP 映射，规模大时不可行。
- 泛洪学习：未知目的就广播/泛洪，容易把大二层问题带回 Overlay。

现代常见方案是 EVPN-BGP：

```text
VTEP / 控制器通过 BGP EVPN 发布：
  某个 MAC/IP 在哪个 VTEP 后面
  某个 VNI 对应哪些 VTEP
  哪些前缀/网关可达
```

常见 EVPN 路由类型（理解方向即可）：

| 类型 | 作用 |
|------|------|
| Type 2 | 发布 MAC/IP 到 VTEP 的映射，减少泛洪 |
| Type 3 | 发布某 VNI 的 VTEP 成员，用于多播/泛洪范围控制 |
| Type 5 | 发布 IP Prefix 路由，支持更三层化的 Overlay 转发 |

EVPN-BGP 的价值：

- 把“谁在哪里”从数据面泛洪变成控制面发布。
- 支持分布式网关和任播网关（Anycast Gateway），VM 迁移后默认网关 IP/MAC 可保持一致。
- 利用 BGP 的成熟邻接、策略、收敛和可观测能力，支撑大规模数据中心 Overlay。

### 10.8 SDN、OpenFlow 与 BGP：不要混成一个概念

SDN（Software-Defined Networking，软件定义网络）是一种架构思想：控制面和转发面分离，由软件系统集中或半集中地编排网络。它不等于 Overlay，也不等于 OpenFlow。

```text
云平台创建/迁移 VM 或 Pod
  → SDN 控制器感知生命周期
  → 计算网络、子网、安全组、路由、MAC/IP/VTEP 映射
  → 下发到交换机、宿主机 OVS、eBPF 数据面或云网关
  → 数据面本地查表转发，不会每个包实时问控制器
```

SDN 可以做两类事：

| 范围 | 例子 |
|------|------|
| Underlay 自动化 | 交换机接口 IP、BGP 邻居、路由策略、链路状态采集 |
| Overlay 编排 | VNI、VTEP 映射、安全组、虚拟路由器、租户隔离 |

OpenFlow 和 BGP 的区别：

| 维度 | OpenFlow | BGP / EVPN-BGP |
|------|----------|----------------|
| 控制模式 | 集中式控制器下发流表 | 分布式对等协议交换可达性 |
| 表项粒度 | 细粒度 match/action，可匹配 MAC/IP/端口/VLAN 等 | 路由可达性；EVPN 扩展 MAC/IP → VTEP |
| 设备角色 | 更像执行器 | 自己跑协议、算路径、保留本地状态 |
| 典型使用 | 早期 SDN、实验网络、精细策略控制 | 互联网路由、IDC Underlay、VXLAN EVPN |
| 风险 | 控制器依赖强，规模和稳定性要求高 | 协议成熟，分布式更稳，但策略设计复杂 |

现代大规模数据中心常见组合：

```text
Underlay：BGP/OSPF/IS-IS + ECMP，保证物理 IP 网络稳定
Overlay ：VXLAN 数据面 + EVPN-BGP 或 SDN 控制器发布映射
运维面 ：控制器/自动化系统负责生命周期、策略、观测和配置一致性
```

控制器短时不可用时，已有数据面表项通常仍能转发；新的 VM 创建、迁移、路由和安全策略变更才会受影响。

### 10.9 NFV、DPDK、SPDK 与基础设施数据面加速

#### 10.9.1 先看一条完整的云基础设施数据路径

前面的章节解决了“物理网络怎样连接、路由和承载租户 Overlay”。云平台还要解决另一个问题：用户创建一台 VM 或一个 Pod 后，流量如何经过虚拟交换、虚拟路由、防火墙、NAT、负载均衡，最后到达业务？

```text
用户创建 VPC / 子网 / VM
  → 云控制器记录租户网络、路由、安全组和服务链
  → SDN 控制面把状态下发到 Leaf、VTEP、宿主机和网关
  → NFV 实例提供 vRouter / vFirewall / vNAT / vLB
  → OVS / VPP / DPDK / eBPF 执行主机或网关数据面
  → SmartNIC / DPU 可卸载虚拟交换、VXLAN、加密和安全处理
  → 业务 VM / Pod 收到报文
```

可以把它类比成一个物流园区：**SDN 是调度中心，NFV 是把海关/安检/分拣中心软件化，OVS 是园区内部道路，DPDK 是减少收费站停顿的快速车道，SmartNIC/DPU 是把部分分拣工作移到车站入口，NUMA 则决定货物、处理工人和装卸口是否在同一个园区。**

NFV、SDN、VXLAN/EVPN 和数据面加速解决的是不同问题：

| 层次 | 它解决的问题 |
|------|--------------|
| SDN | 网络状态和策略由谁计算、如何下发？ |
| NFV | 防火墙、NAT、LB、路由等网络功能如何软件化和弹性部署？ |
| VXLAN/EVPN | 租户 Overlay 如何跨物理网络可达？ |
| OVS/VPP/eBPF | 主机或网关如何执行软件转发？ |
| DPDK/SR-IOV | 如何减少每包处理和虚拟化边界开销？ |
| NUMA | 线程、网卡队列和内存是否位于合适的 CPU 节点？ |
| SmartNIC/DPU | 哪些基础设施任务应该从主机 CPU 卸载出去？ |

#### 10.9.2 NFV 到底是什么：从“买硬件盒子”到“装网络功能 App”

如果只说“NFV 是网络功能虚拟化”，其实还是抽象。更直观地说：**NFV 把过去必须买专用硬件盒子才能跑的网络功能，变成运行在通用服务器上的软件、虚拟机或容器。**

没有 NFV 时，很多能力要靠专用设备：

| 需求 | 传统做法 | 本质问题 |
|------|----------|----------|
| 防火墙 | 买 Palo Alto、Fortinet 等硬件防火墙 | 功能和硬件绑定 |
| 负载均衡 | 买 F5 等硬件 LB | 容量按盒子采购 |
| 企业网关/路由 | 买 Cisco/Juniper 等硬件路由器 | 扩容、迁移和自动化慢 |
| DPI/IDS/NAT | 买对应专用设备 | 每种功能一类盒子 |

NFV 的核心变化：

```text
过去：网络功能 = 专用硬件盒子里的固定能力
现在：网络功能 = 通用 x86/ARM 服务器上的软件服务

像在手机上安装 App 一样：
服务器 + KVM/容器 + vFirewall / vRouter / vNAT / vLB
```

这不是说专用硬件不重要了，而是把“功能”和“硬件”解耦：防火墙、路由器、NAT、负载均衡器可以像 VM/Pod 一样创建、销毁、扩容和升级。

#### 10.9.3 NFV 不绑定某一层：哪里需要网络处理，哪里就可能有 NFV

NFV 不是“接入层技术”，也不是“只负责防火墙”。它可以出现在网络中的多个位置：

| 位置 | 常见 VNF/CNF | 作用 |
|------|--------------|------|
| **边界/出口层** | vFirewall、vRouter、vNAT、DDoS 清洗 | 处理进出数据中心或 VPC 的流量，做安全和地址转换 |
| **业务/服务层** | vLB、WAF、API Gateway | 在业务前面做流量分发、七层防护和协议治理 |
| **运营商/接入网** | vCPE、5G Core 的 UPF/AMF 等网元 | 把分支 CPE、移动核心网用户面/控制面软件化 |
| **云内部租户网络** | 虚拟路由器、虚拟安全组网关 | 为租户 VPC、子网、跨可用区互联提供网络能力 |

一句话：**NFV 是网络领域的“云原生/虚拟化”思路，不是某个固定网络层级。** 只要某段流量需要“过滤、路由、NAT、负载均衡、检测、清洗”，这个功能就可能被 NFV 化。

#### 10.9.4 SDN + NFV：SDN 负责牵线，NFV 负责处理

SDN 和 NFV 最容易混淆。可以先记一个粗略分工：

```text
SDN：决定流量怎么走，负责铺路、牵线、下发转发表
NFV：决定流量经过哪些网络功能，负责过滤、转换、清洗、负载均衡
```

例如一个外部请求必须先经过虚拟防火墙，再经过虚拟负载均衡，最后到达业务 VM：

```text
外部流量
  → vFirewall（NFV：检查安全策略）
  → vLB（NFV：选择后端实例）
  → VM C（业务）

SDN 控制器：
  下发路由/隧道/流表，让流量按这个顺序经过这些节点
```

这就是服务功能链（Service Function Chaining / SFC）：

```text
[ 外部流量 ]
    → [ vFirewall ]
    → [ vLB ]
    → [ 目标业务 VM/Pod ]
```

类比一下：NFV 提供“安检机、海关、分拣机”这些可创建、可扩缩容的功能节点；SDN 负责在这些节点之间画路线、改路由、调度流量。没有 SDN，NFV 节点可能存在，但流量不一定能自动按业务期望的顺序经过它们；没有 NFV，SDN 只能转发，很难弹性提供防火墙、NAT、LB 等高级网络功能。

| 维度 | SDN | NFV |
|------|-----|-----|
| 关注核心 | 路由与转发：怎么铺路、怎么引流 | 网络服务与处理：怎么滤包、怎么 NAT、怎么负载均衡 |
| 替代/改造对象 | 传统网络控制面和手工配置 | 防火墙、LB、DPI、NAT、路由器等专用硬件盒子 |
| 常见载体 | 交换机、Leaf/Spine、VTEP、控制器 | 通用服务器、VM、容器、虚拟网关 |
| 常见技术 | OpenFlow、BGP-EVPN、VXLAN、控制器 | KVM、容器、OVS、DPDK、SR-IOV、SmartNIC/DPU |
| 典型结果 | 流量能自动走到正确位置 | 网络功能能像软件服务一样部署和扩缩容 |

#### 10.9.5 一个具体场景：租户 VM 访问公网

假设租户 VM `10.10.1.20` 访问公网 `203.0.113.8:443`，云平台需要提供安全组检查、私网路由、SNAT、出口路由和返回流量关联：

```text
VM
  → virtio 网卡 / vhost
  → 宿主机 OVS 或 eBPF 数据面
  → VXLAN VTEP：从租户 Overlay 封装到物理 Underlay
  → vFirewall：检查五元组、连接状态和安全策略
  → vRouter：查租户路由表
  → vNAT：10.10.1.20:临时端口 → 公网 IP:端口
  → Leaf/Spine Underlay
  → 公网
```

返回包到达后，vNAT 根据连接跟踪表反向转换，vFirewall 校验连接状态，vRouter 再把报文送回正确的 VTEP 和 VM。

这里 NFV 是“路径中的网络功能节点”，SDN 是“决定路径和下发状态的控制面”，VXLAN/EVPN 是“让租户网络跨物理网络可达的承载机制”。它们不是同一个概念。

#### 10.9.6 NFV 的组成：NFVI、VNF/CNF 与服务链

```text
租户/云平台编排：
  创建 VPC、NAT、LB、防火墙策略

NFV 编排：
  决定网络功能实例、数量、连接顺序和故障策略

VNF / CNF：
  vFirewall、vRouter、vNAT、vLB、UPF 等具体功能

NFVI：
  服务器、网卡、虚拟化、网络、存储和加速设备
```

- **NFVI（NFV Infrastructure）**：承载网络功能的计算、网络、存储和加速资源。
- **VNF（Virtualized Network Function）**：通常以 VM 或进程运行，适合已有成熟网络软件迁移。
- **CNF（Cloud-native Network Function）**：以容器、微服务、声明式配置和云原生生命周期运行；适合弹性和自动化更强的场景，但有状态网络功能改造难度更高。
- **服务功能链（Service Function Chaining）**：把流量依次导入防火墙、IDS、NAT、LB 等功能，类似快递依次经过安检、海关和分拨中心。

#### 10.9.7 NUMA：为什么 CPU 很快，NFV 还是可能很慢？

NUMA（Non-Uniform Memory Access，非统一内存访问）描述多路 CPU 服务器的内存结构。双路服务器不是“所有 CPU 共享一块完全等价的内存”，而是：

```text
NUMA Node 0                         NUMA Node 1
CPU 0/1 + 本地内存                  CPU 2/3 + 本地内存
网卡队列 0 ───── 本地 PCIe          网卡队列 1 ───── 本地 PCIe
       \_________ 跨节点互联 _________/
```

CPU 访问本地内存通常延迟更低、带宽更高；访问另一个 NUMA 节点要经过跨节点互联。高性能 NFV 会反复访问网卡队列、DPDK mbuf 内存池、连接跟踪表、NAT 表和防火墙规则，因此远端内存访问的损失会被放大。

如果网卡在 Node 0，DPDK 线程在 Node 1，mbuf 又从 Node 1 分配，就会出现“CPU 利用率不低但包处理性能很差”。这像仓库、工人和装卸口分属三个园区，大家都在工作，但大量时间花在跨园区运输。

典型优化是让硬件和线程局部性对齐：

```text
网卡 PCIe 在 Node 0
  → DPDK PMD 线程绑到 Node 0 的 CPU
  → mbuf/hugepage 从 Node 0 分配
  → 相关 vCPU、OVS/vhost 线程和连接表尽量放在 Node 0
```

NUMA 不是 NFV 专属概念，但高包速率、用户态轮询和高并发连接跟踪会把 NUMA 远端访问的损失放大。

#### 10.9.8 DPDK、OVS、VPP、eBPF/XDP 与 SR-IOV

基础 VM 网络路径通常是：

```text
VM 应用
  → Guest OS TCP/IP
  → virtio-net
  → vhost/虚拟化边界
  → OVS/Linux bridge
  → 物理 NIC
```

它兼容普通 Socket 和虚拟机迁移，但每个报文可能经历多次拷贝、虚拟化切换、中断和内核路径。

常见优化：

1. **OVS（Open vSwitch）**：连接 VM、Pod、物理网卡，执行 VLAN、VXLAN、ACL 和虚拟端口转发。
2. **vhost-net/vhost-user**：减少 virtio 数据包经过虚拟化边界的开销。
3. **DPDK**：用 PMD 轮询、预分配 mbuf 内存池和批量处理减少中断、系统调用和内核协议栈开销。
4. **VPP**：将多个报文组成向量批量处理，减少每包重复执行的指令。
5. **eBPF/XDP**：在 Linux 网络路径早期做过滤、转发、采样或负载均衡，保留较多内核治理能力。
6. **SR-IOV**：把物理网卡划分为多个 VF，让 VM 更直接访问网卡队列。

```text
普通路径：NIC → 中断/NAPI → 内核协议栈 → Socket
DPDK/VPP：NIC 队列 → 用户态 PMD → mbuf/vector → 网络功能
SR-IOV：NIC 的 VF 队列 → VM/Guest 驱动 → 应用
XDP：NIC/驱动早期 → XDP/eBPF → 丢弃/转发/继续进入内核
```

这些方案不是简单的性能排序：DPDK 牺牲通用 Socket 和部分能耗换吞吐；SR-IOV 牺牲虚拟交换可见性和迁移灵活性换更短路径；XDP 则在可治理性和早期处理之间折中。

#### 10.9.9 SmartNIC 与 DPU：为什么把数据面移出主机 CPU？

服务器 CPU 同时处理业务、虚拟交换、VXLAN、加密、存储和安全策略时，基础设施开销会挤占业务算力：

```text
VM/Pod
  → DPU 上的虚拟交换/安全策略
  → DPU 做 VXLAN 封装、加密或路由卸载
  → 物理 NIC → Leaf/Spine Underlay
```

**SmartNIC** 通常是在网卡上增加可编程处理、专用加速器或 ARM 核；**DPU** 更强调拥有自己的 CPU、内存、加速引擎和管理边界，可以独立运行基础设施软件栈。

```text
普通 NIC：把比特送进主机
SmartNIC：网卡上的“副驾驶”，处理特定网络任务
DPU：网卡侧能独立运行基础设施服务的“小型基础设施服务器”
```

典型卸载任务：

| 任务 | 为什么卸载 | 可能效果 |
|------|------------|----------|
| OVS/vSwitch | 每个 VM/Pod 的东西向流量都经过主机 | 释放 CPU，降低虚拟交换开销 |
| VXLAN/Geneve | 封装/解封装和校验消耗 CPU | 提高 Overlay 转发能力 |
| 安全组/ACL | 每个报文都要匹配策略 | 固定规则可由硬件并行处理 |
| IPsec/TLS | 加密消耗 CPU | 降低业务 CPU 的加密负担 |
| 存储/NVMe-oF | 存储协议和数据搬运占用主机 | 主机更专注于应用 |
| 租户隔离 | 宿主机故障可能影响多租户 | 把基础设施边界移到 DPU |

卸载不是免费性能：主机上可能看不到完整转发路径；硬件支持的协议、ACL 规模和状态类型有限；DPU 还需要自己的固件、驱动、控制面和升级体系。主机、DPU、交换机状态同步失败时，可能出现“控制面正常、数据面丢包”。

#### 10.9.10 这些技术组合起来的完整模型

```text
云平台 / Kubernetes / NFV 编排器
  → 创建 VM、Pod、VPC、vFirewall、vNAT、vLB
  → SDN 控制器计算路由、策略、VNI、VTEP 和服务链
  → Underlay：Leaf/Spine + BGP/ECMP
  → Overlay：VXLAN/EVPN
  → 主机数据面：OVS / vSwitch / eBPF
  → 高性能路径：DPDK / VPP / SR-IOV
  → 资源局部性：CPU 绑核 + NUMA
  → 硬件卸载：SmartNIC / DPU
  → VM/Pod / 外部网络 / 存储
```

最终要记住的不是一串缩写，而是每个技术在链路中的位置：**SDN 决定网络状态，NFV 提供可编排的网络功能，VXLAN/EVPN 提供租户承载，DPDK/OVS/VPP/eBPF 执行软件数据面，NUMA 保证处理资源局部性，SmartNIC/DPU 把合适的基础设施工作卸载出去。**

### 10.10 DCI 与跨 IDC 二层延伸的边界

DCI（Data Center Interconnect，数据中心互联）把多个数据中心连接起来。常见诉求包括跨地域容灾、对象复制、服务互访、流量调度、少量遗留系统的二层延伸。

跨 IDC 直接拉大二层要非常谨慎：

| 风险 | 说明 |
|------|------|
| 延迟 | 二层协议、存储协议、集群心跳可能默认低延迟，跨城/跨国 RTT 会放大故障 |
| 广播域 | ARP/未知单播/广播被拉大，故障扩散范围变大 |
| MTU | VXLAN/MPLS/IPsec 等封装会吃掉 MTU，容易出现大包黑洞 |
| 收敛 | 跨域链路抖动会影响 MAC/VTEP/路由表收敛 |
| 一致性 | 数据库/缓存/存储不是网络打通就能跨城强一致 |

推荐思路：

```text
能用 L7/API/消息复制解决，就不要强行拉 L2
能用对象存储复制/异步同步解决，就不要让业务依赖跨城广播域
必须跨 IDC L2 stretch 时，限制范围、监控 MTU/广播/收敛，并准备快速隔离手段
```

应用超时不一定是应用慢：网卡丢包、软中断打满、内核 backlog 溢出、Socket 队列满都可能造成相同现象。

本文关注容器内路由、宿主机路由、Service 转换、跨节点封装和 MTU；CNI、Service、NetworkPolicy、Ingress 的实现细节放在云原生专题。

### 11.3 防火墙与安全边界

```text
云安全组 / ACL
  → 主机 nftables/iptables
  → 容器 NetworkPolicy
  → 代理/WAF
  → 应用鉴权
```

iptables 经典数据路径：

```text
发给本机：PREROUTING → 路由判断 → INPUT → 本地进程
本机发出：本地进程 → OUTPUT → POSTROUTING

```

Filter 负责允许/拒绝，NAT 负责地址转换，二者常依赖 conntrack。nftables 是现代替代方案，但大量系统仍使用 iptables 兼容接口。

### 11.4 调优原则

先用指标证明瓶颈，再改 sysctl，不复制「万能参数」：

| 现象 | 先看 | 可能相关参数 |
|------|------|--------------|
| SYN 丢失/半连接满 | `nstat`、SYN_RECV 数 | `tcp_max_syn_backlog`、`tcp_syncookies` |
| accept 队列溢出 | `ss -lnt`、ListenOverflows | `somaxconn` + 应用 `listen(backlog)` |
| conntrack 满 | `nf_conntrack_count/max` | `nf_conntrack_max`，同时减少无效连接 |
| 高带宽长 RTT 吞吐低 | BDP、Socket buffer、拥塞算法 | `tcp_rmem/wmem`、BBR/CUBIC |
| 网卡入口丢包 | `ip -s link`、软中断 CPU | `netdev_max_backlog`、队列/RPS/RFS |

变更前记录基线，灰度修改，验证吞吐、延迟、丢包和 CPU，再决定是否保留。

## 12. QUIC 与 HTTP/3 深入

### 12.1 QUIC 设计动机

TCP 作为传输层协议服役数十年，在现代网络环境中暴露出三个核心痛点：

| 痛点 | 具体表现 | 影响 |
|------|----------|------|
| **TCP 队头阻塞** | TCP 是单一有序字节流，一个包丢失会阻塞后续所有数据 | HTTP/2 多路复用的收益被 TCP 层队头阻塞抵消 |
| **握手延迟叠加** | TCP 三次握手（1 RTT）+ TLS 1.3 握手（1 RTT）= 至少 2 RTT | 移动网络首次连接体感慢（RTT 常 100ms+） |
| **连接绑定四元组** | TCP 连接 = (src_ip, src_port, dst_ip, dst_port) | Wi-Fi ↔ 4G 切换 IP 变化即断连，需重新握手 |

### 12.2 QUIC 核心特性

#### 0-RTT / 1-RTT 握手

```
首次连接（1-RTT）：
客户端                              服务器
  |  Initial: ClientHello + Key Share  |
  |──────────────────────────────────→ |
  |                                    |
  |  Initial: ServerHello + Handshake  |
  |  + EncryptedExtensions + Cert      |
  |←────────────────────────────────── |
  |                                    |
  |  [此时已可发送加密应用数据]          |

恢复连接（0-RTT）：
客户端                              服务器
  |  Initial + 0-RTT应用数据（PSK）    |
  |──────────────────────────────────→ |
  |  ← 服务器直接处理数据并响应         |
  |                                    |
  省去1个RTT！首包即携带业务数据
```

> **0-RTT 安全注意**：0-RTT 数据不具备前向保密性且可被重放（Replay），应仅用于幂等请求（如 GET）。

#### 多路复用 — 无队头阻塞

```
HTTP/2 over TCP：
流A: [帧1] [帧2] ─────────────────→  TCP字节流
流B: [帧3] [帧4] ─────────────────→  （共享同一条TCP连接）

帧2丢失 → TCP层等待重传 → 帧3、帧4也被阻塞（即使属于不同流）

HTTP/3 over QUIC：
流A: [帧1] [帧2] ── 独立QUIC流 ──→  各流独立排序
流B: [帧3] [帧4] ── 独立QUIC流 ──→

帧2丢失 → 只有流A等待重传 → 流B不受影响，正常交付
```

#### 连接 ID 迁移

```
QUIC连接标识 = Connection ID（而非四元组）

场景：手机从Wi-Fi切换到4G
- IP地址变化：192.168.1.100 → 10.0.0.50
- TCP：连接断开，需重新握手 + TLS协商
- QUIC：Connection ID不变，验证Path后继续传输，用户无感知

实现：客户端在新路径发送PATH_CHALLENGE帧，服务端回PATH_RESPONSE验证后继续通信
```

#### 内置 TLS 1.3

- QUIC **强制**加密，TLS 1.3 是协议不可分割的一部分（而非像 TCP+TLS 那样分层叠加）
- 连接建立和加密协商合并在同一次握手中完成
- 报头也部分加密，中间设备无法篡改传输参数

### 12.3 QUIC vs TCP+TLS 对比

| 维度 | TCP + TLS 1.3 | QUIC |
|------|---------------|------|
| **首次握手延迟** | 2 RTT（TCP 1 + TLS 1） | 1 RTT（合并握手） |
| **恢复连接延迟** | 1-2 RTT | 0 RTT（携带应用数据） |
| **队头阻塞** | 有（TCP 层） | 无（流级独立排序） |
| **连接迁移** | 不支持（四元组绑定） | 支持（Connection ID） |
| **拥塞控制** | 内核实现，升级需改内核 | 用户态实现，可快速迭代 |
| **NAT 穿越** | 成熟 | UDP 可能被限流/阻断 |
| **加密范围** | 载荷加密，头部明文 | 载荷 + 部分头部加密 |
| **中间设备兼容** | 极好（几十年积累） | 部分企业防火墙/ISP 限制 UDP |

### 12.4 HTTP/3 = HTTP 语义 + QUIC 传输

```
协议栈对比：

HTTP/2                          HTTP/3
┌─────────────┐                ┌─────────────┐
│  HTTP/2     │                │  HTTP/3     │
│  (HPACK)    │                │  (QPACK)    │
├─────────────┤                ├─────────────┤
│  TLS 1.2/1.3│                │   QUIC      │
├─────────────┤                │  (内置TLS   │
│   TCP       │                │    1.3)     │
├─────────────┤                ├─────────────┤
│   IP        │                │   UDP / IP  │
└─────────────┘                └─────────────┘
```

**HTTP/3 vs HTTP/2 关键区别**：

| 区别 | HTTP/2 | HTTP/3 |
|------|--------|--------|
| 头部压缩 | HPACK（依赖有序交付） | QPACK（适配无序交付，单向流传编码表） |
| 流控 | HTTP 帧级 + TCP 级双层流控 | QUIC 流级 + 连接级流控 |
| 优先级 | 复杂的依赖树模型（实践中少有实现） | 简化为 Urgency + Incremental 两个参数 |
| 服务器推送 | 支持（但实践中使用极少） | 保留但进一步弱化 |

### 12.5 QUIC 帧结构简图

```
QUIC Packet（UDP载荷）：
┌────────────────────────────────────────────────┐
│ Header                                         │
│  ├─ Header Form (1 bit): Long/Short            │
│  ├─ Connection ID (0-20 bytes)                 │
│  ├─ Packet Number (1-4 bytes, 加密)             │
│  └─ Version (Long Header only)                 │
├────────────────────────────────────────────────┤
│ Encrypted Payload (一个或多个QUIC帧)             │
│  ┌──────────────┐                              │
│  │ STREAM帧      │ → 携带应用数据（Stream ID +  │
│  │               │   Offset + Length + Data）   │
│  ├──────────────┤                              │
│  │ ACK帧         │ → 确认收到的Packet Number范围 │
│  ├──────────────┤                              │
│  │ CRYPTO帧      │ → TLS握手数据               │
│  ├──────────────┤                              │
│  │ 其他帧...     │ → PATH_CHALLENGE/RESPONSE,  │
│  │               │   NEW_CONNECTION_ID,         │
│  │               │   MAX_STREAM_DATA 等         │
│  └──────────────┘                              │
└────────────────────────────────────────────────┘

关键设计：
- Packet Number 单调递增，不复用（区别于TCP seq），简化丢包判断
- 一个UDP包可携带多个QUIC帧，减少头部开销
- STREAM帧携带Stream ID + Offset，实现流级独立排序
```

### 12.6 实际部署现状与注意事项

**部署现状**（截至2025）：
- Google、Meta、Cloudflare 等大厂已大规模部署 HTTP/3
- 主流浏览器（Chrome、Firefox、Safari、Edge）均已支持
- Nginx 1.25+、Caddy、LiteSpeed 等服务器已支持
- 全球约 30% 的 Web 流量使用 HTTP/3

**部署注意事项**：

```bash
# 1. UDP 限流问题
# 很多企业防火墙和ISP默认限制或阻断UDP流量
# 部署前需确认链路上UDP 443端口畅通
# HTTP/3客户端通常会回退：先尝试QUIC，失败后降级到HTTP/2（Alt-Svc机制）

# 2. 中间设备兼容性
# NAT设备对UDP连接的超时通常比TCP短（30s vs 数小时）
# QUIC需要定期发送keep-alive防止NAT映射过期
# 部分DPI设备无法识别QUIC流量，可能误判为异常

# 3. 服务器配置示例（Nginx）
# nginx.conf
server {
    listen 443 quic reuseport;  # QUIC监听
    listen 443 ssl;              # TLS回退
    http3 on;
    ssl_certificate     /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;
    add_header Alt-Svc 'h3=":443"; ma=86400';  # 告知客户端支持HTTP/3
}

# 4. 调试工具
# - Chrome: chrome://net-internals/#quic 查看QUIC连接状态
# - curl 7.66+: curl --http3 https://example.com
# - Wireshark 3.x+: 支持QUIC解析（需导入TLS密钥日志）
# - qlog: QUIC标准化日志格式，配合qvis可视化工具分析
```

## 13. TCP BBR 拥塞控制算法

### 13.1 传统拥塞控制的问题

传统拥塞控制算法（如 CUBIC、Reno）**以丢包作为拥塞信号**，存在根本性缺陷：

```
理想网络模型：
                          ← BtlBw（瓶颈带宽）
发送速率 ──────────────────┬────────────────
                           │
                           │ ← 缓冲区开始填充
                           │
丢包点 ─────────────────── │ ──────── ← 缓冲区溢出才丢包
                           │
                        实际吞吐量

问题：CUBIC等待丢包才降速，但丢包意味着缓冲区已满
      → 缓冲区长期处于满/近满状态（Bufferbloat）
      → RTT被缓冲区排队延迟大幅抬高
      → 高延迟链路（如跨洋、卫星）表现极差
```

**Bufferbloat（缓冲区膨胀）效应**：
- 现代网络设备缓冲区越来越大
- CUBIC 会填满缓冲区才触发丢包 → RTT 从 50ms 飙到 500ms+
- 用户体感：带宽够但延迟高、交互卡顿

### 13.2 BBR 核心理念

BBR（Bottleneck Bandwidth and Round-trip propagation time）由 Google 于 2016 年提出。

**核心思想：不以丢包为信号，而是持续探测两个关键参数**：

```
BtlBw（Bottleneck Bandwidth）：瓶颈链路的最大带宽
  → 通过观测已确认数据量 / ACK间隔 来估算
  → 取最近10个RTT周期内的最大值

RTprop（Round-trip propagation time）：最小往返传播延迟
  → 通过观测最小RTT来估算（排除排队延迟）
  → 取最近10秒内的最小值

最优发送速率 = BtlBw
最优在途数据量（inflight） = BtlBw × RTprop

目标：发送速率刚好等于瓶颈带宽，在途数据量刚好填满管道但不溢出缓冲区
      → 最大吞吐 + 最小延迟（Kleinrock最优工作点）
```

### 13.3 BBR 四个阶段

```
┌─────────────────────────────────────────────────────────┐
│                  BBR 状态机                               │
│                                                         │
│  ① Startup ──→ ② Drain ──→ ③ ProbeBW ←──→ ④ ProbeRTT  │
│  (指数探测带宽)  (排空队列)   (稳态周期探测)   (探测最小RTT) │
└─────────────────────────────────────────────────────────┘
```

**① Startup（启动阶段）**：
- 类似慢启动，以 2/ln2 ≈ 2.89 倍速率指数增长
- 目标：快速发现瓶颈带宽 BtlBw
- 退出条件：连续 3 轮 RTT 带宽增长不超过 25%（说明已找到瓶颈）

**② Drain（排空阶段）**：
- Startup 结束时缓冲区已积压数据（超发了约 BDP 的数据）
- 降低发送速率（pacing_gain < 1），排空多余队列
- 退出条件：在途数据量 ≤ BtlBw × RTprop（即 1 个 BDP）

**③ ProbeBW（带宽探测 — 稳态阶段）**：
- 大部分时间处于此阶段
- 以 8 轮 RTT 为一个周期，周期性地微调发送速率：
  - 1 轮：pacing_gain = 1.25（略微超发，探测是否有更多带宽）
  - 1 轮：pacing_gain = 0.75（回退，排空可能的队列积压）
  - 6 轮：pacing_gain = 1.0（以估算的 BtlBw 稳定发送）

**④ ProbeRTT（RTT 探测阶段）**：
- 每隔约 10 秒触发一次（如果 RTprop 长期未更新）
- 将在途数据量降至 4 个包，持续 200ms
- 目标：排空缓冲区队列，测量真实的最小传播延迟
- 短暂降低吞吐，但确保 RTprop 估算准确

### 13.4 BBR vs CUBIC 对比

| 维度 | CUBIC | BBR |
|------|-------|-----|
| **拥塞信号** | 丢包 | 带宽和RTT |
| **带宽利用率** | 中等（受丢包率影响大） | 高（接近瓶颈带宽） |
| **延迟表现** | 高（填满缓冲区） | 低（主动控制在途数据量） |
| **高丢包环境** | 吞吐急剧下降 | 受影响小（不把丢包当拥塞信号） |
| **公平性** | 与同类算法公平 | BBRv1与CUBIC共存时可能抢占带宽 |
| **适用场景** | 通用、低丢包链路 | 高延迟/高丢包/跨地域链路 |
| **实现位置** | 内核 | 内核（但设计上易于用户态实现） |

### 13.5 实际效果

Google 于 2016 年在其全球骨干网部署 BBR 后的效果：

```
YouTube 实测数据（Google 2016 公开数据）：
- 全球平均吞吐提升 4%，部分地区提升 14%+
- 全球平均 RTT 降低 33%，部分地区降低 50%+
- 重缓冲率（播放卡顿）降低显著

原因分析：
- YouTube 大量用户在发展中国家（高延迟/高丢包网络）
- CUBIC 在这些网络上因频繁丢包而严重降速
- BBR 不受丢包率影响，持续以瓶颈带宽发送
```

### 13.6 Linux 开启 BBR

```bash
# 1. 检查内核版本（需要 4.9+）
uname -r

# 2. 加载 BBR 模块
modprobe tcp_bbr

# 3. 设置 BBR 为默认拥塞控制算法
sysctl -w net.ipv4.tcp_congestion_control=bbr

# 4. 验证
sysctl net.ipv4.tcp_congestion_control
# 输出：net.ipv4.tcp_congestion_control = bbr

# 5. 确认 BBR 已加载
lsmod | grep bbr
# 输出：tcp_bbr  ...

# 6. 永久生效（写入配置文件）
cat >> /etc/sysctl.conf << 'EOF'
net.core.default_qdisc = fq
net.ipv4.tcp_congestion_control = bbr
EOF
sysctl -p

# 注意：BBR 推荐搭配 fq（Fair Queuing）队列调度器
# fq 提供精确的 pacing（包间距控制），是 BBR 发挥最佳效果的前提
```

### 13.7 BBR 的争议与演进

**公平性争议（BBRv1）**：

```
BBRv1 与 CUBIC 共存时的不公平问题：

场景：10Mbps瓶颈链路，1个BBR流 + 1个CUBIC流共享
- 理论公平：各占5Mbps
- 实测：BBR占约7-8Mbps，CUBIC只剩2-3Mbps

原因：
- BBR不以丢包为信号，持续高速发送
- CUBIC检测到丢包后主动降速
- BBR的"不怕丢包"变成了对CUBIC的带宽侵占

多条BBR流共存时公平性尚可，但与基于丢包的算法共存时存在挤占问题
```

**BBRv2 改进（2019年开始开发，持续迭代中）**：

```
BBRv2 核心改进：
1. 引入丢包和ECN作为辅助信号（不再完全忽略丢包）
   - 显式拥塞通知（ECN）比丢包更早、更精确
2. 更保守的Startup阶段（减少初始超发）
3. 改进与CUBIC的公平共存
4. 更精确的带宽探测（减少ProbeRTT的吞吐波动）

BBRv3（实验中）：
- 进一步优化公平性和收敛速度
- 更好的ECN支持
- Google内部持续测试迭代

当前建议：
- 生产环境优先使用 BBRv1（稳定、内核原生支持）
- 关注 BBRv2/v3 的合入进度
- 如果链路上BBR和CUBIC流混合，需评估公平性影响
```

## 14. 网络排障实战

### 14.1 分层排障 SOP

先定义现象、范围和时间，再按层验证，避免一上来抓包或重启：

```text
0. 范围：单用户/单机房/单版本/全局？何时开始？是否刚变更？
1. 本机：进程是否存活、端口是否监听、资源是否饱和？
2. DNS：解析到什么 IP？不同递归 DNS 是否一致？
3. 路由/L2：源地址、网关、路由、ARP/NDP 是否正确？
4. TCP/UDP：SYN 能否往返？是否重传、RST、队列满、conntrack 满？
5. TLS：证书、SNI、协议版本、时间、mTLS 是否正确？
6. HTTP/RPC：状态码来自哪一层？上游是否超时/限流/无健康实例？
7. 应用：处理时间、依赖调用、连接池、线程池、GC、数据库。
```

坚持端到端证据链：客户端日志 + 入口层指标 + 服务端日志 + 必要时双端抓包。单端看到「重传」不一定代表本端丢包，也可能是对端或中间链路未收到。

### 14.2 常用命令按问题分类

```bash
# 地址、邻居、路由
ip addr
ip neigh
ip route
ip route get 203.0.113.10

# 连通和路径
ping -c 4 203.0.113.10
mtr -rwzc 20 203.0.113.10

# DNS
dig api.example.com
dig @8.8.8.8 api.example.com
dig +trace api.example.com

# 端口和 Socket
ss -lntp
ss -ant state syn-recv
ss -ant state time-wait
ss -ant state close-wait
ss -tin dst 203.0.113.10

# 应用层快速验证
curl -v --connect-timeout 3 https://api.example.com/health
curl --resolve api.example.com:443:203.0.113.10 https://api.example.com/health
openssl s_client -connect api.example.com:443 -servername api.example.com

# 内核统计
nstat
sar -n DEV,TCP,ETCP 1
ip -s link
```

`ping` 不通不等于业务一定不通（ICMP 可能被禁）；`ping` 通也不等于 TCP 端口/TLS/HTTP 正常。每个工具只证明一层。

### 14.3 tcpdump 抓包配方与判断

```bash
# 指定主机和端口，显示时间、序列号与 payload
sudo tcpdump -i any -nn -tttt -S host 203.0.113.10 and port 443

# 只看 TCP 建连/断连标志
sudo tcpdump -i any -nn 'tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0'

# 保存给 Wireshark
sudo tcpdump -i any -nn -s 0 -w incident.pcap host 203.0.113.10

# DNS
sudo tcpdump -i any -nn port 53
```

| 抓包现象 | 常见方向 |
|----------|----------|
| SYN 连续重发，无 SYN-ACK | 服务未监听、防火墙、路由或回包路径问题 |
| 收到 SYN-ACK，客户端不回 ACK | 客户端/中间设备丢包，或抓包点不完整 |
| 握手后立即 RST | 应用主动拒绝、端口复用/协议不匹配、代理重置 |
| Dup ACK + 重传 | 丢包或乱序；需双端抓包判断丢在哪 |
| TCP 往返正常但响应间隔很长 | 更像应用/上游处理慢，不要继续只调网络 |
| TLS Alert | 证书、协议、密码套件、SNI、mTLS 问题 |

TLS 1.3 大部分握手和应用数据是密文；需客户端导出 `SSLKEYLOGFILE` 并导入 Wireshark 才能查看明文（生产环境注意密钥安全）。

### 14.4 高频故障案例

**能连 IP，域名不通**：

1. `dig` 比较本地、公共、权威结果。
2. 查 `/etc/hosts`、缓存、Split DNS、GSLB 策略。
3. 用 `curl --resolve` 固定域名和 IP，保留正确 Host/SNI，隔离 DNS 问题。

**端口偶发超时**：

1. 查入口/服务端是否丢 SYN、accept 队列溢出、conntrack 满。
2. 查客户端临时端口、连接池和 TIME_WAIT。
3. 双端抓包判断是请求没到、响应没回还是应用迟迟没响应。

**小请求正常，大响应/上传超时**：

1. 怀疑 MTU/PMTUD 黑洞。
2. `ping -M do -s ...` 逐步测试；检查 VPN/VXLAN/容器 MTU。
3. 检查中间设备是否丢 ICMP Fragmentation Needed。

**502/503/504**：

```text
502 → 上游连接/协议响应异常
503 → 无可用实例、过载、主动拒绝/熔断
504 → 网关等上游超时
```

先确认状态码由 CDN、LB、网关还是应用生成，再查对应层的上游地址、健康检查、超时和连接池。

## 16. 面试题自查

### 网络排障补充

- 网络题不应只背协议定义，必须能落到故障定位路径：现象分层、抓包验证、指标交叉。
- 排障时建议固定顺序：DNS -> 连接建立 -> 传输质量 -> 应用协议语义，避免盲目抓日志。
- 线上高频问题通常不是“连不上”，而是“偶发慢、偶发丢、偶发重试风暴”。

### 初级高频速刷

**1. OSI 七层模型和 TCP/IP 四层模型怎么对应？**

OSI 七层更细，TCP/IP 四层更贴近实际网络实现。大致可以理解为：OSI 的应用层/表示层/会话层合并成 TCP/IP 的应用层，传输层对应传输层，网络层对应网络层，数据链路层和物理层合并成链路层。

**2. `GET` 和 `POST` 的区别是什么？**

`GET` 语义上用于获取资源，天然适合幂等查询；`POST` 语义上用于提交数据并触发服务端处理。真正的区别首先是语义和缓存/幂等约定，而不是“一个能传参一个不能传参”这种过时回答。

**3. `301`、`302`、`307`、`308` 分别表示什么？**

`301` 永久重定向，`302` 临时重定向，历史上很多客户端会把 `302` 改成 GET；`307` 临时重定向但要求保持原请求方法；`308` 永久重定向且保持原请求方法。这个问题常用来筛掉只会背“301永久302临时”的回答。

**4. Cookie、Session、Token 的区别是什么？**

Cookie 是浏览器存储载体，Session 是服务端保存的会话状态，Token 是认证凭证。它们不是互斥关系，常见组合是 Cookie 里带 SessionID，或者前端持有 JWT Token 访问后端。

**5. 常见 HTTP 状态码 `200/301/302/400/401/403/404/500/502/503` 分别表示什么？**

`200` 成功，`301/302` 重定向，`400` 请求参数错误，`401` 未认证，`403` 禁止访问，`404` 资源不存在，`500` 服务端内部错误，`502` 网关拿到上游无效响应，`503` 服务暂时不可用。真正面试时，经常会接着追问 `502` 和 `503` 的排障差异。

**6. `TCP` 和 `UDP` 的核心差异是什么？**

`TCP` 提供连接、可靠传输、拥塞控制和流量控制；`UDP` 无连接、尽力而为、开销小。真正选型要看业务目标，是要可靠有序，还是要更低时延和更高实时性。

### 中级高频进阶

**7. HTTP Keep-Alive、TCP keepalive、应用层心跳有什么区别？**

HTTP Keep-Alive 解决的是“连接复用”；TCP keepalive 解决的是“内核层面判断长连接是否失活”；应用层心跳解决的是“业务协议自己定义健康探测和超时控制”。三者名字相近，但解决的问题并不在同一层。

**8. 为什么很多 RPC 框架会选择 HTTP/2 或 gRPC？**

因为 HTTP/2 支持多路复用、头部压缩、服务端推送和更适合长连接的传输模型，能减少连接数和队头阻塞问题。gRPC 再叠加 Protobuf 的强约束和高效序列化，非常适合服务间通信。

**9. `401` 和 `403` 在语义上到底怎么区分？**

`401` 是“你还没完成合法认证”，`403` 是“你是谁我知道，但你没有权限做这件事”。这个区分看似细节，实际在网关、鉴权中间件和安全审计里都很重要。

**10. `502`、`503`、`504` 在网关侧分别说明什么？**

`502` 更偏上游返回了无效响应，`503` 更偏服务当前不可用或被限流，`504` 更偏网关等待上游超时。把这三者区分清楚，排障入口会快很多。

**11. 浏览器访问一个 HTTPS URL，从点下到看到结果，中间大致经过哪些阶段？**

按层说：DNS 解析得到入口 IP → 本机路由/ARP 找到网关 → 出口 NAT 改写源地址 → 公网转发到 CDN/LB/网关 → TCP 三次握手 → TLS 握手（证书校验、密钥协商）→ 发送 HTTP 请求 → 网关路由到业务 → 响应沿原路径返回（NAT 还原、TLS 解密）。细节见深入问答 Q27 与 §1.3。

### 深入问答

#### Q1: TCP三次握手每一步的作用是什么？为什么不能两次或四次？

**答**：第一次SYN让服务端确认客户端发送能力正常；第二次SYN-ACK让客户端确认服务端收发能力正常；第三次ACK让服务端确认客户端接收能力正常。两次不够是因为服务端无法确认客户端能收到自己的SYN-ACK（即无法确认客户端的接收能力和自己的发送能力），四次多余是因为第二步SYN和ACK可以合并。核心目的是双方互相确认对方的seq序列号。

#### Q2: SYN Flood攻击原理是什么？syncookie如何防御？

**答**：攻击者大量发送SYN但不回ACK，耗尽服务端半连接队列。syncookie的防御原理是服务端不保存SYN状态，而是将四元组+时间戳做hash生成cookie放入SYN-ACK的seq字段，客户端ACK带回cookie（seq+1），服务端验证通过后直接建立连接，将内存攻击转化为CPU运算。

#### Q3: TIME_WAIT状态为什么是2MSL？TIME_WAIT过多怎么解决？

**答**：2MSL = 1MSL（对方重传FIN的最大延迟）+ 1MSL（我方ACK的最大延迟），确保①最后的ACK能到达对方（否则对方会重传FIN）②旧连接的所有游荡报文消失，不干扰新连接。解决TIME_WAIT过多：启用`tcp_tw_reuse`复用端口（安全，依赖timestamp比较）、使用连接池（最佳方案）、增大端口范围、使用HTTP Keep-Alive减少短连接。

#### Q4: CLOSE_WAIT大量积压说明什么问题？如何排查？

**答**：CLOSE_WAIT说明对端已经关闭连接（发了FIN），但本端应用程序没有调用close()。这是**应用层BUG**，没有内核超时机制保护，必须修复代码。排查：`ss -tapn | grep CLOSE-WAIT`找到对应进程，检查代码中是否有未关闭的连接（如忘记defer conn.Close()、异常分支没有关闭等）。

#### Q5: TCP滑动窗口的作用是什么？发送窗口大小由什么决定？

**答**：滑动窗口允许发送方在不等每个ACK的情况下连续发送多个数据段，实现流水线传输，提高带宽利用率。发送窗口大小 = min(cwnd, rwnd)，受拥塞控制（cwnd拥塞窗口，反映网络能力）和流量控制（rwnd接收窗口，反映接收方缓冲区剩余空间）的双重约束。

#### Q6: 零窗口探测是什么？解决了什么问题？

**答**：当接收方缓冲区满时通告rwnd=0，发送方停止发送。如果后续接收方窗口更新ACK丢失，双方会死锁。零窗口探测（ZWP）解决此问题：发送方启动持续定时器，定期发送1字节探测报文，接收方回复当前rwnd。探测间隔指数退避，超过tcp_retries2次后RST关闭连接。

#### Q7: 流量控制和拥塞控制的区别是什么？

**答**：流量控制防止发送方淹没**接收方**，通过接收方通告rwnd实现，反映接收方缓冲区状态；拥塞控制防止发送方淹没**网络**，通过发送方维护的cwnd实现，根据丢包等网络反馈动态调整。两者协作：实际发送窗口 = min(cwnd, rwnd)。

#### Q8: TCP慢启动为什么是指数增长？到达ssthresh后为什么改为线性增长？

**答**：慢启动阶段指数增长（每RTT cwnd翻倍）是为了快速探测网络可用带宽，避免线性增长时长时间低效传输。到达ssthresh后转为拥塞避免的线性增长（每RTT cwnd+1），因为此时已接近网络容量上限，继续翻倍可能立即引发拥塞，线性增长可以谨慎逼近实际容量。

#### Q9: 快速重传和快速恢复相比传统Tahoe算法有什么改进？

**答**：传统Tahoe收到丢包信号后cwnd=1重新慢启动，过于保守。快速重传：收到3个重复ACK立即重传，不等超时（超时通常1秒）。快速恢复（Reno）：丢包后ssthresh=cwnd/2，cwnd=ssthresh直接进入拥塞避免，跳过慢启动。理由是收到3个重复ACK说明网络仍有传输能力（后续包能到达），没必要重置到cwnd=1。

#### Q10: CUBIC和BBR拥塞控制算法各有什么特点？如何选择？

**答**：CUBIC（Linux默认）：窗口增长函数为三次函数，适合高带宽网络，对丢包敏感。BBR（Google）：不基于丢包而是持续测量带宽和RTT，目标是最大化带宽利用率、最小化延迟。选择：高带宽低延迟选BBR，高丢包率网络CUBIC更稳定，数据中心内部用DCTCP。修改：`sysctl -w net.ipv4.tcp_congestion_control=bbr`。

#### Q11: Nagle算法和延迟ACK叠加会导致什么问题？如何解决？

**答**：Nagle算法让发送方在有未确认数据时积累小包；延迟ACK让接收方等200ms才回ACK。两者叠加：发送方发了小包等ACK（Nagle），接收方等200ms才回（延迟ACK），导致每个小包有200ms额外延迟。解决：设置TCP_NODELAY关闭Nagle算法，适用于游戏、SSH等实时交互场景。

#### Q12: HTTP强缓存和协商缓存的区别是什么？各自的判断字段是什么？

**答**：强缓存直接从本地读取不发请求（200 from cache），由Cache-Control（max-age/no-cache/no-store）和Expires控制，优先级Cache-Control > Expires。协商缓存需要向服务器验证资源是否变化（304 Not Modified），由ETag/If-None-Match和Last-Modified/If-Modified-Since控制，优先级ETag > Last-Modified。ETag基于内容hash更精确，Last-Modified精度只到秒。

#### Q13: HTTP/1.1、HTTP/2、HTTP/3的核心区别是什么？

**答**：HTTP/1.1基于TCP，队头阻塞严重（请求串行或有限并行）。HTTP/2仍基于TCP，引入多路复用（单连接多流）、头部压缩（HPACK）、服务端推送，但TCP层仍有队头阻塞。HTTP/3基于QUIC（UDP），彻底解决队头阻塞（丢包只影响单个流），支持0-RTT握手和连接迁移（网络切换IP变化不断连）。

#### Q14: HTTPS的TLS握手过程是怎样的？TLS 1.3相比1.2有何改进？

**答**：HTTPS = HTTP over TLS。TLS 1.2 完整握手通常 2-RTT：先 Hello/证书，ECDHE 还要等服务端 `ServerKeyExchange` 后客户端才发 `ClientKeyExchange`，再 Finished，之后才能发应用数据（旧 RSA 密钥传输更必须先拿证书）。TLS 1.3 允许 `ClientHello` 直接带 `key_share`（临时公钥，可明文），服务端一趟回复自己的 `key_share` + 证书与 Finished，约 1-RTT 即可加密传 HTTP；ServerHello 之后多数握手消息已加密。注意：1-RTT **不是**因为「解决了提前传密钥的风险」——风险更大的是 **0-RTT Early Data 重放**；`key_share` 与 Early Data 不是一回事。曲线猜错会 `HelloRetryRequest`，可能多一趟。相对 1.2：少一趟 RTT、砍掉不安全套件并强制前向保密、支持 PSK/0-RTT 恢复。详见 §6.3 / §6.4。

#### Q15: WebSocket和HTTP长轮询有什么区别？WebSocket如何保活？

**答**：HTTP长轮询：客户端发请求，服务器hold住直到有数据或超时返回，半双工。WebSocket：通过HTTP Upgrade握手后建立全双工连接，双方可随时推送，头部开销小（2-10字节 vs HTTP几百字节）。保活：通过Ping/Pong帧实现心跳，发送方定时（如30s）发Ping，接收方自动回Pong，超时未收到则判定断连。

#### Q16: DNS解析的完整流程是什么？如何优化DNS性能？

**答**：浏览器缓存 → 系统hosts缓存 → 本地DNS服务器（递归查询）→ 根DNS → 顶级域DNS(.com) → 权威DNS → 返回IP。优化：①DNS预解析（`<link rel="dns-prefetch">`）②合理设置TTL③使用本地DNS缓存④减少DNS查找次数（合并域名）⑤使用HTTPDNS绕过运营商DNS劫持。

#### Q17: BDP（带宽延时积）是什么？为什么高延时网络需要调整Socket缓存？

**答**：BDP = 带宽 × RTT，表示网络"管道"中同时在传的数据量。TCP发送窗口受rwnd限制，rwnd由接收方缓冲区剩余空间决定。如果Socket缓存 < BDP，发送方会因缓冲区满而暂停发送，导致带宽利用率低。例如1Gbps+400ms RTT，BDP=50MB，默认16KB缓存只能利用~10%带宽，需要**同时**调大收发两端缓存。

#### Q18: TCP粘包/拆包问题的原因是什么？有哪些解决方案？

**答**：TCP是字节流协议无消息边界，加上Nagle算法合并小包、MSS拆分大包，接收方无法区分消息边界。解决方案：①固定长度（每个消息固定N字节，简单但浪费）②分隔符（如\n分隔，需要转义）③**长度前缀**（推荐，消息头4字节表示消息体长度，解码时先读长度再读对应字节数）。

#### Q19: 为什么tcp_tw_reuse安全而tcp_tw_recycle不安全（已被移除）？

**答**：`tcp_tw_reuse`只复用客户端出站连接的TIME_WAIT端口，且检查新连接的TCP timestamp > 旧连接timestamp才允许复用，安全。`tcp_tw_recycle`快速回收TIME_WAIT（不等2MSL），在NAT环境下有致命问题：NAT后多个客户端共享公网IP但timestamp各异，服务器可能因为timestamp回退而拒绝合法连接。已在Linux 4.12+移除。

#### Q20: 如果你是一个后端开发，如何排查线上服务大量TIME_WAIT/CLOSE_WAIT？

**答**：**TIME_WAIT过多**：`ss -s | grep TIME-WAIT`查看数量 → `ss -tapn | grep TIME-WAIT`定位进程 → 常见原因：短连接频繁（改用Keep-Alive/连接池）、客户端主动关闭过多（让服务器主动关闭）、健康检查过频 → 临时缓解：`tcp_tw_reuse=1`、增大端口范围。**CLOSE_WAIT过多**：一定是应用代码BUG（没有close连接），查找对应进程的代码，检查异常路径和资源释放。

#### Q21: 四层负载均衡（L4）和七层负载均衡（L7）如何取舍？

**答**：L4 基于 IP/端口转发，性能高、开销小，但对业务语义感知弱；L7 能按 Host/Path/Header/Cookie 路由，支持灰度、鉴权、重写和可观测，但引入更多处理开销和治理复杂度。实践里通常是边缘入口用 L7 做策略治理，内部高吞吐链路保留 L4 以控制时延。

#### Q22: RTT、吞吐、P99 延迟三者是什么关系？为什么“带宽够大”不代表请求快？

**答**：RTT 决定单次往返成本，吞吐决定单位时间可传输总量，P99 体现尾部请求体验。带宽高只能说明“管道宽”，如果 RTT 高、重传多、排队长，P99 依然会很差。面试回答建议强调：容量问题和时延问题是两条不同维度，不能只看带宽。

#### Q23: 线上偶发超时时，如何用抓包快速判断是重传、乱序还是应用处理慢？

**答**：先按时间窗口抓双端包：
1. 看是否出现大量 `Dup ACK`、`Retransmission`，判断是否链路丢包或拥塞。
2. 看请求到达时间和响应发出时间差，区分网络慢还是应用处理慢。
3. 对比客户端与服务端时间线，确认慢点在客户端发送前、网络传输中还是服务端处理阶段。

抓包只是证据源，最终要和应用日志、网关指标、内核网络统计一起交叉验证。

#### Q24: DNS 成为性能瓶颈时，常见治理手段有哪些？

**答**：常见做法有四类：
1. 缓存治理：合理 TTL、本地缓存、连接池复用避免频繁解析。
2. 拓扑治理：就近解析、权威 DNS 高可用、避免单解析链路。
3. 容灾治理：多解析服务商、超时回退策略、熔断异常解析结果。
4. 观测治理：监控解析成功率、延迟分位、NXDOMAIN 比例和上游错误码。

如果只做“加缓存”不做可观测，问题会从高延迟变成“缓存错误放大”。

#### Q25: HTTP/3(QUIC) 在什么场景下明显优于 HTTP/2，什么场景收益不明显？

**答**：
明显收益场景：高丢包、弱网、移动网络切换频繁（IP 变化）的场景。QUIC 在单连接多流下避免 TCP 队头阻塞，且支持连接迁移，能显著改善尾延迟和重连成本。

收益不明显场景：低丢包、低 RTT、同机房或高质量内网链路下，HTTP/2 已经足够稳定，HTTP/3 的收益可能主要体现在边缘场景而非核心链路。

评估应以真实链路分层指标为准，不要只看理论协议优势。

#### Q26: 抓包看到重传不多，但 P99 还是高，下一步你查应用还是内核？为什么？

**答**：
先查**应用侧等待链路**，再下探内核。因为“重传不多”只说明显性丢包不是主因，但高 P99 更常见于应用排队、锁竞争、下游慢调用、连接池等待。

建议顺序：
1. 应用侧：线程池队列、连接池等待、慢接口分布、依赖超时。
2. 内核侧：run queue、软中断、socket backlog、磁盘/网络队列。

这样能先定位最可能的瓶颈层，再决定是否深入内核调优。

#### Q27: 从客户端发起一个 HTTPS 请求，到服务端返回响应，完整过程是怎样的？（越详细越好）

**答**：以访问 `https://api.example.com/users` 为例。答题要按**时间顺序 + 协议层次**讲，并点明「解析到的 IP 往往是入口，不是最终 Pod」。

**0）应用意图**

客户端构造逻辑请求：`GET /users`、`Host: api.example.com`、鉴权 Header 等。因是 HTTPS，**不能立刻发 HTTP**，必须先完成：DNS → TCP → TLS。

**1）DNS：域名 → IP**

- 查浏览器缓存 / OS 缓存 / `hosts`
- 未命中则问递归 DNS（运营商/企业/公共 DNS）
- 递归 DNS 必要时迭代查询：根 → TLD（`.com`）→ 权威 DNS
- 得到 `A/AAAA`，如 `203.0.113.10`（常为 CDN/GSLB/Anycast 入口）
- 注意：这是**入口地址**，后面还有 LB、网关、业务实例

**2）本机选路与二层封装**

- 判断目的 IP 是否同网段；跨网段则查路由表，走默认网关
- 用 ARP/NDP 解析**下一跳**（网关）MAC
- 分配临时源端口（如 `52341`），形成四元组
  `(srcIP, srcPort, dstIP, dstPort) = (10.0.0.8, 52341, 203.0.113.10, 443)`
- 封装：应用数据（稍后才是 HTTP）会走 TCP → IP → Ethernet；此时先发握手报文

关键点：**目的 IP 仍是最终入口 IP；MAC 只表示这一跳交给谁**。

**3）出口 NAT / 防火墙**

- SNAT：`10.0.0.8:52341` → `198.51.100.8:40001`
- conntrack 记录映射，供回程还原
- 有状态防火墙通常放行该出站连接及其回包

**4）公网转发**

- 路由器按最长前缀匹配转发，每跳 TTL--、更换链路层封装
- 若入口为 Anycast，BGP 将流量导向路由上最近的 POP
- 到达 CDN/云 LB/机房入口 `203.0.113.10:443`

**5）入口链路（服务端侧常见分层）**

```text
CDN/WAF → L4 LB（可透传/代理 TCP）→ L7 Gateway（拿到 TCP 字节流后终止 TLS，随后按 Host/Path 路由）
       → 业务进程（如 10.20.0.15:8080）
```

- CDN：静态可直接命中返回；动态 API 多半回源
- L4：基于 IP/端口/连接，不解析 HTTP；可做四层转发，也可作为 TCP 代理重新连后端
- L7：不是在 TCP 之前工作；它拿到 TCP 字节流后完成 TLS，之后才能解析 HTTP `Host`、路径、Header，写 `X-Forwarded-For`/`Forwarded` 并转发上游

**6）TCP 三次握手**

```text
SYN(seq=x) → SYN-ACK(seq=y, ack=x+1) → ACK(ack=y+1) → ESTABLISHED
```

协商 MSS、窗口等选项。NAT 回包按映射还原。此时**管道通了，但未加密，也未发业务请求**。

**7）TLS 握手（以 TLS 1.3 为例）**

```text
ClientHello：supported_versions、cipher_suites、SNI=api.example.com、
             key_share、ALPN(h2/http/1.1)…
ServerHello：选定版本/套件、服务端 key_share；
             随后加密发送 Certificate、CertificateVerify、Finished
客户端：校验证书链、SAN 是否匹配域名、有效期、吊销状态；
        验证 CertificateVerify（证明对方持有证书私钥）
双方：由 ECDHE 等导出握手密钥与应用流量密钥（AEAD）
客户端 Finished → 可开始加密应用数据（约 1-RTT）
```

- TLS 1.2 通常还需额外密钥交换飞行，约 2-RTT
- 若网关终止 TLS，证书校验发生在客户端↔网关；网关到业务可能是明文或 mTLS

**8）发送 HTTP 并处理**

- TLS Record 内发送 HTTP/1.1 文本，或 HTTP/2 HEADERS/DATA 帧（取决于 ALPN）
- 网关路由到用户服务；业务鉴权、查库/缓存、生成响应体
- 响应经网关/LB/CDN 返回

链路上始终是：`HTTP → TLS Record → TCP → IP → 帧`；HTTPS 只是让 HTTP 位于密文中。

**9）回程与收尾**

- 公网回包 → 出口 NAT 把 `40001` 还原为 `10.0.0.8:52341`
- 客户端 TCP 重组、TLS 解密、应用渲染
- 短连接则 FIN 挥手（主动方常进 TIME_WAIT）；Keep-Alive/HTTP/2 则复用连接

**面试加分点**

1. 明确顺序：DNS → 路由/ARP → NAT → 到达入口组件 → TCP → TLS → HTTP（L7 路由发生在 TLS/HTTP 可解析之后）
2. 区分「入口 IP」与「最终业务实例」
3. 区分 TCP ESTABLISHED 与 TLS 完成、HTTP 发出
4. 能说出 SNI、证书链、ALPN、SNAT/conntrack、L4/L7 差异
5. 能对应排障：解析错 / SYN 丢 / 证书错 / 502·504 分别卡在哪一层

完整展开与示意图见正文 §1.3。

#### Q28: DNS 配置改了之后，客户端是不是只能等缓存过期？还能做什么？

**答**：对全网用户基本只能等；对单机/自有链路可以做局部加速，但改变不了「别人家递归 DNS 还握着旧 TTL」这件事。

分层看缓存：

```text
浏览器缓存 → OS 缓存 → 递归 DNS（运营商/公司/公共）→ 权威 DNS
```

权威侧一改，只保证「新查询权威的人」能拿到新值；中间每一层都可能继续返回旧 IP，直到各自 TTL 到期。运营商还可能钳制 TTL，所以实际等待时间不一定等于你配的 TTL。

客户端 / 排障侧常见动作：

1. 清浏览器 DNS 缓存，或重开浏览器。
2. 清 OS DNS 缓存（如 macOS `dscacheutil -flushcache`、Windows `ipconfig /flushdns`、Linux `resolvectl flush-caches`）。
3. 临时改用公共 DNS，看是否已返回新值；用 `dig @权威NS` / `dig +trace` 确认权威是否已切。
4. 本机临时写 `hosts`（仅调试，别当长期方案）。
5. 若是 App，走 HTTPDNS 时可主动缩短/失效应用缓存。

做不到的事：

- 无法一键清空全球 ISP 递归 DNS。
- 清了本机缓存，也不等于运营商递归已更新。

生产迁移应靠预案，不靠用户手动 flush：

1. 提前把 TTL 降到 60～300 秒并等旧 TTL 过期。
2. 切换时新旧入口并行服务，覆盖「还拿旧 IP 的用户」。
3. 观察流量/错误率后再把 TTL 调回。
4. 企业内网可额外清自建递归；公网用户仍看 TTL。

详见 §8.3。

#### Q29: RTMP 现在还常用吗？直播为什么大量使用 UDP 系协议？

**答**：RTMP 仍常用于推流兼容，但不再是视频传输的全部。现代链路通常是：主播端 RTMP/SRT 推流 → 源站转码切片 → 观众端 HLS/DASH/LL-HLS/HTTP/3 拉流；超低延迟互动用 WebRTC。

TCP/RTMP 的问题是有序字节流会产生队头阻塞：一个包丢了，后续数据即使到了也要等重传。视频有时效性，迟到的帧可能已经没价值。UDP 系协议可在应用层做 FEC、选择性重传、码率自适应和抖动缓冲，宁可跳过非关键帧，也要保证低延迟和连续播放。

注意：大规模直播播放不一定全走 UDP。HLS/DASH 仍大量基于 HTTP/TCP，因为切片适合 CDN 缓存和海量并发；HTTP/3 则是把 HTTP 分发跑在 QUIC/UDP 上。

#### Q30: 体育直播卡顿时，怎么判断是用户侧、CDN 侧还是源站侧？

**答**：先看影响范围，再看链路阶段。

```text
信号源/推流 → 源站/转码/切片 → CDN 中心层/边缘节点 → 运营商/最后一公里 → 播放器
```

- 只有单个用户卡：优先查 Wi-Fi/移动网络、设备解码、播放器缓冲和本地 DNS 调度。
- 同地区/同运营商大量用户卡：优先查 CDN 边缘节点带宽、节点调度、运营商互联和丢包。
- 全国大面积同时卡：优先查信号源、推流、转码、源站、CDN 中心层或回源链路。
- 开赛/进球瞬间卡：常见是热点流量、边缘节点打满、缓存未命中、回源风暴。

CDN 在大型直播中通常是必须的：源站无法承受千万观众直连。直播 CDN 通过树状分发、切片缓存、动态调度、防回源风暴、多 CDN 和 P2P-CDN 分摊压力。真正难的是在低延迟和抗抖动之间取平衡。

#### Q31: CDN 和边缘计算有什么区别？公网 CDN 能解决内网跨 IDC 同步吗？

**答**：CDN 解决「内容放近」，边缘计算解决「计算放近」。CDN 擅长缓存图片、视频切片、安装包；边缘计算可在边缘做鉴权、防盗链、A/B、广告决策、轻量转码、AI 推理等。

公网商业 CDN 不适合直接拿来解决内网跨 IDC 同步。因为它默认工作在公网：内网资源要上传到第三方公网边缘，另一个 IDC 再从公网拉回来，安全边界、合规、防火墙、回源路径都很别扭。

正确方向：公网用户访问静态内容用商业 CDN；内网跨 DC 大文件/图片同步用对象存储跨区域复制、专线同步、消息队列异步复制，或自建内网 CDN（Nginx/Varnish/对象存储网关 + 内网 DNS/GSLB）。

#### Q32: Bond、LACP、堆叠、M-LAG 分别解决什么问题？

**答**：Bond 是服务器侧多网卡绑定，LACP/Port-Channel/Eth-Trunk 是交换机侧链路聚合，解决链路冗余和多流带宽聚合。单条 TCP 流通常不会因为两块 10G 网卡就跑到 20G，因为 LACP 多按五元组 hash，同一流固定走一条成员链路。

堆叠是多台交换机逻辑合成一台，管理简单、可跨设备聚合、减少 STP 阻塞，但控制面强耦合，堆叠分裂/主控 bug/升级失败可能影响整组。M-LAG 是两台交换机控制面独立、数据面协同，对服务器看起来像同一台 LACP 伙伴，故障域更小，适合现代 IDC 双上联。

#### Q33: 传统大二层、STP、TRILL/RBridge 和现代 L3 Spine-Leaf 的关系是什么？

**答**：传统大二层靠 VLAN 扩展广播域，STP 通过阻塞冗余链路避免环路，代价是链路浪费和故障域大。TRILL/RBridge 是过渡方案：保留二层语义，用 IS-IS 计算 RBridge 之间的最短路径，并用 Hop Count 防环，让二层 Fabric 也能多路径转发。

现代主流云数据中心进一步解耦：物理 Underlay 做纯 L3 Spine-Leaf，跑 BGP/OSPF/IS-IS + ECMP；业务需要的二层/三层租户网络由 VXLAN/EVPN Overlay 提供。TRILL 不是错误方案，而是 STP 到 VXLAN/EVPN 之间的重要演进路线。

#### Q34: Spine-Leaf、Underlay/Overlay、VXLAN、VTEP 和 EVPN 是什么关系？

**答**：Spine-Leaf 是物理拓扑；Underlay 是真实三层 IP 网络；Overlay 是在其上虚拟出来的租户网络；VXLAN 是数据面封装；VTEP 是封装/解封装端点；EVPN-BGP 是常见 Overlay 控制面。

```text
Underlay：Leaf/Spine 三层 IP 网络，跑 BGP/OSPF + ECMP
VXLAN   ：把原始二层帧封进 UDP/IP，外层目的 IP 是目标 VTEP
VTEP    ：硬件 Leaf 或宿主机软件数据面，负责封装/解封装
EVPN    ：发布 MAC/IP/VNI/VTEP 映射，减少泛洪
```

VXLAN 使用 UDP 4789 作为封装载体，但 Underlay 仍主要按外层 IP 做三层路由，不是说 Underlay 变成了 L4。中间 Spine 只关心 VTEP A 到 VTEP B 的外层 IP 包；VM 的真实地址和租户 VNI 由边缘 VTEP 处理。

#### Q35: OpenFlow 和 BGP 在 SDN/数据中心网络里有什么区别？

**答**：OpenFlow 是集中控制器下发 match/action 流表，交换机更像执行器；BGP 是分布式路由协议，交换机/路由器彼此交换可达性并本地计算路径。

| 对比 | OpenFlow | BGP / EVPN-BGP |
|------|----------|----------------|
| 控制模式 | 集中式主从 | 分布式对等 |
| 下发内容 | 细粒度流表，可匹配 MAC/IP/端口/VLAN 等 | 路由可达性；EVPN 可发布 MAC/IP → VTEP |
| 设备角色 | 偏执行器 | 自己跑协议、算路径 |
| 典型使用 | 早期 SDN、细粒度策略 | 数据中心 Underlay、VXLAN EVPN、互联网路由 |

现代大规模数据中心更常见 BGP/EVPN-BGP：既保留自动化和 Overlay 映射能力，又避免控制器成为每个包转发路径上的单点。SDN 控制器可编排 Underlay 和 Overlay，但已有数据面的每个包不会实时问控制器。

#### Q36: NFV、DPDK、SPDK、SmartNIC/DPU 以及 OVS、VPP、eBPF、RDMA 分别是什么？

**答**：

- **NFV** 是架构/部署范式：把防火墙、NAT、负载均衡、vRouter 等网络功能从专用盒子软件化，运行在通用服务器的 VM 或容器中。
- **VNF** 是虚拟机/软件形态的网络功能；**CNF** 是进一步云原生化、容器化的网络功能。
- **DPDK** 是网络数据面加速框架，让应用通过用户态 PMD、内存池、轮询和 CPU/NUMA 优化高速收发包。
- **SPDK** 是存储数据面加速框架，让应用通过用户态 NVMe 驱动和异步轮询减少内核存储栈开销。
- **SmartNIC/DPU** 是把虚拟交换、VXLAN、加密、存储或安全策略等基础设施任务卸载到网卡或独立处理器。
- **OVS** 是主机上的软件交换机，**VPP** 是高性能用户态向量化转发框架，**eBPF/XDP** 是 Linux 内核早期可编程数据路径。
- **SR-IOV** 让 VM/容器更直接使用网卡虚拟功能，**RDMA/RoCE** 提供低 CPU 介入的远程内存/存储通信，**P4** 用于描述可编程交换芯片的数据面。

它们不是同一层概念：

```text
SDN：控制和编排网络状态
NFV：网络功能的软件化/虚拟化部署范式
VNF/CNF：具体的软件网络功能
DPDK：网络 I/O 数据面加速
SPDK：存储 I/O 数据面加速
SmartNIC/DPU：硬件/独立处理器卸载基础设施数据面
```

典型组合是：SDN/NFV 编排虚拟防火墙或 vRouter，底层可能由 OVS/VPP + DPDK 加速，VXLAN/EVPN 提供网络承载；主机存储服务则可能用 SPDK 或 RDMA/RoCE，部分网络/存储/安全工作进一步卸载到 SmartNIC/DPU。代价是 CPU 绑核、NUMA、内存、网卡队列、固件兼容、无损网络配置和故障排障复杂度都会成为系统设计的一部分。

#### Q37: 专线、VPN、GRE、MPLS、VXLAN 和 SD-WAN 分别解决什么问题？

**答**：

- **专线**是运营商或云厂商提供的受管控 WAN 承载，重点是路径隔离、SLA、时延和带宽；不必然端到端加密。
- **VPN**是在已有 IP 网络上建立逻辑隧道；IPsec VPN 负责认证、完整性和加密，但底层公网质量仍会影响体验。
- **GRE**负责封装内层协议或动态路由，本身不加密，常与 IPsec 组合。
- **MPLS L3VPN**由运营商通过 VRF/标签隔离多个客户的三层 WAN，不应自动理解为端到端加密。
- **VXLAN**主要用于 IDC/云内部的租户 Overlay，不是面向公网的安全 VPN。
- **SD-WAN**是多条 WAN 链路的控制与编排方式，可以统一管理专线、互联网、4G/5G，并按应用质量和策略选路。

高可用还需要双 CPE/双网关、BGP/BFD、回程路由、会话状态、MTU/MSS 和备用链路验证；VPN 客户端显示 `Connected` 只代表隧道建立，不代表业务路由和防火墙已经正确。

#### Q38: DH 已经可以不传私钥地协商对称密钥，为什么 HTTPS 还要用“性能很差”的非对称密码？

**答**：这个问题里混合了三个概念：

1. **DH/ECDHE 本身就是公钥密码学中的密钥协商算法**，不是对称加密算法。它只在握手阶段参与生成共享秘密，不负责持续加密 HTTP 数据。
2. HTTPS **不会用 RSA/ECDSA/ECDHE 去加密每个 HTTP 包**。握手完成后，实际应用数据使用 AES-GCM 或 ChaCha20-Poly1305 这类高性能对称 AEAD 加密。
3. HTTPS 仍需要证书和非对称签名，是因为 DH 只回答“双方能算出同一个秘密”，没有回答“对方是不是目标服务器”。证书链和 `CertificateVerify` 用来认证服务端身份、抵御中间人攻击。

简化后的 TLS 1.3：

```text
ECDHE：客户端和服务端协商临时共享秘密
证书/签名：证明服务端拥有受信任证书对应的私钥
HKDF：从共享秘密导出握手密钥和应用密钥
AES-GCM/ChaCha20-Poly1305：高效加密后续所有 HTTP 数据
```

因此正确的说法不是“HTTPS 用非对称加密传输全部数据”，而是：**用公钥密码学完成身份认证和密钥协商，用对称密码学完成大规模数据加密。** 非对称运算只发生在握手/重新协商等少量阶段，换来的是互联网环境下可验证的服务器身份和前向保密。

### 开放式设计题

**D1：设计一个全球化部署的实时通信系统（如视频会议），网络层需要考虑什么？**

**参考思路**：
- 传输协议：实时音视频用UDP（RTP/RTCP）、信令用WebSocket/gRPC、考虑QUIC替代UDP+自研可靠层
- 全球加速：Anycast接入→就近POP节点→专线骨干网转发→目的地区POP出口（类似GSLB+SD-WAN）
- 弱网对抗：FEC前向纠错、Jitter Buffer、自适应码率（根据RTT和丢包率动态调整）
- NAT穿越：STUN/TURN/ICE、Relay兜底
- 质量监控：RTT/丢包率/抖动实时采集→动态选路（多路径同时传输选最优）

**D2：TCP连接数突然从正常的1万暴涨到50万，导致服务不可用，如何排查和应对？**

**参考思路**：
- 紧急止血：限制新连接速率（iptables/Nginx limit_conn）、重启负载均衡摘除问题节点
- 排查：ss -s查连接状态分布、大量CLOSE_WAIT说明应用未关闭连接、大量TIME_WAIT说明大量短连接
- CLOSE_WAIT：定位哪个goroutine/线程持有未关闭的conn（pprof/jstack）、常见原因（HTTP Response Body未读完/未Close）
- TIME_WAIT：开启SO_REUSEADDR/SO_REUSEPORT、调整tcp_tw_reuse、改用长连接池
- 根因治理：连接池化、超时设置、连接数监控告警

## 总结

后端开发和网络运维应形成一条完整因果链：

1. **分层与寻址**：理解帧、IP 包、TCP/UDP、端口、CIDR、ARP、路由、MTU、NAT，以及专线/VPN 的 Underlay/Overlay 边界。
2. **传输可靠性**：理解 TCP 建连/关闭、流量控制、拥塞控制、Socket 队列与 UDP 取舍。
3. **应用协议**：掌握 HTTP 语义/缓存/状态码、TLS/PKI、实时通信、视频传输与 DNS。
4. **流量入口**：区分 GSLB、Anycast、CDN、边缘计算、L4 LB、L7 网关各自解决的问题。
5. **运行环境**：能沿 Linux 协议栈、conntrack、防火墙、容器网络、主机/容器数据面定位故障。
6. **数据中心网络**：理解 Bond、堆叠、M-LAG、Spine-Leaf、ECMP、VXLAN、EVPN、SDN、NFV 和高性能数据面的边界。
7. **排障方法**：固定按 DNS → 路由 → 端口/连接 → TLS → HTTP/RPC → 应用依赖建立证据链。

协议定义不是终点；真正目标是能回答：**数据包经过哪些层、状态存在哪里、哪一层可能丢弃或延迟、用什么证据验证。**
