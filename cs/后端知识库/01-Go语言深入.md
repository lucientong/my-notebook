## 核心类型底层实现

### slice 底层结构与扩容⭐⭐⭐

#### 底层结构

```go
// runtime/slice.go
type slice struct {
    array unsafe.Pointer // 指向底层数组的指针
    len   int            // 当前长度
    cap   int            // 容量
}
```

```
slice 变量（24字节）          底层数组（连续内存）
┌─────────────────┐         ┌───┬───┬───┬───┬───┐
│ array ──────────────────→ │ 1 │ 2 │ 3 │ 0 │ 0 │
│ len = 3         │         └───┴───┴───┴───┴───┘
│ cap = 5         │
└─────────────────┘
```

**关键理解**：slice 是引用类型，但 slice 变量本身是值（包含指针+len+cap），传参时复制的是这三个字段，不是底层数组。

#### slice 传参语义⭐⭐

Go **没有** C++ 那种真正的「引用传参」。slice 作为参数传递时，仍然是**值传递**——复制的是 header（指针 + len + cap），不是底层数组。caller 和 callee 的 header 副本里的 `array` 指针通常指向**同一块底层数组**。

```text
caller: a (header) ──→ 底层数组
callee: s (header 副本) ──→ 同一块底层数组
```

```go
func modify(s []int) {
    s[0] = 99         // ✅ 改元素：caller 看得见
    s = append(s, 4)  // ⚠️ 改 header：默认只影响函数内副本
}

func main() {
    a := []int{1, 2, 3}
    modify(a)
    fmt.Println(a) // [99, 2, 3] —— 元素变了，但没有 append 进 4
}
```

| 操作 | 是否影响 caller |
|------|-----------------|
| `s[i] = x` | ✅ 会，改的是共享底层数组 |
| `append` 且 **未扩容** | ⚠️ 可能写入共享数组，但 caller 的 `len` 不变 |
| `append` 且 **触发扩容** | ❌ 不会，callee 指向新数组 |
| `s = s[:0]`、`s = nil` 等改 header | ❌ 不会，只改了函数内的 header 副本 |

若要让函数**改变 caller 的 len/cap**（例如 append 后 caller 也要变长），需要把结果写回 caller：

```go
// 方式 1：return slice（最常用）
func grow(s []int) []int {
    return append(s, 4)
}
a = grow(a)

// 方式 2：*[]T（可行，但不 idiomatic）
func grow(s *[]int) {
    *s = append(*s, 4)
}
grow(&a)

// 方式 3：指针接收者（如 container/heap 的 Push/Pop）
func (h *MinHeap) Push(x any) { /* 修改 h 这个 slice 变量的 len */ }
```

> **记忆**：改元素 → 值传参就够；改 slice 本身（len/cap/指针）→ 需要 `return`、`*[]T` 或指针接收者。`&slice` 能工作，但 Go 里更推荐 `return append(...)`。

#### 创建方式

```go
// 1. 字面量
s := []int{1, 2, 3}

// 2. make（推荐，可以控制 len 和 cap）
s := make([]int, 3, 5) // len=3, cap=5

// 3. 从数组切片（共享底层数组！）
arr := [5]int{1, 2, 3, 4, 5}
s := arr[1:3] // s = [2, 3], len=2, cap=4（从索引1到数组末尾）
```

#### make 的 len 与 cap：两种使用模式⭐⭐

`make([]T, len)` 和 `make([]T, len, cap)` 容易混用，核心在于 **后续用下标写还是 append 追加**：

| 写法 | 含义 | 适用场景 |
|------|------|----------|
| `make([]T, n)` | 创建 n 个零值元素，`len == cap == n` | 已知最终长度，用 `arr[i] = v` 填充 |
| `make([]T, 0, n)` | 空 slice，预分配容量 n | 长度不确定或从空开始，用 `append` 构建 |

```go
// 模式 A：索引填充——make 的长度就是最终长度
dp := make([]int, n+1)
for i := 0; i <= n; i++ {
    dp[i] = compute(i)
}

// 模式 B：append 构建——len 从 0 开始
results := make([][]string, 0, len(m))
for _, v := range m {
    results = append(results, v)
}

// 模式 A 的另一种写法：已知分组数，同样用索引而非 append
groups := make([][]string, len(m))
i := 0
for _, v := range m {
    groups[i] = v
    i++
}
```

**决策流程**：

```
会用 append 吗？
├─ 会 → make([]T, 0) 或 make([]T, 0, cap)，len 必须为 0
└─ 不会 → make([]T, n)，用 arr[i] = v 填充
```

> **记忆**：`make([]T, n)` = 「我要 n 个槽，等会用下标填」；`make([]T, 0, cap)` = 「从空开始，往后 append」。二者不要混用。

#### 扩容机制（Go 1.18+ 版本）

```go
// runtime/slice.go（简化）
func growslice(et *_type, old slice, cap int) slice {
    newcap := old.cap
    doublecap := newcap + newcap

    if cap > doublecap {
        newcap = cap
    } else {
        const threshold = 256
        if old.cap < threshold {
            // 小于 256：直接翻倍
            newcap = doublecap
        } else {
            // 大于等于 256：每次增长 25% + 192（平滑过渡）
            for 0 < newcap && newcap < cap {
                newcap += (newcap + 3*threshold) / 4
            }
            if newcap <= 0 {
                newcap = cap
            }
        }
    }
    // 最终 newcap 会做内存对齐（向上取整到内存分配器的 size class）
}
```

```
扩容策略总结：
┌──────────────────────────────────────────────────┐
│ 容量 < 256  →  翻倍扩容                           │
│ 容量 ≥ 256  →  每次增长约 25%（渐进式增长）         │
│ 无论哪种，最终容量都会做内存对齐                      │
└──────────────────────────────────────────────────┘

示例：
cap=4 → append → cap=8（翻倍）
cap=512 → append → cap=832 左右（≈ 512 + 512*25% + 192）
```

> **注意**：Go 1.18 之前的分界点是 1024（而非 256），增长策略是 `<1024 翻倍，≥1024 增长 25%`，面试中需要说明版本差异。

#### slice 的常见陷阱

**陷阱1：切片共享底层数组**

```go
a := []int{1, 2, 3, 4, 5}
b := a[1:3] // b = [2, 3]，与 a 共享底层数组

b[0] = 99   // 修改 b 也会影响 a！
fmt.Println(a) // [1, 99, 3, 4, 5]

// ✅ 安全做法：使用 copy
c := make([]int, len(b))
copy(c, b) // c 有独立的底层数组
```

> **注意**：从大数组切出的小 slice 仍可能持有整个底层大数组的引用，导致内存无法及时释放；需要独立内存时用 `copy`。

**陷阱2：append 可能导致底层数组不共享**

```go
a := make([]int, 3, 5)  // len=3, cap=5
b := a[0:3]

b = append(b, 4) // cap 够用，a 和 b 仍共享底层数组
b = append(b, 5) // cap 够用
b = append(b, 6) // cap 不够，b 扩容，分配新数组！a 和 b 不再共享
```

**陷阱3：nil slice 与空 slice**

```go
var s1 []int       // nil slice: s1 == nil, len=0, cap=0
s2 := []int{}      // 空 slice: s2 != nil, len=0, cap=0
s3 := make([]int, 0) // 空 slice: s3 != nil, len=0, cap=0

// 行为上三者都可以 append、range，但 JSON 序列化不同：
// nil slice → null
// 空 slice → []
```

**陷阱4：`make` 带 len 再 `append`（前后模式混用）**

```go
m := map[string][]int{ /* ... */ }

// ❌ 反模式：已预填 len(m) 个 nil，append 追加到末尾
results := make([][]int, len(m))
for _, v := range m {
    results = append(results, v) // 追加到 index len(m) 之后
}
// 结果: [[],[],[],[1,2,3],...]  前面全是零值槽位

// ✅ 与模式 B 一致
results := make([][]int, 0, len(m))
for _, v := range m {
    results = append(results, v)
}
```

**陷阱5：`range` 遍历 slice 时的原地写入**

`for i, v := range s` 中 `v` 是元素拷贝，但 `s[i] = x` 或维护独立写指针 `s[write] = v` 是安全的。原地双指针（如去重）的不变量是 **读下标 ≥ 写下标**，写不会覆盖尚未读取的数据；这与 `append(s[:i], s[i+1:]...)` 边删边遍历不同——后者会因元素前移而跳过元素。

### 数组与 map key 的类型限制⭐⭐

数组长度是类型的一部分（`[3]int` 与 `[4]int` 是不同类型），但数组本身是**值类型且可比较**，因此可以作为 map 的 key。slice、map、func **不可比较**，不能作 key。

```go
// ✅ 固定大小数组 —— comparable
freq := map[[26]int][]string{}  // 26 个小写字母的计数向量

// ❌ slice 不可比较，编译错误
// bad := map[[]int][]string{}

// ✅ struct 的所有字段均可比较时，struct 也可作 key
type key struct{ a, b int }
m := map[key]string{}
```

**典型用法**：需要将「字符频次」「位图」等固定维度特征作为哈希 key 时，用 `[26]int` / `[128]int` 数组而非 `[]int`，既满足 comparable 约束，又避免排序字符串的开销。

> 详见 [map 底层实现](#map-底层实现) 中的 key 类型说明。

### map 底层实现⭐⭐⭐

Go 的 map 底层是**哈希表 + 桶（bucket）**实现：每个 map 对应一个 `hmap`，管理 `2^B` 个桶；每个桶最多存 8 个 key-value，冲突时用溢出桶链接。

#### hash 与桶定位

对 key 计算一次 64 位 hash，然后拆成两段使用：

```text
hash = 0x1A 2B 3C 4D 5E 6F 70 81
       └─高8位─┘ └────低 B 位选桶────┘

高 8 位 → tophash（桶内先比 1 字节，再比完整 key）
低 B 位 → bucket_index = hash & (2^B - 1)
```

例：`B = 2` 时有 4 个桶（0~3），掩码为 `3`。

```text
hash("alice") = ...70 81
  bucket_index = 81 & 3 = 1
  tophash      = 0x81

hash("bob") = ...70 01
  bucket_index = 1 & 3 = 1    // 不同 key 落在同一桶，属正常冲突
  tophash      = 0x01
```

多个 key 落在同一桶时，靠桶内 8 个槽位 + 溢出桶链表存放。每桶固定 8 槽，是为 cache 友好的顺序扫描；超过 8 个则链式挂 overflow bucket。

#### 底层结构

```go
// runtime/map.go（简化）
type hmap struct {
    count     int    // 元素数量（len()返回的值）
    flags     uint8  // 状态标记（是否在写入等）
    B         uint8  // 桶的数量 = 2^B
    noverflow uint16 // 溢出桶数量
    hash0     uint32 // 哈希种子（随机化，防止哈希碰撞攻击）
    buckets    unsafe.Pointer // 桶数组（2^B个桶）
    oldbuckets unsafe.Pointer // 扩容时的旧桶数组
    nevacuate  uintptr        // 扩容进度
    // ...
}

// 每个桶最多存 8 个 key-value 对
type bmap struct {
    tophash [8]uint8   // 每个 key 哈希值的高8位（快速比较）
    // 后面紧跟 8 个 key 和 8 个 value（编译期确定布局）
    // keys   [8]keytype
    // values [8]valuetype
    // overflow *bmap     // 溢出桶指针
}
```

```
hmap
┌──────────────┐
│ count = 5    │
│ B = 2        │  → 2^2 = 4 个桶
│ buckets ─────────→ ┌────────────┐
│              │     │ bucket 0   │
│              │     │ tophash[8] │
│              │     │ keys[8]    │
│              │     │ values[8]  │
│              │     │ overflow ──────→ 溢出桶
│              │     ├────────────┤
│              │     │ bucket 1   │
│              │     ├────────────┤
│              │     │ bucket 2   │
│              │     ├────────────┤
│              │     │ bucket 3   │
│              │     └────────────┘
└──────────────┘
```

#### 查找、插入与删除

查找：

```text
key = "hello"
    │
    ▼
1. hash = hash("hello", hash0)
2. bucket_index = hash & (2^B - 1)
3. tophash = hash >> (64 - 8)
4. 扫描桶内 tophash[0..7]：
   ├── tophash 匹配 → 比较完整 key → 相等则返回 value
   ├── 不匹配 → 下一个槽位
   └── 8 槽均无 → 查 overflow 链 → 仍无则返回零值
```

插入：前半段同查找；key 已存在则覆盖 value，有空槽则写入，8 槽已满则写入 overflow bucket。

删除：定位 key 后清空对应槽位并标记删除。**Go map 不会因为 `delete` 自动缩容**；删除大量 key 后，桶数组可能仍保留，内存通常要等整个 map 不再被引用并被 GC 回收，或由业务新建一个 map 后重新拷贝有效数据来“压缩”。

#### 扩容机制

**触发条件**：

```
条件1：负载因子 > 6.5（count / 2^B > 6.5）
→ 翻倍扩容（2^B → 2^(B+1)）

条件2：溢出桶过多（noverflow > 2^B 且 B < 15，或 noverflow > 2^15）
→ 等量扩容（桶数量不变，重新整理数据，消除稀疏的溢出桶）
```

**渐进式扩容**：

```text
扩容时保留 oldbuckets；之后每次读写 map 顺带迁移 1~2 个旧桶到新 buckets。
全部搬完后再释放 oldbuckets。成本分摊到后续访问，而非一次性 stop-the-world rehash。
```

#### 与 Java HashMap 的对比

Java 8+ 在 bucket 内用链表处理冲突；链长 ≥ 8 且 table 容量 ≥ 64 时转为**红黑树**，单 bucket 最坏 O(log n)。

Go **不做树化**，靠以下机制控制冲突链长度：

| | Java HashMap | Go map |
|---|---|---|
| 冲突结构 | bucket 内链表 → 红黑树 | 固定 8 槽 + overflow bucket 链 |
| 单 bucket 扫描 | 链表 O(n) 或树 O(log n) | 恒 O(1)，最多 8 槽 |
| 防退化手段 | 树化 | 负载因子扩容 + overflow 等量整理 + 随机 `hash0` |

**Go 的三道控制**：

1. **桶内定长 8 槽**：不是 n 个节点的长链表，而是 `bucket → overflow bucket → ...`，每跳最多扫 8 次。
2. **负载因子 > 6.5 翻倍扩容**：增加桶数、重新散列，缩短 overflow 链。6.5 是「平均每桶元素数」阈值（每桶本身能装 8 个），不是 Java 那种 0.75 的槽位负载率。
3. **overflow 过多时等量扩容**：元素总数未必超标，但冲突链过长时重新整理，摊平 overflow。

**能否保证不退化成 O(n)？** 严格意义上不能。若所有 key 落入同一 bucket（恶意碰撞或极差 hash），overflow 链可达 O(n/8) 个桶，总复杂度仍是 O(n)，只是常数小（每跳最多 8 槽 + tophash 过滤）。Go 的取舍是：平均情况靠 hash 分散和提前扩容维持 O(1)，实现更简单、内存更紧凑，代价是理论 worst case 无 O(log n) 的结构保证。

#### 迭代顺序

map 的物理布局本身没有逻辑顺序，`for range m` 的遍历顺序**不保证稳定**，Go 还会**故意随机化**迭代顺序，防止代码依赖偶然顺序。不要写依赖 map 遍历顺序的业务逻辑。

#### key 的类型要求

map 的 key 必须是 **comparable** 类型：基本类型、指针、channel、interface、struct（字段均可比较）、**数组**（元素均可比较）等。slice、map、func 不可比较。

查找时先用 key 的 `==` 判等（数组逐元素比较），因此 `[26]int` 这类固定数组天然适合表达「字符频次签名」类的 key；若用 `[]int` 则无法通过编译。更多 key 选型见上文 [数组与 map key 的类型限制](#数组与-map-key-的类型限制)。

#### map 的并发安全问题

```go
// ❌ map 不是并发安全的！并发读写会触发 fatal error
m := map[string]int{}
go func() { m["a"] = 1 }()
go func() { _ = m["a"] }()
// fatal error: concurrent map read and map write

// ✅ 方案1：sync.Mutex
// ✅ 方案2：sync.RWMutex（读多写少）
// ✅ 方案3：sync.Map（特定场景）
// ✅ 方案4：分片 map（高并发写）
```

并发读只有在**没有并发写**时才安全。

> **面试陷阱**：Go 的 map 在运行时会检测并发写入（通过 `flags` 标记位），一旦检测到直接 `throw("concurrent map writes")`，这是 **fatal error 不可恢复**，不是 panic。

常见方案的使用场景：

**1. `sync.Mutex`：读写都不算特别多，逻辑简单**

```go
type Counter struct {
    mu sync.Mutex
    m  map[string]int
}

func (c *Counter) Inc(key string) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.m[key]++
}

func (c *Counter) Get(key string) int {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.m[key]
}
```

**2. `sync.RWMutex`：读多写少**

```go
type Cache struct {
    mu sync.RWMutex
    m  map[string]string
}

func (c *Cache) Get(key string) (string, bool) {
    c.mu.RLock()
    defer c.mu.RUnlock()
    v, ok := c.m[key]
    return v, ok
}

func (c *Cache) Set(key, value string) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.m[key] = value
}
```

**3. `sync.Map`：读多、key 相对稳定、一次写多次读**

```go
var users sync.Map // key: userID, value: *User

func GetUser(id string) (*User, bool) {
    v, ok := users.Load(id)
    if !ok {
        return nil, false
    }
    return v.(*User), true
}

func SetUser(id string, u *User) {
    users.Store(id, u)
}
```

`sync.Map` 适合只增不频繁删的缓存、注册表、配置快照等；如果需要复杂不变量（例如同时更新多个 key），用 `Mutex + map` 更直接。`sync.Map` 的 read/dirty 实现机制、与 `Mutex+map` 的对比见 [Map（并发安全 Map）](#map并发安全-map)。

**4. 分片 map：高并发写，降低单把锁竞争**

```go
const shardCount = 32

type shard struct {
    mu sync.Mutex
    m  map[string]int
}

type ShardedMap struct {
    shards [shardCount]shard
}

func fnv32(key string) uint32 {
    h := fnv.New32a() // import "hash/fnv"
    _, _ = h.Write([]byte(key))
    return h.Sum32()
}

func (sm *ShardedMap) Inc(key string) {
    s := &sm.shards[fnv32(key)%shardCount]
    s.mu.Lock()
    defer s.mu.Unlock()
    s.m[key]++
}
```

分片 map 的核心是按 key hash 到不同 shard，每个 shard 一把锁。它提升写入并发，但实现复杂度更高，也不适合需要跨 shard 原子更新的场景。

### interface 底层实现⭐⭐⭐

#### 两种 interface 结构

Go 的 interface 在底层有两种结构：

```go
// 1. eface —— 空接口 interface{}
type eface struct {
    _type *_type          // 类型信息
    data  unsafe.Pointer  // 数据指针
}

// 2. iface —— 非空接口（有方法的接口）
type iface struct {
    tab  *itab            // 接口表（类型+方法集）
    data unsafe.Pointer   // 数据指针
}

type itab struct {
    inter *interfacetype  // 接口的类型信息
    _type *_type          // 实际类型信息
    hash  uint32          // 类型哈希（用于类型断言快速比较）
    _     [4]byte
    fun   [1]uintptr      // 方法地址表（变长数组）
}
```

```
var w io.Writer = os.Stdout

iface
┌──────────────────┐
│ tab ──→ itab     │
│         ┌────────────────────┐
│         │ inter: *Writer     │  接口类型
│         │ _type: *os.File    │  实际类型
│         │ fun: [Write]       │  方法地址表
│         └────────────────────┘
│ data ──→ os.Stdout 实例       │
└──────────────────┘
```

#### 接口的 nil 判断陷阱

```go
// ⚠️ 经典陷阱
type MyError struct{}
func (e *MyError) Error() string { return "error" }

func getError() error {
    var err *MyError = nil
    return err  // 返回的 interface 不是 nil！
}

func main() {
    err := getError()
    fmt.Println(err == nil) // false！

    // 原因：err 是 iface{tab: *itab(MyError), data: nil}
    // tab 不为 nil，所以 err != nil
    // 即使 data 是 nil，只要 tab 有值，interface 就不等于 nil
}

// ✅ 正确做法：直接返回 nil，而不是返回带类型的 nil 指针
func getError() error {
    var err *MyError = nil
    if err == nil {
        return nil  // 返回真正的 nil interface
    }
    return err
}
```

#### 类型断言的性能

```go
// 类型断言（O(1)，通过 itab.hash 快速比较）
v, ok := i.(ConcreteType)

// 类型 switch
switch v := i.(type) {
case *os.File:
    // ...
case *bytes.Buffer:
    // ...
}
```

> **itab 缓存**：Go 运行时会缓存已计算的 `itab`（在全局哈希表中），同一个 `<interface, type>` 组合只会计算一次方法表，后续直接查表，性能很高。

### 方法集、接口实现与泛型⭐⭐

#### 方法集：为什么 `T` 和 `*T` 实现接口的结果不同？

Go 判断一个类型是否实现接口，看的是**方法集**，不是看结构体字段长得像不像。核心规则：

| 类型 | 方法集包含 | 能赋值给接口的条件 |
|------|------------|--------------------|
| `T` | 接收者为 `T` 的方法 | 接口只要求值接收者方法 |
| `*T` | 接收者为 `T` 和 `*T` 的方法 | 接口可要求值接收者或指针接收者方法 |

```go
type Writer interface { Write([]byte) (int, error) }

type Buffer struct{}
func (b *Buffer) Write(p []byte) (int, error) { return len(p), nil }

var w Writer
// w = Buffer{}  // ❌ Buffer 的方法集不包含 (*Buffer).Write
w = &Buffer{}    // ✅ *Buffer 的方法集包含 Write
```

选择值接收者还是指针接收者时，不要只看是否修改字段：

- 方法需要修改接收者状态，必须用指针接收者。
- 结构体较大、包含锁或不可复制资源时，优先指针接收者。
- 同一类型的方法集通常保持一致，避免一半值接收者、一半指针接收者造成接口实现困惑。

#### 泛型：解决什么问题，不解决什么问题？

Go 1.18 引入泛型后，可以把“类型不同、逻辑相同”的代码抽出来，例如集合工具、缓存容器、算法模板。

```go
type Ordered interface {
    ~int | ~int64 | ~float64 | ~string
}

func Max[T Ordered](a, b T) T {
    if a > b {
        return a
    }
    return b
}
```

这里 `T` 是类型参数，`Ordered` 是约束。`~int` 表示底层类型为 `int` 的自定义类型也可以匹配。

泛型适合：

- 容器、集合、队列、堆、Set、Map 工具。
- 算法模板，如 `Min/Max/Filter/Reduce`。
- 保留类型安全，避免 `any` + 类型断言。

泛型不适合：

- 为了“看起来高级”而抽象业务代码。
- 运行时根据字段名/标签做动态逻辑；这仍然是 reflect 的领域。
- 把接口多态和泛型混用到难以阅读。接口描述行为，泛型描述一组可替换的具体类型。

性能上，Go 编译器会对泛型函数做类型字典/形状等实现优化；多数业务场景不需要手动关心。但在极热路径上，泛型、接口、闭包、reflect 的实际开销都应以 benchmark 为准，不要凭直觉判断。


### string 与 []byte⭐⭐

#### string 底层结构

```go
// runtime/string.go
type stringStruct struct {
    str unsafe.Pointer // 指向底层字节数组（不可变）
    len int            // 字节长度（不是字符数！）
}
```

**string 的不可变性**：

```go
s := "hello"
// s[0] = 'H'  // 编译错误！string 是不可变的

// 修改 string 必须转换为 []byte
b := []byte(s) // ⚠️ 会发生内存拷贝
b[0] = 'H'
s = string(b)  // ⚠️ 又一次内存拷贝
```

#### string 与 []byte 的转换：拷贝 vs 零拷贝

**标准写法（默认用这个）**

```go
b := []byte(s)  // 分配新 []byte，拷贝 s 的内容
s2 := string(b) // 分配新 string，拷贝 b 的内容
```

Go 规定 string **不可变**、[]byte **可变**。标准转换每次都拷贝，是为了保证安全：

```go
s := "hello"
b := []byte(s)
b[0] = 'H'      // 只改了 b，s 仍是 "hello"
s2 := string(b) // s2 是 "Hello"，与 b 不共享内存
```

如果零拷贝共享同一块内存，上面改 `b[0]` 就会连 `s` 一起改掉，破坏语言对 string 的约定。

**unsafe 零拷贝（Go 1.22+ 用 `unsafe.String` / `unsafe.StringData`）**

```go
func stringToBytes(s string) []byte {
    return unsafe.Slice(unsafe.StringData(s), len(s)) // 不分配、不拷贝
}

func bytesToString(b []byte) string {
    return unsafe.String(unsafe.SliceData(b), len(b)) // 不分配、不拷贝
}
```

| | `[]byte(s)` / `string(b)` | `unsafe` 零拷贝 |
|---|---|---|
| 是否拷贝 | 是，每次分配新内存 | 否，共用底层字节 |
| 安全性 | 安全，语言保证 | 需自己保证生命周期和不修改 |
| 改 []byte 是否影响 string | 不影响 | **会影响**（同一内存） |
| append 后 string 是否仍有效 | 不适用（已拷贝） | `bytesToString` 后 append 可能让 string 指向失效内存 |
| 典型用途 | 日常业务代码 | 解析器热路径、只读扫描 |

**为什么说「推荐 API，但要慎用」？**

- **推荐**：Go 1.22 起 `unsafe.String` / `unsafe.StringData` 是官方零拷贝 API，比旧的 `reflect.StringHeader`  hack 更清晰。
- **慎用**：它绕过了标准转换的安全保障，你必须自己承担：
  1. **不能修改** `stringToBytes` 得到的 []byte（否则修改了 string 底层，未定义行为）
  2. **`bytesToString` 后不能再改 b**，也不能 append 触发重分配
  3. 确保底层内存在 string/slice 使用期间一直有效

```go
// ❌ unsafe 典型误用
s := "hello"
b := stringToBytes(s)
b[0] = 'H' // 破坏了 string 不可变性

b = []byte("world")
s2 := bytesToString(b)
b[0] = 'W' // s2 的内容也被改了
```

**选型**：绝大多数场景用 `[]byte(s)` / `string(b)` 即可，拷贝成本通常远小于网络 IO、序列化等开销。只有 profile 证明转换是热点、且能保证只读或不修改底层时，才考虑 unsafe。

**编译器优化**：以下场景编译器会自动避免 `string ↔ []byte` 的拷贝：
- `map` 查找：`m[string(b)]` 不会拷贝
- 字符串拼接：`"prefix" + string(b)` 可能优化
- `for range []byte(s)` 不会拷贝

## 语言语义与算法附录

### `:=` 与 `=`：短变量声明与赋值

| 写法 | 含义 |
|------|------|
| `x := val` | 在当前块 **新声明** 变量；若同名变量已存在于外层，则 **遮蔽（shadow）** 外层 |
| `x = val` | 给 **当前作用域内已声明** 的变量赋值 |

```go
head := listHead
for head != nil {
    head, tail := reverse(head, tail) // ❌ := 新建局部 head，遮蔽 for 的 head
    head = tail.Next                  // 改的是内层 head，循环条件永远不变 → 死循环
}

// ✅ 循环体内更新循环变量，用 =
for head != nil {
    head, tail = reverse(head, tail)
    head = tail.Next
}
```

**高发场景**：`for` / `if` init 块 / `switch` 短语句中的 `:=`。排查时看左侧变量是否本应更新外层同名变量——若是，必须改用 `=`。

### 递归闭包：先声明再赋值

函数字面量用 `:=` 定义时，**名字在赋值完成前不在自身函数体的作用域内**，因此无法在函数体内递归调用自身：

```go
// ❌ 编译错误：undefined: inorder
inorder := func(node *TreeNode) {
    inorder(node.Left)
}

// ✅ 先声明变量，再赋值——闭包捕获已存在的变量
var inorder func(node *TreeNode)
inorder = func(node *TreeNode) {
    if node == nil {
        return
    }
    inorder(node.Left)
    // ...
    inorder(node.Right)
}
```

对比：`var f func(); f = func() { f() }` 合法，而 `g := func() { g() }` 非法——前者变量先存在，后者名字尚未进入作用域。

**替代写法**：提取为包级/方法级命名函数，或改用迭代 + 显式栈，避免递归闭包。

### 整数取模与负数

Go 的 `%` 是**余数（remainder）**，不是数学意义上的总为非负的模（modulo）。结果符号与**被除数**一致：

```go
 5 % 4  //  1
-5 % 4  // -1
 5 % -4 //  1
-5 % -4 // -1
```

这个规则和 C / C++ / Java / JavaScript 基本一致；Python 不同，Python 的 `%` 结果符号与**除数**一致，所以 `-1 % 4 == 3`。

| 语言 | 表达式 | 结果 | 规则 |
|------|--------|------|------|
| Go | `-1 % 4` | `-1` | 余数符号跟被除数 |
| Java | `-1 % 4` | `-1` | 余数符号跟被除数 |
| C/C++ | `-1 % 4` | `-1` | 余数符号跟被除数 |
| JavaScript | `-1 % 4` | `-1` | remainder，不是数学 modulo |
| Python | `-1 % 4` | `3` | 结果符号跟除数 |

环形数组、循环队列、轮盘下标等场景，左移时要先补一圈长度：

```go
// 环上右移
next = (i + 1) % n

// 环上左移
prev = (i - 1 + n) % n   // 例：(0-1+4)%4 = 3
```

如果位移可能超过一圈，使用通用写法：

```go
func mod(i, n int) int {
    return (i%n + n) % n
}

mod(-1, 4) // 3
mod(-5, 4) // 3
```

面试和算法题里常见 bug 是把 Python 的 `%` 直觉带到 Go，写出 `prev = (i - 1) % n`，当 `i == 0` 时会得到 `-1`，再用于数组下标就会 panic。

### container/heap 优先队列⭐⭐⭐

Go 标准库 **没有内置堆类型**，而是提供 `container/heap` 包，通过 **接口 + slice** 实现通用优先队列。算法题中的 Top K、合并 K 路有序流、Dijkstra 等场景都会用到。

#### 为什么这样设计？

| 设计选择 | 原因 |
|----------|------|
| 不内置 `Heap[T]` 类型 | Go 1.18 之前无泛型；即使有了泛型，标准库仍保持「接口 + 算法函数」风格（类似 `sort.Slice`） |
| 堆建立在 **slice** 上 | 堆本质是数组存储的完全二叉树，与 slice 天然契合，无额外指针开销 |
| 用户实现 `heap.Interface` | 「比较规则」和「元素类型」因题而异，交给调用方定义 `Less` |
| `Push`/`Pop` 由用户实现 | 标准库只负责 **heapify**（上浮/下沉），slice 如何增删由用户控制 |

```
标准库的职责划分：

  你的 slice  ──实现──→  heap.Interface (Len/Less/Swap/Push/Pop)
                              │
  container/heap  ──调用──→  Init / Push / Pop / Fix
                              │
                         内部 fixUp / fixDown 维护堆序
```

> **类比**：`sort.Interface` 定义「怎么比」，``sort.Sort`` 负责排序；``heap.Interface`` 定义「怎么比、怎么存」，``heap.Push/Pop`` 负责维护堆序。

---

#### heap.Interface 五个方法

```go
type Interface interface {
    sort.Interface // Len(), Less(i,j), Swap(i,j)
    Push(x any)    // 往 slice 末尾追加元素
    Pop() any      // 从 slice 末尾移除并返回元素
}
```

##### 方法分工

| 方法 | 谁调用 | 作用 |
|------|--------|------|
| `Len` / `Less` / `Swap` | `heap` 包内部 `fixUp`/`fixDown` | 比较、交换，维护堆序 |
| `Push` | 用户通过 `heap.Push(h, x)` 间接调用 | 把元素 **append 到 slice 末尾** |
| `Pop` | 用户通过 `heap.Pop(h)` 间接调用 | **移除 slice 最后一个元素** 并返回 |

##### 为什么 `Pop` 删的是末尾而不是堆顶？

`heap.Pop(h)` 的完整流程（标准库内部）：

```
1. 交换 h[0] 和 h[n-1]     // 堆顶移到最后
2. fixDown(h, 0, n-1)      // 对新的堆顶下沉，范围不含末尾
3. 调用你的 h.Pop()         // 从 slice 末尾删掉刚才换下来的旧堆顶
4. 返回被删元素
```

因此 **你实现的 `Pop()` 只需 `old[:n-1]` 截断末尾**——标准库已经先把堆顶换到末尾了。这是最容易写错的地方。

##### 为什么 `Push`/`Pop` 用指针接收者？

```go
func (h MinHeap) Len() int           // 值接收者：只读
func (h *MinHeap) Push(x any)        // 指针接收者：要修改 slice
func (h *MinHeap) Pop() any          // 指针接收者：要修改 slice
```

`Push`/`Pop` 会改变 slice 长度，必须指针接收者；`Len`/`Less`/`Swap` 用值接收者即可（`Swap` 通过 slice 底层数组修改元素，值接收者也能工作）。

---

#### 小根堆 vs 大根堆

**堆的类型完全由 `Less` 决定**：

```go
// 小根堆：堆顶最小
func (h MinHeap) Less(i, j int) bool { return h[i].cnt < h[j].cnt }

// 大根堆：堆顶最大
func (h MaxHeap) Less(i, j int) bool { return h[i].cnt > h[j].cnt }
```

---

#### 完整模板

```go
import "container/heap"

type MinHeap []int

func (h MinHeap) Len() int           { return len(h) }
func (h MinHeap) Less(i, j int) bool { return h[i] < h[j] }
func (h MinHeap) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }
func (h *MinHeap) Push(x any)        { *h = append(*h, x.(int)) }
func (h *MinHeap) Pop() any {
    old := *h
    n := len(old)
    x := old[n-1]
    *h = old[:n-1]
    return x
}

// 使用
h := &MinHeap{3, 1, 4}
heap.Init(h)              // 建堆 O(n)，已有数据时必须调
heap.Push(h, 2)           // 入堆 O(log n)
min := heap.Pop(h).(int)  // 出堆 O(log n)，返回当前最值
top := (*h)[0]            // 只看不取：堆顶是 h[0]，不要直接 h.Pop
```

**常用 API**：

| 函数 | 作用 |
|------|------|
| `heap.Init(h)` | 无序 slice 建堆，O(n) |
| `heap.Push(h, x)` | 入堆 |
| `heap.Pop(h)` | 弹出堆顶（最值） |
| `heap.Fix(h, i)` | 修改 `h[i]` 后恢复堆序 |
| `heap.Remove(h, i)` | 删除索引 i 的元素 |

#### Top K 问题（算法原理）

> 完整推导、决策表、LC347 手推、经典题型对照见 **[01-算法与数据结构 §5.4 应用1 Top K](./01-算法与数据结构.md#应用1top-k-问题-)**。

**一句话**：找 Top K **大** → size=k **小根堆**守门；找 Top K **小** → size=k **大根堆**守门。堆顶是「第 K 名门槛」，不是冠军。

Go 语言 `container/heap` 的接口实现与常见陷阱见 **[01-Go语言深入 §container/heap](../后端知识库/01-Go语言深入.md#containerheap-优先队列)**。

#### 实战：LeetCode 347 前 K 个高频元素

**思路**：统计频次 → 维护大小为 k 的小根堆（按频次）→ 超过 k 就 Pop 频次最小的。

```go
for num, cnt := range countMap {
    heap.Push(h, pair{num, cnt})
    if h.Len() > k {
        heap.Pop(h)
    }
}
```

**复杂度**：O(n log k) 时间，O(k) 空间。桶排序 O(n) 为本题特化解法，见算法文档。

#### 常见陷阱

**陷阱1：`Pop` 写成弹堆顶**

```go
// ❌ 破坏了 heap.Pop 的协作约定
func (h *MinHeap) Pop() any {
    x := (*h)[0]
    *h = (*h)[1:]
    return x
}

// ✅ 只删末尾，堆顶交换由标准库完成
func (h *MinHeap) Pop() any {
    old := *h
    x := old[len(old)-1]
    *h = old[:len(old)-1]
    return x
}
```

**陷阱2：忘记 `heap.Init`**

已有数据的 slice 在使用 `heap.Push`/`heap.Pop` 前必须 `heap.Init`，否则堆序未建立。

**陷阱3：直接 `append` 而不走 `heap.Push`**

```go
// ❌ 堆序未维护
*h = append(*h, x)

// ✅
heap.Push(h, x)
```

**陷阱4：值接收者的 `Push`/`Pop`**

```go
h := MinHeap{}
heap.Push(&h, x)  // 必须传指针，否则 Push 修改的是副本
```

## GMP调度模型

### 为什么需要 GMP？⭐⭐⭐

Go 需要用少量 OS 线程高效调度大量 goroutine。GMP 就是 Go runtime 的用户态调度模型：

```text
G：Goroutine，用户态任务
M：Machine，OS 线程
P：Processor，调度上下文，持有本地运行队列和资源
```

没有 P 时，所有 M 会竞争全局调度状态；P 通过本地队列降低锁竞争，让调度尽量在本地完成。

在理解 GMP 之前，先理解 Go 面临的核心问题：

**操作系统线程的代价太大**：

```
创建一个 OS 线程：
- 栈空间：默认 1MB~8MB（固定分配）
- 创建耗时：约 10~100 微秒（需要内核态切换）
- 上下文切换：约 1~10 微秒（保存/恢复寄存器、刷新 TLB）
- 数量上限：受内存限制，通常几千~几万个

创建一个 Goroutine：
- 栈空间：初始 2KB（按需增长，最大 1GB）
- 创建耗时：约 0.3 微秒（纯用户态操作）
- 上下文切换：约 0.1~0.2 微秒（不经过内核）
- 数量上限：轻松创建百万级
```

**核心矛盾**：Go 希望支持百万级并发，但操作系统只能高效管理几千个线程。

**解决方案**：在用户态实现一个调度器，用少量 OS 线程运行大量 Goroutine → 这就是 GMP 模型。

> **类比**：把 GMP 想象成一家公司——
> - **G（Goroutine）= 待办任务**（工单），数量巨大
> - **M（Machine）= 员工**（OS 线程），数量有限
> - **P（Processor）= 工位 + 工具箱**（执行环境），员工必须坐在工位上才能干活
>
> 公司不可能为每个任务雇一个员工（太贵），所以用少量员工轮流处理大量任务。

### 核心概念（G、M、P 详解）⭐⭐⭐

#### G — Goroutine（任务）

```go
// 每一个 go 关键字都会创建一个 G
go func() {
    fmt.Println("我是一个 G")
}()
```

G 的内部结构（简化）：

```go
// runtime/runtime2.go（简化）
type g struct {
    stack       stack    // 栈内存（初始 2KB，可增长）
    stackguard0 uintptr  // 栈溢出检测（用于抢占调度）
    sched       gobuf    // 保存的寄存器状态（SP、PC、BP 等）
    atomicstatus uint32  // G 的状态
    goid         int64   // goroutine ID
    m            *m      // 当前绑定的 M（正在执行时）
    // ...
}
```

**G 的状态流转**：

```
                  go func()
                     │
                     ▼
    ┌──────────── _Gidle ──────────────┐
    │           （刚分配，未初始化）       │
    │                │                  │
    │                ▼                  │
    │         _Grunnable ◄─────────────┤
    │         （在队列中等待）            │
    │                │                  │
    │       被 P 调度 │                  │
    │                ▼                  │
    │          _Grunning               │
    │          （正在执行）               │
    │           │      │               │
    │    系统调用 │      │ channel/IO    │
    │           ▼      ▼               │
    │     _Gsyscall  _Gwaiting ────────┘
    │     （系统调用） （等待唤醒）  唤醒后回到 _Grunnable
    │           │
    │           ▼
    │     系统调用返回 → _Grunnable
    │
    │     函数返回
    │         │
    │         ▼
    └──→  _Gdead（执行完毕，可复用）
```

> **关键理解**：G 不是线程，它只是一个"任务描述"（保存了函数入口、参数、栈），需要被调度到 M 上才能真正执行。

---

#### M — Machine（OS 线程）

M 是真正的操作系统线程，是 CPU 调度的基本单位。

```go
// runtime/runtime2.go（简化）
type m struct {
    g0      *g     // 调度栈（每个 M 都有一个 g0，专门用于执行调度代码）
    curg    *g     // 当前正在执行的 G
    p       puintptr // 当前绑定的 P（M 必须持有 P 才能执行 G）
    spinning bool   // 是否处于自旋状态
    // ...
}
```

**M 的关键特性**：
- M 的数量**没有硬上限**（默认最大 10000，可通过 `runtime/debug.SetMaxThreads` 调整）
- **M 必须持有 P 才能执行 G**（没有 P 的 M 要么在执行系统调用，要么在休眠）
- M 有一个特殊的 `g0`，不执行用户代码，专门负责调度（在 G 之间切换）

```
M 的工作循环：

     ┌──────────────────────────────────┐
     │                                  │
     ▼                                  │
  g0 栈：schedule()                     │
     │  寻找可运行的 G                   │
     │  找到 G                          │
     ▼                                  │
  切换到 G 的栈：执行用户代码             │
     │  G 执行完毕 / 被抢占 / 阻塞       │
     │                                  │
     └──── 切回 g0 栈 ─────────────────┘
```

> **类比**：M 就像员工的双手——真正干活的部分。`g0` 是员工的"大脑"，负责决定接下来干哪个任务。

---

#### P — Processor（执行环境）

P 是 Go 调度器最精妙的设计，它**不是**CPU、不是线程，而是一个"执行上下文"。

```go
// runtime/runtime2.go（简化）
type p struct {
    id          int32
    status      uint32   // P 的状态
    m           muintptr // 当前绑定的 M
    runqhead    uint32   // 本地队列头
    runqtail    uint32   // 本地队列尾
    runq        [256]guintptr // 本地运行队列（固定 256 个槽位）
    runnext     guintptr // 下一个优先执行的 G（快速通道）
    // 还包含：内存分配缓存(mcache)、defer池、sudog缓存等
}
```

**为什么需要 P？（不能直接让 M 执行 G 吗？）**

```
假设没有 P，只有 G 和 M：

方案A：一个全局队列
┌────────────────────────────────────┐
│ 全局队列：G1 G2 G3 G4 G5 G6 ... │  ← 所有 M 竞争同一把锁
└────────────────────────────────────┘
      ↑   ↑   ↑   ↑
     M0  M1  M2  M3

问题：所有 M 抢同一把锁，高并发下锁竞争严重，性能急剧下降

方案B：引入 P（每个 P 有本地队列）
┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│ P0       │  │ P1       │  │ P2       │  │ P3       │
│ G1 G2 G3 │  │ G4 G5 G6 │  │ G7 G8 G9 │  │ G10 G11  │
└─────┬────┘  └─────┬────┘  └─────┬────┘  └─────┬────┘
      │             │             │              │
     M0            M1            M2             M3

优势：
- 大部分情况下 M 从自己 P 的本地队列取 G，无锁操作！
- 本地队列空了才去全局队列或偷其他 P 的
- P 还携带了内存缓存(mcache)等资源，减少全局竞争
```

> **P 的数量** = `GOMAXPROCS`（默认 = CPU 核心数），表示最多有多少个 G 能**同时**执行。

### 调度流程（一个 Goroutine 的一生）⭐⭐⭐

#### 第一步：创建 G

```go
go func() {
    fmt.Println("Hello")
}()
```

**底层发生了什么？**

```go
// 编译器将 go func() 转换为 runtime.newproc 调用
// runtime/proc.go（简化）
func newproc(fn *funcval) {
    // 1. 获取当前 G 和 P
    gp := getg()
    pp := gp.m.p.ptr()

    // 2. 尝试从 P 的空闲 G 缓存中获取（复用，避免频繁分配）
    newg := gfget(pp)
    if newg == nil {
        // 3. 缓存没有，则新建一个 G（分配 2KB 栈）
        newg = malg(stackMin) // stackMin = 2048 bytes
    }

    // 4. 初始化 G 的状态（设置 PC 指向 fn，SP 指向栈顶）
    newg.sched.pc = fn.fn  // 程序计数器 → 函数入口
    newg.sched.sp = ...    // 栈指针

    // 5. 放入 P 的队列
    runqput(pp, newg, true) // true 表示优先放 runnext

    // 6. 如果有空闲 P，唤醒一个 M 来执行
    if atomic.Load(&sched.npidle) != 0 {
        wakep()
    }
}
```

**G 被放入队列的优先级**：

```
go func() 创建新 G
    │
    ▼
① P.runnext（快速通道，只能放1个）
    │ 如果 runnext 已有旧 G → 旧 G 被踢到本地队列
    ▼
② P.runq（本地队列，容量 256）
    │ 如果满了（256个）
    ▼
③ Global Run Queue（全局队列，需要加锁）
    会把本地队列一半的 G + 新 G 一起移到全局队列
```

> **runnext 的设计用意**：刚创建的 G 通常会很快被执行（时间局部性），放在 runnext 可以减少一次队列操作。

**runnext 常见误解与核心结论**

`runnext` 不是「正在执行的 G 的 VIP 通道」，而是 **P 上“下一个待运行 G”的单槽位**。它存放的是 `_Grunnable` 状态的 G，还没开始执行用户代码，因此“被新 G 顶掉”只是在调整排队位置，不是执行到一半再重来。

```text
当前 M 正在执行 G_cur

runnext = G_a          // G_a 还没跑，只是下一个优先
go func() 创建 G_b
  → G_a 挪到 runq 尾部
  → runnext = G_b

G_cur 让出 CPU 后：
  runqget() 先取 runnext 里的 G_b 执行
  G_a 之后在 runq 里按队列顺序执行
```

为什么要有这个单槽？常见模式是“父 G 创建子 G 后很快 park”，例如等待 channel 握手、锁竞争或某个异步结果。若新 G 只能进入本地队列尾部，它可能被早就在队列中的无关 G 挡住，父 G 已经在等，子 G 却迟迟没机会运行。`runnext` 让刚创建的、通常与当前 G 局部性更强的子 G 优先接棒，降低延迟。

```text
没有 runnext：父 park → 先跑队列里的 B/C → 子 G 终于运行
有 runnext：  父 park → 子 G 先运行 → 再跑队列里的 B/C
```

连续创建多个 G 时，新的 G 会替换旧的 `runnext`，旧 G 被放回 `runq`，形成轻微 LIFO 倾向。它只影响调度延迟和局部性，不提供业务语义上的顺序保证。**Go 不保证全局 FIFO**；如果业务需要顺序，必须用 channel、WaitGroup、errgroup 或显式队列表达，不要依赖调度器。

---

#### 第二步：M 获取 G 并执行

M 从绑定的 P 中找 G，找不到就扩大搜索范围：

```go
// runtime/proc.go（简化）
func schedule() {
    pp := getg().m.p.ptr()

    // === 第一优先级：每 61 次调度检查一次全局队列 ===
    // 为什么是 61？质数，避免与其他周期性行为产生共振
    if pp.schedtick%61 == 0 {
        if gp := globrunqget(pp, 1); gp != nil {
            execute(gp)
            return
        }
    }

    // === 第二优先级：P 的本地队列（无锁，最快） ===
    if gp := runqget(pp); gp != nil {
        execute(gp)
        return
    }

    // === 第三优先级：扩大搜索范围 ===
    // 这是一个复杂的函数，按顺序尝试：
    gp := findrunnable() // 会阻塞直到找到
    execute(gp)
}

func findrunnable() *g {
    // 1. 再次检查本地队列（防止并发放入）
    // 2. 检查全局队列
    // 3. 检查 netpoller（网络IO就绪的G）
    // 4. 从其他 P 偷取（Work Stealing）
    // 5. 都没有 → 休眠等待
}
```

**图解查找过程**：

```
M 需要一个 G 来执行：

  ① 本地队列有吗？ ───有──→ 拿到，执行！（无锁，最快）
         │
         无
         ▼
  ② 全局队列有吗？ ───有──→ 拿到（加锁），执行！
         │                   顺便多拿一批到本地队列
         无
         ▼
  ③ netpoller 有就绪的？─有→ 拿到，执行！
         │
         无
         ▼
  ④ 从其他 P 偷取     ───有──→ 偷一半，执行！
         │
         无
         ▼
  ⑤ 休眠（等待被唤醒）
```

#### 第三步：抢占调度（确保公平性）

**问题**：如果一个 G 一直执行不让出 CPU，其他 G 就会饿死。

**Go 1.14 之前：协作式抢占**

```go
// 编译器在函数入口插入检查代码
func someFunc() {
    // 编译器自动插入：
    if stackguard0 == stackPreempt {
        // 被标记为"需要抢占"，主动让出
        gopreempt()
    }
    // ... 用户代码 ...
}
```

依赖函数调用时的栈检查 → **死循环没有函数调用就无法抢占**：

```go
// Go 1.13 及之前，这个 goroutine 会霸占 CPU
func evil() {
    for {
        // 纯计算，无函数调用，永远不会触发栈检查
        // 其他 goroutine 全部饿死！
    }
}
```

**Go 1.14+：基于信号的异步抢占**

```
工作流程：

Sysmon（后台监控线程，每 10ms~10s 检查一次）
    │
    │ 发现 G 运行超过 10ms
    │
    ▼
发送 SIGURG 信号给 G 所在的 M
    │
    │ M 收到信号，进入信号处理函数
    ▼
asyncPreempt()
    │ 保存当前 G 的所有寄存器状态
    │ 将 G 状态设为 _Grunnable，放回队列
    │
    ▼
M 切回 g0，调用 schedule() 执行下一个 G
```

```go
// Go 1.14+，死循环也能被抢占了
func notSoEvil() {
    for {
        // 运行超过 10ms 会被 SIGURG 信号强制中断
        // 保存状态，放回队列，其他 G 有机会执行
    }
}
```

> **为什么选 SIGURG？** 因为 SIGURG 几乎没有其他用途（原本用于 TCP 带外数据），不会和用户程序的信号处理冲突。

#### Sysmon 监控线程

Sysmon 是一个特殊的后台 M，**不需要绑定 P**，独立运行，负责"兜底"：

```go
// runtime/proc.go（简化）
func sysmon() {
    for {
        // 动态调整检查频率：空闲时慢（10ms→10s），忙碌时快
        usleep(delay)

        // 1. 抢占长时间运行的 G（> 10ms）
        retake(now)

        // 2. 检查 netpoller（有网络IO就绪的G需要唤醒）
        if netpollinited() {
            list := netpoll(0) // 非阻塞检查
            injectglist(&list) // 将就绪的 G 放入全局队列
        }

        // 3. 强制 GC（超过 2 分钟未 GC）
        if t := (gcTrigger{kind: gcTriggerTime, now: now}); t.test() {
            forcegchelper()
        }

        // 4. 释放长时间 syscall 中的 P（Hand Off）
        // 如果 M 被系统调用阻塞了超过 10ms，
        // 把 P 从这个 M 上摘下来给其他 M 用
    }
}
```

### 重要机制详解⭐⭐⭐

#### 1. Work Stealing（工作窃取）

当 P 的本地队列空了，先去全局队列找，还没有就去**偷**其他 P 的任务。

```
偷取之前：                              偷取之后：
┌────────────┐  ┌────────────┐       ┌────────────┐  ┌────────────┐
│ P0         │  │ P1         │       │ P0         │  │ P1         │
│ G1 G2 G3 G4│  │ (空)       │       │ G1 G2      │  │ G3 G4      │
│ 很忙！      │  │ 闲着没事   │  →    │ 还在忙     │  │ 有活干了   │
└────────────┘  └────────────┘       └────────────┘  └────────────┘
```

```go
// runtime/proc.go（简化）
func stealWork(pp *p) (gp *g, inheritTime bool) {
    // 随机选择一个 P 开始偷（避免总偷同一个）
    for i := 0; i < 4; i++ {  // 尝试 4 次
        victim := allp[fastrand()%len(allp)]
        if victim == pp {
            continue
        }
        // 偷取 victim 本地队列的一半
        if gp := runqsteal(pp, victim, stealRunNextG); gp != nil {
            return gp, false
        }
    }
    return nil, false
}
```

**设计要点**：
- 偷一半（而不是一个），减少偷取次数
- 随机选择目标 P，避免热点竞争
- 无锁 CAS 实现，偷取过程高效

---

#### 2. Hand Off（P 移交）

**问题**：M 执行系统调用（如文件 IO）会阻塞，如果 P 跟着一起阻塞，P 上排队的其他 G 全部停滞。

```
系统调用前：                   Hand Off 后：
┌──────────┐                 ┌──────────┐  ┌──────────┐
│ M0 + P0  │                 │ M0 (无P) │  │ M2 + P0  │
│ G1(执行)  │                 │ G1(阻塞)  │  │ G2(执行)  │
│ G2 G3    │  ───────→       │ syscall  │  │ G3       │
│ (等待中)  │                 │ 中...    │  │ 继续运行  │
└──────────┘                 └──────────┘  └──────────┘

                             M0 系统调用返回后：
                             - 尝试获取一个空闲 P
                             - 有 → 绑定 P，继续执行 G1
                             - 没有 → 将 G1 放入全局队列，M0 休眠
```

```go
// 当 G 进入系统调用时
func entersyscall() {
    // 1. 保存 G 的状态
    save(gp.sched.pc, gp.sched.sp)
    // 2. 标记 P 为 _Psyscall
    pp.status = _Psyscall
    // 3. 解除 M 和 P 的绑定（逻辑上）
    // Sysmon 发现后会把 P 交给其他 M
}
```

> **为什么不在进入 syscall 时立即 Hand Off？** 因为大部分系统调用很快就返回了，立即 Hand Off 反而浪费。所以由 Sysmon 在 10ms 后检查，如果还在阻塞才执行 Hand Off。

---

#### 3. Spinning Thread（自旋线程）

当 M 暂时找不到 G 时，不立即休眠，先**自旋**（空转）一段时间。

```
为什么自旋而不是直接休眠？

时间线（没有自旋）：
M 空闲 → 休眠（耗时~10μs）→ 新 G 来了 → 唤醒 M（耗时~10μs）→ 开始执行
                                                               总延迟 ≈ 20μs

时间线（有自旋）：
M 空闲 → 自旋等待（消耗少量 CPU）→ 新 G 来了 → 立即执行
                                                总延迟 ≈ 0
```

**限制**：最多 `GOMAXPROCS` 个 M 同时自旋（避免所有 CPU 都在空转浪费电）。

### 关键问题

**Q1: GOMAXPROCS 是什么？如何设置？**

```go
// GOMAXPROCS 控制 P 的数量（≠ M 的数量！≠ G 的数量！）
// P 的数量 = 最大同时并行执行的 G 的数量

// 设置最大 P 数量（默认等于 CPU 核心数）
runtime.GOMAXPROCS(8)

// 查看当前值
n := runtime.GOMAXPROCS(0) // 传 0 不修改，只查询
fmt.Println("GOMAXPROCS:", n)
```

**原则**：
- **CPU密集型**：设置为 CPU 核心数（默认值就好）
- **IO密集型**：可以略大于 CPU 核心数（更多 P 意味着更多 G 能同时发起 IO）
- **容器环境**：注意 cgroup 限制，Go 默认读 `runtime.NumCPU()` 可能拿到宿主机核心数

```go
// 容器环境推荐使用 uber 的库自动适配
import _ "go.uber.org/automaxprocs"

func main() {
    // 自动根据 cgroup 限制设置 GOMAXPROCS
    // 例如容器限制 4 核，就设置为 4（而不是宿主机的 64）
}
```

---

**Q2: G、M、P 的数量关系？**

```text
P 的数量：GOMAXPROCS（默认 = CPU 核心数），固定
M 的数量：按需创建，默认最多 10000（阻塞系统调用时会额外创建 M）
G 的数量：用户创建多少就有多少，可以远大于 P

更准确的关系：
- 同时在 CPU 上执行 Go 代码的 G ≤ P（= GOMAXPROCS）
- 同一时刻，一个 P 最多绑一个 M，一个 M 跑 Go 代码时也最多持有一个 P（1:1）
- M 可能 > P：多出来的 M 通常卡在系统调用里，此时没有 P，不会抢队列
- G >> P：大量 G 在 P 本地队列、全局队列或 netpoller 中等待
```

**Q3: M > P 时，是不是多个 M 绑定同一个 P，一起抢 P 的队列？**

不是。这是 GMP 里最常见的误解。

```text
正常执行：
  P0 ──1:1── M0 ──跑── G1
  P1 ──1:1── M1 ──跑── G2

G 进入阻塞系统调用（如 read/write）：
  1. G 进入 _Gsyscall
  2. M2 把 P 交出去（hand off）
  3. M2 留在内核里阻塞，此时 M2 没有 P
  4. 其他 M3 可以接管这个 P，继续跑 P 队列里的其他 G
```

所以 **M > P** 的含义是：有些 M 在 syscall 里「占着线程但不占 P」，runtime 需要额外 M 保证仍有 `GOMAXPROCS` 个 P 能继续跑 Go 代码。不是多个 M 同时绑同一个 P 抢 runq。

**Q4: 百万 goroutine 真的几乎不占内存吗？**

不是。G 比 OS 线程轻很多，但**每个 G 仍有独立栈和元数据**，总量仍受内存限制。

| | M（OS 线程） | G（Goroutine） |
|---|---|---|
| 栈 | 通常 MB 级预留（1~8MB） | 初始约 2KB，按需增长，单 G 最大约 1GB |
| 调度开销 | 内核线程 + g0 | 小结构体 + 堆上栈 |
| 等待时 | 线程仍占资源 | runq 里只存 G 指针，栈在堆上 |

P 的 runq 存的是 **G 的指针**，不是把百万 G 的执行上下文都塞进 P。真正占内存的是：

```text
所有 G 的栈总和 + G 结构体 + 业务持有的对象
```

粗算：100 万个 G，若平均栈 2KB，仅栈就约 2GB；栈增长、闭包引用、channel 缓冲、业务对象都会继续推高内存。说「百万级没问题」是指相对百万 OS 线程**可行**，不是说不占内存、不会 OOM。

工程上应控制 goroutine 数量：用 worker pool、context 取消、避免无界 `go func()`，并监控 `runtime.NumGoroutine()` 和 heap。

### Go 协程 vs Python 协程⭐⭐⭐

> Go 和 Python 都有"协程"概念，但设计理念和实现方式**完全不同**。

#### 核心差异对比

| 维度 | Go Goroutine | Python Coroutine (`async/await`) |
|------|-------------|----------------------------------|
| **调度方式** | **抢占式**（Go 1.14+，运行时自动切换） | **协作式**（必须遇到 `await` 才让出） |
| **调度器** | Go runtime 内置 GMP 调度器（用户态） | 事件循环 `asyncio.EventLoop`（用户态） |
| **并行能力** | ✅ 真正并行（多个 M 绑定多核 CPU） | ❌ 单线程并发（受 GIL 限制，同一时刻只有一个协程执行） |
| **栈模型** | **有栈协程**（每个 G 有独立栈，2KB 起步，可增长） | **无栈协程**（基于生成器/状态机，无独立栈） |
| **创建方式** | `go func()` | `async def` + `await` |
| **通信方式** | Channel（CSP 模型） | `asyncio.Queue` / `Future` |
| **适用场景** | CPU 密集 + IO 密集（通用） | IO 密集（网络请求、文件IO） |
| **创建成本** | 极低（~0.3μs，2KB内存） | 低（~1μs，但比 goroutine 略重） |
| **数量上限** | 百万级 | 万级~十万级（受事件循环性能限制） |

---

#### 调度方式差异（最关键的区别）

**Go：运行时自动调度，开发者不用操心**

```go
func main() {
    // 开发者只管 go，调度器自动处理一切
    for i := 0; i < 100000; i++ {
        go func(id int) {
            // 无论是 CPU 计算还是 IO，都会被自动调度
            result := heavyComputation(id) // CPU密集 → 运行10ms后被抢占
            resp := httpGet(url)           // IO密集 → 阻塞时自动切换
            fmt.Println(result, resp)
        }(i)
    }
    select {} // 阻塞主协程
}
// 开发者完全不需要关心"什么时候让出 CPU"
```

**Python：开发者必须显式用 `await` 让出控制权**

```python
import asyncio

async def main():
    tasks = []
    for i in range(1000):
        tasks.append(fetch_data(i))
    await asyncio.gather(*tasks)

async def fetch_data(id):
    # ✅ 这里会让出控制权，事件循环可以切换到其他协程
    resp = await aiohttp.get(f"http://api.com/{id}")

    # ❌ 这里不会让出！如果计算很久，整个事件循环都卡住
    result = heavy_computation(id)  # 阻塞整个线程！

    return result

# 如果忘记写 await，协程就不会让出，其他协程全部饿死
```

> **关键区别**：Go 的 goroutine 即使在做 CPU 密集计算也会被抢占调度（10ms 强制切换），Python 的协程只有遇到 `await` 才会让出，CPU 密集计算会阻塞整个事件循环。

---

#### 并行能力差异

```
Go（真正并行）：
┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│ CPU 核心0 │  │ CPU 核心1 │  │ CPU 核心2 │  │ CPU 核心3 │
│ M0 → G1  │  │ M1 → G2  │  │ M2 → G3  │  │ M3 → G4  │
└──────────┘  └──────────┘  └──────────┘  └──────────┘
→ 4 个 goroutine 在 4 个核心上同时执行（并行）

Python asyncio（只能并发，不能并行）：
┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│ CPU 核心0 │  │ CPU 核心1 │  │ CPU 核心2 │  │ CPU 核心3 │
│ 事件循环  │  │ (空闲)   │  │ (空闲)   │  │ (空闲)   │
│ → 协程1   │  │          │  │          │  │          │
└──────────┘  └──────────┘  └──────────┘  └──────────┘
→ 所有协程在同一个线程中交替执行（并发但不并行）
→ 受 GIL 限制，即使用多线程也无法并行执行 Python 字节码
```

---

#### 有栈 vs 无栈协程

```
Go（有栈协程）：
每个 Goroutine 有自己独立的栈（初始 2KB，可增长到 1GB）
┌─────────┐  ┌─────────┐  ┌─────────┐
│  G1 栈   │  │  G2 栈   │  │  G3 栈   │
│ 2KB~1GB │  │ 2KB~1GB │  │ 2KB~1GB │
│ 函数调用 │  │ 函数调用 │  │ 函数调用 │
│ 局部变量 │  │ 局部变量 │  │ 局部变量 │
└─────────┘  └─────────┘  └─────────┘

优势：
- 可以在任意位置暂停/恢复（包括深层函数调用中）
- 编程模型简单：写同步代码，享受异步性能

Python（无栈协程）：
协程本质是一个状态机对象，没有独立栈
┌──────────────────────┐
│  协程对象（状态机）    │
│  状态: SUSPENDED     │
│  下一步: await 之后   │
│  局部变量: {...}      │
└──────────────────────┘

优势：
- 内存开销更小（不需要预分配栈）
限制：
- 只能在 await 点暂停（不能在普通函数调用中暂停）
- 需要 async/await 语法传染（调用链上所有函数都要标记 async）
```

**"async 传染性"问题**（Python 特有）：

```python
# Python 的 async 会"传染"整个调用链
async def top_level():
    result = await middle_layer()   # middle_layer 必须是 async
    return result

async def middle_layer():
    data = await bottom_layer()     # bottom_layer 必须是 async
    return process(data)

async def bottom_layer():
    return await aiohttp.get(url)   # 最底层的IO操作

# 如果底层要改成异步，整个调用链都要改成 async
# 这就是"函数颜色"问题（What Color is Your Function?）
```

```go
// Go 没有这个问题——所有函数都是"同一颜色"
func topLevel() Result {
    return middleLayer()  // 普通调用
}

func middleLayer() Data {
    return bottomLayer()  // 普通调用
}

func bottomLayer() Data {
    resp, _ := http.Get(url)  // IO 操作，goroutine 自动挂起
    // 看起来是同步代码，实际上 runtime 自动处理了异步
    return parse(resp)
}
```

**Q2: Goroutine 泄漏如何发现和解决？**

**场景1：channel 永久阻塞**

```go
// ❌ 泄漏
func leak() {
    ch := make(chan int)
    go func() {
        val := <-ch // 永远阻塞，goroutine 泄漏
        fmt.Println(val)
    }()
    // ch 没有写入，goroutine 永远等待
}

// ✅ 修复：使用 context 超时
func fixed() {
    ch := make(chan int)
    ctx, cancel := context.WithTimeout(context.Background(), 1*time.Second)
    defer cancel()
    
    go func() {
        select {
        case val := <-ch:
            fmt.Println(val)
        case <-ctx.Done():
            fmt.Println("timeout")
            return
        }
    }()
}
```

**场景2：无限循环不退出**

```go
// ❌ 泄漏
func poll() {
    go func() {
        for {
            // 无退出条件
            time.Sleep(1 * time.Second)
        }
    }()
}

// ✅ 修复：使用 done channel
func fixed() {
    done := make(chan struct{})
    
    go func() {
        for {
            select {
            case <-done:
                return
            default:
                time.Sleep(1 * time.Second)
            }
        }
    }()
    
    // 停止时关闭 done
    close(done)
}
```

**2. Goroutine 池（Worker Pool）**

```go
func workerPool(tasks <-chan Task, results chan<- Result, workers int) {
    var wg sync.WaitGroup
    
    for i := 0; i < workers; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for task := range tasks {
                result := process(task)
                results <- result
            }
        }()
    }
    
    wg.Wait()
    close(results)
}

// 使用
tasks := make(chan Task, 100)
results := make(chan Result, 100)

go workerPool(tasks, results, 10) // 10 个 worker

// 生产任务
for _, task := range allTasks {
    tasks <- task
}
close(tasks)

// 消费结果
for result := range results {
    fmt.Println(result)
}
```

### Channel 深入

**1. Channel 底层结构**

```go
type hchan struct {
    qcount   uint           // 当前队列中的元素数量
    dataqsiz uint           // 环形队列大小
    buf      unsafe.Pointer // 环形队列指针
    elemsize uint16         // 元素大小
    closed   uint32         // 是否关闭
    sendx    uint           // 发送索引
    recvx    uint           // 接收索引
    recvq    waitq          // 接收者队列
    sendq    waitq          // 发送者队列
    lock     mutex          // 互斥锁
}
```

---

**2. Channel 操作**

**发送数据**：
```go
ch <- value
```

流程：
1. 获取锁
2. 如果有等待的接收者（recvq），直接传递
3. 否则，放入环形队列（buf）
4. 队列满了，发送者进入 sendq 等待
5. 释放锁

**接收数据**：
```go
value := <-ch
```

流程：
1. 获取锁
2. 如果有等待的发送者（sendq），直接接收
3. 否则，从环形队列（buf）取出
4. 队列空了，接收者进入 recvq 等待
5. 释放锁

---

**3. Channel 关闭规则**

**黄金法则**：
- ✅ **发送方关闭 channel**
- ❌ 接收方不要关闭 channel
- ❌ 不要向已关闭的 channel 发送数据（panic）

```go
// ✅ 正确
func producer(ch chan<- int) {
    for i := 0; i < 10; i++ {
        ch <- i
    }
    close(ch) // 发送方关闭
}

func consumer(ch <-chan int) {
    for val := range ch { // range 会在 channel 关闭时退出
        fmt.Println(val)
    }
}

// ❌ 错误
func consumer(ch chan int) {
    for val := range ch {
        fmt.Println(val)
    }
    close(ch) // 接收方不应该关闭
}
```

**检查 channel 是否关闭**：

```go
val, ok := <-ch
if !ok {
    fmt.Println("channel closed")
}
```

**6. select 运行时语义**

`select` 不是简单的 `if/else`，它会在多个 channel 操作之间做一次运行时仲裁：

```go
select {
case v := <-ch1:
    use(v)
case ch2 <- x:
    sent()
case <-ctx.Done():
    return ctx.Err()
default:
    // 所有 case 都不能立即执行时走 default
}
```

关键规则：

1. 只有可立即执行的 case 才会被选中；没有可执行 case 且没有 `default` 时，当前 goroutine park。
2. 多个 case 同时就绪时，运行时会做伪随机选择，不能依赖源码顺序表达优先级。
3. `nil` channel 的收发永远不会就绪，因此常用来动态关闭某个 select 分支。
4. `default` 会让 select 变成非阻塞轮询；若放在 tight loop 里，可能打满 CPU，需要配合 timer、backoff 或阻塞等待。

从运行时视角看，阻塞的 channel case 会把当前 G 挂到对应 channel 的 `sendq/recvq`（以 `sudog` 表示等待关系），等另一个 goroutine 完成匹配后再 `goready` 唤醒。这也是 channel 和 GMP 调度发生联系的位置：channel 负责同步语义，调度器负责让被唤醒的 G 重新获得 P/M 执行。

**6. 并发模式**

**Fan-Out / Fan-In**

```go
// Fan-Out：一个生产者，多个消费者
func fanOut(input <-chan int, workers int) []<-chan int {
    outputs := make([]<-chan int, workers)
    
    for i := 0; i < workers; i++ {
        out := make(chan int)
        outputs[i] = out
        
        go func(out chan<- int) {
            defer close(out)
            for val := range input {
                out <- val * 2 // 处理
            }
        }(out)
    }
    
    return outputs
}

// Fan-In：多个生产者，一个消费者
func fanIn(inputs ...<-chan int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup
    
    for _, input := range inputs {
        wg.Add(1)
        go func(ch <-chan int) {
            defer wg.Done()
            for val := range ch {
                out <- val
            }
        }(input)
    }
    
    go func() {
        wg.Wait()
        close(out)
    }()
    
    return out
}
```

**Pipeline**

```go
func pipeline() {
    // Stage 1: 生成数据
    gen := func() <-chan int {
        out := make(chan int)
        go func() {
            defer close(out)
            for i := 0; i < 10; i++ {
                out <- i
            }
        }()
        return out
    }
    
    // Stage 2: 处理数据
    square := func(in <-chan int) <-chan int {
        out := make(chan int)
        go func() {
            defer close(out)
            for val := range in {
                out <- val * val
            }
        }()
        return out
    }
    
    // Stage 3: 过滤数据
    filter := func(in <-chan int) <-chan int {
        out := make(chan int)
        go func() {
            defer close(out)
            for val := range in {
                if val%2 == 0 {
                    out <- val
                }
            }
        }()
        return out
    }
    
    // 组装 pipeline
    for val := range filter(square(gen())) {
        fmt.Println(val)
    }
}
```

### Channel vs Mutex

**什么时候用 Channel？**
- 数据传递、流式处理
- 多个 goroutine 协作
- 事件通知

**什么时候用 Mutex？**
- 共享状态修改
- 临界区很小
- 需要高性能

```go
// ✅ 使用 Channel（传递数据）
func process(tasks <-chan Task) {
    for task := range tasks {
        // 处理
    }
}

// ✅ 使用 Mutex（共享状态）
type Counter struct {
    mu    sync.Mutex
    count int
}

func (c *Counter) Increment() {
    c.mu.Lock()
    c.count++
    c.mu.Unlock()
}
```

**口诀**：
> **Don't communicate by sharing memory; share memory by communicating.**
> 
> 不要通过共享内存来通信，通过通信来共享内存。

## context上下文

### 核心概念

`context.Context` 用于：
- **超时控制**：WithTimeout、WithDeadline
- **取消信号**：WithCancel
- **传递数据**：WithValue

**接口定义**：
```go
type Context interface {
    Deadline() (deadline time.Time, ok bool)  // 返回截止时间
    Done() <-chan struct{}                     // 返回取消信号channel
    Err() error                                // 返回取消原因
    Value(key interface{}) interface{}         // 获取存储的值
}
```

### 底层实现原理

#### 1. emptyCtx（根Context）

**源码解析**：
```go
// context包内部定义
type emptyCtx int

func (*emptyCtx) Deadline() (deadline time.Time, ok bool) {
    return  // 永不超时
}

func (*emptyCtx) Done() <-chan struct{} {
    return nil  // 永不取消
}

func (*emptyCtx) Err() error {
    return nil
}

func (*emptyCtx) Value(key interface{}) interface{} {
    return nil
}

var (
    background = new(emptyCtx)
    todo       = new(emptyCtx)
)

func Background() Context { return background }
func TODO() Context       { return todo }
```

**为什么需要emptyCtx？**
- 作为Context树的根节点
- 永不超时、永不取消，作为长期存在的顶层Context
- 性能优化：空实现，零开销

---

#### 2. cancelCtx（可取消Context）

**源码解析**：
```go
type cancelCtx struct {
    Context  // 内嵌父Context

    mu       sync.Mutex            // 保护以下字段
    done     chan struct{}         // 懒加载，第一次调用Done()时创建
    children map[canceler]struct{} // 所有子Context（形成取消链）
    err      error                 // 取消原因
}

func (c *cancelCtx) Done() <-chan struct{} {
    c.mu.Lock()
    if c.done == nil {
        c.done = make(chan struct{})  // 懒加载
    }
    d := c.done
    c.mu.Unlock()
    return d
}

func (c *cancelCtx) Err() error {
    c.mu.Lock()
    err := c.err
    c.mu.Unlock()
    return err
}
```

**取消机制**：
```go
func (c *cancelCtx) cancel(removeFromParent bool, err error) {
    if err == nil {
        panic("context: internal error: missing cancel error")
    }
    
    c.mu.Lock()
    if c.err != nil {
        c.mu.Unlock()
        return  // 已经被取消
    }
    c.err = err
    
    if c.done == nil {
        c.done = closedchan  // 直接使用预先关闭的channel
    } else {
        close(c.done)  // 关闭channel，通知所有等待者
    }
    
    // ⭐ 关键：递归取消所有子Context
    for child := range c.children {
        child.cancel(false, err)
    }
    c.children = nil
    c.mu.Unlock()
    
    if removeFromParent {
        removeChild(c.Context, c)  // 从父Context移除
    }
}
```

**为什么取消是递归的？**
- Context形成树状结构：父→子→孙
- 父Context取消时，所有子孙Context必须同步取消
- 通过`children map`维护子Context集合，取消时遍历通知

---

#### 3. timerCtx（带超时Context）

**源码解析**：
```go
type timerCtx struct {
    cancelCtx        // 内嵌cancelCtx
    timer *time.Timer  // 定时器
    deadline time.Time // 截止时间
}

func (c *timerCtx) Deadline() (deadline time.Time, ok bool) {
    return c.deadline, true
}

func (c *timerCtx) cancel(removeFromParent bool, err error) {
    c.cancelCtx.cancel(false, err)
    if removeFromParent {
        removeChild(c.cancelCtx.Context, c)
    }
    c.mu.Lock()
    if c.timer != nil {
        c.timer.Stop()  // 停止定时器，避免泄漏
        c.timer = nil
    }
    c.mu.Unlock()
}
```

**WithTimeout实现**：
```go
func WithTimeout(parent Context, timeout time.Duration) (Context, CancelFunc) {
    return WithDeadline(parent, time.Now().Add(timeout))
}

func WithDeadline(parent Context, d time.Time) (Context, CancelFunc) {
    // 如果父Context的截止时间更早，直接使用父Context
    if cur, ok := parent.Deadline(); ok && cur.Before(d) {
        return WithCancel(parent)
    }
    
    c := &timerCtx{
        cancelCtx: newCancelCtx(parent),
        deadline:  d,
    }
    propagateCancel(parent, c)  // 父取消时，子也取消
    
    dur := time.Until(d)
    if dur <= 0 {
        c.cancel(true, DeadlineExceeded)  // 已经超时
        return c, func() { c.cancel(false, Canceled) }
    }
    
    c.mu.Lock()
    defer c.mu.Unlock()
    if c.err == nil {
        // ⭐ 启动定时器，到时自动取消
        c.timer = time.AfterFunc(dur, func() {
            c.cancel(true, DeadlineExceeded)
        })
    }
    return c, func() { c.cancel(true, Canceled) }
}
```

**为什么超时后自动取消？**
- `time.AfterFunc`启动后台goroutine，到时调用`c.cancel`
- 自动关闭`Done()` channel，通知所有等待者
- 避免goroutine泄漏

---

#### 4. valueCtx（携带值Context）

**源码解析**：
```go
type valueCtx struct {
    Context          // 内嵌父Context
    key, val interface{}  // 只存一个key-value对
}

func (c *valueCtx) Value(key interface{}) interface{} {
    if c.key == key {
        return c.val  // 当前层匹配
    }
    return c.Context.Value(key)  // ⭐ 向父Context递归查找
}
```

**WithValue实现**：
```go
func WithValue(parent Context, key, val interface{}) Context {
    if key == nil {
        panic("nil key")
    }
    if !reflectlite.TypeOf(key).Comparable() {
        panic("key is not comparable")
    }
    return &valueCtx{parent, key, val}
}
```

**为什么只存一个key-value？**
- Context设计为不可变（immutable）
- 每次WithValue创建新节点，形成链表结构
- 查找Value需要O(n)遍历（n为层级深度）
- **不适合存储大量数据，只用于请求域的少量元数据**

---

### 为什么不要存储Context？⭐⭐⭐

这是一个**非常重要的最佳实践**，原因如下：

#### 原因1：生命周期不匹配

```go
// ❌ 错误示例
type Server struct {
    ctx context.Context  // 存储在结构体中
}

func NewServer() *Server {
    ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
    // ⚠️ 问题：5秒后ctx自动取消，但Server可能存活更久
    return &Server{ctx: ctx}
}

func (s *Server) Handle() {
    // 可能在ctx已取消后调用，导致所有操作立即失败
    if err := s.doSomething(s.ctx); err != nil {
        // 总是返回"context canceled"
    }
}
```

**底层原因**：
- Context的生命周期通常是**请求级别**（request-scoped）
- 结构体的生命周期通常是**应用级别**（application-scoped）
- 存储后，短生命周期的Context可能已取消，但结构体仍在使用

---

#### 原因2：内存泄漏

```go
// ❌ 错误示例
type Cache struct {
    ctx context.Context
}

func NewCache(ctx context.Context) *Cache {
    return &Cache{ctx: ctx}
}

// ⚠️ 问题：如果ctx是timerCtx，内部有time.Timer
// Cache存在期间，Timer的goroutine一直运行，无法被GC
```

**底层原因**：
- `timerCtx`内部有`time.Timer`，会启动后台goroutine
- 如果Context被长期存储，Timer goroutine无法结束
- 导致goroutine泄漏和内存泄漏

**验证泄漏**：
```go
func TestContextLeak(t *testing.T) {
    before := runtime.NumGoroutine()
    
    for i := 0; i < 1000; i++ {
        ctx, cancel := context.WithTimeout(context.Background(), 1*time.Hour)
        _ = ctx
        cancel()  // ✅ 必须调用cancel释放资源
    }
    
    time.Sleep(100 * time.Millisecond)
    after := runtime.NumGoroutine()
    
    // 如果不调用cancel，after会比before多很多
    if after-before > 10 {
        t.Errorf("goroutine leak: %d -> %d", before, after)
    }
}
```

---

#### 原因3：并发安全问题

```go
// ❌ 错误示例
type Worker struct {
    ctx context.Context
    mu  sync.Mutex
}

func (w *Worker) Process() {
    // ⚠️ 问题：多个goroutine共享同一个ctx
    // 如果其中一个调用cancel，所有goroutine都会受影响
    go w.doWork(w.ctx)
    go w.doWork(w.ctx)
}
```

**底层原因**：
- Context设计为**只读**，但cancel操作是**可写**
- 多个goroutine共享同一个Context，任何一个调用cancel都会影响所有goroutine
- 存储后很难控制取消的影响范围

---

#### 原因4：违反Context设计原则

Context设计原则（来自官方文档）：
> "Context should be passed as the first parameter, not stored in structs."

**为什么这样设计？**
1. **显式传递**：让调用链清晰可见
2. **按需创建**：每个请求创建独立的Context树
3. **自动清理**：请求结束，Context自动释放
4. **避免全局状态**：Context不是全局变量

---

### ✅ 正确的使用方式

#### 方式1：作为函数参数传递

```go
type Server struct {
    db *sql.DB
}

func (s *Server) Handle(ctx context.Context, req *Request) (*Response, error) {
    // ✅ Context作为参数传递，不存储

    if err != nil {
        return nil, err
    }
    
    data, err := s.fetchData(ctx, user.ID)
    if err != nil {
        return nil, err
    }
    
    return &Response{Data: data}, nil
}

func (s *Server) getUser(ctx context.Context, userID int) (*User, error) {
    // ✅ 继续向下传递
    return s.db.QueryContext(ctx, "SELECT * FROM users WHERE id = ?", userID)
}
```

#### 方式2：为每个请求创建独立Context

#### 方式3：需要长期存在时，存储cancel函数而非Context

    }

## sync同步原语

### Mutex（互斥锁）

**使用场景**：保护临界区，同一时间只有一个 goroutine 访问。

```go
type Counter struct {
    mu    sync.Mutex
    count int
}

func (c *Counter) Increment() {
    c.mu.Lock()
    c.count++
    c.mu.Unlock()
}

func (c *Counter) Get() int {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.count
}
```

**注意**：
- Mutex 不可复制（使用指针传递）
- Lock 和 Unlock 必须成对出现
- 避免重复 Lock（死锁）

---

### RWMutex（读写锁）

**使用场景**：读多写少的场景，允许多个读者，但只允许一个写者。

```go
type Cache struct {
    mu   sync.RWMutex
    data map[string]string
}

func (c *Cache) Get(key string) (string, bool) {
    c.mu.RLock() // 读锁
    defer c.mu.RUnlock()
    val, ok := c.data[key]
    return val, ok
}

func (c *Cache) Set(key, value string) {
    c.mu.Lock() // 写锁
    defer c.mu.Unlock()
    c.data[key] = value
}
```

**性能对比**：
- 读多写少：RWMutex > Mutex
- 写多：RWMutex ≈ Mutex（因为写锁需要等待所有读锁释放）

---

### WaitGroup（等待组）

**使用场景**：等待多个 goroutine 完成。

```go
func process(urls []string) {
    var wg sync.WaitGroup
    
    for _, url := range urls {
        wg.Add(1)
        go func(url string) {
            defer wg.Done()
            fetch(url)
        }(url)
    }
    
    wg.Wait() // 等待所有 goroutine 完成
    fmt.Println("all done")
}
```

**注意**：
- Add 必须在 goroutine 启动前调用
- Done 等价于 Add(-1)
- Wait 会阻塞直到计数器归零

---

### Once（单次执行）

**使用场景**：确保某个操作只执行一次（初始化、单例）。

```go
var (
    instance *Singleton
    once     sync.Once
)

func GetInstance() *Singleton {
    once.Do(func() {
        instance = &Singleton{}
        fmt.Println("init singleton")
    })
    return instance
}
```

**特性**：
- 线程安全
- 即使 panic 也只会执行一次（不会重试）

---

### Pool（对象池）

**使用场景**：复用对象，减少 GC 压力。

```go
var bufferPool = sync.Pool{
    New: func() interface{} {
        return new(bytes.Buffer)
    },
}

func process(data []byte) {
    buf := bufferPool.Get().(*bytes.Buffer)
    defer bufferPool.Put(buf)
    
    buf.Reset() // 清理
    buf.Write(data)
    // 使用 buf
}
```

**注意**：
- Pool 中的对象可能随时被 GC 回收
- 使用前必须重置对象状态
- 适合临时对象（buffer、临时结构体）

---

### Map（并发安全 Map）

**使用场景**：并发读写 map，且符合「读多、key 稳定、一次写多次读」模式。

```go
var cache sync.Map

// 存储
cache.Store("key", "value")

// 读取
if val, ok := cache.Load("key"); ok {
    fmt.Println(val)
}

// 删除
cache.Delete("key")

// LoadOrStore（原子操作）
actual, loaded := cache.LoadOrStore("key", "value")
if loaded {
    fmt.Println("already exists:", actual)
}

// Range（遍历）
cache.Range(func(key, value interface{}) bool {
    fmt.Println(key, value)
    return true // 返回 false 停止遍历
})
```

#### sync.Map 的实现机制

`sync.Map` 不是「给普通 map 套一把锁」，内部是 **read + dirty 双 map**：

```go
// sync/map.go（简化）
type Map struct {
    mu     Mutex
    read   atomic.Pointer[readOnly] // 无锁读路径
    dirty  map[any]any              // 写入缓冲区
    misses int                      // Load 未命中 read 的次数
}

type readOnly struct {
    m       map[any]any
    amended bool // dirty 里是否有 read 中不存在的 key
}
```

**Load 流程**：

```text
1. 无锁读取 read.m
   ├── 命中 → 直接返回（热路径，不加锁）
   └── 未命中
       ├── amended=false → 确认不存在，返回
       └── amended=true  → 加 mu，查 dirty，misses++
2. misses 足够大 → 把 dirty 提升为新的 read（promote），清空 dirty
```

**Store / Delete 流程**：

```text
key 已在 read 且 dirty 为空 → 更新 read（仍可能走锁，但路径较短）
否则 → 加 mu，写入 dirty，amended=true
```

可以把它理解成：**读走快照，写走缓冲区，miss 多了再合并快照**。

#### sync.Map vs RWMutex + map

两者都常用于读多写少，但机制不同，不能简单当成「sync.Map 是 RWMutex 的升级版」。

| | `RWMutex + map` | `sync.Map` |
|---|---|---|
| 读路径 | 每次 `RLock` → 查 map → `RUnlock` | 命中 `read` 时可**无锁**读 |
| 写路径 | `Lock` → 改 map → `Unlock` | 写 `dirty`，必要时 promote 合并 |
| 写是否阻塞读 | 写锁期间新读者等待，读写互斥 | 读者不被写锁直接挡住 |
| 写后可见性 | `Unlock` 后下一次读立即可见 | `Store` 后满足同步语义；新 key 可能让后续 `Load` 走加锁慢路径查 `dirty`，不是必须等 promote 才可见 |
| 类型 | `map[K]V`，编译期类型安全 | `any`，需类型断言 |
| Range / 多 key 原子更新 | 持锁遍历或一次锁住多步更新 | 语义更绕，不适合复杂不变量 |
| 代码复杂度 | 低，行为直观 | 高，需理解 read/dirty |
| 典型模式 | 通用读多写少缓存 | 一次写入、长期只读；`LoadOrStore` 懒初始化 |

**RWMutex + map 的特点**

```go
type Cache struct {
    mu sync.RWMutex
    m  map[string]string
}

func (c *Cache) Get(key string) (string, bool) {
    c.mu.RLock()
    v, ok := c.m[key]
    c.mu.RUnlock()
    return v, ok
}

func (c *Cache) Set(key, value string) {
    c.mu.Lock()
    c.m[key] = value
    c.mu.Unlock()
}
```

每次读都有 `RLock` 开销；一旦有写，写锁会等待现有读者释放，新读者也要等写完成。优点是语义清晰：**写完立刻对所有读者可见**，适合「读多但仍需较快读到最新写入」的缓存。

**sync.Map 的特点**

读已稳定在 `read` 里的 key 时，大量 goroutine 可以无锁并发读，这是它相对 `RWMutex + map` 的核心优势。代价是：

1. **新 key 会降低读路径性能**：新 key 先进入 `dirty` 并标记 `amended=true`，后续 `Load` 若在 `read` miss，会加锁查 `dirty`；多次 miss 后才 promote。问题主要是慢路径和语义复杂度，不是“必须等 promote 才能读到”。
2. **写操作变多后优势消失**：`amended=true` 时 Load 频繁加锁查 dirty，内部 bookkeeping 开销上升，可能不如 `RWMutex + map`。
3. **API 和类型不如普通 map 直接**：`any` + 断言，复杂逻辑不如自己包一层锁清晰。

**选型建议**

```text
优先 RWMutex + map：
- 读多写少，但写入后需要尽快被其他 goroutine 读到
- 需要 map[K]V、Range、或在锁内做多 key 原子更新
- 团队更熟悉、行为更可预测（默认首选）

考虑 sync.Map：
- key 集合稳定，写入后长期只读（配置、注册表、对象池）
- 极高并发读同一批热 key，profile 显示 RLock 成为瓶颈
- 典型模式是 LoadOrStore 懒初始化：每个 key 只构造一次，之后海量读

不要用 sync.Map：
- 计数器、LRU、频繁改同一 key
- 写操作虽少但仍在持续发生，导致 read 快照频繁失效
```

典型适合 `sync.Map` 的模式：`LoadOrStore(key, factory())` 做 per-key 懒初始化，之后大量并发读同一批 key。

#### 适用与不适用

**适用**：
- 键值对写入后长期只读（配置、注册表、对象缓存）
- 多个 goroutine 读同一批稳定 key
- `LoadOrStore` 懒初始化（每个 key 只构造一次）

**不适用**：
- 频繁更新/删除同一 key（计数器、LRU）
- 需要跨多个 key 的原子更新
- 需要强类型 map 且不想做类型断言
- 写入后需要立刻被所有 goroutine 读到

读写都较多、需要强类型、或需要在多步操作里维护复杂不变量时，用 `RWMutex + map`；读写都简单、争用不高时，用 `Mutex + map` 即可。

## 并发正确性：内存模型、atomic 与 race

### Go 内存模型：happens-before 讲的是什么？

并发程序里，“我先写了，另一个 goroutine 就一定能看到”不是天然成立的。Go 内存模型定义的是：哪些同步事件能建立 **happens-before** 关系，从而保证一个 goroutine 的写入对另一个 goroutine 可见。

常见同步边界：

| 同步动作 | 可见性保证 |
|----------|------------|
| `Mutex.Unlock` → 之后的 `Mutex.Lock` | 解锁前的写入对加锁后可见 |
| channel 发送 → 对应接收 | 发送前的写入对接收后可见 |
| `close(ch)` → 接收到关闭状态 | close 前的写入对观察到关闭的 goroutine 可见 |
| `sync.Once.Do(f)` 返回 | `f` 中完成的初始化对所有返回者可见 |
| atomic store/load/CAS | 通过原子操作建立受限的顺序与可见性 |

```go
var x int
done := make(chan struct{})

go func() {
    x = 42
    close(done)
}()

<-done
fmt.Println(x) // 一定能看到 42
```

如果没有同步，只靠 `time.Sleep`、调度顺序或“通常先执行”，就是 data race。

### `sync/atomic` 适合什么场景？

`sync/atomic` 适合维护单个变量或少量独立状态，例如计数器、开关、只读配置指针。它不适合维护多个字段之间的不变量。

```go
var enabled atomic.Bool
var total atomic.Int64

func record() {
    if enabled.Load() {
        total.Add(1)
    }
}
```

如果状态需要“检查 A 后修改 B，再更新 C”这种复合不变量，用锁更清晰：

```text
单变量状态：atomic
多字段不变量：Mutex / RWMutex
一次写入长期读取的配置：atomic.Value / atomic.Pointer[T]
需要阻塞等待条件：Cond / channel
```

`atomic.Value` 常用于热更新配置：写入整份不可变配置对象，读路径无锁拿快照。注意不要读出后再修改对象内部字段，否则“快照”就变成共享可变状态。

### race detector：怎么用，能发现什么？

Go 的竞态检测不是 `go vet -race`，而是：

```bash
go test -race ./...
go run -race main.go
go build -race ./cmd/server
```

它能发现运行过程中实际发生的 data race，因此测试覆盖不到的路径不会报告。典型模式：

```go
var n int

func bad() {
    var wg sync.WaitGroup
    for i := 0; i < 2; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            n++ // read-modify-write，不是原子操作
        }()
    }
    wg.Wait()
}
```

修复方式不是“让它大概率正确”，而是引入明确同步：`atomic.Int64.Add`、`Mutex`、channel 汇聚，或让每个 goroutine 使用局部变量后统一归并。

## 错误与控制流

### defer机制

#### defer 执行顺序⭐⭐⭐

**核心规则**：LIFO（后进先出），函数返回前按注册的逆序执行。

```go
func main() {
    fmt.Println("start")
    defer fmt.Println("first")
    defer fmt.Println("second")
    defer fmt.Println("third")
    fmt.Println("end")
}
// 输出：
// start
// end
// third
// second
// first
```

#### defer 与 return 的执行顺序⭐⭐⭐

**关键理解**：`return xxx` 不是原子操作，实际分三步：

```
1. 返回值赋值：result = xxx
2. 执行 defer 函数
3. RET 指令（真正返回）
```

```go
// 命名返回值 + defer 可以修改返回值
func f() (result int) {
    defer func() {
        result++  // 在 return 之后、RET 之前执行
    }()
    return 0
}
// 返回 1（不是 0！）
// 执行过程：result = 0 → defer: result++ → RET(result=1)

// 匿名返回值 + defer 不能修改返回值
func g() int {
    result := 0
    defer func() {
        result++  // 修改的是局部变量，不是返回值
    }()
    return result
}
// 返回 0
// 执行过程：_retval = result(0) → defer: result++ → RET(_retval=0)
```

#### defer 参数预计算⭐⭐

```go
func main() {
    x := 1
    defer fmt.Println(x) // x 在 defer 注册时就被求值为 1
    x = 2
}
// 输出 1（不是 2）

// 如果要捕获最新值，用闭包
func main() {
    x := 1
    defer func() {
        fmt.Println(x) // 闭包引用，取 defer 执行时的值
    }()
    x = 2
}
// 输出 2
```

#### defer 的底层实现演进

```
Go 1.12 及之前：堆上分配（heap-allocated defer）
- 每个 defer 在堆上分配一个 _defer 结构体，链到 goroutine 的 defer 链表
- 性能较差：涉及堆分配和 GC

Go 1.13：编译器优化（open-coded defer）
- 对于确定不会在循环中的 defer，编译器直接在栈上分配
- 性能提升约 30%

Go 1.14+：内联 defer
- 编译器将 defer 直接内联为函数末尾的代码调用
- 性能接近直接调用，几乎零开销
- 但循环中的 defer 仍然使用堆分配

性能对比：
直接调用：~0.5ns
Go 1.14 内联 defer：~1ns
Go 1.12 堆 defer：~35ns
```

#### defer 在 panic/recover 中的作用

```go
func safeFunc() {
    defer func() {
        if r := recover(); r != nil {
            fmt.Println("recovered:", r)
        }
    }()

    panic("something went wrong")
}

// recover 只能在 defer 函数中调用才有效
// 直接调用 recover()（不在 defer 中）永远返回 nil
```

> **重要**：`recover()` 只能捕获当前 goroutine 的 panic。子 goroutine 的 panic 无法被父 goroutine 的 recover 捕获，会导致整个进程崩溃。

### 错误处理

#### Go 的错误哲学⭐⭐

Go 选择显式错误处理（而非异常机制）的原因：
1. **错误是值**：`error` 是一个接口，可以携带丰富的上下文信息
2. **显式处理**：调用者必须决定如何处理错误，不会被隐藏
3. **没有隐藏的控制流**：不像 try/catch 那样可能跳过中间代码

```go
type error interface {
    Error() string
}
```

#### `error`、`panic`、`fatal error` 的区别

| 机制 | 来源 | 是否可恢复 | 典型场景 |
|------|------|------------|----------|
| `error` | 普通返回值 | 调用方决定 | IO 失败、参数非法、业务状态不满足 |
| `panic` | 程序主动触发或运行时 panic | 可被同 goroutine 的 `recover` 捕获 | 数组越界、空指针、内部不变量被破坏 |
| `fatal error` | runtime 直接 `throw` | **不可恢复** | 并发写 map、栈耗尽、运行时内部一致性错误 |

普通业务失败不要用 `panic`，应返回 `error`。`panic` 适合表达「代码继续执行已经没有意义」的异常状态；`fatal error` 比 `panic` 更底层，runtime 认为进程状态已不可信，会直接打印堆栈并退出，`recover` 捕获不到。

#### 错误包装与链式错误（Go 1.13+）⭐⭐⭐

```go
import (
    "errors"
    "fmt"
    "os"
)

// 包装错误（添加上下文信息）
func readConfig(path string) error {
    data, err := os.ReadFile(path)
    if err != nil {
        return fmt.Errorf("read config %s: %w", path, err) // %w 包装错误
    }
    // ...
    return nil
}

// errors.Is —— 判断错误链中是否包含特定错误
if errors.Is(err, os.ErrNotExist) {
    fmt.Println("file not found")
}

// errors.As —— 从错误链中提取特定类型的错误
var pathErr *os.PathError
if errors.As(err, &pathErr) {
    fmt.Println("path:", pathErr.Path)
}
```

**errors.Is vs == 的区别**：

```go
err := fmt.Errorf("outer: %w", os.ErrNotExist)

err == os.ErrNotExist        // false（err 是包装后的新错误）
errors.Is(err, os.ErrNotExist) // true（递归解包检查整条错误链）
```

#### 自定义错误类型

```go
// 业务错误码
type BizError struct {
    Code    int
    Message string
    Cause   error
}

func (e *BizError) Error() string {
    if e.Cause != nil {
        return fmt.Sprintf("[%d] %s: %v", e.Code, e.Message, e.Cause)
    }
    return fmt.Sprintf("[%d] %s", e.Code, e.Message)
}

func (e *BizError) Unwrap() error {
    return e.Cause // 支持 errors.Is / errors.As 解包
}

// 使用
var ErrUserNotFound = &BizError{Code: 404, Message: "user not found"}

func getUser(id int) (*User, error) {
    user, err := db.Find(id)
    if err != nil {
        return nil, &BizError{
            Code:    500,
            Message: "query user failed",
            Cause:   err,
        }
    }
    if user == nil {
        return nil, ErrUserNotFound
    }
    return user, nil
}
```

#### panic 与 recover 的运行机制

`panic` 发生后，当前 goroutine 会停止继续执行普通语句，按 LIFO 顺序执行已注册的 `defer`。如果某个 defer 中调用 `recover()` 且拿到了非 nil 值，panic 被截断，函数从 defer 之后的返回路径退出；如果没有 recover，panic 继续向上冒泡，最终导致进程崩溃。

```go
func parseConfig(raw string) (err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("parse config panic: %v", r)
        }
    }()

    mustParse(raw) // 内部 panic 会被当前 goroutine 的 defer 捕获
    return nil
}
```

`recover` 的限制：

1. 必须在 deferred function 中直接调用才有效。
2. 只能捕获**当前 goroutine** 的 panic，父 goroutine 捕获不到子 goroutine 的 panic。
3. 不能捕获 runtime fatal error，例如 `concurrent map writes`。

```go
func main() {
    defer func() {
        recover() // 捕获不到下面 goroutine 里的 panic
    }()

    go func() {
        panic("worker failed")
    }()

    time.Sleep(time.Second)
}
```

如果要保护子 goroutine，需要在 goroutine 入口处放 `defer recover`：

```go
go func() {
    defer func() {
        if r := recover(); r != nil {
            log.Printf("worker panic: %v", r)
        }
    }()

    runWorker()
}()
```

#### fatal error 与 runtime throw

`fatal error` 通常来自 runtime 的 `throw`，不是普通 `panic`。它表示运行时发现了无法安全恢复的状态，会直接终止进程。

```go
m := map[string]int{}

go func() { m["a"] = 1 }()
go func() { m["b"] = 2 }()

// fatal error: concurrent map writes
// recover 无法捕获
```

常见 fatal 场景：

- concurrent map writes
- concurrent map read and map write
- stack overflow
- runtime 内部一致性错误

工程上不要指望用 `recover` 兜住 fatal error；正确做法是避免触发，例如并发访问 map 时使用 `Mutex/RWMutex/sync.Map/分片 map`。

#### 使用原则

```text
优先返回 error：
✅ 业务规则不满足
✅ 参数校验失败
✅ 外部依赖错误（DB、RPC、文件、网络）

谨慎使用 panic：
✅ 程序内部不变量被破坏
✅ main/init 阶段无法继续启动
❌ 不要用 panic/recover 模拟 try/catch

谨慎使用 recover：
✅ HTTP/RPC 框架边界，避免单个请求打崩进程
✅ goroutine 顶层保护，记录日志并释放资源
❌ 不要吞掉 panic 后继续假装系统正常
```

## 内存管理与GC

### 逃逸分析：变量到底在栈上还是堆上？

Go 源码里没有 `new` 就一定上堆、局部变量就一定上栈的规则。编译器会做逃逸分析：如果一个值的生命周期可能超过当前栈帧，或编译器无法证明它只在当前函数内使用，就会把它分配到堆上。

常见逃逸场景：

| 场景 | 为什么可能逃逸 |
|------|----------------|
| 返回局部变量指针 | 调用方仍要使用该对象 |
| 闭包捕获变量 | 闭包生命周期可能超过当前函数 |
| 转成 `interface{}` / `any` | 动态派发让编译器更难证明具体生命周期 |
| 向 channel 发送指针或对象 | 接收方可能在另一个 goroutine 中稍后使用 |
| 大对象或变长对象 | 栈空间/复制成本不合适 |

```go
func escape() *int {
    x := 42
    return &x // x 逃逸到堆
}

func noEscape() int {
    x := 42
    return x // x 通常可在栈上
}
```

查看逃逸分析：

```bash
go build -gcflags='-m -m' ./...
```

优化时不要机械地“消灭所有逃逸”。堆分配是否值得优化，要看 pprof 中的分配热点、GC 压力和代码可读性。为了少一次分配把代码写成难维护的 unsafe，通常不划算。

### Go 内存分配器：mcache、mcentral、mheap

Go 分配器的目标是让小对象分配尽量走无锁或低锁路径，减少每次分配都向操作系统申请内存的成本。可以把它看成三级仓库：

```text
G 申请对象
  → 当前 P 的 mcache：本地小对象缓存，最快
  → mcentral：某个 size class 的 span 池，需要加锁协调
  → mheap：全局堆，必要时向 OS 申请/归还页
```

关键概念：

| 概念 | 作用 |
|------|------|
| size class | 小对象按大小分档，减少碎片 |
| span | 一组连续页，被切成同一 size class 的槽位 |
| mcache | 每个 P 的本地缓存，小对象分配热路径 |
| mcentral | 给各个 mcache 补充 span |
| mheap | 管理全局页和大对象 |
| tiny allocator | 把多个无指针极小对象合并到一块内存里 |

分配路径大致是：

```text
小对象：size class → P.mcache 有空槽 → 直接分配
中等对象：mcache 不足 → mcentral 拿 span → 切槽
大对象：直接走 mheap，按页分配
```

这也是为什么高频小对象分配会影响 GC：对象越多，标记和扫描成本越高；如果对象包含指针，GC 还要继续沿引用图扫描。

### GC：三色标记、写屏障与 STW

Go 使用并发标记清扫 GC。核心目标不是“完全没有 STW”，而是把大部分标记工作和用户 goroutine 并发执行，把 STW 控制在较短时间内。

三色标记用于描述对象状态：

| 颜色 | 含义 |
|------|------|
| 白色 | 尚未确认可达，最终可能被回收 |
| 灰色 | 已发现，但它引用的对象还没扫描完 |
| 黑色 | 已扫描完成，它引用的对象也已被处理 |

并发标记时，业务代码仍在修改指针关系，可能出现“黑色对象指向白色对象”的遗漏风险。写屏障就是在指针写入时插入一小段运行时代码，维护 GC 标记不变式。现代 Go 使用混合写屏障，结合插入/删除屏障思路，减少重新扫描栈带来的 STW 压力。

一次 GC 周期可以粗略理解为：

```text
短 STW：开启写屏障，扫描根集合准备开始
并发标记：GC worker 与业务 goroutine 并行标记对象图
标记辅助：分配太快的 goroutine 帮忙做一部分标记工作
短 STW：标记终止，关闭写屏障，完成收尾
并发清扫：回收不可达对象占用的 span
```

### GOGC、GOMEMLIMIT 与 pacer

`GOGC` 控制下一次 GC 的目标堆增长比例。默认 `GOGC=100`，含义可以近似理解为：如果上次 GC 后存活堆是 1GB，下一轮目标堆大约是 2GB。

```bash
GOGC=50   # 更频繁 GC，更低内存，更高 CPU
GOGC=200  # 更少 GC，更高内存，更低 GC CPU
GOGC=off  # 通常不建议，除非极特殊短生命周期任务
```

Go 1.19 引入 `GOMEMLIMIT`，用于给运行时一个软内存上限，容器环境尤其重要：

```bash
GOMEMLIMIT=3GiB ./server
```

它不是硬性 cgroup limit，也不能阻止所有内存增长；它告诉 GC pacer：在接近这个目标时更积极地回收，避免堆无限向容器上限逼近。实践中常把它设置为容器 limit 的 70%~90%，给非 Go 堆内存、栈、mmap、cgo、页缓存留余量。

### 如何读 gctrace？

开启：

```bash
GODEBUG=gctrace=1 ./server
```

示例：

```text
gc 12 @10.235s 2%: 0.04+12+0.02 ms clock, 0.3+45/80/0+0.1 ms cpu, 256->300->180 MB, 360 MB goal, 8 P
```

常看字段：

| 字段 | 含义 | 关注点 |
|------|------|--------|
| `0.04+12+0.02 ms clock` | STW 开始 + 并发标记 + STW 结束耗时 | 两段 STW 是否异常 |
| `256->300->180 MB` | GC 前堆、GC 结束堆、存活堆 | 存活堆是否持续上涨 |
| `360 MB goal` | 下一轮目标堆 | 是否被 GOMEMLIMIT 压低 |
| `2%` | GC CPU 占比 | GC 是否消耗过高 |

调优顺序：先用 pprof 找分配热点，再判断是减少对象数量、复用 buffer、优化数据结构，还是调整 `GOGC/GOMEMLIMIT`。不要只看到 GC 频繁就盲目调大 `GOGC`，那可能只是把 CPU 问题换成内存问题。

// 超时中间件：只把带 deadline 的 context 注入请求链路。
// 不要在新 goroutine 里调用 c.Next()：gin.Context 不是为并发写设计的，
// 超时后的真正中断要依赖下游 handler/DB/RPC 主动监听 ctx.Done()。
func TimeoutMiddleware(timeout time.Duration) gin.HandlerFunc {
    return func(c *gin.Context) {
        ctx, cancel := context.WithTimeout(c.Request.Context(), timeout)
        defer cancel()

        c.Request = c.Request.WithContext(ctx)
        c.Next()

        if ctx.Err() == context.DeadlineExceeded && !c.Writer.Written() {
            c.AbortWithStatusJSON(504, gin.H{"error": "timeout"})
        }
    }
}

// 使用：handler 内部的 DB/RPC 调用必须接收 c.Request.Context()，否则只能设置 deadline，不能强行杀掉正在执行的业务逻辑。

    ticker := time.NewTicker(10 * time.Second)

    for {
        select {
        case <-ticker.C:
            if err := cm.LoadConfig(ctx); err != nil {
                log.Printf("load config failed: %v", err)
            }
        case <-ctx.Done():
            log.Println("config watcher stopped")
            return
        }
    }
}

### 金融支付：分布式锁

```go
import "github.com/go-redis/redis/v8"

type RedisLock struct {
    client *redis.Client
    key    string
    value  string
    ttl    time.Duration
}

func NewRedisLock(client *redis.Client, key string, ttl time.Duration) *RedisLock {
    return &RedisLock{
        client: client,
        key:    key,
        value:  uuid.New().String(),
        ttl:    ttl,
    }
}

func (l *RedisLock) Lock(ctx context.Context) error {
    // SET key value NX EX ttl
    ok, err := l.client.SetNX(ctx, l.key, l.value, l.ttl).Result()
    if err != nil {
        return err
    }
    if !ok {
        return errors.New("lock failed")
    }
    return nil
}

func (l *RedisLock) Unlock(ctx context.Context) error {
    // Lua 脚本：只删除自己持有的锁
    script := `
        if redis.call("get", KEYS[1]) == ARGV[1] then
            return redis.call("del", KEYS[1])
        else
            return 0
        end
    `
    return l.client.Eval(ctx, script, []string{l.key}, l.value).Err()
}

// 使用
func deductBalance(ctx context.Context, userID string, amount int) error {
    lock := NewRedisLock(redisClient, fmt.Sprintf("lock:user:%s", userID), 5*time.Second)
    
    if err := lock.Lock(ctx); err != nil {
        return err
    }
    defer lock.Unlock(ctx)
    
    // 查询余额
    balance, err := db.GetBalance(ctx, userID)
    if err != nil {
        return err
    }
    
    // 扣款
    if balance < amount {
        return errors.New("insufficient balance")
    }
    
    return db.UpdateBalance(ctx, userID, balance-amount)
}
```

## 面试题自查

### 初级高频速刷

**1. `new` 和 `make` 的区别是什么？分别用于哪些类型？**

`new` 是通用内存分配，返回 `*T`，对象内容是零值；`make` 只用于 `slice`、`map`、`channel`，返回初始化后的值本身而不是指针。面试里最容易被追问的是：`map` 和 `channel` 只 `new` 不 `make` 不能直接正常使用。追问 slice 时还会考：`make([]T, n)` 预填 n 个零值适合索引写入，`make([]T, 0, n)` 从空开始适合 append，二者不可混用。

**2. 数组和切片的区别是什么？切片作为参数传递时到底传了什么？**

数组长度是类型的一部分，赋值和传参都会复制整个数组；切片是一个三元组描述符，包含底层数组指针、长度和容量。切片传参时复制的是这个描述符，不是整个底层数组，所以多个切片可能共享同一块底层内存。数组是 comparable 的、可作 map key；slice 不行。

**3. 值接收者和指针接收者怎么选？哪些情况下必须用指针接收者？**

小对象、只读方法可以用值接收者；需要修改状态、避免大对象拷贝、结构体里带锁时应使用指针接收者。尤其是带 `sync.Mutex` 的类型，复制后会破坏并发语义，这是典型的“必须用指针接收者”的场景。

**4. `nil` slice、空 slice、`nil` map、`nil` channel 分别有什么行为差异？**

`nil slice` 和空 slice 都能 `len` 和 `append`，但是否为 `nil` 不同；`nil map` 能读不能写；`nil channel` 读写都会永久阻塞。资深面试官常用这个问题检查你是否真的理解 Go 运行时对象，而不是只会语法。

**5. `panic`、`recover`、`error` 三者分别该在什么场景下使用？**

业务失败、参数校验失败、外部依赖错误都应该优先返回 `error`；程序内部不变量被破坏、出现绝不该发生的状态时才考虑 `panic`；`recover` 只能在同一 goroutine 的 defer 中捕获 panic，常用于 goroutine 顶层或 HTTP 中间件兜底。`fatal error` 来自 runtime throw，例如 concurrent map writes，不能被 recover 捕获。

### 中级高频进阶

**6. `close(channel)` 之后，读和写分别会发生什么？**

读已关闭 channel 会立即返回元素类型零值，且 `ok=false`；写已关闭 channel 会直接 panic。这类题在面试里经常被用来追问你是否真的理解 channel 生命周期，而不是只会 `for range ch`。

**7. Go 里接口值由什么组成？为什么“带类型的 nil”不等于 `nil`？**

接口值本质上由动态类型信息和动态值两部分组成。把一个 `(*MyErr)(nil)` 赋给 `error` 后，动态类型不为空、动态值为空，所以整个接口值不等于 `nil`。这也是 Go 面试里最经典的陷阱题之一。

**8. 为什么 `range` 遍历 `slice`、`map`、`channel` 的行为不一样？**

遍历 `slice/array` 时本质是在按索引取值；遍历 `map` 时顺序不保证稳定；遍历 `channel` 时会持续接收直到 channel 被关闭。资深面试官常继续追问：为什么遍历 `map` 不能依赖顺序，以及遍历 channel 为什么必须考虑关闭时机。

**9. `:=` 和 `=` 有什么区别？循环里用错会导致什么问题？**

`:=` 是短变量声明，在当前块创建新变量；若与外层同名则遮蔽外层。`=` 是给已声明变量赋值。循环体内若用 `head, tail := f(head, tail)` 而 `head` 本是 `for` 的循环变量，实际更新的是内层新变量，外层条件永远不变，典型表现是死循环或 TLE。应改用 `head, tail = f(head, tail)`。

**10. 递归闭包为什么必须先 `var f func(...)` 再赋值？**

`:=` 定义的函数字面量，其名字在赋值完成前不在自身函数体作用域内，函数体内调用自身会编译报错 `undefined`。先声明变量再赋值，闭包捕获的是已存在的变量，递归才能编译通过。替代方案是提取为命名函数，或改用迭代 + 栈。

**11. `container/heap` 和标准库堆类型有什么区别？`Pop()` 为什么要删 slice 末尾？**

Go 没有内置堆，`container/heap` 是操作 `heap.Interface` 的算法包。用户用 slice 存数据并实现 `Len/Less/Swap/Push/Pop`。`heap.Pop` 内部会先把堆顶换到末尾再 `fixDown`，然后调用用户的 `Pop()` 删除末尾——所以用户的 `Pop` 不是弹 `h[0]`，而是 `old[:n-1]` 截断末尾。`Push`/`Pop` 必须指针接收者。

### 深入问答

#### Q1: 请完整描述 GMP 模型中 G、M、P 各自的角色，以及为什么需要引入 P？

G 是 Goroutine（用户态协程），代表一个待执行的任务，保存了函数入口、参数和栈；M 是 Machine（OS线程），是真正执行代码的载体；P 是 Processor（逻辑处理器），持有本地运行队列和内存缓存 mcache，M 必须绑定 P 才能执行 G。引入 P 的核心原因是：如果没有 P，所有 M 共享一个全局队列需要加锁，高并发下锁竞争严重。P 提供了本地无锁队列（容量256），大部分情况下 M 从自己的 P 本地队列取 G，只在本地队列空时才访问全局队列或偷取其他 P 的任务，大幅减少了锁竞争。

#### Q2: Go 1.14 之前和之后的抢占调度有什么区别？为什么选用 SIGURG 信号？

Go 1.14 之前是**协作式抢占**，依赖编译器在函数入口插入栈检查代码，只有函数调用时才有机会被抢占。缺陷是纯计算的死循环（没有函数调用）无法被抢占，会导致其他 goroutine 饿死。Go 1.14+ 引入**基于信号的异步抢占**：Sysmon 发现 G 运行超过 10ms 后，向 G 所在的 M 发送 SIGURG 信号，M 收到信号后保存 G 的寄存器状态，将 G 设为 `_Grunnable` 放回队列，然后执行下一个 G。选用 SIGURG 是因为该信号几乎没有其他用途（原本用于 TCP 带外数据），不会与用户程序的信号处理冲突。

#### Q3: Work Stealing 机制是如何工作的？为什么偷一半而不是偷一个？

当 P 的本地队列为空时，M 会随机选择另一个 P，偷取其本地队列中一半的 G 到自己的队列。偷一半而非一个的原因是：偷取操作本身有成本（需要 CAS 原子操作），偷一半可以减少偷取次数，让窃取者有足够的任务执行一段时间，避免频繁偷取带来的开销。随机选择目标 P 则避免了总偷同一个 P 造成的热点竞争。

#### Q4: slice 的底层结构是什么？append 操作可能导致什么问题？`make([]T, n)` 和 `make([]T, 0, n)` 怎么选？

slice 底层是一个包含三个字段的结构体：`array`（指向底层数组的指针）、`len`（当前长度）、`cap`（容量）。传参时复制的是 header，不是底层数组，所以 `s[i]=x` 会影响 caller，但函数内 `s=append(s,x)` 默认只改 header 副本——要让 caller 也变长，需 `return`、`*[]T` 或指针接收者。append 的关键问题：1）cap 不够时分配新底层数组，原共享 slice 不再共享；2）cap 够用时在原数组追加，共享 slice 可能互相覆盖。`make([]T, n)` 创建 n 个零值元素，适合 `arr[i]=v` 索引填充；`make([]T, 0, n)` 创建空 slice 并预分配容量，适合 append 构建——混用「make 带 len + append」会在前面留下零值槽位。Go 1.18+ 扩容：容量 <256 翻倍，≥256 每次约增长 25%+192。

#### Q5: map 为什么不是并发安全的？哪些类型能作为 map 的 key？

Go 的 map 底层是哈希表（hmap），出于性能考虑没有内置锁。并发写 map 时，运行时检测到并发写入会直接 `throw("concurrent map writes")`，这是 fatal error，不是普通 panic，不能 recover；仅有并发读、没有并发写时是安全的。解决方案：`sync.Mutex` 用于普通共享状态，`sync.RWMutex` 用于读多写少，`sync.Map` 用于 key 相对稳定、一次写多次读的缓存/注册表，分片 map 用于高并发写但不适合跨 shard 原子更新。key 必须是 comparable 类型：基本类型、指针、channel、interface、struct（字段均可比较）、**数组**等；**slice、map、func 不可比较**，不能作 key。固定大小数组如 `[26]int` 可表达字符频次签名，既满足 comparable 又便于 O(k) 统计。`for range m` 遍历顺序不稳定且会被随机化，不能依赖。

#### Q6: interface 的底层实现 eface 和 iface 有什么区别？interface 的 nil 判断有什么陷阱？

空接口 `interface{}` 底层是 `eface`，包含 `_type`（类型信息）和 `data`（数据指针）两个字段。非空接口底层是 `iface`，包含 `tab`（指向 itab，存储接口类型+实际类型+方法地址表）和 `data`。nil 陷阱：当一个具体类型的 nil 指针赋值给 interface 变量时，interface 的 `tab`/`_type` 字段不为 nil（记录了类型信息），只有 `data` 为 nil，因此 `interface != nil`。正确做法是直接返回 `nil` 而非带类型的 nil 指针。

#### Q7: channel 的底层数据结构是什么？发送和接收数据的完整流程是怎样的？

channel 底层是 `hchan` 结构体，核心字段：环形缓冲区（`buf`）、发送/接收索引（`sendx`/`recvx`）、等待队列（`sendq`/`recvq`，双向链表存储阻塞的 goroutine）、互斥锁（`lock`）。发送流程：加锁 → 如果 recvq 有等待的接收者，直接将数据拷贝给它（唤醒该 goroutine）→ 否则放入环形缓冲区 → 缓冲区满则将当前 goroutine 封装为 sudog 挂入 sendq 等待 → 解锁。接收流程类似但方向相反。

#### Q8: context 的底层有几种实现？WithValue 查找的时间复杂度是多少？为什么不要把 context 存储在 struct 中？

context 有四种底层实现：`emptyCtx`（根节点，Background/TODO）、`cancelCtx`（可取消）、`timerCtx`（带超时）、`valueCtx`（携带值）。WithValue 查找是 O(n)，因为 valueCtx 每次只存一个 key-value 对，查找时沿着 Context 链（子→父）逐层比较。不要存储 context 的原因：1）生命周期不匹配（context 是请求级，struct 可能是应用级）；2）timerCtx 内部有 timer goroutine，长期存储导致泄漏；3）多 goroutine 共享同一 context，任何一方 cancel 影响所有方。

#### Q9: defer 的执行顺序是什么？defer 与 return 的关系是怎样的？能否用 defer 修改函数返回值？

defer 按 LIFO（后进先出）顺序执行。`return xxx` 实际分三步：① 返回值赋值 `result = xxx` → ② 执行 defer 函数 → ③ RET 指令。因此命名返回值 + defer 可以修改返回值（defer 中修改的是已命名的返回值变量，在 RET 之前生效），而匿名返回值 + defer 不能（defer 修改的是局部变量，返回值已经被拷贝到返回寄存器了）。另外 defer 的参数在注册时就已求值，如需捕获最新值应使用闭包。

#### Q10: Go 的 GC 使用什么算法？什么是写屏障？GC 的触发条件有哪些？

Go 使用并发标记清扫 GC，核心是三色标记 + 写屏障 + pacer。白色表示尚未确认可达，灰色表示已发现但引用未扫描完，黑色表示自身和引用都已扫描。并发标记时业务 goroutine 仍在改指针，如果没有写屏障，可能出现黑色对象指向白色对象导致误回收；现代 Go 使用混合写屏障来维持标记不变式并减少 STW。一次 GC 包含短 STW 开启屏障、并发标记、标记辅助、短 STW 标记终止、并发清扫。触发条件包括堆增长达到 pacer 根据 `GOGC` 计算的目标、接近 `GOMEMLIMIT` 时更积极回收、长时间未 GC 的 sysmon 触发，以及手动 `runtime.GC()`。追问时要能说明：`GOGC` 控制堆增长比例，`GOMEMLIMIT` 是软内存目标，二者一个偏 CPU/内存权衡，一个偏容器内存上限保护。

#### Q11: 什么是逃逸分析？有哪些常见的逃逸场景？如何查看变量是否逃逸？

逃逸分析是编译器判断对象生命周期是否可能超过当前栈帧的静态分析。常见逃逸包括：返回局部变量指针、闭包捕获变量、赋给 `interface{}`/`any`、向 channel 发送给其他 goroutine、对象过大或动态大小无法安全放栈。查看方式建议用 `go build -gcflags='-m -m' ./...`，第二个 `-m` 会给出更详细原因。优化时不要追求“零逃逸”，要结合 pprof 看分配热点；有些逃逸换来更清晰的 API 是值得的。真正要优化的通常是高频路径上的临时对象、可复用 buffer、无谓 interface 装箱和闭包捕获。

#### Q12: sync.Pool 的作用是什么？对象什么时候会被回收？适合什么场景？

sync.Pool 是对象复用池，用于缓存临时对象，减少频繁的堆分配和 GC 压力。核心方法：`Get()` 获取对象（池空则调用 `New` 创建）、`Put()` 归还对象。Pool 中的对象不保证持久存在——**每次 GC 时，Pool 中的对象可能被全部清除**。因此 Pool 只适合缓存**临时、无状态**的对象（如 bytes.Buffer、临时结构体），使用前必须重置对象状态。不适合缓存需要持久化的连接、文件句柄等资源。

#### Q13: Go 协程和 Python 协程有什么本质区别？什么是"函数颜色"问题？

核心区别有三：① **调度方式**：Go 是抢占式（运行时自动调度），Python asyncio 是协作式（必须遇到 await 才让出）；② **并行能力**：Go goroutine 可真正并行（多 M 绑定多核 CPU），Python 受 GIL 限制只能并发不能并行；③ **栈模型**：Go 是有栈协程（每个 G 独立栈，可在任意位置挂起），Python 是无栈协程（状态机，只能在 await 点挂起）。"函数颜色"问题是 Python 特有的：如果底层函数改成 async，整个调用链上的所有函数都要标记为 async（传染性），Go 没有这个问题——所有函数都是"同一颜色"。

#### Q14: 如何发现和定位 Goroutine 泄漏？有哪些常见原因？

定位方法：① `runtime.NumGoroutine()` 监控 goroutine 数量变化；② `pprof.Lookup("goroutine").WriteTo(os.Stdout, 1)` 导出堆栈；③ HTTP pprof 端点 `GET /debug/pprof/goroutine?debug=1` 查看详细堆栈。常见原因：① channel 永久阻塞（发送/接收无对端）；② 无限循环缺少退出条件；③ context 未取消导致 goroutine 一直等待；④ 第三方库内部 goroutine 未正确关闭。修复手段：用 context 超时/取消控制 goroutine 生命周期，用 done channel 通知退出，确保 channel 在不需要时能被关闭。

#### Q15: errors.Is 和 errors.As 有什么区别？为什么 Go 1.13 之后推荐用 %w 包装错误？

`errors.Is(err, target)` 沿着错误链递归解包，判断链中是否存在与 target **值相等**的错误，替代了 `==` 比较（`==` 只能比较最外层，无法穿透 wrap 层）。`errors.As(err, &target)` 沿着错误链递归解包，提取链中第一个能**类型断言**为 target 类型的错误。`%w` 包装错误的意义：保留原始错误信息的同时添加上下文（如"read config /etc/app.conf: file not found"），调用方可以通过 errors.Is/As 检查根因，又不失去上层的描述信息。这比 Go 1.13 之前用 `%v` 丢失错误链要好得多。

#### Q16: GOMAXPROCS 控制的是什么？设置过大或过小有什么影响？在容器环境下有什么注意事项？

GOMAXPROCS 控制 P 的数量，即最多有多少个 Goroutine 可以**同时并行**执行（≠ M 的数量，≠ G 的数量）。设置过小：CPU 利用率不足，吞吐量受限。设置过大：增加调度开销和上下文切换次数，对 CPU 密集型任务反而降低性能。默认值等于 `runtime.NumCPU()`。容器环境注意：Go 默认读到的是**宿主机**的 CPU 核心数而非 cgroup 限制的核心数，可能导致 GOMAXPROCS 远大于容器实际可用核心，建议使用 `uber-go/automaxprocs` 库自动适配容器的 CPU 限制。

#### Q17: select 语句的执行机制是什么？所有 case 都不满足时会怎样？nil channel 在 select 中有什么作用？

select 会把多个 channel 收发交给运行时仲裁：可立即执行的 case 才会被选中，多个 case 同时就绪时伪随机选择，不保证源码顺序；没有就绪 case 且有 `default` 时走 default，否则当前 goroutine park。阻塞时，运行时会把当前 G 通过 `sudog` 挂到对应 channel 的 `sendq/recvq`，匹配成功后再 `goready` 唤醒。nil channel 的收发永远不会就绪，因此可用于动态禁用某个分支。追问点：`default` 放在 tight loop 中会变成忙轮询，可能打满 CPU，通常要配合 timer、backoff 或阻塞等待。

#### Q18: sync.Once 的实现原理是什么？如果 Once.Do 中的函数 panic 了，再次调用 Do 会重新执行吗？

sync.Once 底层使用 `done uint32` 原子标记 + `Mutex` 互斥锁实现。第一次调用 `Do(f)` 时获取锁、执行 f、将 done 标记为 1；后续调用先用 `atomic.LoadUint32` 检查 done 标记，为 1 直接返回（快速路径，无锁）。如果 f 执行过程中 panic 了，done **仍然被标记为已完成**，后续再调用 Do **不会重新执行** f。这意味着如果初始化函数可能 panic，需要在函数内部自行处理恢复逻辑，或使用其他机制保证初始化成功。

#### Q19: Gin 框架的中间件机制是怎样的？c.Next() 和 c.Abort() 分别做了什么？

Gin 的中间件是洋葱模型：上游中间件执行前半段，调用 `c.Next()` 进入下游，所有下游返回后再继续执行 `c.Next()` 之后的逻辑。`c.Abort()` 会阻止后续 handler 继续执行，但不会像异常一样跳出当前函数，当前中间件后面的代码仍会运行。超时中间件要特别注意：不要为了“抢超时”在新 goroutine 里调用 `c.Next()`，`gin.Context` 不是并发写安全的；正确方向是把 deadline 写入 `Request.Context()`，让下游 DB/RPC/业务逻辑主动监听 `ctx.Done()`，边界层只负责返回超时响应和记录日志。

#### Q20: Go 的 pprof 工具能分析哪些维度的性能？如何在线上环境安全地使用？

pprof 支持多个维度：① **CPU Profile**（函数 CPU 耗时占比）；② **Heap Profile**（堆内存分配热点）；③ **Goroutine Profile**（goroutine 数量和堆栈）；④ **Block Profile**（channel/锁阻塞时间）；⑤ **Mutex Profile**（锁竞争耗时）。线上安全使用方式：通过 `import _ "net/http/pprof"` 注册 HTTP 端点，但要**限制访问**（绑定内部端口、加认证中间件，不要暴露到公网）。采集时指定 `seconds=30` 限制采样时间，避免长时间 profiling 影响性能。火焰图（`go tool pprof -http=:8080`）是最直观的分析方式。

#### Q21: Go 中 `%` 对负数取模的结果是什么？环形下标如何处理？（附录语法题）

Go 的 `%` 运算结果符号与被除数相同，因此 `-1 % 4 == -1`（不是 3）。环形数组/队列左移时需写 `(i - 1 + n) % n`，先加 n 再取模；右移则 `(i + 1) % n` 即可。

#### Q22: 为什么 `g := func() { g() }` 非法，而 `var f func(); f = func() { f() }` 合法？（附录语法题）

`:=` 声明的函数字面量，其标识符在赋值完成前不在自身函数体作用域内，递归自引用编译失败。先 `var f func()` 声明变量，再赋值，闭包捕获的是外层已存在的变量 `f`，因此合法。工程上也可直接提取为命名函数避免此模式。

#### Q23: `range` 遍历 slice 时能否原地修改元素？与 splice 删除有何区别？（附录语法题）

可以：`s[i] = v` 或通过写指针 `s[write] = v` 原地覆盖是安全的，前提是写指针不超过读指针（读下标 ≥ 写下标）。`for _, v := range s` 的 `v` 是拷贝，不影响写入 `s[i]`。但若用 `append(s[:i], s[i+1:]...)` 边遍历边删除，元素前移会导致 `range` 跳过元素——这是算法层面的坑，不是 Go 语法限制。

#### Q24: Go 的 `container/heap` 怎么用？Top K 为什么找「最大」却用小根堆？（附录算法题）

Go 用 slice + `heap.Interface` 实现优先队列，用户 `Pop()` 只删 slice 末尾；API 细节见 Go 语言深入文档。**算法原理**：Top K 用 size=k 堆当守门员——找最大 K 个用小根堆、找最小 K 个用大根堆，见 [算法与数据结构 §5.4 Top K](../算法与数据结构/01-算法与数据结构.md#应用1top-k-问题-)。

#### Q25: `T` 和 `*T` 的方法集有什么区别？为什么有时值类型没有实现接口？

方法集规则是：`T` 的方法集只包含接收者为 `T` 的方法；`*T` 的方法集同时包含接收者为 `T` 和 `*T` 的方法。如果接口要求的方法是指针接收者实现的，那么只有 `*T` 实现接口，`T` 没有实现。追问点：如果结构体包含 `sync.Mutex` 或内部状态需要修改，即使方法当前看起来只读，也通常应统一使用指针接收者，避免复制锁或复制大对象。

#### Q26: Go 泛型适合解决什么问题？约束里的 `~T` 和 `comparable` 分别是什么意思？

泛型适合容器、集合、算法模板和类型安全工具函数，避免大量 `any` + 类型断言。约束定义类型参数能做哪些操作；`~int` 表示底层类型为 `int` 的自定义类型也匹配；`comparable` 表示可用 `==/!=` 比较，因此可作为 map key 的泛型约束。泛型不替代接口：接口描述行为，泛型描述一组可替换的具体类型。性能是否更好要 benchmark，不要默认认为泛型一定比接口快。

#### Q27: Go 内存模型里的 happens-before 是什么？channel、Mutex、Once 分别提供什么同步保证？

happens-before 描述一个 goroutine 的写入何时对另一个 goroutine 可见。`Mutex.Unlock` happens-before 后续成功 `Lock`；channel 发送 happens-before 对应接收；`close(ch)` happens-before 接收到关闭状态；`sync.Once.Do` 中函数完成 happens-before 所有 `Do` 返回。没有这些同步，只靠 sleep 或调度顺序，就是 data race。

#### Q28: `sync/atomic` 和 Mutex 怎么选？`atomic.Value` 常见用途是什么？

atomic 适合单变量计数、开关、指针替换等简单状态；Mutex 适合多字段不变量和复合操作。`atomic.Value`/`atomic.Pointer[T]` 常用于热更新只读配置：写入一整份不可变快照，读路径无锁读取。注意读出后的对象不能再被原地修改，否则会把快照变成共享可变状态。

#### Q29: race detector 怎么用？它能保证程序没有并发 bug 吗？

命令是 `go test -race ./...`、`go run -race main.go`、`go build -race`，不是 `go vet -race`。race detector 能发现测试运行中实际发生的数据竞争，但不能证明没有覆盖到的路径没有 race；它也不能替代死锁、泄漏、原子性不变量检查。实践上应把 `-race` 放进 CI 的核心测试集，同时用 pprof/goroutine dump 观察泄漏和阻塞。

#### Q30: `GOGC` 和 `GOMEMLIMIT` 分别控制什么？容器里如何设置？

`GOGC` 控制下一轮 GC 的堆增长比例，值越小 GC 越频繁、内存越低、CPU 越高；值越大则相反。`GOMEMLIMIT` 是 Go 1.19+ 的软内存目标，告诉 runtime 接近该目标时更积极回收，适合容器环境。一般把 `GOMEMLIMIT` 设为容器 limit 的 70%~90%，给栈、非 Go 堆、mmap、cgo 和系统开销留余量；再用 pprof/gctrace 观察是否需要调整 `GOGC`。

#### Q31: Go benchmark 怎么写才可信？`b.N`、`ResetTimer`、`ReportAllocs` 分别有什么用？

benchmark 循环必须围绕被测代码跑 `b.N` 次，测试框架会自动调整 `b.N` 直到结果稳定。准备数据、打开文件、初始化连接等不属于被测逻辑，应在循环前完成并调用 `b.ResetTimer()`。`b.ReportAllocs()` 可以报告每次操作的分配次数和字节数，是优化 GC 压力时的重要指标。常用命令是 `go test -bench=. -benchmem ./...`。

### 开放式设计题

**D1：如果让你设计一个支持百万连接的 Go 长连接网关，你会怎么考虑？**

**参考思路**：
- 连接管理：epoll/kqueue + goroutine-per-connection vs netpoll模型（gnet/nbio），百万连接时 goroutine 初始栈约 2KB，数量级上就是 GB 级内存，还要考虑栈增长、连接缓冲和 GC 扫描成本
- 内存优化：连接空闲时回收goroutine（reactor模式）、sync.Pool复用Buffer、减少GC压力
- 协议设计：自定义二进制协议 vs WebSocket、心跳保活、断线重连
- 水平扩展：一致性哈希分配连接、跨节点消息路由（Redis PubSub/Kafka）
- 可观测性：连接数/消息吞吐/延迟P99监控、优雅关闭（先停止新连接、等待存量消息处理完）
- 关键取舍：goroutine-per-conn简单但内存多 vs reactor模式省内存但复杂，根据业务消息频率决定

**D2：设计一个 Go 实现的分布式任务调度系统（类似简化版 Airflow），核心需要考虑什么？**

**参考思路**：
- DAG任务编排：任务依赖关系建模、拓扑排序执行

- 任务分发：Worker注册发现、负载均衡分配、任务幂等执行
- 容错：Worker宕机后任务重新调度、超时检测、重试策略（指数退避+最大次数）
- 状态管理：任务状态机（Pending→Running→Success/Failed）、持久化（MySQL+Redis）
- 可扩展性：插件式Executor、多租户隔离、资源配额
