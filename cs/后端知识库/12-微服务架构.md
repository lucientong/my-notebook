## 1. 服务拆分与迁移

### 1.1 单体 vs 微服务：差在哪里？

把单体想成「一栋大楼共用一套水电」；微服务是「每栋楼自己装水电表」。好处是扩容、故障、技术栈可以按楼独立演进；代价是楼与楼之间要修路（网络）、对账（一致性）、统一物业（平台治理）。

**单体架构**：

```
┌─────────────────────────────────┐
│           单体应用              │
│  ┌──────┬──────┬──────┬──────┐ │
│  │ 用户 │ 订单 │ 商品 │ 支付 │ │
│  └──────┴──────┴──────┴──────┘ │
│              ↓                  │
│           单一数据库            │
└─────────────────────────────────┘

优点：开发/部署/本地调试简单
缺点：整体扩展、整体发版、技术栈锁定、故障面大
```

**微服务架构（拓扑自上而下）**：

```
              外部请求
                 ↓
            API 网关（统一入口）
                 ↓
    ┌────────┬────────┬────────┬────────┐
    │用户服务│订单服务│商品服务│支付服务│
    │  DB    │  DB    │  DB    │  DB    │
    └────────┴────────┴────────┴────────┘

优点：独立部署、独立扩展、技术异构、故障隔离
缺点：运维复杂、分布式事务、网络开销、排障链路长
```

> 常见画反：把「外部请求 → 网关 → 服务」画成「服务在上、请求在下」。记法：**流量从上往下走，网关永远在服务前面。**

---

### 1.2 拆分原则：先边界，再代码

**按业务能力拆，不按技术层拆**：

```
❌ 按技术层：UserController 服务 / UserService 服务 / UserDAO 服务
✅ 按业务能力：用户服务 / 订单服务 / 商品服务
```

**三个硬标准**：

| 标准 | 含义 | 反例 |
|------|------|------|
| 单一职责 | 一个服务对应一个清晰业务能力 | OrderService 里塞支付、物流、库存 |
| 高内聚 | 强相关写操作尽量落在同一服务 | 创建订单与订单状态机拆到两个服务 |
| 低耦合 | 跨服务只通过 API/事件，不直连对方库 | 订单服务 `JOIN` 用户表 |

---

### 1.3 DDD 限界上下文与数据所有权⭐⭐⭐

微服务拆不好，十有八九是**边界没画清**。DDD 的限界上下文（Bounded Context）不是「名词表」，而是「同一业务语言在同一边界内含义一致」。

```
电商例子：
┌──────── 交易上下文 ────────┐   ┌──────── 履约上下文 ────────┐
│ 订单、支付意图、优惠分摊   │   │ 发货单、物流轨迹、签收    │
│ 「订单」= 可支付的交易单据 │   │ 「订单」= 待履约的履约单  │
└────────────────────────────┘   └────────────────────────────┘
           │ 事件：OrderPaid                    ▲
           └────────────────────────────────────┘
```

**数据所有权（Data Ownership）铁律**：

1. **每个表只属于一个服务**；别的服务只能读副本/查 API，不能写主人的库。
2. **跨服务查询**用 API 聚合、CQRS 读模型或事件同步，不跨库 JOIN。
3. **共享数据库 = 分布式单体**：服务进程拆开了，schema 变更仍跨团队耦合。

**什么时候还不该拆？**

- 团队 < 5 人、业务边界每周都在变
- 强一致事务跨多实体且无法用最终一致性改写
- 运维/可观测/发布门禁尚未就绪

---

### 1.4 从单体迁移：Strangler、反腐层、拆库顺序⭐⭐⭐

**Strangler Fig（绞杀者）模式**：像藤蔓包住老树——新流量先走新服务，老模块逐步萎缩，而不是「停业装修式重写」。

```
阶段1：网关把 /api/user/* 仍指向单体
阶段2：抽出用户读路径到新服务，写路径仍走单体
阶段3：写路径切换到新服务，单体该模块下线
阶段4：拆库、删遗留表
```

**反腐层（Anti-Corruption Layer, ACL）**：新旧模型语义不一致时，在边界做翻译，避免新服务被老模型「腐蚀」。

```
新订单服务 ──ACL──→ 老 ERP（字段名、状态枚举、错误码全部映射）
```

**拆库顺序（稳妥路径）**：

```
1. 先拆服务进程（仍可临时共享库，但禁止新跨服务写）
2. 建立同步/对账（双写或 CDC + 校验任务）
3. 读切换到新库/新服务
4. 写切换到新库
5. 停双写、删旧表依赖
```

> 反过来「先拆库再拆服务」往往让事务与对账先爆炸。**先边界、后数据、再事务改造。**

迁移优先拆哪块：**变更频繁、容量热点、故障爆炸半径大、边界清晰**的模块；先建注册发现、配置、追踪、灰度与回滚，再动业务刀。

## 2. 服务间通信

### 2.1 同步 vs 异步

```
同步（REST / gRPC）：
订单 ─调用→ 库存 ─响应→ 订单
优点：实时、链路直观
缺点：耦合、调用方阻塞、超时预算难分

异步（消息队列）：
订单 ─发消息→ MQ ─消费→ 库存
优点：解耦、削峰
缺点：最终一致、排障从「调用栈」变成「事件链」

选择：
- 需要立即给用户结果 → 同步
- 可延迟且要削峰 → 异步
- 同步链路过长（>3–4 跳）→ 优先改异步或并行聚合
```

---

### 2.2 REST vs gRPC：别把 REST 绑死在 HTTP/1.1

| 维度 | REST（典型实现） | gRPC |
|------|------------------|------|
| 接口风格 | 资源 + HTTP 语义 | RPC + Protobuf 契约 |
| 传输 | **多为 HTTP**（1.1 或 2 均可） | **默认 HTTP/2** |
| 载荷 | JSON 常见，也可其它 | Protobuf 二进制 |
| 浏览器 | 原生友好 | 需 grpc-web / 网关转换 |
| 调试 | 文本可读，工具成熟 | 需反射/专用工具 |
| 流式 | 有限（SSE/分块等） | 单/双向流一等公民 |

> **REST ≠ HTTP/1.1。** REST 是架构风格；HTTP/1.1、HTTP/2 是传输。很多 REST API 已跑在 HTTP/2 上。
> **性能不要写死「gRPC 快 10 倍」**——取决于载荷、序列化、连接复用与业务逻辑占比。内部高频 RPC 优先 gRPC；对外公网 API 优先 REST/JSON。

**版本策略**：

```
1. URL：/api/v1/orders（最直观）
2. Header：Accept: application/vnd.api.v1+json
3. 兼容：可加字段；勿删/改类型；废弃要有窗口期
```

---

### 2.3 分布式 ID⭐⭐

微服务不能再靠「单库自增」当全局主键。常见方案：

| 方案 | 思路 | 优点 | 注意 |
|------|------|------|------|
| UUID/ULID | 本地生成 | 无中心依赖 | UUID v4 无序，二级索引友好性差；ULID/UUIDv7 更好 |
| 号段（Leaf/美团） | DB/缓存发号段 | 吞吐高、趋势递增 | 要防号段耗尽与时钟回拨策略 |
| Snowflake 类 | 时间+机器+序列 | 本地生成、大致有序 | 机器 ID 分配与时钟回拨 |

**选型口诀**：要趋势递增便于索引 → 号段或雪花；要完全去中心且可接受无序 → ULID/UUIDv7。

---

### 2.4 跨服务读数据

```
1. API 组合（网关/BFF 聚合）——简单查询首选
2. 数据冗余（事件同步只读副本）——热点读
3. CQRS 读模型——复杂查询
4. 禁止：跨服务直连对方库做 JOIN
```

## 3. 服务注册与发现

### 3.1 为什么需要注册发现？

```go
// 硬编码：扩缩容一次改一次
resp, err := http.Get("http://192.168.1.101:8080/user/123")

// 注册发现：
// 1) 服务启动注册  2) 调用方发现健康实例  3) 客户端负载均衡
instances := discover("user-service")
resp, err := http.Get(pick(instances) + "/user/123")
```

---

### 3.2 Consul 原理要点⭐⭐⭐

```
Consul 集群（3–5 个 Server，Raft）
        ↑ 注册/发现
Consul Agent（每节点）
        ↑ 健康检查
    微服务实例
```

```go
registration := &consul.AgentServiceRegistration{
    ID:      "user-service-1",
    Name:    "user-service",
    Address: "192.168.1.101",
    Port:    8080,
    Check: &consul.AgentServiceCheck{
        HTTP:     "http://192.168.1.101:8080/health",
        Interval: "10s",
        Timeout:  "3s",
    },
}
_ = client.Agent().ServiceRegister(registration)

services, _, _ := client.Health().Service("user-service", "", true, nil)
```

**为什么注册用 Raft、健康状态可用 Gossip？**

- 注册表写入需要**强一致**，避免脑裂导致「各看到各的实例集」。
- 健康状态可短暂不一致，Gossip 传播更快（约 O(log n)）。

---

### 3.3 Etcd vs Consul vs Nacos（含 CP/AP）

| 特性 | Etcd | Consul | Nacos |
|------|------|--------|-------|
| **一致性模型** | **CP**（Raft） | **CP**（Raft；健康/WAN 有 Gossip） | 可切换：命名/配置偏 **CP**（Raft），服务发现可走 **AP**（Distro） |
| 健康检查 | 常需自建/租约 | 内置 HTTP/TCP/脚本 | 内置 |
| 负载均衡 | 通常客户端自建 | 生态完善 | 客户端/DNS 等 |
| 多数据中心 | 弱于 Consul 场景化能力 | 原生多 DC 设计 | 支持 |
| UI | 弱 | 有 | 有 |
| 典型场景 | K8s 元数据、强一致配置 | 注册发现 + 服务网格配套 | 注册发现 + 配置中心一体 |

> 面试别背「谁绝对更好」：先答 **一致性模型与故障行为**，再答团队栈（Spring Cloud / K8s / 多 DC）。

---

### 3.4 注册中心 vs Kubernetes DNS⭐⭐

| 维度 | 独立注册中心（Consul/Nacos） | K8s Service + DNS/Endpoint |
|------|------------------------------|----------------------------|
| 抽象 | 应用级服务名与实例元数据 | 集群内 Service 名解析到 Pod IP |
| 健康 | 自定义检查、权重、元数据标签 | Readiness/Liveness + Endpoint 摘除 |
| 跨集群/多运行时 | 更自然 | 需多集群方案（多集群 Service、Mesh） |
| 适用 | 混合云、VM+容器、多语言老栈 | **工作负载已全面 K8s 化**时往往够用 |

**实践**：纯 K8s 内东向流量，可用 CoreDNS + Service；需要异构环境、丰富元数据路由、跨集群统一命名时，再上注册中心或 Mesh 控制面。

---

### 3.5 优雅上线与优雅下线⭐⭐⭐

```
上线：
1. 进程启动，先不接流量（或 Readiness=false）
2. 预热连接池/缓存
3. 注册到注册中心 / Readiness=true
4. 观察错误率与延迟再放量

下线：
1. 先从注册中心摘除 / Readiness=false（停止新流量）
2. 等待 in-flight 请求完成（grace period）
3. 关闭连接、退出进程
4. 避免：直接 kill -9 导致调用方超时风暴
```

配合：客户端缓存实例列表要有过期与失败重试；网关/Mesh 侧连接排空（connection draining）。

## 4. 配置中心

### 4.1 为什么需要？

```
本地 yml 的痛点：改配置要发版、多实例难一致、无审计回滚
配置中心：集中管理、热更新、版本/灰度、权限审计
```

### 4.2 Apollo 热更新（长轮询）

```
1. Client 启动拉取配置
2. 长轮询 /notifications（服务端 hold，如 60s）
3. Portal 改配置 → Config Service 立刻唤醒长轮询
4. Client 再拉全量/增量 → 触发监听回调（无需重启）
```

同类能力也可用 Nacos Config、Spring Cloud Config 等；选型看是否与注册中心一体、是否要多环境权限模型。

**热更新注意**：线程池大小、连接串等「半初始化」配置，热更后可能要重建资源，不是改个变量就完事。

## 5. API 网关、BFF 与 Mesh 边界

### 5.1 为什么需要网关？

```
无网关：客户端直连所有服务 → 地址耦合、鉴权重复、CORS/协议转换分散
有网关：统一入口做路由、鉴权、限流、观测、协议转换
```

```
客户端 → API 网关 → 用户 / 订单 / 商品 ...
```

---

### 5.2 Kong / Spring Cloud Gateway：讲机制，不背虚高 QPS

**Kong**：OpenResty（Nginx + LuaJIT）+ 插件链（认证 → 限流 → 日志 → 转发）。强项是高性能反向代理生态与插件扩展。

**Spring Cloud Gateway**：WebFlux 反应式网关，和 Spring 生态（发现、配置、安全）集成深，适合 Java 体系统一治理。

> **不要背「Kong 单机 10 万 / SCG 5 万」这类不可核实数字。** 吞吐取决于插件复杂度、TLS、载荷、机器规格与后端耗时。选型比的是生态、团队技能、动态配置与可观测，而不是口口相传的 QPS。

**路由示例**：

```yaml
routes:
  - path: /api/user/*
    service: user-service
  - path: /api/order/*
    match:
      headers:
        X-Version: v2
    service: order-service-v2
```

---

### 5.3 Gateway vs BFF vs Service Mesh

| 层 | 面向谁 | 典型职责 | 不该干什么 |
|----|--------|----------|------------|
| **API Gateway** | 南北向（外部→内部） | 鉴权、限流、路由、TLS 终结、协议转换 | 塞大量业务编排 |
| **BFF** | 特定前端（App/Web/运营） | 字段裁剪、聚合编排、适配交互节奏 | 变成第二个单体上帝服务 |
| **Service Mesh** | 东西向（服务↔服务） | mTLS、重试/超时、泳道、观测标准化 | 替代业务 API 设计 |

```
App/Web → Gateway → BFF（可选）→ 领域服务 ←── Mesh 治理东向流量 ──→
```

## 6. 弹性四件套

> 算法细节（令牌桶/漏桶/滑动窗口、熔断状态机语义）见 [09 §1 限流](./09-系统设计与架构.md#1-限流策略) 与 [09 §2 熔断降级](./09-系统设计与架构.md#2-熔断与降级)。本节讲**微服务里怎么串起来**。

### 6.1 优先级：超时 → 限流 → 熔断 → 重试

把调用链当成「有预算的水管」：

1. **超时**：先钉死等待上限，防止线程/连接被慢调用拖死。
2. **限流**：控制入口与关键依赖的并发/QPS，把超额挡在边界外。
3. **熔断**：依赖持续失败时快速失败，给下游喘息，防雪崩。
4. **重试**：最后才用，且仅幂等、有上限、有退避；否则变成重试风暴。

附加：**舱壁隔离**（线程池/信号量按依赖分隔）+ **依赖分级**（强依赖失败要失败；弱依赖失败可降级）。

```
雪崩直觉：
商品服务变慢 5s → 订单线程池堵死 → 用户服务也堵死 → 全站不可用
四件套：超时切开等待，限流挡住洪峰，熔断隔离坏依赖，重试只在安全预算内补枪
```

---

### 6.2 限流（与熔断并列，不是附属）⭐⭐⭐

微服务常见挂载点：

| 位置 | 目的 |
|------|------|
| 网关 | 保护整个后端，按用户/IP/API 限流 |
| 服务入口 | 防止网关之后的横向流量打满 |
| 出站调用 | 保护第三方/弱依赖，避免拖垮自己 |

算法选型（详见 09）：用户侧突发友好 → 令牌桶；必须平滑打下游 → 漏桶；分布式共享配额 → Redis + Lua。

---

### 6.3 熔断与降级：Resilience4j / Spring Cloud CircuitBreaker 主线⭐⭐⭐

**状态机（Closed / Open / Half-Open）** 仍然成立，但工程主线应是：

- **Java**：Resilience4j（或经由 **Spring Cloud CircuitBreaker** 抽象）
- **多语言/平台**：Envoy/Istio outlier detection、Sentinel（偏流量治理与规则动态化）
- **Hystrix**：进入「历史演进」——Netflix 已停维，新项目不要当默认方案

**可运行的简化熔断器（Go）**：

```go
package circuit

import (
    "errors"
    "sync"
    "time"
)

type State int

const (
    Closed State = iota
    Open
    HalfOpen
)

var ErrCircuitOpen = errors.New("circuit open")

type Breaker struct {
    mu              sync.Mutex
    state           State
    failureCount    int
    successCount    int
    totalCount      int
    failureRatio    float64
    volumeThreshold int
    successThreshold int
    openUntil       time.Time
    coolDown        time.Duration
}

func New(failureRatio float64, volume, success int, coolDown time.Duration) *Breaker {
    return &Breaker{
        state:            Closed,
        failureRatio:     failureRatio,
        volumeThreshold:  volume,
        successThreshold: success,
        coolDown:         coolDown,
    }
}

func (b *Breaker) Call(fn func() error) error {
    b.mu.Lock()
    if b.state == Open {
        if time.Now().Before(b.openUntil) {
            b.mu.Unlock()
            return ErrCircuitOpen
        }
        b.state = HalfOpen
        b.successCount = 0
    }
    b.mu.Unlock()

    err := fn()

    b.mu.Lock()
    defer b.mu.Unlock()
    b.totalCount++
    if err != nil {
        b.failureCount++
        if b.state == HalfOpen ||
            (b.totalCount >= b.volumeThreshold &&
                float64(b.failureCount)/float64(b.totalCount) >= b.failureRatio) {
            b.state = Open
            b.openUntil = time.Now().Add(b.coolDown)
        }
        return err
    }
    if b.state == HalfOpen {
        b.successCount++
        if b.successCount >= b.successThreshold {
            b.state = Closed
            b.failureCount, b.totalCount, b.successCount = 0, 0, 0
        }
    }
    return nil
}
```

**降级**：熔断是「停止调用」；降级是「给兜底结果」（默认值、缓存、备用通道、关闭非核心功能）。

---

### 6.4 历史演进：Hystrix → Resilience4j / Spring Cloud CircuitBreaker

| 阶段 | 代表 | 说明 |
|------|------|------|
| 1.0 时代 | Netflix Hystrix | 普及了熔断/舱壁思想；**已停维** |
| 当代 Java | Resilience4j | 函数式、轻量；熔断/限流/重试/隔舱模块化 |
| Spring 抽象 | Spring Cloud CircuitBreaker | 统一 API，底层可接 Resilience4j 等 |
| 流量治理套件 | Sentinel | 规则动态、控制台、热点参数限流等强 |
| 平台侧 | Envoy/Istio | 把部分弹性策略下沉到数据面 |

**Sentinel vs Resilience4j（对比表不要再以 Hystrix 当「现代主列」）**：

| 特性 | Resilience4j / SCCB | Sentinel |
|------|---------------------|----------|
| 定位 | 库级弹性原语，嵌入业务调用 | 流量治理平台（限流/熔断/热点/系统自适应） |
| 规则下发 | 代码/配置为主，可接动态源 | 控制台动态规则是一等能力 |
| 隔离 | 舱壁（Bulkhead）等模块 | 信号量等，偏流量整形 |
| 生态 | Spring Cloud 一等公民 | 阿里系/多语言客户端，控制台成熟 |
| 选型 | Java 服务内稳健默认 | 需要强动态限流与热点治理时 |

### 6.5 舱壁与依赖分级

```
舱壁：订单调商品、调积分用不同线程池/信号量
→ 积分打满不会抽干商品调用的并发额度

依赖分级：
- 强依赖（支付）：失败 → 接口失败，可排队/快速失败
- 弱依赖（推荐）：失败 → 降级为空列表，主流程继续
```

## 7. 分布式事务与最终一致性

### 7.1 挑战：本地 ACID 不够用了

```
单体：一库 @Transactional
微服务：订单库 / 库存库 / 账户库 各自提交
下单：建单成功 + 扣库存成功 + 扣款失败 → 必须有补偿或预留机制
```

---

### 7.2 为什么生产少用经典 2PC？⭐⭐

两阶段提交（Prepare → Commit）在微服务里通常不推荐作为默认：

1. **同步阻塞**：参与者资源长时间锁定，吞吐差。
2. **协调者风险**：协调者宕机可能让参与者卡在不确定态。
3. **与异地多活/超时现实冲突**：网络分区时「要么牺牲可用性，要么牺牲一致性」。
4. **运维面**：XA/数据库支持与中间件耦合重。

工程默认走向：**本地事务 + 可靠消息（Outbox）/ Saga / TCC（资金场景）**，追求业务可接受的最终一致。

---

### 7.3 Saga：补偿，不是「脏读」⭐⭐⭐

```
T1 → T2 → T3 成功
       ↓ 失败
C2 ← C1 补偿

下单：
T1 建单(待支付) / C1 取消订单
T2 扣库存     / C2 恢复库存
T3 扣余额     / C3 恢复余额
```

**编排式（Choreography）**：事件驱动，松耦合，复杂流程难追踪。
**协调式（Orchestration）**：中心协调器，流程清晰，注意协调器高可用。

> **术语纠正**：Saga 中间态被别人读到，应称为**业务可见的中间状态 / 读到未完成流程的数据**，属于隔离性与业务语义问题；**不要误叫数据库事务里的「脏读」（Dirty Read）**。脏读特指读到**未提交**事务数据；Saga 各步本地事务通常已提交。

---

### 7.4 TCC：Try / Confirm / Cancel

```
Try：冻结资源（如 frozen += 100，余额校验）
Confirm：真实扣减
Cancel：解除冻结
```

适合资金等需要更强业务隔离的场景；代价是业务侵入大（三套接口 + 幂等）。

---

### 7.5 Outbox / Inbox / 本地消息表 / 事务消息⭐⭐⭐

**本地消息表 ≈ 应用层 Outbox**，正确流程是「生产方只保证发出，消费方自己幂等」，**不是**生产方等消费确认再回写。

```
【生产方 Outbox】
BEGIN;
  INSERT INTO orders ...;
  INSERT INTO outbox (id, topic, payload, status) VALUES (..., 'pending');
COMMIT;

后台转发器/CDC：
  读 pending → 发到 MQ → 标记 status='sent'（或删出盒记录）
  （失败则保持 pending，下次重试——至少一次投递）

【消费方 Inbox】
BEGIN;
  INSERT INTO inbox(message_id) VALUES (?)  -- 唯一键，重复则忽略
  -- 执行业务（扣库存等）
COMMIT;
  ACK MQ
```

```
❌ 错误说法：消费者 ack 后，回写生产方消息表为 consumed
✅ 正确模型：生产方 pending → sent；消费侧 Inbox/业务唯一键保证幂等
```

| 方案 | 机制 | 优点 | 代价 |
|------|------|------|------|
| **本地消息表 / Outbox** | 同库事务写出盒，异步发 MQ | 不依赖特定 MQ 事务能力 | 转发组件 + 表膨胀治理 |
| **Inbox** | 消费侧去重表 | 明确幂等落点 | 要清理策略 |
| **事务消息（如 RocketMQ）** | Half 消息 + 本地事务回查 | 少维护出盒表 | 绑定 MQ 能力与回查接口 |

---

### 7.6 Seata 选型（点到为止）

| 模式 | 近似语义 | 适用 |
|------|----------|------|
| AT | 自动补补偿 SQL，业务侵入小 | 同构 JDBC、可接受脏写窗口的业务 |
| TCC | 业务三阶段 | 资金等高一致性诉求 |
| Saga | 长事务补偿 | 长流程、跨分钟级 |
| XA | 强一致 2PC | 少用，性能与可用性代价高 |

选型先问：**能否改成「本地事务 + 消息最终一致」？** 能则优先 Outbox；不能再谈 TCC/AT。

---

### 7.7 最大努力通知

支付结果回调商户：失败则按退避重试，超过阈值转人工/对账。一致性要求低于 Outbox，但要对账兜底。

---

### 7.8 幂等三要件⭐⭐⭐

1. **唯一业务键**：订单号、RequestId、消息 ID。
2. **写入去重**：DB 唯一约束 / Inbox 表 / Redis SETNX（注意过期与落库顺序）。
3. **状态机可重入**：同一事件重复到达，状态不变或走同一终态。

缺一不可：只有 Redis 去重没有唯一约束，仍可能双写；只有唯一约束没有状态机，补偿重放可能走错分支。

## 8. 分布式追踪与可观测

### 8.1 为什么需要？

一次请求穿越网关与多个服务时，没有 Trace 就只能「每段日志各说各话」。Trace 把因果链串成树，定位慢点与错误点。

```
TraceID = 0af7651916cd43dd8448eb211c80319c
  ├─ Span 网关 10ms
  ├─ Span 用户 20ms
  └─ Span 订单 100ms
        ├─ 商品 50ms  ← 瓶颈
        └─ 库存 30ms
```

---

### 8.2 OpenTelemetry 与 W3C `traceparent`⭐⭐⭐

核心：Trace / Span / Context 传播。标准头是 **W3C Trace Context**：

```
traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01
             │  │                                │                │
             │  │                                │                └─ flags（01=采样）
             │  │                                └─ parent-id（16 个十六进制字符 = 8 字节）
             │  └─ trace-id（32 个十六进制字符 = 16 字节）
             └─ version（00）
```

> **常见硬伤**：写成 `00-abc123-span1-01`。长度与字符集都不合规；示例必须用十六进制定长。

传播过程：入口生成/提取 `traceparent` → 每跳新建 Child Span → 出站注入新的 parent-id → 后端按 TraceId 拼树。

---

### 8.3 导出路径：OTLP → Collector（Jaeger Agent 已过时）

```
旧：App → Jaeger Agent（sidecar/本地）→ Jaeger Collector → 存储
新：App（OTel SDK）→ OTLP → OpenTelemetry Collector → Jaeger/Tempo/SkyWalking 等后端
```

**采样**：开发可全量；生产常用概率采样、限速采样或尾部采样（先收后再决定是否保留错误/慢请求）。

指标 / 日志 / 追踪三角：Trace 串因果，Metrics 看态势，Log 看细节；用同一 `trace_id` 关联。

## 9. 发布治理与 Service Mesh

### 9.1 灰度：金丝雀 / 蓝绿 / A/B

```
金丝雀：5% → 10% → 50% → 100%，小步验证
蓝绿：两套环境切换，回滚快，资源成本高
A/B：按用户特征分流，偏产品实验
```

**流量染色**：网关打 `X-Traffic-Tag`，HTTP Header / gRPC Metadata 全链路透传，路由到对应版本。

```go
package middleware

import (
    "context"
    "net/http"
)

const TrafficTagKey = "X-Traffic-Tag"

func TrafficTagMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        tag := r.Header.Get(TrafficTagKey)
        if tag == "" {
            tag = "stable"
        }
        ctx := context.WithValue(r.Context(), TrafficTagKey, tag)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}
```

---

### 9.2 全链路压测

生产/准生产压测要用标记隔离：影子库表、缓存 key 前缀、影子 Topic、禁止打真实第三方。标记同样全链路透传（`X-Stress-Test`）。

容量节奏：按目标峰值逐步加压（如 20%→50%→80%→100%→120%），观察错误率、饱和度与尾延迟，而不是一次打满。

---

### 9.3 Service Mesh：本文只留选型，细节链到 11

Mesh 把超时、重试、mTLS、泳道从业务 SDK 下沉到 Sidecar/数据面。
**VirtualService / DestinationRule、mTLS、Ambient 等详解** → [11-云原生与容器 · Service Mesh](./11-云原生与容器.md#3-service-mesh)。

**微服务场景怎么选 SDK vs Mesh**：

| 条件 | 更合适 |
|------|--------|
| 多语言、强一致治理、平台团队成熟 | Mesh |
| 栈统一、规模中小、要控 sidecar 成本 | SDK（Resilience4j/Sentinel 等） |
| 现实路径 | 核心策略平台化，业务特殊逻辑保留 SDK |

## 11. 面试题自查

> 编号统一为一条轨道；高频题带「追问」。答案已与正文硬伤修正对齐。

### 11.1 高频速刷

**1. 单体和微服务的本质区别？**
部署单元、数据边界、团队拓扑一起变了，不只是「代码拆目录」。
**追问**：什么叫分布式单体？——服务拆了但共享库/超长同步链/无独立发布。

**2. 为什么通常不共享数据库？**
共享库会让 schema 与事务成为隐藏耦合，边界名存实亡。

**3. 注册中心解决什么？与 K8s DNS 如何选？**
解决实例动态变化下的发现与健康摘除。纯 K8s 可用 Service DNS；异构/多运行时/富元数据路由再用注册中心或 Mesh。
**追问**：Consul 为何注册走 Raft？——注册表需要强一致，避免脑裂视图。

**4. 网关常见职责？会不会变成业务中心？**
路由、鉴权、限流、协议转换、灰度入口。业务聚合优先放 BFF/应用服务，避免网关上帝化。

**5. BFF 什么时候值得引入？**
多端差异大（字段、聚合、节奏不同）时，用 BFF 隔离前端与领域服务。

**6. 为什么配置中心优于本地写死配置？**
多实例一致变更、审计回滚、热更新；注意半初始化资源要重建。

**7. 契约测试为何更重要？**
跨服务只靠契约协作，格式/语义破坏往往运行时才爆；契约测试前移到 CI。

---

### 11.2 机制与选型

**8. 熔断三种状态？现代主线用什么？**
Closed / Open / Half-Open。新项目主线 **Resilience4j / Spring Cloud CircuitBreaker**（或 Sentinel/Mesh）；Hystrix 仅作历史。
**追问**：和限流谁先？——先定超时，入口限流，再熔断坏依赖，重试最后。

**9. Sentinel 和 Resilience4j 怎么选？**
要强动态规则、热点限流、控制台 → Sentinel；要 Spring 生态库级熔断/重试/舱壁 → Resilience4j/SCCB。

**10. REST 和 gRPC 区别？REST 是否等于 HTTP/1.1？**
REST 是风格，常跑在 HTTP 上（1.1/2 皆可）；gRPC 默认 HTTP/2 + Protobuf。不要断言「固定快 10 倍」。对外 REST，对内可 gRPC。

**11. 限流算法与令牌桶/漏桶？**
固定/滑动窗口、令牌桶（允许突发）、漏桶（平滑）。细节见 09；微服务要答挂载点（网关/入站/出站）。

**12. 如何设计超时 + 重试 + 并发预算？**
先定端到端 SLO，再拆分每跳超时；重试限次数+退避+仅幂等；关键依赖设并发上限（舱壁）。

**13. 分布式追踪 TraceId 怎么传？`traceparent` 长什么样？**
W3C：`00-<32hex-traceid>-<16hex-parentid>-<flags>`。经 OTLP 打到 Collector，再进 Jaeger/Tempo 等。
**追问**：为何不提 Jaeger Agent？——Agent 模式过时，统一 OTel Collector。

**14. Outbox/本地消息表正确流程？**
本地事务写业务+outbox(pending) → 转发 MQ 后标 sent → 消费侧 Inbox/唯一键幂等。
**追问**：要不要等消费 ack 回写生产方 consumed？——不要。

**15. Saga 和 TCC 区别？Saga 会脏读吗？**
Saga：已提交步骤 + 补偿，可能读到**业务中间态**（不是 DB 脏读）。TCC：预留/确认/取消，隔离更强、侵入更大。

**16. 为什么不太用 2PC？Seata 怎么选？**
阻塞、协调者风险、与超时分区现实冲突。优先 Outbox；需要时再 AT/TCC/Saga；XA 慎用。

**17. 幂等三要件？**
唯一键 + 去重存储 + 可重入状态机。

**18. 分布式 ID 方案？**
UUID/ULID、号段、Snowflake。看是否要趋势递增与是否接受中心发号。

**19. Gateway / BFF / Mesh 边界？**
南北向入口 / 前端适配聚合 / 东西向治理。

**20. 优雅上下线步骤？**
先摘流量（反注册/Readiness=false）→ 排空 in-flight → 再停进程；上线相反并预热。

---

### 11.3 治理与实战

**21. 灰度如何做？染色如何透传？**
网关打标，Header/Metadata 透传，按标签选版本；配合监控与秒级回滚。
**追问**：金丝雀和蓝绿怎么选？——要小步验证用金丝雀；要瞬间切换且有双倍资源用蓝绿。

**22. 全链路压测如何避免污染生产数据？**
压测标记透传 + 影子库表/缓存前缀/影子 Topic + 第三方走沙箱；指标按标记分维。

**23. Mesh 一定优于 SDK 吗？**
否。看多语言治理需求、平台能力、sidecar 成本。可平台化与 SDK 并存。细节见 11。

**24. 事件驱动如何同时处理幂等、重复、乱序？**
唯一键去重、状态机可重入、分区键保序或版本号校验；死信与可回放。

**25. 异步化后为何更难排障？**
调用栈变事件链。要透传 trace/event id，分生产/积压/消费延迟/死信指标，支持按业务键回放。

**26. 从单体迁移的稳妥顺序？**
基础设施门禁 → Strangler 先拆清晰热点 → 反腐层 → 先服务后拆库 → 对账后再弱化分布式事务。

**27. 跨服务复杂查询怎么办？**
BFF/API 组合、只读冗余、CQRS；禁止跨库 JOIN。

**28. API 向后兼容？**
可加不可删改类型；版本共存与下线窗口。

**29. 混沌工程怎么做？**
定义稳态 → 假设 → 注入故障 → 看熔断/降级是否生效 → 修复再实验。

**30. 常见反模式？**
分布式单体、纳米服务、共享库地狱、超长同步链、无限重试、无熔断、忽略数据所有权。

### 11.4 开放式设计题

**D1：单体拆微服务，策略与路径？**
按限界上下文拆；Strangler + 网关切流；先服务后拆库；Outbox/Saga 替代乱上 2PC；治理（发现/配置/追踪/灰度）先行。

**D2：5 跳同步链路如何压到 100ms 内？**
并行无依赖调用、减跳数/合并 RPC、缓存、按总预算切分超时、内部用 gRPC、弱依赖降级。

**D3：设计订单-库存的最终一致方案（Outbox 实战）**
订单库本地事务写订单+outbox；转发器至少一次投递；库存 Inbox 去重后扣减；失败进死信并对账；禁止生产方等待库存 ack 回写。

**D4：K8s 上还要不要注册中心？**
集群内东向：Service/DNS + Readiness 往往足够；要跨集群、VM 混合、按元数据路由或统一多运行时命名，再引入注册中心/Mesh 控制面。说明优雅上下线与连接排空。

**D5：压测染色与灰度染色如何共存？**
两套标记正交（如 `X-Traffic-Tag` 与 `X-Stress-Test`）；路由规则优先级明确；压测流量强制进影子存储；监控按两维打标，避免金丝雀指标被压测污染。

## 总结

1. **边界**：DDD 限界上下文 + 数据所有权；迁移用 Strangler/反腐层，先服务后拆库。
2. **通信**：同步有预算，异步要可观测；REST ≠ HTTP/1.1；分布式 ID 按序与中心化权衡。
3. **平台三角**：发现（含 vs K8s DNS）/ 配置 / 网关（与 BFF、Mesh 划界）。
4. **弹性四件套**：超时 → 限流 → 熔断 → 重试，外加舱壁与依赖分级；熔断主线 Resilience4j/SCCB，Hystrix 归历史。
5. **一致性**：慎用 2PC；Outbox/Inbox 正确分流；Saga 中间态 ≠ 脏读；幂等三要件。
6. **可观测与发布**：W3C `traceparent` + OTLP/Collector；灰度/压测染色；Mesh 细节见 11，算法语义见 09。
