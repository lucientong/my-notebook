## 0. 操作系统全局视角

操作系统不是一组零散概念，而是一层运行在硬件和应用之间的控制系统。它主要解决四件事：

1. **抽象硬件**：把 CPU、内存、磁盘、网卡抽象成进程、虚拟内存、文件、socket。
2. **分配资源**：决定谁获得 CPU、内存、IO、网络带宽。
3. **隔离与保护**：让不同进程互不踩内存、互不直接操作硬件。
4. **提供内核服务**：通过系统调用让应用访问文件、网络、进程、时间、设备等能力。

```text
  │
  ├─ 系统调用：read/write/open/socket/epoll_wait/futex/mmap
  │
操作系统内核
  ├─ 进程调度：进程、线程、上下文切换、CFS
  ├─ 内存管理：虚拟内存、页表、TLB、缺页、Page Cache
  ├─ 文件系统：inode、目录、页缓存、fsync、块设备
  ├─ 网络协议栈：socket、TCP/IP、软中断、拥塞控制
  ├─ 资源隔离：namespace（视图）+ cgroup（配额）
  └─ 硬件驱动：磁盘、网卡、时钟、中断
  │

```

### 0.2 用户态与内核态

CPU 用不同特权级隔离应用和内核。普通应用运行在用户态，不能直接访问硬件和内核内存；内核运行在内核态，可以操作硬件、页表、调度器、文件系统和网络协议栈。

| 维度 | 用户态（User Mode） | 内核态（Kernel Mode） |
|------|----------------------|------------------------|
| 执行主体 | 普通应用进程 | OS 内核、驱动、中断处理 |
| 权限 | 受限，不能直接访问硬件和内核内存 | 最高权限，可访问硬件和所有物理资源 |
| 典型代码 | 业务逻辑、GC、序列化、算法计算 | 系统调用、调度、网络协议栈、文件系统 |
| 出错影响 | 通常只影响当前进程 | 可能影响整个系统 |

进入内核态的常见路径：

```text
应用代码
  ├─ 系统调用：read/write/open/socket/epoll_wait
  ├─ 缺页异常：访问的虚拟页还没映射
  ├─ 中断：网卡、磁盘、时钟
  └─ 信号/异常：signal、trap、divide-by-zero
      ↓
内核处理
      ↓
返回用户态继续执行
```

### 0.3 系统调用：用户态和内核态的边界

系统调用不是普通函数调用。一次 `read()` 需要从用户态切到内核态，校验 fd 和 buffer，执行 VFS/文件系统/设备驱动逻辑，再把结果返回用户态。

| 系统调用 | 场景 |
|----------|------|
| `openat/read/write/close` | 文件 IO |
| `socket/connect/accept/sendto/recvfrom` | 网络 IO |
| `epoll_wait` | IO 多路复用 |
| `clone/fork/execve/wait4` | 进程/线程创建与回收 |
| `mmap/munmap/brk` | 内存映射与堆扩展 |
| `futex` | 用户态锁竞争后进入内核等待 |

观测系统调用：

```bash
strace -c -p <PID>                         # 统计系统调用耗时和次数
strace -tt -T -p <PID> -e trace=network,file,process
perf trace -p <PID>
```

### 0.4 从现象到模块：Linux 观测入口

Linux 命令应该服务于问题定位，而不是孤立背诵。先判断资源维度，再进入对应章节。

| 想判断什么 | 先看什么 | 常用命令 |
|------------|----------|----------|
| CPU 是用户态高还是内核态高 | `us/sy/wa/si` | `top`, `pidstat -u -p <PID> 1` |
| 进程是否在跑、睡眠、D 状态、僵尸 | `STAT`, `wchan` | `ps -p <PID> -o pid,ppid,stat,wchan:32,cmd`, `top -Hp <PID>` |

| 内存是否泄漏或被 OOM | RSS、page cache、cgroup | `free -h`, `pmap -x <PID>`, `cat /proc/<PID>/smaps`, `dmesg -T` |
| 磁盘是否慢 | await、util、队列深度 | `iostat -x 1`, `pidstat -d -p <PID> 1`, `iotop` |
| 网络连接是否异常 | 连接状态、重传、队列 | `ss -s`, `ss -lntp`, `netstat -s`, `tcpdump` |
| 是否受容器限制 | cgroup quota/limit/pressure | `cat /sys/fs/cgroup/*`, `kubectl top`, `crictl stats` |

CPU 字段的含义：


网络命令选择：


## 1. 进程与线程管理

### 1.1 进程vs线程

进程是资源隔离边界，线程是 CPU 调度单位。Linux 内核实际调度的是 task，进程和线程都可看作不同资源共享程度的 task；用户态通常按“进程/线程”理解即可。

| 维度 | 进程 | 线程 |
|------|------|------|
| **定义** | 资源分配的基本单位 | CPU 调度的基本单位 |
| **内存** | 独立地址空间 | 共享地址空间 |
| **通信** | IPC（管道、消息队列、共享内存） | 直接访问全局变量 |
| **创建开销** | 较大（复制 mm/fd 等，通常数十 μs～ms 量级，视工作集而定） | 较小（共享地址空间，通常数 μs 级） |
| **切换开销** | 同核进程切换约数 μs（含 CR3/TLB 扰动） | 同进程线程切换约 1～3 μs（不必换页表） |
| **稳定性** | 一个进程崩溃不影响其他进程 | 一个线程崩溃通常拖垮整个进程 |

> 口径统一：上下文**切换**按 **μs** 记；**创建**更贵，且随地址空间/打开文件数变化。不要把“创建开销”和“切换开销”混成一句话。

### 1.3 进程调度算法

#### 1.3.1 CFS 与演进注记（EEVDF）

长期以来 Linux 默认用 **CFS**：用 vruntime 近似“谁亏欠 CPU 最多谁上”。

```c
// 虚拟运行时间（vruntime）
vruntime += delta_exec * (NICE_0_LOAD / weight)

// nice=-20 → weight 大；nice=19 → weight 小
// nice=0 默认 weight=1024
```

```bash
# 进程A：nice=0, weight=1024；进程B：nice=5, weight≈335
# 同跑 10ms 后 B 的 vruntime 涨得更快 → 下次更倾向调度 A
```

**演进**：Linux **6.6+** 普通调度类逐步以 **EEVDF**（Earliest Eligible Virtual Deadline First）接棒 CFS 思想——仍追求公平，但用“合格虚拟截止时间”改善延迟与滞后任务体验。面试答法：

- 原理题仍可讲 CFS/vruntime（大量资料与旧内核）
- 补充一句：新内核主线已转向 EEVDF，观测调度行为以当前发行版内核为准

```bash
uname -r
# 查调度相关：/sys/kernel/debug/sched*（需 debugfs）、perf sched
```

**调整优先级**：
```bash
# 降低优先级（nice值越大，优先级越低）
nice -n 10 ./myapp

# 提高优先级（需要root）
nice -n -10 ./myapp

# 修改正在运行的进程
renice -n 5 -p 1234
```

#### 1.3.2 实时调度（RT）
```bash
# 查看实时进程
ps -eo pid,class,rtprio,comm | grep RR
# PID  CLS  RTPRIO  COMMAND
# 123  RR   50      realtime-app

# 设置实时优先级（0-99，99最高）
chrt -r -p 50 1234
```

#### 1.4.2 共享内存（最快的IPC）

`IPC_PRIVATE` **不是**“任意进程都能用的私有钥匙”，而是“创建一个**新**、尚未命名给第三方查找的 System V 段”。子进程可经 `fork` 继承 `shmid`；无关进程通常要用 `ftok` 生成的 key，或改用 POSIX `shm_open`。

```c
#include <sys/shm.h>
#include <sys/wait.h>
#include <unistd.h>
#include <string.h>
#include <stdio.h>

int main(void) {
    // IPC_PRIVATE：创建无名段；配合 fork 把 shmid 传给子进程
    int shmid = shmget(IPC_PRIVATE, 1024, IPC_CREAT | 0666);
    char *shmaddr = (char *)shmat(shmid, NULL, 0);

    pid_t pid = fork();
    if (pid == 0) {
        // 子进程：附加同一段并写入
        char *child = (char *)shmat(shmid, NULL, 0);
        strcpy(child, "hello from child");
        shmdt(child);
        _exit(0);
    }

    wait(NULL);
    printf("%s\n", shmaddr);  // hello from child

    shmdt(shmaddr);
    shmctl(shmid, IPC_RMID, NULL);  // 标记删除，最后一附解除后销毁
    return 0;
}
```

**现代更常见：POSIX 共享内存 / 文件 mmap**：
```go
// 进程 A 写入文件，进程 B 用 mmap 读；两端打开同一路径即可
f, _ := os.OpenFile("/dev/shm/shared.dat", os.O_RDWR|os.O_CREATE, 0600)
f.Truncate(4096)
// 再用 syscall.Mmap / golang.org/x/sys/unix.Mmap 映射后读写
```

### 1.5 线程模型

#### 1.5.1 用户级线程 vs 内核级线程

类比：纯用户级线程像“只有一个窗口的办事大厅”——切换快，但窗口只有一个就无法并行；内核线程是“每个窗口一个柜员”；Go 的 M:N 则是“大量协程任务单，映射到有限柜员（M）+ 逻辑窗口（P）”。

| 类型 | 实现 | 优点 | 缺点 |
|------|------|------|------|
| **纯用户级线程（1:1 之前的 N:1）** | 用户态自己调度，内核只见一个线程 | 创建/切换极轻 | **单核并行**：一个阻塞 syscall 可卡住整个进程内所有用户线程 |
| **内核级线程（1:1）** | 内核调度（pthread） | 天然利用多核 | 创建与切换成本更高 |
| **混合模型（M:N）** | 如 Go 的 G:P:M | 轻量调度 + 多核并行 | 运行时复杂（阻塞、抢占、网络多路复用要自己接） |

> 常见误区：把「用户级线程」直接写成「Go runtime」。Go 是 **M:N 混合模型**，靠多个 M（内核线程）跑在多核上；“无法利用多核”只适用于经典 N:1 用户级线程，不适用于 goroutine。

#### 1.5.2 Go的GMP模型

```
┌─────────────────────────────────────┐
│         G (Goroutine)               │
│  轻量级线程，2KB初始栈               │
└──────────┬──────────────────────────┘
           │ 调度
┌──────────↓──────────────────────────┐
│         P (Processor)               │
│  逻辑处理器，GOMAXPROCS数量          │
└──────────┬──────────────────────────┘
           │ 绑定
┌──────────↓──────────────────────────┐
│         M (Machine)                 │
│  内核线程，真正执行代码               │
└─────────────────────────────────────┘
```

**工作窃取（Work Stealing）**：
```go

// P2的G队列：[]（空闲）

// P2会从P1偷一半任务
// P1的G队列：[G1]
// P2的G队列：[G2, G3]
```


### 1.6 僵尸进程与孤儿进程

**僵尸进程（Zombie）**：

```
产生原因：
- 子进程退出后，父进程未调用wait()回收

状态：
- 进程已结束，但进程表项未删除
- 占用PID资源（PID有限）

查看僵尸进程：
ps aux | grep Z
# USER  PID  STAT  COMMAND
# root  123  Z     [myapp] <defunct>

解决方法：
1. 父进程调用wait()/waitpid()
2. 杀死父进程（僵尸进程变成孤儿进程，由init回收）
```

**孤儿进程**：

```
产生原因：
- 父进程退出，子进程仍在运行

处理方式：
- 由init进程（PID=1）收养
- init进程会调用wait()回收

孤儿进程是正常的，不会造成资源泄漏
```

**Go代码示例**：

```go
// ❌ 可能产生僵尸进程
func badExample() {
    cmd := exec.Command("sleep", "10")
    cmd.Start()
    // 忘记调用 cmd.Wait()
}

// ✅ 正确做法
func goodExample() {
    cmd := exec.Command("sleep", "10")
    cmd.Start()
    cmd.Wait()  // 回收子进程
}
```

### 1.7 上下文切换

**什么是上下文切换？**

把 CPU 从任务 A 挪到任务 B，要先把 A 的“作业现场”收好，再铺开 B 的现场。单位统一用 **μs**：

```
进程上下文切换（同核典型约数 μs）：
1. 保存当前进程的 CPU 寄存器、程序计数器、栈指针
2. 切换页表基址（CR3）；无 PCID 时可能整表冲刷 TLB
3. 切到新进程地址空间，恢复其 CPU 状态

同进程内线程切换（典型约 1～3 μs）：
- 共享 mm，不必换页表
- 主要是寄存器/栈切换与调度器开销
- 仍可能因 cache 冷启动变慢，但通常轻于跨进程切换

注意：创建进程/线程（fork/clone）≠ 上下文切换；创建是一次性更重的工作。
```

**查看上下文切换次数**：

```bash
# 系统级别
vmstat 1
# procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
#  r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st

#                                                      context switches/s
```

**减少上下文切换**：

```go
// ❌ 频繁切换（阻塞式）
for i := 0; i < 10000; i++ {
    go func() {
        time.Sleep(1 * time.Second)  // 每次都切换
    }()
}

// ✅ 批量处理（减少切换）
go func() {
    for i := 0; i < 10000; i++ {
        // 批量处理，减少goroutine数量
    }
}()
```

## 2. 内存管理

### 2.1 虚拟内存

**为什么需要虚拟内存？**
1. **隔离**：每个进程有独立地址空间，互不干扰
2. **扩展**：虚拟内存可以大于物理内存（通过swap）
3. **共享**：多个进程共享同一物理页（如libc.so）

**地址转换**：
```
虚拟地址 (48位) = 页号 (36位) + 页内偏移 (12位)
                  ↓ 查页表
物理地址 (48位) = 页框号 (36位) + 页内偏移 (12位)
```

**查看进程内存布局**：
```bash
cat /proc/1234/maps
# 输出：
# 地址范围              权限  偏移  设备  inode  路径
# 00400000-00452000  r-xp  0     08:01  123    /usr/bin/myapp  # 代码段
# 00651000-00652000  r--p  51000 08:01  123    /usr/bin/myapp  # 只读数据
# 00652000-00653000  rw-p  52000 08:01  123    /usr/bin/myapp  # 读写数据
# 7ffff7a0d000-...   r-xp  0     08:01  456    /lib/libc.so.6  # 共享库
# 7ffffffde000-...   rw-p  0     00:00  0      [stack]         # 栈
# 7ffff7ff9000-...   rw-p  0     00:00  0      [heap]          # 堆
```

### 2.2 页表与TLB

**多级页表（x86_64）**：
```
虚拟地址 (48位)
├─ PGD索引 (9位) ────→ 页全局目录
├─ PUD索引 (9位) ────→ 页上层目录
├─ PMD索引 (9位) ────→ 页中间目录
├─ PTE索引 (9位) ────→ 页表项
└─ 页内偏移 (12位) ──→ 物理页内偏移
```

**TLB（Translation Lookaside Buffer）**：
- 缓存虚拟地址→物理地址的映射
- 命中时无需查页表（快100倍）
- TLB Miss时触发Page Walk（查多级页表）

**查看TLB Miss率**：
```bash
perf stat -e dTLB-load-misses,dTLB-loads ./myapp
# 输出：
# 1,234,567  dTLB-loads
# 12,345     dTLB-load-misses  # Miss率=1%
```

**优化TLB Miss**：
```c
// ❌ 跨步访问（TLB Miss多）
for (int i = 0; i < N; i += 1024) {
    sum += arr[i];
}

// ✅ 顺序访问（TLB命中高）
for (int i = 0; i < N; i++) {
    sum += arr[i];
}
```

### 2.3 缺页中断（Page Fault）

**分类**：
1. **Minor Page Fault**：页在内存中，但未映射到页表
2. **Major Page Fault**：页不在内存，需要从磁盘读取

**查看 Page Fault**：
```bash
# 正确入口：进程计数 / perf；缺页是异常，不是 syscall
ps -o pid,min_flt,maj_flt,comm -p <PID>
perf stat -e page-faults,minor-faults,major-faults ./myapp
sar -B 1 5

# strace -c 只统计系统调用，不会出现名为 page_fault 的 syscall
strace -c ./myapp
# % time  calls  errors  syscall
# 45.00   10     0       mmap
# 30.00   100    0       read
```

**减少 Page Fault**：
```go
slice := make([]int, 0, 1000000) // 预分配容量，减少扩容缺页
for i := 0; i < 1000000; i++ {
    slice = append(slice, i)
}
```

### 2.4 fork、COW 与 mmap

`fork` 看起来快，是因为 **Copy-On-Write**：父子先共享物理页，任一方写入再复制该页。`mmap` 成功时往往只建 VMA，真正访问才缺页落物理页。

```text
fork() → 页表标 COW → 写时复制单页
mmap(文件) → 建 VMA → 首次访问缺页 → 从文件/Page Cache 填页
MAP_PRIVATE 写 → COW；MAP_SHARED 写 → 改共享页（可回写文件）
```

大进程 `fork` 后若父子都猛写，会把 COW 成本摊成一串 fault；静态资源可 `mmap`/`sendfile`，随机写密集时未必比显式 `read` 更稳。

### 2.5 内存回收链：水位线 → kswapd → direct reclaim → swap → OOM

物理内存像水库，水位线（watermark）决定何时“抽水”：

```text
水位低于 low / 分配吃紧
  ├─ 异步：唤醒 kswapd（后台回收 file 页、不活跃匿名页）
  └─ 紧急：direct reclaim（分配路径上同步回收，应用易抖动）
        ├─ 优先回收干净 file 页；脏页可能写回
        ├─ 匿名页可换出到 swap（若启用）
        └─ 仍不够 → OOM Killer（按 oom_score 选牺牲者）
```

```bash
grep -E 'low|min|high' /proc/zoneinfo | head
cat /proc/vmstat | grep -E 'pgsteal|pgscan|oom_kill'
cat /proc/<PID>/oom_score
cat /proc/<PID>/oom_score_adj   # -1000~1000
vmstat 1 5                      # si/so 持续 >0 → 内存紧张
```

容器还有 cgroup `memory.max`：组内先触达限额，可能在主机仍空闲时就对组内进程 OOM。

### 2.6 透明大页（THP）

4KB 小页 vs 2MB/1GB 大页：大页降低页表深度与 TLB miss，但可能引入压缩/拆页延迟。

```bash
cat /sys/kernel/mm/transparent_hugepage/enabled
# always / madvise / never
# 延迟敏感服务常见 madvise 或 never，避免 khugepaged 合并抖动
cat /proc/vmstat | grep -E 'thp_|compact_'
```

数据库、JVM 大堆是否开 THP 要实测：吞吐可能升，尾延迟也可能抖。

### 2.7 CPU 缓存、MESI 与内存屏障

> 从进程章挪入：缓存一致性是多核共享存储问题，不是调度器问题。

```text
CPU 核心 → L1（~32–64KB）→ L2 → L3（多核共享）→ 主存
缓存行通常 64B；读一字节会拉整行
```

伪共享：两线程改同行不同字段，互相把对方行打成 Invalid。

```go
// ❌ a、b 可能同属一行
type Counter struct{ a, b int64 }

// ✅ 填充到缓存行边界
type Counter struct {
    a int64
    _ [56]byte
    b int64
    _ [56]byte
}
```

**MESI**：Modified / Exclusive / Shared / Invalid。写共享行会使其他核对应行失效。

**内存屏障**：CPU/编译器可重排；`atomic` 与锁的 acquire/release 带屏障。Go 的 `sync.Once`、mutex 已提供可见性，业务少手写屏障。

```bash
perf stat -e cache-references,cache-misses ./myapp
```

### 2.8 内存分配器

#### 2.8.1 Buddy System（Linux）
```
伙伴系统：块大小 2^n（4KB、8KB、16KB...）
申请 6KB → 取 8KB；无则拆 16KB → 两个 8KB，分一留一
```

```bash
cat /proc/buddyinfo
# Node 0, zone Normal   100 50  20  10  5   2   1   0   0   0   0
```

#### 2.8.2 TCMalloc 与线程缓存思想

TCMalloc 把小对象放每线程缓存，不够再向 central/page heap 取，用 size class 降碎片。

> 这是经典**分层思想**；Chrome PartitionAlloc、jemalloc、Go 的 mcache/mcentral/mheap **同属线程缓存谱系或并行演进**，不等于“Go/Chrome 直接使用 TCMalloc”。Go 自有分配器，见 `01-Go语言深入.md`。

```text
Thread Cache（无锁快路径）→ Central Cache → Page Heap / mmap
```

## 3. IO模型与异步IO

### 3.1 五种IO模型

| 模型 | 阻塞 | 说明 |
|------|------|------|
| **阻塞IO** | ✅ | read()阻塞直到数据到达 |
| **非阻塞IO** | ❌ | read()立即返回，需轮询 |
| **IO多路复用** | ✅ | select/epoll阻塞，监听多个fd |
| **信号驱动IO** | ❌ | 数据到达时发送信号 |
| **异步IO** | ❌ | 内核完成IO后通知应用 |

#### 3.1.1 阻塞IO
```c
// 阻塞直到收到数据
char buf[1024];
int n = read(sockfd, buf, sizeof(buf));  // 阻塞
printf("received: %s\n", buf);
```

#### 3.1.2 非阻塞IO
```c
// 设置为非阻塞
fcntl(sockfd, F_SETFL, O_NONBLOCK);

// 轮询
while (1) {
    int n = read(sockfd, buf, sizeof(buf));
    if (n > 0) {
        printf("received: %s\n", buf);
        break;
    } else if (errno == EAGAIN) {
        // 数据还没到，继续轮询
        usleep(1000);
    }
}
```

#### 3.1.3 IO多路复用（epoll）
```c
int epfd = epoll_create1(0);

// 添加监听的fd
struct epoll_event ev;
ev.events = EPOLLIN;
ev.data.fd = sockfd;
epoll_ctl(epfd, EPOLL_CTL_ADD, sockfd, &ev);

// 等待事件
struct epoll_event events[10];
while (1) {
    int nfds = epoll_wait(epfd, events, 10, -1);  // 阻塞
    for (int i = 0; i < nfds; i++) {
        if (events[i].events & EPOLLIN) {
            // 可读
            int fd = events[i].data.fd;
            read(fd, buf, sizeof(buf));
        }
    }
}
```

### 3.2 epoll vs select：复杂度与事件传递

| 特性 | select / poll | epoll |
|------|---------------|-------|
| **fd 规模** | select 常受 `FD_SETSIZE`（常见 1024）限制；poll 无此硬限但仍线性扫描 | 实用上受系统 fd 上限约束，无 1024 那种集合硬限 |
| **注册/修改** | 每次调用携带全集 | `epoll_ctl`：内核用红黑树管兴趣集，**增删改 O(log N)** |
| **等待返回** | 扫描全部感兴趣 fd，**O(N)** | 只返回就绪事件，**O(R)**（R=就绪数） |
| **用户↔内核传递** | 每次拷贝 fd 集合 | `epoll_wait` 把就绪事件拷到用户 buffer；**不是** mmap 共享事件表 |
| **适用场景** | 少量连接、可移植性 | 高并发（C10K+） |

> 误传纠正：网上常说 epoll「O(1)+共享内存」。更准确是：**管理兴趣集 O(log N)，返回就绪 O(R)**；事件经 `copy_to_user` 一类路径交给用户态，**不是**把就绪队列 mmap 给进程。

```c
epoll_wait(epfd, events, maxevents, -1); // 只遍历返回的 R 个就绪 fd
for (int i = 0; i < nfds; i++) {
    int fd = events[i].data.fd;
    read(fd, buf, sizeof(buf));
}
```

### 3.3 epoll 模式：LT / ET / ONESHOT、惊群与 Go netpoller

类比：LT（水平触发）像“水位灯一直亮到水退”；ET（边缘触发）像“只在水位刚变化时响一声”——漏听就要自己负责把数据读干。

| 模式 | 行为 | 注意点 |
|------|------|--------|
| **LT（默认）** | 只要仍可读/可写，`epoll_wait` 会反复报到 | 编程简单；忘读完也会再通知 |
| **ET** | 状态变化时通知一次 | 必须非阻塞 + 循环读到 `EAGAIN`，否则丢事件 |
| **EPOLLONESHOT** | 触发一次后自动从兴趣集摘掉 | 多线程下避免同 fd 被多 worker 同时处理；处理完要 `epoll_ctl` 重新武装 |

**accept 惊群**：多个进程/线程对同一 listen fd `epoll_wait`，连接到达时可能都被唤醒，只有一人 `accept` 成功，其余空转。现代内核有 `SO_REUSEPORT`、以及部分场景的互斥唤醒缓解；仍需在业务侧避免“盲目多进程抢同一 listen”。

**与 Go netpoller 对照**：

```text
应用 goroutine  →  runtime netpoller（Linux 上 epoll）
       ↓ 阻塞在 conn.Read
把 G 挂起，M 去跑别的 G；epoll 就绪后再把 G 放回可运行队列
```

```go
// 业务只写同步风格 I/O；运行时用 epoll 把“阻塞”变成 goroutine 挂起
listener, _ := net.Listen("tcp", ":8080")
for {
    conn, _ := listener.Accept()
    go handleConn(conn) // 大量 G，少量 M；不是每个连接一个内核线程
}
```

Go 侧通常由运行时统一 `epoll_ctl`/`epoll_wait`，业务很少直接碰 LT/ET；自己写 C 网络库时才必须显式选模式。

### 3.4 io_uring：提交环与完成环

`io_uring` 用用户态可见的 **SQ（提交队列）/ CQ（完成队列）** 批量投递异步请求，减少“一次 syscall 一事”的往返。适合高 IOPS 存储、部分网络路径；复杂度高于 epoll，库与内核版本要求更高。

```text
应用填 SQE →（可选）io_uring_enter 提交 → 内核处理 → CQE 回结果
可配合固定 buffer、注册文件，进一步砍映射与 fd 查找成本
```

和 epoll 分工：epoll 擅长“等就绪再同步读写”；io_uring 擅长“把读写本身异步化并批处理”。Go 生态仍以 netpoller+epoll 为主，存储密集组件可评估 io_uring 绑定库。

### 3.5 零拷贝（Zero Copy）

#### 3.5.1 传统 read + write（4 次拷贝，4 次上下文切换）

一次“读文件再发给 socket”的用户态路径，典型是 **两次系统调用**，每次 syscall 各有进入内核 + 返回用户，合计 **4 次用户态/内核态切换**；数据路径则是 **4 次拷贝**（2×DMA + 2×CPU）：

```text
read:  磁盘 →（DMA）Page Cache →（CPU）用户 buf     ← 进入/返回内核 各 1
write: 用户 buf →（CPU）Socket 缓冲 →（DMA）网卡   ← 进入/返回内核 各 1
```

> 旧口径“4 拷贝 2 切换”少算了两次返回用户态；面试答 **4 拷贝 + 4 切换**（针对 read+write 这一对）。

#### 3.5.2 sendfile（减少到约 2 次拷贝）
```c
sendfile(sockfd, filefd, NULL, file_size);
// 文件页 → socket（可经 DMA gather）；不经用户缓冲
```

```go
// Linux 上 io.Copy(socket, file) 常能走到 sendfile
io.Copy(w, f)
```

#### 3.5.3 mmap 与静态文件服务

```c
char *data = mmap(NULL, file_size, PROT_READ, MAP_PRIVATE, fd, 0);
// 访问 data 触发缺页；可少一次显式 read，但仍可能有用户↔内核路径上的拷贝
```

**Nginx**：静态文件主路径是 **`sendfile on`**（再配合 `tcp_nopush` 等），不是“Nginx 用 mmap 做零拷贝”这种笼统说法。`mmap` 是另一种映射模型，和 Nginx 配置里的 sendfile 不是同一句话。

```nginx
location /static/ {
    sendfile on;
    tcp_nopush on;
}
```
### 3.6 直接IO（Direct IO）

**绕过页缓存，直接读写磁盘**：
```c
int fd = open("file.txt", O_DIRECT | O_RDONLY);
// 要求：buf地址对齐、大小为512字节的倍数
char *buf = aligned_alloc(512, 4096);
read(fd, buf, 4096);
```

**使用场景**：
- 数据库（自己管理缓存，不需要页缓存）
- 流媒体（大文件，不需要缓存）

**对比**：
```bash
# 普通IO（使用页缓存）
dd if=/dev/zero of=test bs=1M count=1000
# 1000+0 records in
# 1000+0 records out
# 1048576000 bytes (1.0 GB) copied, 0.5 s, 2.0 GB/s

# Direct IO（绕过缓存）
dd if=/dev/zero of=test oflag=direct bs=1M count=1000
# 1000+0 records in
# 1000+0 records out
# 1048576000 bytes (1.0 GB) copied, 2.0 s, 500 MB/s
```

## 4. 文件系统

### 4.1 inode与目录结构

**inode（索引节点）**：
```bash
ls -li /etc/hosts
# 123456 -rw-r--r-- 1 root root 123 Jan 1 00:00 /etc/hosts
#   ↑ inode号

stat /etc/hosts
# File: /etc/hosts
# Inode: 123456
# Links: 1
# Access: (0644/-rw-r--r--)
# Size: 123
# Blocks: 8
```

**inode包含的信息**：
- 文件类型（普通文件、目录、符号链接）
- 权限
- 所有者
- 大小
- 时间戳（atime、mtime、ctime）
- **数据块指针**（指向实际数据的位置）

**硬链接vs软链接**：
```bash
# 硬链接：多个文件名指向同一个inode
ln /etc/hosts /tmp/hosts_link
ls -li /etc/hosts /tmp/hosts_link
# 123456 -rw-r--r-- 2 root root 123 Jan 1 00:00 /etc/hosts
# 123456 -rw-r--r-- 2 root root 123 Jan 1 00:00 /tmp/hosts_link
# 同一个inode，Links=2

# 软链接：新文件，inode不同，内容是目标路径
ln -s /etc/hosts /tmp/hosts_symlink
ls -li /tmp/hosts_symlink
# 789012 lrwxrwxrwx 1 root root 10 Jan 1 00:00 /tmp/hosts_symlink -> /etc/hosts
```

### 4.2 文件系统布局（ext4）

```
┌──────────────────────────────────────────┐
│  Super Block（超级块）                    │
│  - 文件系统大小、块大小、inode数量等      │
└──────────────────────────────────────────┘
┌──────────────────────────────────────────┐
│  Block Group Descriptor（块组描述符）     │
│  - 每个块组的inode表、数据块位置          │
└──────────────────────────────────────────┘
┌──────────────────────────────────────────┐
│  Inode Bitmap（inode位图）                │
│  - 标记哪些inode空闲                      │
└──────────────────────────────────────────┘
┌──────────────────────────────────────────┐
│  Block Bitmap（块位图）                   │
│  - 标记哪些数据块空闲                     │
└──────────────────────────────────────────┘
┌──────────────────────────────────────────┐

└──────────────────────────────────────────┘
┌──────────────────────────────────────────┐

│  - 实际文件内容                           │
```


### 4.3 文件IO缓冲

#### 4.3.1 用户空间缓冲（stdio）
```c
// fwrite()：先写到用户空间缓冲区
FILE *fp = fopen("file.txt", "w");
fwrite("hello", 5, 1, fp);  // 写到用户缓冲区
// 此时还没写到内核

fflush(fp);  // 刷新到内核
fclose(fp);  // 关闭时自动fflush
```

#### 4.3.2 内核空间缓冲（page cache）
```c
// write()：写到内核页缓存
int fd = open("file.txt", O_WRONLY);
write(fd, "hello", 5);  // 写到page cache
// 此时还没写到磁盘

fsync(fd);  // 强制刷新到磁盘
close(fd);
```

**查看page cache**：
```bash
free -h
#               total  used   free   shared  buff/cache  available
# Mem:          16Gi   2Gi    8Gi    100Mi   6Gi         13Gi
#                                             ↑ page cache

# 清空page cache（测试用，生产慎用）
sync
echo 3 > /proc/sys/vm/drop_caches
```

### 4.4 文件系统性能优化

#### 4.4.1 批量操作
```go
// ❌ 逐条写入（10000次系统调用）
for _, line := range lines {
    file.WriteString(line + "\n")
}

// ✅ 批量写入（1次系统调用）
var buf bytes.Buffer
for _, line := range lines {
    buf.WriteString(line + "\n")
}
file.Write(buf.Bytes())
```

#### 4.4.2 异步刷盘
```go
// ❌ 每次都fsync（慢）
file.Write(data)
file.Sync()  // 每次都刷盘

// ✅ 定时刷盘
ticker := time.NewTicker(1 * time.Second)
go func() {
    for range ticker.C {
        file.Sync()  // 每秒刷盘一次
    }
}()
```

## 5. 网络协议栈（内核路径视角）

> **本章边界**：只写「包如何进/出本机内核」——socket、软中断、NAPI、队列与主机侧参数。
> TCP/HTTP/TLS/拥塞控制细节、抓包解读与协议选型见 [`06-网络基础与协议.md`](./06-网络基础与协议.md)。两篇不要重复背两套握手故事。

### 5.1 收发包与 softirq / NAPI

把网卡想象成传送带：硬中断只负责“铃响一声”，真正卸货在 **softirq（软中断，Linux 下半部机制）** 里做——不要和 x86 的 `int` 软件中断指令混称。

```text
【收包】
网卡 DMA 写入 ring buffer → 硬中断（尽量短）
  → 触发 NET_RX softirq
  → NAPI poll：关中断风暴，批量从 ring 取包
  → 协议栈（IP/TCP）→ socket 接收队列 → 唤醒阻塞在 recv/epoll 的进程

【发包】
send/sendto → socket 发送队列 → 协议栈封装
  → qdisc（如 fq_codel）→ 驱动 TX ring → DMA 出网卡
  → 完成路径常走 NET_TX softirq
```

**NAPI**：高负载时从“每包中断”切到轮询批量处理，降低中断风暴；空闲再退回中断。观测：

```bash
cat /proc/interrupts | grep -i eth
cat /proc/softirqs          # 看 NET_RX / NET_TX
mpstat -P ALL 1             # si% 升高常与收包 softirq 相关
ss -s
nstat -az | grep -E 'Tcp|Ip|Udp|TcpExt'
```

### 5.2 主机侧队列：半连接 / 全连接

握手状态机细节见网络篇；主机排障先看队列是否打满：

```bash
ss -lnt
# State   Recv-Q  Send-Q  Local Address:Port
# LISTEN  0       128     0.0.0.0:80
#         ↑ 当前全连接积压    ↑ backlog 上限

sysctl net.core.somaxconn
sysctl net.ipv4.tcp_max_syn_backlog
# 溢出线索：nstat /netstat -s 中的 ListenOverflows、ListenDrops、SYNFIFO
```

### 5.3 拥塞窗口初值与主机观测

教材慢启动常画 `cwnd=1`；**现代 Linux 默认初始拥塞窗口约 10 个 MSS**（RFC 6928 一类实践），别再答“永远从 1 开始”。

```bash

# ... cubic ... cwnd:10 ssthresh:20
sysctl net.ipv4.tcp_congestion_control   # cubic / bbr ...
# BBR、Cubic 算法对比与调参 → 06-网络基础与协议.md
```

### 5.4 Socket 参数（主机侧常用旋钮）


## 6. Namespace 与 Cgroup 资源隔离

> 容器 ≈ **Namespace（看什么）** + **Cgroup（用多少）**。前者改可见性与隔离边界，后者卡 CPU/内存/IO 配额。

### 6.1 Namespace：进程眼里的“小宇宙”

类比：同一栋大楼（内核）里，给每户发不同门牌与水电表——Namespace 换门牌（视图），Cgroup 定水电额度。

| Namespace | 隔离内容 | 典型现象 |
|-----------|----------|----------|
| **pid** | 进程 ID 视图 | 容器内 PID 1 是入口进程，不是宿主机 init |
| **mnt** | 挂载点 | 容器根文件系统与宿主机目录树分离 |
| **net** | 网卡、路由、iptables、socket | 独立 eth0/lo、独立端口空间 |
| **uts** | hostname / domainname | `hostname` 在容器内不同 |
| **ipc** | System V IPC、POSIX 消息队列等 | 信号量/共享内存不串台 |
| **user** | UID/GID 映射 | 容器内 root 可映射为宿主机普通用户 |
| **cgroup** | cgroup 根视图 | 进程看到的 cgroup 层级虚拟化 |

```bash
lsns                              # 列出命名空间
ls -l /proc/<PID>/ns              # 某进程加入了哪些 ns
# 进入已有容器网络命名空间观察
nsenter -t <PID> -n ss -lntp
unshare --net --pid --fork --mount-proc /bin/bash  # 实验用，慎在生产乱试
```

Docker/K8s 默认组合上述命名空间；`--net=host` / `hostPID` 等是故意削弱隔离换性能或可观测性。

### 6.2 Cgroup概述

**四大资源子系统**：
| 子系统 | 控制对象 | 关键文件/工具 |
|--------|----------|---------------|
| **CPU** | 计算时间、核心绑定 | cpuset, cpu.cfs_quota_us, cpu.shares |
| **Memory** | 内存用量、Swap | memory.limit_in_bytes, memory.oom_control |
| **BlkIO** | 磁盘带宽、IOPS | blkio.throttle.*, blkio.weight |
| **Net** | 网络带宽 | net_cls + tc（流量控制） |

**查看系统Cgroup版本**：
```bash
# Cgroup V1（传统，各子系统独立挂载）
mount | grep cgroup
# cgroup on /sys/fs/cgroup/cpu type cgroup (rw,...,cpu,cpuacct)
# cgroup on /sys/fs/cgroup/memory type cgroup (rw,...,memory)

# Cgroup V2（unified hierarchy，单一挂载点）
mount | grep cgroup2
# cgroup2 on /sys/fs/cgroup type cgroup2 (rw,...,nsdelegate)
```

### 6.3 CPU资源隔离

Linux通过CFS（完全公平调度器）实现CPU时间的分配，Cgroup提供三种隔离方式：

#### 6.3.1 cpuset — 核心绑定

将进程绑定到指定CPU核心运行，实现**物理隔离**：

```bash
# 查看/设置cgroup绑定的CPU核心
cat /sys/fs/cgroup/cpuset/mygroup/cpuset.cpus
echo "0-3" > /sys/fs/cgroup/cpuset/mygroup/cpuset.cpus

# 必须同时设置内存节点（NUMA）
echo "0" > /sys/fs/cgroup/cpuset/mygroup/cpuset.mems
```

**超线程陷阱**：在开启超线程的服务器上，需注意核心编号的物理对应关系：
```bash
# 查看物理核心与逻辑核心的映射
cat /proc/cpuinfo | grep -e "core id" -e "physical id"
# physical id: 0, core id: 0  → 逻辑核心 0 和 12 是同一物理核心
# 绑定 0-5 和 12-17 才是"半数物理核心"
# 绑定 0-11 看似一半，实际覆盖了所有物理核心（超线程部分无法倍增算力）
```

**实验数据对比**（24逻辑核心服务器，筛质数测试）：
| 配置 | 核心数 | 执行时间 |
|------|--------|----------|
| 0-23（全部） | 24 | 8.9s |
| 0-11（全物理核心） | 12 | 9.5s ≈ 无变化！ |
| 0-5,12-17（半物理核心） | 12 | 17.8s ≈ 翻倍 |

#### 6.3.2 cpuquota — 配额限制（硬限制）

按时间比例限制CPU使用上限，**即使系统空闲也不能超额**：

```bash
# 时间周期（默认100ms = 100000μs）
cat /sys/fs/cgroup/cpu/mygroup/cpu.cfs_period_us   # 100000

# 配额（-1表示不限制）
# 限制单核50%：echo 50000
# 限制4核满载：echo 400000
# 限制24核50%：echo 1200000
echo "50000" > /sys/fs/cgroup/cpu/mygroup/cpu.cfs_quota_us
```

**计算公式**：`quota = 目标百分比 × period × CPU核心数`

#### 6.3.3 cpushares — 权重比例（弹性限制）

按权重比例分配CPU时间，**系统空闲时可借用其他cgroup的资源**：

```bash
# 权重范围：2-262144，默认1024
echo "1024" > /sys/fs/cgroup/cpu/groupA/cpu.shares  # A
echo "2048" > /sys/fs/cgroup/cpu/groupB/cpu.shares  # B

# 效果：
# 竞争时：A占1/3，B占2/3
# B空闲时：A可占满所有CPU
```

**三种方式对比**：
| 特性 | cpuset | cpuquota | cpushares |
|------|--------|----------|-----------|
| **隔离类型** | 物理核心隔离 | 时间配额硬限制 | 时间权重弹性分配 |
| **空闲借用** | ❌ 不能 | ❌ 不能 | ✅ 可以 |
| **最小粒度** | 1个核心 | 任意百分比 | 任意比例 |
| **隔离强度** | 最强（核心独占） | 强（硬上限） | 弱（按比例） |
| **适用场景** | 延迟敏感型、NUMA | 多租户硬隔离 | 弹性共享、超卖 |

**内核资源冲突的影响**：当多个cgroup的进程访问相同的内核资源（如同一文件的自旋锁竞争），cpuset由于物理隔离表现最优，cpuquota在此场景下性能损失最大。

### 6.4 内存资源隔离

> 主机回收链（水位线 / kswapd / OOM）见 [2.5](#25-内存回收链水位线--kswapd--direct-reclaim--swap--oom)；此处只谈 **cgroup 限额**。

#### 6.4.1 内存限制配置

```bash
# 硬限制：内存使用上限（超出触发OOM或挂起）
echo "512M" > /sys/fs/cgroup/memory/mygroup/memory.limit_in_bytes

# 内存+Swap总量限制（设为与limit相同 = 禁用Swap）
echo "512M" > /sys/fs/cgroup/memory/mygroup/memory.memsw.limit_in_bytes

# 软限制：用于内存超卖场景，全局内存紧张时按此值回收
echo "256M" > /sys/fs/cgroup/memory/mygroup/memory.soft_limit_in_bytes

# 查看当前使用量
cat /sys/fs/cgroup/memory/mygroup/memory.usage_in_bytes
```

#### 6.4.2 OOM控制

```bash
cat /sys/fs/cgroup/memory/mygroup/memory.oom_control
# oom_kill_disable 0   → 0=启用OOM Killer（默认），1=禁用（进程挂起为D状态）
# under_oom 0          → 0=正常，1=当前已OOM

# 禁用OOM Killer（进程挂起而非被杀）
echo 1 > /sys/fs/cgroup/memory/mygroup/memory.oom_control
# 恢复方式：增加内存限制、杀进程、迁移进程到其他cgroup
```

#### 6.4.3 内存压力通知（eventfd）

```c
// 通过 eventfd + memory.pressure_level 实现内存压力监控
int efd = eventfd(0, 0);
int cfd = open("/sys/fs/cgroup/memory/mygroup/memory.pressure_level", O_RDONLY);
// 写入 cgroup.event_control: "<efd> <cfd> <level>"
// level: "low" | "medium" | "critical"

// 压力级别：
// low     → 开始内存回收
// medium  → 开始Swap换出、活跃Cache写回
// critical → 触发OOM Killer
```

### 6.5 IO资源隔离

#### 6.5.1 Linux IO 路径分层（简图）

```text
应用 read()/write()
  → VFS → 文件系统 → Page Cache（Buffered IO）
  → 通用块层（带宽/IOPS throttle 多在此）
  → IO 调度器 → 驱动 → 设备
```

#### 6.5.2 IO 调度算法：legacy vs multi-queue

面试别背死 `cfq/deadline/noop` 三件套当“当今默认”。多队列块层普及后，常见是：

| 调度器 | 时代 | 特点 | 适用 |
|--------|------|------|------|
| **none** | mq | 基本不排序，开销最低 | NVMe/SSD 常见首选 |
| **mq-deadline** | mq | 按期限排序，防饿死 | 通用、混部、不少 HDD |
| **bfq** | mq | 按进程公平、偏交互延迟 | 桌面/共享 HDD |
| cfq / deadline / noop | **legacy 单队列** | 旧内核常见 | 仅在老系统或非 mq 设备上还会看到 |

```bash
cat /sys/block/nvme0n1/queue/scheduler
# [none] mq-deadline bfq          ← 现代常见
# 老盘/老内核才可能看到：noop deadline [cfq]

# SSD/NVMe：none 或 mq-deadline
# HDD：mq-deadline 或 bfq（视负载）
echo mq-deadline > /sys/block/sda/queue/scheduler
```

V1 `blkio.weight` 依赖旧 CFQ 一类路径，**现代机器上往往不可用或无效**；限速优先用 throttle（V1）或 cgroup v2 的 `io.max` / `io.weight`。

#### 6.5.3 blkio 限速配置

```bash
# 带宽 / IOPS（通用块层；V1 对 Buffered IO 常“限不住”）
echo "8:0 1048576" > /sys/fs/cgroup/blkio/mygroup/blkio.throttle.write_bps_device
echo "8:0 100" > /sys/fs/cgroup/blkio/mygroup/blkio.throttle.write_iops_device
```

**重要限制**：Cgroup V1 的 blkio 对 **Buffered IO 往往无法有效限速**（回写路径难归属）。V2 的 `io` 控制器对此改善明显。

### 6.6 网络资源隔离

Cgroup网络隔离复用Linux的 **tc（Traffic Control）** 机制，通过 `net_cls` 子系统给数据包打标签，配合tc队列规则实现限速。

#### 6.6.1 tc队列规则（qdisc）概览

| 类型 | qdisc | 核心机制 | 特点 |
|------|-------|----------|------|
| **不可分类** | pfifo_fast | 3优先级FIFO | 旧版默认，不可调参 |
| **不可分类** | fq_codel | 公平队列+CoDel | **新版默认**，解决Bufferbloat |
| **不可分类** | tbf | 令牌桶 | 简单限速 |
| **可分类** | htb | 分层令牌桶 | **推荐**，支持带宽借用和分类 |

**Bufferbloat问题**：过大的网络缓冲区导致数据包驻留时间超过超时阈值，引发全部请求超时失败，系统看似满载实则不可用。CoDel算法通过控制**驻留时间**而非队列长度来解决此问题。

#### 6.6.2 使用cgroup限制网络带宽

```bash
# 1. 创建cgroup并标记classid
mkdir /sys/fs/cgroup/net_cls/mygroup
echo 0x00010010 > /sys/fs/cgroup/net_cls/mygroup/net_cls.classid
# 0xAAAABBBB → AAAA:BBBB = 1:10

# 2. 配置HTB队列规则
tc qd add dev eth0 root handle 1: htb default 100
tc cl add dev eth0 parent 1: classid 1:1 htb rate 100mbit burst 20k
tc cl add dev eth0 parent 1:1 classid 1:10 htb rate 10mbit ceil 50mbit burst 20k
tc qd add dev eth0 parent 1:10 handle 10: fq_codel

# 3. 添加cgroup过滤器
tc fi add dev eth0 parent 1: protocol ip prio 1 handle 1: cgroup

# 4. 将进程加入cgroup
echo $PID > /sys/fs/cgroup/net_cls/mygroup/tasks
```

### 6.7 Cgroup V2（Unified Hierarchy）

Cgroup V2将所有资源控制器统一到单一层级，简化配置并新增重要功能：

**开启方法**：
```bash
# 内核引导参数
grubby --update-kernel=ALL --args=systemd.unified_cgroup_hierarchy=1
```

#### 6.7.1 V2核心变化

| 特性 | V1 | V2 |
|------|----|----|
| 层级结构 | 每个资源独立层级 | **统一层级** |
| Buffer IO限速 | ❌ 不支持 | ✅ **支持** |
| 压力通知 | eventfd（仅memory） | **PSI机制**（cpu/memory/io） |
| 线程级控制 | ❌ | ✅ threaded模式 |
| 配置复杂度 | 高 | **大幅简化** |

#### 6.7.2 V2配置示例

```bash
# 创建cgroup
mkdir /sys/fs/cgroup/mygroup

# 启用资源控制器
echo '+cpu +memory +io +pids' > /sys/fs/cgroup/cgroup.subtree_control

# CPU配额（max period格式）
echo "50000 100000" > /sys/fs/cgroup/mygroup/cpu.max      # 单核50%
echo "100" > /sys/fs/cgroup/mygroup/cpu.weight             # 权重（1-10000）

# 内存限制
echo "512M" > /sys/fs/cgroup/mygroup/memory.max            # 硬限制
echo "256M" > /sys/fs/cgroup/mygroup/memory.high           # 软限制（触发回收）
echo "128M" > /sys/fs/cgroup/mygroup/memory.min            # 硬保护（不被回收）
echo "1" > /sys/fs/cgroup/mygroup/memory.oom.group         # 整组OOM

# IO限速（支持Buffer IO！）
echo "253:0 wbps=2097152" > /sys/fs/cgroup/mygroup/io.max  # 写2MB/s
echo "253:0 rbps=10485760 wiops=100" > /sys/fs/cgroup/mygroup/io.max

# PIDS限制
echo "1000" > /sys/fs/cgroup/mygroup/pids.max

# 添加进程
echo $PID > /sys/fs/cgroup/mygroup/cgroup.procs
```

#### 6.7.3 PSI（Pressure Stall Information）

V2引入的**统一压力监控机制**，可监控cpu/memory/io的资源压力：

```bash
cat /sys/fs/cgroup/mygroup/cpu.pressure
# some avg10=4.56 avg60=2.30 avg300=1.15 total=234567
# full avg10=0.00 avg60=0.00 avg300=0.00 total=0

# some：至少有一个任务在等待资源的时间比例
# full：所有任务都在等待资源的时间比例（cpu无此项）
```

## 7. 系统调用与性能

系统调用不是“慢函数”，而是一次**特权级往返 + 内核路径**。优化时先拆成本，再选批量、vDSO 或用户态旁路。

### 7.1 成本拆解：一次 syscall 贵在哪

```text
用户态准备参数
  → 陷入内核（syscall 指令 / 特权切换）
  → 保存/恢复寄存器与部分上下文
  → 内核校验（fd、缓冲、权限）
  → 真正干活（VFS / 协议栈 / 调度 / 可能睡眠）
  → 返回用户态
  → 附带：I-cache/TLB/分支预测扰动
```

| 成本项 | 量级直觉 | 说明 |
|--------|----------|------|
| 纯陷入往返 | 约几十～数百 ns（硬件与微架构而异） | 空 syscall 基准 |
| 参数校验与查找 | 视路径 | 如 fd → file 结构 |
| 真正工作 | μs～ms | 磁盘、网络、锁等待主导 |
| 调度与睡眠 | 不确定 | 可能被换出，延迟远大于“切换本身” |

别背死“系统调用 = 100ns”：那是空路径量级；线上 `read` 慢往往慢在等待，不在陷入。

### 7.2 怎么测

```bash
# 按进程汇总次数与耗时占比
strace -c -p <PID>
# 注意：只含 syscall；缺页、软中断不在这里

# 带时间戳看单次延迟
strace -tt -T -p <PID> -e trace=network,file,desc

# 更轻量：perf
perf trace -p <PID>
perf stat -e raw_syscalls:sys_enter ./myapp

# 从 CPU 画像反推是否 syscall 过多
pidstat -u -p <PID> 1    # %system 高 + strace 热点 → 内核路径嫌疑
```

### 7.3 批量 IO：把 N 次往返收成 1 次

```go
// ❌ 每次一字节一次 write
for i := 0; i < 10000; i++ {
    syscall.Write(fd, []byte("x"))
}

// ✅ 用户态聚合再一次 write；或 writev/readv、sendmmsg/recvmmsg
var buf bytes.Buffer
for i := 0; i < 10000; i++ {
    buf.WriteByte('x')
}
syscall.Write(fd, buf.Bytes())
```

网络高 QPS 还可：应用层 batch、`epoll` 一次捞多事件、存储侧评估 `io_uring` 批量提交（见第 3 章）。

### 7.4 vDSO：有些“syscall”根本不进内核

内核把只读数据页映射进每个进程，libc 对部分调用走用户态快路径。

```c
gettimeofday(&tv, NULL);   // 常见走 vDSO
clock_gettime(CLOCK_MONOTONIC, &ts);
getcpu(...);               // 视架构/内核
```

```bash
ldd /bin/ls
# linux-vdso.so.1 => (0x00007ffe123ab000)
cat /proc/self/maps | grep vdso
```

高频打点时间用 monotonic + vDSO 友好接口，避免无必要的 `time` 类陷入。

### 7.5 futex：用户态锁的内核等待点

`mutex`/`channel` 竞争不激烈时在用户态 CAS；拿不到锁才 `futex` 睡眠——这是 Go/`pthread` 锁的常见内核出口。

```bash
# 看是否大量卡在 futex
perf top -p <PID>
strace -c -e futex -p <PID>
# /proc/<PID>/stack 或 gdb 看锁持有栈
```

优化方向：降临界区、分片锁、避免惊群式广播唤醒；不是“少用锁”一句话了事。

### 7.6 优化清单（按性价比）

1. **先测**：`strace -c` / `perf` 确认是 syscall 次数问题还是等待问题
2. **批量**：缓冲写、vectored IO、事件驱动一次处理多 fd
3. **能走 vDSO 就别强行 syscall**
4. **锁竞争看 futex，不是只看 us**
5. **极端路径**再考虑 io_uring、DPDK/XDP（代价是复杂度与运维面）

## 8. Linux内核深入

> 本节覆盖Linux内核的核心机制，包括内存寻址模型、中断与异常处理、内核同步机制、内核抢占、lockup检测、D状态与load计算、系统调用传参方式等，帮助深入理解操作系统底层行为。

### 8.1 内存寻址：物理地址、逻辑地址、线性地址

**三种地址的关系**：

```
逻辑地址（Logical Address）
    = 段选择符(Segment Selector) : 段内偏移(Offset)
        ↓ 分段机制（Segmentation）
线性地址（Linear Address / 虚拟地址）
    = 段基址 + 偏移量
        ↓ 分页机制（Paging）
物理地址（Physical Address）
    = 页框号 + 页内偏移
```

**x86_64下的实际情况**：
- Linux在x86_64下**几乎绕过了分段**：所有段基址设为0，段限制设为最大值
- 因此：逻辑地址 ≈ 线性地址 ≈ 虚拟地址（平坦内存模型）
- 分页是实际使用的地址转换机制

#### 分段（Segmentation）

```
# x86中的段描述符（GDT / LDT）
段描述符包含：
- Base Address：段基地址（32位 or 64位下为0）
- Limit：段界限
- DPL：描述符特权级（0=内核，3=用户）
- Type：代码段/数据段/系统段

# Linux的平坦模型：
__KERNEL_CS: base=0, limit=0xFFFFFFFF, DPL=0  # 内核代码段
__KERNEL_DS: base=0, limit=0xFFFFFFFF, DPL=0  # 内核数据段
__USER_CS:   base=0, limit=0xFFFFFFFF, DPL=3  # 用户代码段
__USER_DS:   base=0, limit=0xFFFFFFFF, DPL=3  # 用户数据段

# 所有段基地址为0 → 逻辑偏移 = 线性地址
```

#### 分页（Paging）

**x86_32 vs x86_64页表结构**：

| 特性 | x86_32（普通） | x86_32（PAE） | x86_64 |
|------|-------------|-------------|--------|
| **级数** | 2级 | 3级 | 4级（PML4） |
| **虚拟地址位** | 32位（4GB） | 32位（4GB） | 48位（256TB） |
| **物理地址位** | 32位（4GB） | 36位（64GB） | 52位（4PB） |
| **页表项大小** | 4字节 | 8字节 | 8字节 |
| **目录结构** | PGD→PTE | PGD→PMD→PTE | PGD→PUD→PMD→PTE |

**x86_64 四级页表**：
```
虚拟地址(48位) = PGD[9] + PUD[9] + PMD[9] + PTE[9] + Offset[12]

页表项标记位（PTE flags）：
- P (Present)：页是否在内存中
- R/W (Read/Write)：读写权限
- U/S (User/Supervisor)：用户态/内核态访问权限
- A (Accessed)：是否被访问过（供LRU页面回收参考）
- D (Dirty)：是否被修改过（决定是否需要写回磁盘）
- NX (No Execute)：禁止执行（安全防护，防止栈溢出攻击）
```

**页表切换**：
```c
// 进程切换时，通过加载CR3寄存器切换页表
// CR3 存储当前进程的PGD（页全局目录）物理地址
mov cr3, <新进程PGD物理地址>

// 切换CR3会导致TLB全部失效！
// 这是进程上下文切换开销大的主要原因之一

// 优化：PCID（Process Context ID）
// 支持PCID的CPU可以为不同进程的TLB条目打标签
// 切换CR3时不需要刷新整个TLB
```

### 8.2 中断与异常处理

#### 中断 vs 异常（先分清两套“软中断”）

| 类型 | 来源 | 示例 |
|------|------|------|
| **硬中断（Hardware IRQ）** | 外部设备 | 网卡收包、磁盘完成、时钟 |
| **softirq（Linux 软中断 / 下半部）** | 内核延迟处理机制 | `NET_RX_SOFTIRQ`、`TIMER_SOFTIRQ` |
| **异常（Exception）** | CPU 执行指令时 | 缺页 `#PF`、除零、GP |

> **术语陷阱**：CPU/教材里的 **software interrupt**（如 x86 `int n`）≠ Linux 的 **softirq**。本文说“软中断”默认指 **softirq 下半部**；与硬中断配对的是上半部/下半部，不是“软件触发的硬中断”。

#### 中断处理完整流程

```
硬件设备产生中断
    ↓
中断控制器（APIC）→ 选择目标CPU
    ↓
CPU暂停当前任务
    ↓ 保存现场（压栈：RIP/CS/RFLAGS/RSP/SS）
    ↓
查IDT（中断描述符表）→ 找到中断处理函数入口
    ↓
┌─────────────────────────────────┐
│ 上半部（Top Half / Hardirq）    │
│ - 关中断执行，必须快速完成      │
│ - 读取设备状态、清中断标志      │
│ - 将数据放入缓冲区             │
│ - 如需延迟处理，标记下半部      │
└─────────────────────────────────┘
    ↓ 退出上半部，开中断
┌─────────────────────────────────┐
│ 下半部（Bottom Half）           │
│ 负责耗时的后续处理              │
│ - softirq / tasklet / workqueue │
└─────────────────────────────────┘
    ↓
恢复现场，继续执行被中断的任务
```

#### 三种下半部机制对比

| 机制 | 执行上下文 | 并发性 | 可否睡眠 | 适用场景 |
|------|-----------|--------|---------|---------|
| **softirq** | 软中断上下文 | 同类型可多CPU并发 | ❌ 不可 | 网络收发包(NET_RX/TX)、块设备 |
| **tasklet** | 软中断上下文 | 同实例不可并发 | ❌ 不可 | 驱动中较简单的延迟处理 |
| **workqueue** | 内核线程 | 可并发 | ✅ 可以 | 需要睡眠的操作（分配内存、IO等） |

```c
// softirq示例（网络收包）
// 定义在 kernel/softirq.c
enum {
    HI_SOFTIRQ = 0,           // 高优先级tasklet
    TIMER_SOFTIRQ,             // 定时器
    NET_TX_SOFTIRQ,            // 网络发送
    NET_RX_SOFTIRQ,            // 网络接收 ← 最常见
    BLOCK_SOFTIRQ,             // 块设备
    TASKLET_SOFTIRQ,           // 普通tasklet
    SCHED_SOFTIRQ,             // 调度器
    RCU_SOFTIRQ,               // RCU回调
};

// tasklet示例
struct tasklet_struct my_tasklet;
void my_tasklet_handler(unsigned long data) {
    // 延迟处理逻辑（不可睡眠）
}
tasklet_init(&my_tasklet, my_tasklet_handler, 0);
tasklet_schedule(&my_tasklet);  // 调度执行

// workqueue示例
struct work_struct my_work;
void my_work_handler(struct work_struct *work) {
    // 可以睡眠的处理逻辑
    kmalloc(1024, GFP_KERNEL);  // 可以分配内存
}
INIT_WORK(&my_work, my_work_handler);
schedule_work(&my_work);  // 放入系统默认workqueue
```

### 8.3 内核锁机制

| 锁类型 | 可否睡眠 | 适用场景 | 开销 |
|--------|---------|---------|------|
| **spinlock** | ❌ 忙等 | 短临界区、中断上下文 | 极低（CPU自旋） |
| **mutex** | ✅ 可睡眠 | 长临界区、进程上下文 | 中等（涉及调度） |
| **rwlock** | ❌ 忙等 | 读多写少 | 低 |
| **rwsem** | ✅ 可睡眠 | 读多写少、可能睡眠 | 中等 |
| **RCU** | ✅/❌ | 读极多写极少 | 读端零开销 |

#### spinlock（自旋锁）

```c
spinlock_t lock;
spin_lock_init(&lock);

// 普通自旋锁（进程上下文）
spin_lock(&lock);
// 临界区（必须极短，不能睡眠！）
spin_unlock(&lock);

// 中断安全版本（中断上下文也要用此锁时）
spin_lock_irqsave(&lock, flags);    // 关本地中断 + 加锁
// 临界区
spin_unlock_irqrestore(&lock, flags); // 恢复中断 + 解锁

// ⚠️ 在持有spinlock时绝不能睡眠/调度
// 否则会导致死锁（持锁CPU被调度走，其他CPU自旋等待）
```

#### mutex（互斥锁）

```c
struct mutex lock;
mutex_init(&lock);

mutex_lock(&lock);      // 获取不到则睡眠等待
// 临界区（可以做耗时操作、可以睡眠）
mutex_unlock(&lock);

// ⚠️ 不能在中断上下文使用（中断中不能睡眠）
// ⚠️ 用户态持有mutex锁时，进程处于S状态（可中断睡眠），不是D状态
```

#### RCU（Read-Copy-Update）

**核心思想**：读端零开销，写端负责延迟释放旧数据

```c
// 读端（零开销，无锁！）
rcu_read_lock();           // 仅禁止抢占（不是真正的锁）
p = rcu_dereference(gp);  // 读取受RCU保护的指针
// 使用 p 访问数据
rcu_read_unlock();

// 写端（Copy-on-Write模式）
struct data *new_data = kmalloc(sizeof(*new_data), GFP_KERNEL);
*new_data = *old_data;     // 复制旧数据
new_data->field = new_val; // 修改新副本
rcu_assign_pointer(gp, new_data);  // 原子替换指针
synchronize_rcu();         // 等待所有读端退出（Grace Period）
kfree(old_data);           // 安全释放旧数据
```

**RCU原理图**：
```
写者：           读者A（旧数据）    读者B（新数据）
修改 → 复制新副本 ──→ 原子替换指针 ──→ 等待Grace Period ──→ 释放旧数据
                      │                    │
                      └── 此时读者A仍在读旧数据，安全
                                           └── 读者A退出后，旧数据可安全释放
```

**应用场景**：路由表、进程列表、文件系统dcache等读远多于写的数据结构

### 8.4 内核抢占（Kernel Preemption）

**什么是内核抢占？**
- 普通进程在**用户态**可被调度器抢占（时间片用完、更高优先级任务到来）
- **内核抢占**指：进程在**内核态**执行系统调用/中断处理时，也可被高优先级任务抢占

**内核抢占模型（发行版并不统一）**：

| 模型 | CONFIG 选项 | 特点 | 常见取向 |
|------|-------------|------|----------|
| **无强制抢占** | `PREEMPT_NONE` | 内核路径少抢占点，偏吞吐 | 部分服务器定制核 |
| **自愿抢占** | `PREEMPT_VOLUNTARY` | 显式检查点可抢占 | 不少通用/服务器发行版实际如此 |
| **抢占式** | `PREEMPT` / `PREEMPT_DYNAMIC` 等 | 除持锁等临界区外更易抢占 | 桌面、低延迟、部分云镜像 |

```bash
# 以运行中的配置为准，不要背“服务器一定是 PREEMPT_NONE”
cat /boot/config-$(uname -r) | grep -E '^CONFIG_PREEMPT'
uname -v
# 输出含 PREEMPT / PREEMPT_DYNAMIC / VOLUNTARY 等字样，含义随内核版本略有差异
```

> 绝对化说法“服务器内核都是 PREEMPT_NONE”不成立：RHEL/Ubuntu/云厂商镜像选项不同，且新内核还有动态抢占。结论应来自 `config` / `uname -v`，再谈延迟与吞吐权衡。

**抢占计数器（preempt_count）**：
```c
// 内核通过preempt_count判断是否可以抢占
// preempt_count > 0 时不可抢占

preempt_disable();   // preempt_count++
// 临界区
preempt_enable();    // preempt_count--，检查是否需要重新调度

// 持有spinlock时自动禁用抢占
spin_lock(&lock);    // 隐含 preempt_disable()
// ...
spin_unlock(&lock);  // 隐含 preempt_enable()
```

### 8.5 Lockup检测：Hard Lockup与Soft Lockup

#### Soft Lockup（软锁定）

**定义**：CPU被内核代码**持续占用超过阈值**（默认20秒），不调度其他任务

**检测原理**：
```
watchdog内核线程（每个CPU一个，优先级最高的SCHED_FIFO）
    - 正常情况下：watchdog线程周期性被调度执行，更新时间戳
    - 异常情况下：某个任务长时间占用CPU（如死循环、长时间持锁）
                  watchdog线程无法被调度
                  时钟中断检查发现watchdog时间戳过期
                  → 触发 soft lockup 警告
```

```bash
# 内核日志
dmesg | grep -i lockup
# BUG: soft lockup - CPU#2 stuck for 22s! [kworker/2:1:1234]

# 调整阈值
sysctl -w kernel.watchdog_thresh=30  # 默认10（soft lockup在2倍=20s触发）
```

#### Hard Lockup（硬锁定）

**定义**：CPU被**中断也无法打断**的代码持续占用（通常是关中断后死循环）

**检测原理**：
```
NMI watchdog（不可屏蔽中断）
    - 基于PMU（Performance Monitoring Unit）的NMI中断
    - NMI不受关中断（cli）影响
    - 如果soft lockup的watchdog线程超过阈值未更新，
      NMI watchdog检测到 → 触发 hard lockup panic
```

```bash
# 内核日志
# Watchdog detected hard LOCKUP on cpu 3

# 检查NMI watchdog是否启用
cat /proc/sys/kernel/nmi_watchdog  # 1=启用

# hard lockup常见原因：
# 1. 关中断后进入死循环
# 2. 内核spinlock死锁（A等B，B等A）
# 3. 硬件故障（如PCIe设备卡死）
```

**对比总结**：

| 特性 | Soft Lockup | Hard Lockup |
|------|------------|-------------|
| **定义** | CPU不调度其他任务 | CPU连中断都无法响应 |
| **检测机制** | 时钟中断 + watchdog线程 | NMI watchdog（PMU） |
| **默认阈值** | 20秒 | 10秒 |
| **关中断** | 可以响应中断 | 中断也被屏蔽 |
| **严重程度** | 警告（可恢复） | Panic（通常不可恢复） |
| **常见原因** | 长时间持锁、死循环（未关中断） | spinlock死锁、关中断死循环 |

### 8.6 进程D状态与Load Average

#### D状态详解

**D状态（TASK_UNINTERRUPTIBLE）**：不可中断的睡眠

```
进程状态对比：
S (Sleeping)    - 可中断睡眠，可被信号唤醒（如等待用户输入）
D (Disk Sleep)  - 不可中断睡眠，不能被信号唤醒（如等待磁盘IO）
                  → kill -9 也杀不死D状态进程！

为什么需要D状态？
- 保护内核数据结构的一致性
- 例如：进程正在通过NFS读取文件
  如果此时被信号中断，内核中的IO状态可能不一致
  因此设为D状态，直到IO操作完成

常见触发D状态的场景：
1. 磁盘IO等待（read/write系统调用进入内核后）
2. NFS/CIFS网络文件系统访问（网络延迟导致长时间D状态）
3. 内核中等待mutex锁（部分内核路径）
4. 页面换出/换入（swap操作）
```

```bash
# 查看D状态进程
ps aux | awk '$8 ~ /D/ {print}'

# 查看D状态进程的内核栈（定位卡在哪里）
cat /proc/<pid>/stack
# [<0>] nfs_wait_bit_killable+0x1c/0x30 [nfs]
# [<0>] __wait_on_bit+0x42/0x80
# [<0>] out_of_line_wait_on_bit+0x89/0xb0
# → 说明卡在NFS等待上
```

**注意**：用户态持有mutex锁的进程**不处于D状态**，而是S状态或R状态。只有**内核态**的不可中断等待才是D状态。

#### Load Average计算原理

```
Linux的load average = 处于R状态 + 处于D状态的任务数的指数移动平均

公式：
load(t) = load(t-1) * e^(-1/τ) + n * (1 - e^(-1/τ))

其中：
- n = 当前R + D状态的任务数
- τ = 时间常数（1分钟/5分钟/15分钟）
- 每5秒（HZ/12 tick）采样一次
```

```bash
# 查看load average
uptime
# 14:00:00 up 10 days,  load average: 2.50, 3.20, 4.10
#                                     1分钟  5分钟  15分钟

cat /proc/loadavg
# 2.50 3.20 4.10 3/256 12345
# ↑               ↑     ↑
# load avg        R/总进程数  最新PID

# 判断标准：
# load / CPU核心数 > 1 → 过载
# 例：4核CPU，load=4.0 表示刚好满载
# load=8.0 表示有一半任务在等待
```

**为什么D状态计入load？**
- D状态进程虽然不占CPU，但占用了系统资源（IO子系统繁忙）
- 大量D状态进程说明IO是瓶颈（即使CPU空闲，load也会很高）
- 这是Linux特有的设计（其他Unix系统load只计R状态）

### 8.7 系统调用传参方式

**x86_64系统调用的三种触发方式**：

| 方式 | 指令 | 适用架构 | 特点 |
|------|------|---------|------|
| **int 0x80** | int $0x80 | x86_32 | 软中断方式，开销大（~400 cycles） |
| **sysenter/sysexit** | sysenter | x86_32（Pentium II+） | 快速系统调用（~200 cycles） |
| **syscall/sysret** | syscall | x86_64 | 64位快速系统调用（~100 cycles） |

**x86_64系统调用传参规则**：
```asm
; 系统调用号 → rax
; 参数1     → rdi
; 参数2     → rsi
; 参数3     → rdx
; 参数4     → r10  （注意：不是rcx！因为syscall指令会用rcx保存返回地址）
; 参数5     → r8
; 参数6     → r9
; 返回值    → rax

; 示例：write(1, "hello\n", 6)
; write的系统调用号 = 1
mov rax, 1          ; 系统调用号 (SYS_write)
mov rdi, 1          ; fd = 1 (stdout)
lea rsi, [msg]      ; buf = "hello\n"
mov rdx, 6          ; count = 6
syscall             ; 触发系统调用
```

**普通函数 vs 系统调用的传参对比**：
```
普通函数调用（System V AMD64 ABI）：
参数顺序：rdi, rsi, rdx, rcx, r8, r9（第4个用rcx）

系统调用：
参数顺序：rdi, rsi, rdx, r10, r8, r9（第4个用r10）

差别在第4个参数：函数用rcx，系统调用用r10
原因：syscall指令隐式使用rcx保存返回地址（RIP）
```

**系统调用完整流程（x86_64）**：
```
用户态                              内核态
────────                            ────────
syscall指令
  ├─ RCX = 返回地址(RIP)
  ├─ R11 = RFLAGS
  ├─ 加载MSR_LSTAR → RIP           → entry_SYSCALL_64
  │                                    ├─ 保存用户态寄存器到pt_regs
  │                                    ├─ 查sys_call_table[rax]
  │                                    ├─ 调用具体系统调用函数
  │                                    └─ sysret返回用户态
  ↓
sysret指令
  ├─ 从RCX恢复RIP
  └─ 从R11恢复RFLAGS
```

### 9.1 CPU 100% 排查完整SOP

#### Step 1：确认现象——谁在吃CPU？

```bash
# 1. 整体概览：确认是哪个进程在吃CPU
top -b -n 1 | head -20          # 批处理模式取一次快照
# 关注 %Cpu(s) 行：
#   us (user)    — 用户态CPU
#   sy (system)  — 内核态CPU
#   wa (iowait)  — IO等待
#   si (softirq) — 软中断

# 2. 拿到进程PID后确认进程信息
ps -p <PID> -o pid,ppid,cmd,%cpu,%mem

# 3. 进一步区分：到底是用户态高还是内核态高？
pidstat -u -p <PID> 1 5          # 每秒采样，共5次
# 看 %usr 和 %system 列
```

**判断分支**：
- `us` 高 → 业务代码/GC/正则回溯等，走 **用户态路径**
- `sy` 高 → 系统调用频繁/锁竞争/网络收发包，走 **内核态路径**

#### Step 2a：Go 服务排查路径（用户态CPU高）

```bash
# 1. 开启 pprof（通常已在服务中注册）
#    import _ "net/http/pprof"
#    go func() { http.ListenAndServe(":6060", nil) }()

# 2. 采集 30 秒 CPU Profile
go tool pprof -http=:8080 http://localhost:6060/debug/pprof/profile?seconds=30

# 3. 查看火焰图，定位热点函数
# 在浏览器中 View → Flame Graph

# 4. 同时抓 goroutine 堆栈，看有无异常积压
curl http://localhost:6060/debug/pprof/goroutine?debug=2 > goroutine.txt
wc -l goroutine.txt              # goroutine 数量异常多说明可能泄漏
grep -c "^goroutine" goroutine.txt

# 5. 查看GC情况
curl http://localhost:6060/debug/pprof/heap?debug=1 | grep -A5 "gc"
# 或通过 GODEBUG=gctrace=1 观察GC日志
```

**Go 服务 CPU 高常见根因**：

| 根因 | 特征 | 解决方案 |
|------|------|----------|
| 死循环/忙等待 | 火焰图某函数占比 >80% | 修复循环逻辑，加退出条件 |
| GC 频繁 | `runtime.gcBgMarkWorker` 占比高 | 减少小对象分配，用 sync.Pool |
| 正则回溯 | `regexp.(*machine).match` 占比高 | 预编译正则，避免贪婪匹配 |
| JSON 序列化 | `encoding/json` 相关函数 | 换用 jsoniter / sonic |
| 锁竞争 | `runtime.lock` / `sync.Mutex` | 减小临界区，换用分段锁或无锁结构 |

#### Step 2b：Java 服务排查路径（用户态CPU高）

```bash
# 1. 找到 Java 进程 PID
jps -lv | grep <服务名>

# 2. 找到进程内最耗CPU的线程
top -Hp <PID>                    # 注意 -H 表示显示线程
# 记录高CPU的线程TID，例如 12345

# 3. TID 转 16 进制（jstack 用 nid=0x 匹配）
printf "%x\n" 12345              # 输出 3039

# 4. 抓线程堆栈
jstack <PID> > jstack.txt

# 5. 搜索对应线程
grep -A 30 "nid=0x3039" jstack.txt

# 6. 多次采样对比（间隔3-5秒，取3次）
for i in 1 2 3; do
    jstack <PID> > jstack_$i.txt
    sleep 3
done
# 如果同一线程始终在同一位置 → 死循环或长时间计算
```

**Java 服务 CPU 高常见根因**：

| 根因 | 特征 | 解决方案 |
|------|------|----------|
| Full GC 频繁 | 线程在 `VM Thread` / `GC task` | 调大堆、排查内存泄漏 |
| 死锁 | jstack 底部显示 `Found deadlock` | 调整加锁顺序 |
| 忙等待/自旋 | 同一线程反复执行同一代码段 | 改为阻塞等待或加 sleep |
| 正则回溯 | `java.util.regex` 相关堆栈 | 修正正则表达式 |
| 日志序列化 | `toString()` / `JSON.toJSONString` | 降低日志级别，异步打印 |

#### Step 2c：内核态CPU高排查

```bash
# 1. 用 perf 查看内核热点
perf top -g                      # 实时查看内核态热点函数

# 2. 采集并生成报告
perf record -g -p <PID> -- sleep 30
perf report

# 3. 系统调用统计
strace -c -p <PID> -e trace=all  # 统计系统调用频率
# 关注 calls 列最高的系统调用

# 4. 软中断分布
watch -n 1 'cat /proc/softirqs'  # 观察 NET_RX/NET_TX 增长速度
```

**内核态 CPU 高常见根因**：

| 根因 | 特征 | 解决方案 |
|------|------|----------|
| 大量短连接 | `sys_connect`/`tcp_v4_connect` 频繁 | 改用连接池/长连接 |
| 频繁内存分配 | `__alloc_pages` / `kmalloc` 热点 | 减少 mmap，用内存池 |
| 锁竞争（内核锁） | `_raw_spin_lock` 占比高 | 减少并发写同一文件/socket |
| 网络收包风暴 | `NET_RX` 软中断单核打满 | 开启 RSS/RPS 多队列 |

```
                    │                         │
```

### 9.2 内存OOM排查完整SOP

#### Step 1：确认现象——是不是被OOM Killer杀了？

```bash
# 1. 检查系统日志中的 OOM 记录
dmesg | grep -i "oom" | tail -20
# 或
journalctl -k | grep -i "oom"

# 2. 查看被杀进程的详细信息
dmesg | grep -i "killed process"
# 输出示例：
# Out of memory: Killed process 12345 (java) total-vm:8192000kB ...

# 3. 当前内存概览
free -h                          # 总体内存使用
cat /proc/meminfo | head -20     # 详细内存分布

# 4. 查看各进程内存占用排名
ps aux --sort=-%mem | head -20
# 或
smem -r -s pss | tail -20       # 按 PSS（比例分摊共享内存）排序
```

**关键指标解读**：
- `MemFree` 接近 0 不一定有问题（Linux会用空闲内存做page cache）
- 看 `MemAvailable`：这才是真正可用内存
- `SwapUsed` 持续增长 → 物理内存确实不够了

#### Step 2a：Go 服务内存泄漏排查

```bash
# 1. 查看堆内存概况
go tool pprof http://localhost:6060/debug/pprof/heap

# 在 pprof 交互界面中：
#   top 20          — 查看内存分配 Top 20 函数
#   list <函数名>   — 查看函数逐行分配
#   web             — 生成调用图（需安装 graphviz）

# 2. 对比两个时间点的 heap profile（差分分析）
curl http://localhost:6060/debug/pprof/heap > heap_t1.prof
# 等待一段时间（如5分钟）
curl http://localhost:6060/debug/pprof/heap > heap_t2.prof
go tool pprof -base heap_t1.prof heap_t2.prof
# top 查看增长最多的分配点

# 3. goroutine 泄漏检测（goroutine 泄漏 = 间接内存泄漏）
curl http://localhost:6060/debug/pprof/goroutine?debug=1 | head -30
# 如果 goroutine 数量持续增长，定位创建它们的代码

# 4. 运行时内存统计
curl http://localhost:6060/debug/pprof/heap?debug=1 | grep -E "Alloc|Sys|HeapIdle|HeapReleased|NumGC"
```

**Go 服务内存泄漏常见根因**：

| 根因 | 特征 | 解决方案 |
|------|------|----------|
| goroutine 泄漏 | goroutine 数量持续增长 | 确保 channel 有发送/接收对、用 context 控制生命周期 |
| 未关闭 HTTP Response Body | `net/http` 相关分配增长 | 必须 `defer resp.Body.Close()` |
| time.After 在循环中使用 | `time` 包分配增长 | 改用 `time.NewTimer` + `Reset` |
| 全局 map 无限增长 | 堆分配持续增长 | 加 TTL / LRU 淘汰策略 |
| slice 底层数组未释放 | 大 slice 切片后仍持有底层数组 | `copy` 到新 slice |
| cgo 内存泄漏 | Go heap 正常但 RSS 持续增长 | 检查 C 代码的 malloc/free |

#### Step 2b：Java 服务内存泄漏排查

```bash
# 1. 查看堆内存概况
jmap -heap <PID>

# 2. 导出堆转储（注意：会触发STW，生产环境谨慎）
jmap -dump:format=b,file=heap.hprof <PID>
# 或在启动参数中预设自动导出：
# -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp/

# 3. 使用 MAT（Eclipse Memory Analyzer）分析
# 打开 heap.hprof → Leak Suspects Report → 自动定位可疑对象

# 4. 快速查看对象统计（不dump全量）
jmap -histo <PID> | head -30    # 查看实例数和大小 Top 30

# 5. GC 日志分析
# 启动参数加：-Xloggc:/tmp/gc.log -XX:+PrintGCDetails
# 使用 GCViewer 或 gceasy.io 分析

# 6. 堆外内存排查（NIO DirectByteBuffer 等）
jcmd <PID> VM.native_memory summary
# 需要启动参数 -XX:NativeMemoryTracking=summary
```

**Java 服务内存泄漏常见根因**：

| 根因 | 特征 | 解决方案 |
|------|------|----------|
| ThreadLocal 未清理 | 线程池中 ThreadLocal 累积 | 用完 `remove()`，或用 TransmittableThreadLocal |
| 缓存无上限 | HashMap/ConcurrentHashMap 持续增长 | 改用 Guava Cache / Caffeine 设置 maxSize |
| 类加载器泄漏 | Metaspace 持续增长 | 排查动态类生成（CGLIB/反射），限制 `-XX:MaxMetaspaceSize` |
| 未关闭的连接/流 | `Finalizer` 队列积压 | 用 try-with-resources |
| 大对象直接进老年代 | Old Gen 快速填满 | 调整 `-XX:PretenureSizeThreshold` |
| 堆外内存泄漏 | 堆内正常但 RSS 异常增长 | 检查 DirectByteBuffer，开启 NMT |

#### Step 2c：系统级内存排查

```bash
# 1. 内存详细分布
cat /proc/meminfo
# 关注：
#   MemAvailable  — 真正可用内存
#   Buffers       — 块设备缓存
#   Cached        — 页缓存（文件缓存）
#   Slab          — 内核 slab 分配器
#   SReclaimable  — 可回收 slab
#   SUnreclaim    — 不可回收 slab

# 2. Slab 缓存详情（内核态内存泄漏排查）
slabtop -o | head -20            # 查看 slab 对象排名
cat /proc/slabinfo | sort -k 3 -nr | head -20

# 3. Page Cache 分析
# 如果 Cached 很大但 MemAvailable 也够，不是问题
# 如果要手动释放 page cache（应急用）：
sync && echo 3 > /proc/sys/vm/drop_caches

# 4. 各进程实际内存占用
# /proc/<PID>/smaps 提供最精确的内存分布
cat /proc/<PID>/smaps_rollup
# 或
pmap -x <PID> | tail -5         # 查看内存映射汇总

# 5. 交换分区分析
swapon -s                        # 查看 swap 使用
vmstat 1 5                       # 关注 si/so 列（swap in/out）
# si/so 持续 >0 说明物理内存严重不足

# 6. NUMA 内存不均衡
numastat                         # 查看各 NUMA 节点内存分配
# numa_miss 高说明跨节点分配频繁，影响性能
```

#### Step 3：OOM Score 调整和保护措施

```bash
# 1. 查看进程的 OOM Score（分数越高越容易被杀）
cat /proc/<PID>/oom_score
cat /proc/<PID>/oom_score_adj    # 可调整值：-1000 ~ 1000

# 2. 保护关键进程（降低被 OOM Kill 的概率）
echo -1000 > /proc/<PID>/oom_score_adj   # -1000 = 永不被杀

# 3. 让不重要的进程优先被杀
echo 1000 > /proc/<PID>/oom_score_adj    # 1000 = 最先被杀

# 4. 系统级 OOM 策略调整
# 0 = 默认启发式策略（可能过度提交）
# 1 = 允许过度提交（不检查）
# 2 = 禁止过度提交（分配超过 swap + ratio% * 物理内存 则失败）
cat /proc/sys/vm/overcommit_memory
echo 2 > /proc/sys/vm/overcommit_memory   # 生产建议：禁止过度提交
echo 80 > /proc/sys/vm/overcommit_ratio   # 允许分配 swap + 80% 物理内存

# 5. 设置内存 cgroup 限制（更精细的保护）
# 限制单个服务的内存使用，避免一个服务OOM拖垮整台机器
# cgroup v2 示例：
echo 4G > /sys/fs/cgroup/<服务>/memory.max
echo 3G > /sys/fs/cgroup/<服务>/memory.high  # 超过 high 触发回收，超过 max 触发 OOM
```

**生产环境OOM防护清单**：
- [ ] 关键服务设置 `oom_score_adj = -1000`
- [ ] 所有服务通过 cgroup 限制内存上限
- [ ] 配置 `-XX:+HeapDumpOnOutOfMemoryError`（Java）
- [ ] 接入内存监控告警（>80% 预警，>90% 告警）
- [ ] 定期检查 goroutine / 线程数趋势
- [ ] `vm.overcommit_memory = 2`，杜绝内存过度提交

### 9.3 磁盘IO慢排查SOP

#### Step 1：确认现象——IO到底慢在哪？

```bash
# 1. 整体IO概览
iostat -x 1 5                    # 每秒采样，共5次
# 关键指标：
#   %util   — 磁盘繁忙度（>80% 说明磁盘接近饱和）
#   await   — 平均IO等待时间（ms），包含队列等待+实际服务时间
#   r_await — 读等待    w_await — 写等待
#   avgqu-sz — 平均队列长度（>2 说明IO积压）
#   rrqm/s wrqm/s — 合并读写请求数（合并多说明顺序IO较多）

# 2. 定位到具体磁盘后，找出哪个进程在做IO
iotop -o -P                      # -o 只显示有IO的进程
# 或
pidstat -d 1 5                   # 每秒采样进程级IO统计

# 3. 查看进程打开的文件
lsof -p <PID> | grep -E "REG|DIR"
# 或
ls -la /proc/<PID>/fd/ | wc -l  # 打开的文件描述符数量
```

#### Step 2：iowait高的常见原因和解决方案

```bash
# 确认是否是 iowait 导致 CPU 看起来"很忙"
vmstat 1 5
# wa 列 > 20% → 说明大量CPU时间在等IO

# 排查 iowait 高的具体原因：
# 1) 大量同步写日志
strace -e trace=write -c -p <PID>
# 如果 write 调用极频繁 → 考虑异步日志/批量写

# 2) 数据库大量随机IO
iostat -x 1 | grep <磁盘设备>
# 如果 rrqm/s 和 wrqm/s 都很低，但 IOPS 很高 → 随机IO
# 解决方案：加内存做缓存、换SSD、优化查询减少随机读

# 3) Swap 导致的 IO（内存不足引发）
vmstat 1 5    # si/so > 0 → 正在换入换出
# 解决方案：增加物理内存、优化应用内存使用
```

**iowait 高常见原因总结**：

| 根因 | 诊断方法 | 解决方案 |
|------|----------|----------|
| 同步写日志过多 | strace 统计 write 调用 | 异步日志、日志级别调高、批量刷盘 |
| 数据库随机IO | iostat 看合并率低+IOPS高 | 加缓存、换SSD、优化索引 |
| Swap IO（内存不足）| vmstat 看 si/so 列 | 加内存、优化应用、关闭 swap |
| 大文件顺序读写 | iotop 定位进程+文件 | 限速、IO调度器调优、分时段执行 |
| RAID 重建/磁盘坏道 | dmesg 看硬件错误 | 更换磁盘、RAID 修复 |

#### Step 3：文件系统层面排查

```bash
# 1. 磁盘空间是否写满
df -h                            # 查看各分区使用率
# 使用率 100% → 写操作会失败
# 找出大文件：
du -sh /* 2>/dev/null | sort -rh | head -10
# 找出大日志文件（常见元凶）：
find /var/log -type f -size +100M -exec ls -lh {} \;

# 2. inode 是否耗尽（空间有剩余但无法创建文件）
df -i                            # 查看 inode 使用率
# inode 100% → 大量小文件导致
# 定位小文件目录：
find / -xdev -type d -exec sh -c 'echo "$(find "$1" -maxdepth 1 | wc -l) $1"' _ {} \; | sort -rn | head -10

# 3. 文件系统错误检查
dmesg | grep -i "ext4\|xfs\|error\|readonly"
# 如果看到 "Remounting filesystem read-only" → 文件系统损坏
# 修复（需卸载分区）：fsck -y /dev/sdX

# 4. 已删除但未释放的文件（进程仍持有文件句柄）
lsof | grep deleted | sort -k 7 -rn | head -10
```

## 10. 面试题自查

> **双轨编号**
> - **速刷轨**：S1–Sn（初级/中级口答，先建立口径）
> - **深问轨**：Q1–Qn（可展开追问）
> 每题固定：**要点 → 易错点 → 观测命令 → 追问链**。细节回正文，不在此复读长文。

### 速刷轨（S）

#### S1: 用户态 / 内核态差在哪？系统调用为什么“慢”？

**要点**：特权级不同；syscall = 陷入 + 校验 + 内核路径 + 返回，还可能睡眠。
**易错点**：把慢归因成“函数写得复杂”，忽略等待与 cache/TLB 扰动。
**观测**：`top`/`pidstat -u` 看 `us/sy/wa/si`；`strace -c -p <PID>`；`perf trace -p <PID>`。
**追问**：`sy` 高下一步看什么？→ 热点 syscall 与内核栈（`perf top`）。`wa` 高呢？→ 更像 IO 等待，不是算力不够。

#### S2: 进程和线程的区别？创建开销和切换开销能混说吗？

**要点**：进程是资源边界，线程是调度实体（Linux 都是 task）；切换按 **μs**，创建更贵且随工作集变。
**易错点**：写“进程切换 3–5ms”；把创建成本当切换成本。
**观测**：`pidstat -w`；`vmstat 1` 的 `cs`；`perf stat`。
**追问**：同进程线程切换为何通常更轻？→ 一般不换 mm/CR3，TLB 扰动更小。

#### S3: Page Cache 是什么？为什么干扰 IO 判断？

**要点**：文件页在内存的缓存；命中时“磁盘 IO”其实没碰盘。
**易错点**：压测不抛 cache 就宣称磁盘很强。
**观测**：`free -h`；`/proc/meminfo` 的 `Cached`；`vmtouch`/`fio` 时注意 `drop_caches` 仅测试用。
**追问**：Dirty 很高时 `fsync` 为何抖？→ 集中写回与设备队列。

#### S4: `mmap` 和 `read/write` 怎么选？

**要点**：`read/write` 显式拷贝；`mmap` 映射后按内存访问，常伴随缺页。
**易错点**：断言 mmap 一定更快。
**观测**：`ps` 的 minflt/majflt；`perf stat -e page-faults`；`strace -c` 看 mmap/read 比例。
**追问**：静态文件对外发送优先谁？→ 常 `sendfile`，不是空喊 mmap。

#### S5: 阻塞/非阻塞 vs 同步/异步？

**要点**：前一对看调用是否挂起；后一对看完成通知由谁驱动。epoll 多是“同步多路复用 + 非阻塞读写”。
**易错点**：把 epoll 直接叫异步 IO（和 io_uring/AIO 混）。
**观测**：应用日志 + `strace -e epoll_wait,read,write`。
**追问**：Go 里 `conn.Read` 阻塞了线程吗？→ 阻塞的是 goroutine；M 可去跑别的 G（netpoller）。

#### S6: 排障入口命令怎么串？

**要点**：先定资源维（CPU/内存/磁盘/网络/cgroup），再下钻。
**易错点**：一上来就 `tcpdump` 或只盯 `%CPU`。
**观测**：`ps/top/pidstat` → `vmstat/iostat` → `ss/nstat` → `strace/perf` → cgroup/`dmesg`。
**追问**：CPU 不高但延迟高？→ run queue、锁/futex、IO、缺页、重传、steal。

#### S7: fd 泄漏怎么表现？

**要点**：fd 是内核对象句柄；泄漏致 `EMFILE`、建连失败、文件打不开。
**易错点**：只重启不查泄漏点。
**观测**：`ls /proc/<PID>/fd | wc -l`；`lsof -p <PID>`；`ulimit -n`。
**追问**：容器里还要看什么？→ cgroup/`pids` 与容器 nofile 限制。

#### S8: 为什么 `fork` 常常看起来很快？

**要点**：COW，不立刻复制全部物理页。
**易错点**：以为地址空间被完整 memcpy。
**观测**：fork 后父子狂写时 `min_flt` 飙升；`perf stat -e page-faults`。
**追问**：大进程 fork 后马上 exec，COW 成本如何？→ 通常可接受；父子都长期写才痛。

#### S9: 用户态等 mutex 会进 D 状态吗？

**要点**：通常是 S（可中断睡眠）+ 可能 `futex`；D 是不可中断内核等待（磁盘/NFS 等）。
**易错点**：把“拿不到锁”说成 D。
**观测**：`ps -o stat,wchan`；`cat /proc/<PID>/stack`；`strace -e futex`。
**追问**：D 状态进程 `kill -9`？→ 往往杀不死，要先解决底层 IO/驱动。

#### S10: “CPU 不高但很慢”怎么拆？

**要点**：延迟来自排队/等待，不单来自利用率。
**易错点**：只看 `top` 的 `%CPU`。
**观测**：`vmstat`（r/b/cs）、`pidstat -w`、`iostat`、`ss -i`、`mpstat` 的 `steal`。
**追问**：`steal` 高说明什么？→ vCPU 被宿主机抢占。

### 深问轨（Q）

#### Q1: 进程/线程本质区别？何时多进程、何时多线程？goroutine 呢？

**要点**：隔离边界 vs 调度实体；多进程强隔离，多线程共享内存通信便宜。Goroutine 是 **M:N 用户态调度**，不是“多进程安全性”。
**易错点**：说 goroutine“兼顾多进程安全性”——同进程共享地址空间，一个坏掉仍可拖垮进程；隔离性弱于多进程。
**观测**：`runtime.NumGoroutine` / pprof；`ps -eLf` 看线程数；对比多进程部署的故障域。
**追问**：纯用户级 N:1 为何难用多核？→ 内核只见一线程。Go 为何能用多核？→ 多个 M。

#### Q2: 僵尸进程与孤儿进程？

**要点**：僵尸=未 wait 的已退出子进程占 PID 槽；孤儿=父死后被 init/子 reaper 收养，属正常。
**易错点**：把孤儿当泄漏。
**观测**：`ps aux | awk '$8~/Z/'`；`pstree -p`。
**追问**：只杀僵尸行吗？→ 应修父进程 wait 或重启父进程。

#### Q3: 虚拟内存与页表/TLB？

**要点**：隔离、超售、共享；多级页表翻译；TLB 缓存翻译结果。
**易错点**：忽略 TLB shootdown/进程切换代价。
**观测**：`perf stat -e dTLB-load-misses,dTLB-loads`；`cat /proc/<PID>/maps`。
**追问**：PCID 缓解什么？→ 切 CR3 时减少整表冲刷。

#### Q4: Minor vs Major Page Fault？能用 `strace -c` 看缺页吗？

**要点**：Minor=页已在内存只补映射；Major=要读写存储/swap。缺页是 **fault**，不是 syscall。
**易错点**：在 `strace -c` 里写 `page_fault` 行。
**观测**：`ps -o min_flt,maj_flt`；`perf stat -e minor-faults,major-faults`；`sar -B`。
**追问**：容器内存触顶时 majflt/si/so 可能怎样？→ 回收、swap、OOM。

#### Q5: epoll 相对 select 为何更合适高并发？是 O(1)+mmap 吗？

**要点**：兴趣集红黑树，`epoll_ctl` **O(log N)**；`epoll_wait` 返回就绪 **O(R)**；事件拷到用户 buffer，**不是 mmap 共享就绪表**。
**易错点**：背“共享内存 O(1)”。
**观测**：`strace -e epoll_ctl,epoll_wait`；压测连接数与延迟；`/proc/net/sockstat`。
**追问**：LT 与 ET 差在哪？ONESHOT 解决什么？→ 见正文 3.3；多线程避免同 fd 并发处理。

#### Q6: 传统发送文件路径几拷贝几切换？零拷贝常见手段？

**要点**：`read+write` 典型 **4 拷贝 + 4 次用户/内核切换**；`sendfile`/`splice` 减少用户态绕行。
**易错点**：答“4 拷贝 2 切换”；说“Nginx 用 mmap 做零拷贝”——Nginx 静态主路径是 **sendfile**。
**观测**：`strace -e sendfile,read,write`；对比 `io.Copy` 是否走 sendfile。
**追问**：mmap 还算不算零拷贝？→ 常减少一次显式 read，但仍可能有缺页与后续拷贝，别神化。

#### Q7: 伪共享是什么？

**要点**：不同变量同缓存行，写触发 MESI 失效抖动。
**易错点**：当成普通数据竞争（data race）。
**观测**：`perf c2c` / `perf stat -e cache-misses`；对比 padding 前后。
**追问**：和真正共享计数器的区别？→ 伪共享逻辑不共享，只物理同行。

#### Q8: 三次握手为何三次？（协议细节指向网络篇）

**要点**：双方各确认收发能力，并缓解旧 SYN；本篇主机侧盯 backlog。
**易错点**：在操作系统篇展开拥塞控制长文。
**观测**：`ss -lnt`；`nstat` 的 ListenOverflows；`tcpdump`。
**追问**：半连接/全连接队列打满现象？→ SYN 丢、Accept 变慢、溢出计数涨。详见 `06-网络基础与协议.md`。

#### Q9: 上下文切换是什么？如何减少？

**要点**：保存/恢复现场；进程切换常伴页表/TLB 扰动，单位 **μs**。
**易错点**：ms 级口径；把 goroutine 调度和内核线程切换完全等同。
**观测**：`vmstat 1` 的 `cs`；`pidstat -w`（自愿/非自愿）。
**追问**：自愿切换高说明什么？→ 多在等锁/IO；非自愿高→抢占或 CPU 紧。

#### Q10: Cgroup CPU 三种限制？

**要点**：cpuset 绑核；quota 硬上限；shares/weight 比例弹性。
**易错点**：以为 shares 在空闲时仍卡死额度。
**观测**：`cpu.max`/`cpu.cfs_quota_us`；`kubectl top`；`/sys/fs/cgroup/...`。
**追问**：与 Namespace 分工？→ ns 管看见什么，cgroup 管用多少。

#### Q11: 现代 IO 调度器还有 cfq/noop 吗？

**要点**：多队列常见 **none / mq-deadline / bfq**；cfq/deadline/noop 属 legacy 叙事。
**易错点**：SSD 一律背 noop，却对着 `[none] mq-deadline` 的机器答题。
**观测**：`cat /sys/block/<dev>/queue/scheduler`；`iostat -x`。
**追问**：V1 blkio.weight 在 mq+none 上还有效吗？→ 常常无效，改看 throttle / cgroup v2 io。

#### Q12: CFS/vruntime 与 EEVDF？

**要点**：CFS 用 vruntime 近似公平；6.6+ 普通调度类走向 **EEVDF**。
**易错点**：坚称“现行内核一定是 CFS”。
**观测**：`uname -r`；发行版内核文档；`perf sched`。
**追问**：nice 如何影响？→ 权重变 → 虚拟时间/合格截止时间累积变慢或变快。

#### Q13: `mmap` / `sendfile` / `read/write` 怎么选？

**要点**：通用读写；文件→socket 直传优先 sendfile；随机访问/共享可考虑 mmap。
**易错点**：无场景排名速度。
**观测**：延迟与 CPU `sy`、缺页、是否出现 sendfile syscall。
**追问**：数据库为何常用 Direct IO？→ 自管缓存，避免 double cache。

#### Q14: OOM Killer 与 oom_score？

**要点**：内存走投无路时按分数选牺牲者；cgroup 限额可先于主机 OOM。
**易错点**：只加 swap 当永久方案。
**观测**：`dmesg -T | grep -i oom`；`/proc/<PID>/oom_score(_adj)`；`memory.events`。
**追问**：回收链顺序？→ 水位线 → kswapd/direct reclaim → swap → OOM。

#### Q15: GMP 为何这样设计？

**要点**：G 轻量任务，M 执行载体，P 持本地队列与 mcache，降全局锁、可 work-stealing。
**易错点**：把 G 说成内核线程；说有多进程级隔离。
**观测**：`GOMAXPROCS`；`go tool pprof` 的 goroutine/cpu；`runtime.NumGoroutine`。
**追问**：syscall 阻塞时 M 怎么办？→ 可能把手 M 留下、再找 M 跑 P 上其余 G（简化表述即可）。

#### Q16: Direct IO 何时用？

**要点**：绕过 Page Cache；库自管缓存、大顺序流。
**易错点**：对齐/大小约束不提。
**观测**：`oflag=direct` 的 `dd` 对比；应用 `O_DIRECT`；`iostat`。
**追问**：和小文件大量随机读？→ 通常更伤，更需要 page cache。

#### Q17: 慢启动 initcwnd 还是 1 吗？

**要点**：现代 Linux 初始 cwnd 常约 **10 MSS**；拥塞控制细节见网络篇。
**易错点**：死背 cwnd 从 1 指数爬。
**观测**：`ss -i`；`sysctl net.ipv4.tcp_congestion_control`。
**追问**：Cubic vs BBR 直觉差？→ 丢包驱动 vs 带宽/RTT 模型（链到 06）。

#### Q18: 内存泄漏怎么查（Go / C）？

**要点**：Go：pprof heap 差分 + goroutine；C：ASan/Valgrind。
**易错点**：只看 RSS 一次快照。
**观测**：`go tool pprof -base`；`valgrind --leak-check=full`；`/proc/<PID>/smaps`。
**追问**：goroutine 泄漏如何间接触发内存涨？→ 栈+引用图无法回收。

#### Q19: SIGTERM 优雅退出要点？

**要点**：可捕获；停新请求→排空→落盘→退出；SIGKILL 不可捕。
**易错点**：正式环境依赖 SIGKILL。
**观测**：`kill -15`；应用日志；K8s preStop/terminationGracePeriod。
**追问**：为何还要设超时？→ 防止优雅退出挂死。

#### Q20: Cgroup V2 相对 V1？

**要点**：统一层级、Buffered IO 限速改善、PSI、配置更简单。
**易错点**：背文件名却分不清 v1/v2 路径。
**观测**：`mount | grep cgroup`；`*.pressure`；`cpu.max`/`memory.max`/`io.max`。
**追问**：PSI some/full 含义？→ 部分任务等 vs 全部任务等。

#### Q21: Soft Lockup vs Hard Lockup？

**要点**：soft=能进中断但不调度；hard=连中断都卡住（常关中断死循环），NMI watchdog 抓。
**易错点**：两者混名。
**观测**：`dmesg | grep -i lockup`；`nmi_watchdog`；`sysctl kernel.watchdog_thresh`。
**追问**：和 softirq 风暴区别？→ lockup 是“卡住”；softirq 高是“下半部很忙”。

#### Q22: 内核抢占？服务器一定是 PREEMPT_NONE 吗？

**要点**：内核态是否可被抢占分 NONE/VOLUNTARY/PREEMPT（及动态变体）；**发行版不统一**。
**易错点**：绝对化“服务器都是 PREEMPT_NONE”。
**观测**：`grep PREEMPT /boot/config-$(uname -r)`；`uname -v`。
**追问**：持 spinlock 时为何不能睡？→ 关抢占/忙等假设被破坏会死锁。

#### Q23: D 状态与 Load Average？

**要点**：D=不可中断睡眠；Load≈可运行+不可中断的指数平均。
**易错点**：Load 高就加 CPU，实际可能是 NFS/磁盘 D。
**观测**：`ps -eo pid,stat,wchan,cmd`；`uptime`；`/proc/loadavg`。
**追问**：用户态 mutex 等待计不进 D？→ 不计。

#### Q24: 中断上半部/下半部？softirq 是软件中断指令吗？

**要点**：上半部短、下半部（softirq/tasklet/workqueue）做耗时活；**softirq ≠ x86 software interrupt**。
**易错点**：混称“软件中断”。
**观测**：`/proc/interrupts`；`/proc/softirqs`；`mpstat` 的 `si`。
**追问**：收包路径如何串起来？→ 硬中断 → NET_RX softirq → NAPI → 协议栈 → socket。

#### Q25: 内核锁与 RCU 直觉？

**要点**：spinlock 短临界区不可睡；mutex 可睡；RCU 读端极轻、写端延迟释放。
**易错点**：中断里用 mutex。
**观测**：`perf lock`（若可用）；锁持有导致的延迟与 softlockup 日志。
**追问**：RCU grace period 在等什么？→ 所有已存在读侧临界区结束。

#### Q26: Namespace 有哪些？和 cgroup 如何配对？

**要点**：pid/mnt/net/uts/ipc/user/cgroup；ns=视图，cgroup=配额。
**易错点**：以为 Docker 只靠 cgroup。
**观测**：`lsns`；`/proc/<PID>/ns`；`nsenter`。
**追问**：`hostNetwork` 牺牲了什么？→ net ns 隔离。

#### Q27: 内存回收链怎么叙述？

**要点**：watermark → kswapd / direct reclaim → swap → OOM（再叠加 cgroup limit）。
**易错点**：跳过回收直接讲 OOM。
**观测**：`/proc/zoneinfo`；`vmstat` 的 si/so；`pgsteal*`；`oom_score`。
**追问**：direct reclaim 为何伤尾延迟？→ 分配路径上同步回收。

#### Q28: futex 在性能题里出现说明什么？

**要点**：用户态锁竞争升级到内核等待的桥。
**易错点**：当成普通文件 IO syscall。
**观测**：`strace -c -e futex`；`perf top` 见 `futex_wait`。
**追问**：如何降 futex？→ 减持锁时间、分片、避免广播惊群。

### 开放式设计题（D）

#### D1: 用户态网络协议栈（bypass 内核）要考虑什么？

**要点**：UIO/VFIO + 轮询环、大页、CPU 隔离、自研协议/TCP；放弃 iptables/tcpdump 等内核生态。
**易错点**：只谈快，不谈运维与安全边界。
**观测/验证**：PPS/带宽、CPU busy poll、丢包计数；对比内核栈基线。
**追问**：何时 XDP/DPDK，何时内核 + io_uring 就够？→ 看 PPS 与团队成本。

#### D2: 机器 SSH/Ping 都不通但电源还亮，如何诊断？

**要点**：带外 BMC/IPMI → 看 panic/lockup；事后 kdump/vmcore；预防 watchdog/kdump。
**易错点**：只在原 SSH 会话里空等。
**观测**：串口/KVM 控制台、`dmesg` 最后痕迹、管理口日志。
**追问**：soft vs hard lockup 在控制台分别像什么？→ 见 Q21。

**主线记忆**：

1. **进程/线程**：创建 vs 切换（μs）、CFS/EEVDF 注记、IPC（`IPC_PRIVATE`+fork）、GMP（非“多进程安全”）
2. **内存**：虚拟内存、缺页（非 syscall）、回收链、COW/mmap、THP、缓存/MESI、分配器思想
3. **IO**：epoll（log N / O(R)，非 mmap 事件）、LT/ET/ONESHOT、io_uring、零拷贝（4 拷贝 4 切换）、sendfile
4. **文件系统**：inode、Page Cache、fsync
5. **网络（本篇）**：softirq/NAPI 收发包；协议细节 → `06-网络基础与协议.md`（initcwnd≈10）
6. **隔离**：Namespace 七类视图 + Cgroup 配额；V2/PSI；IO 调度器看 mq（none/mq-deadline/bfq）
7. **syscall 性能**：成本拆解、批量、vDSO、futex
8. **内核**：中断上下部（softirq≠软件中断指令）、锁、抢占（看发行版配置）、D/Load、lockup

**优化优先序**：先观测定位 → 减等待/减 syscall 次数 → 再谈零拷贝与旁路。
